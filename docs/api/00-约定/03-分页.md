# 分页

2026-10-19 定的规矩，`/api/v1/jobs` 一族和 `GET /documents/{document_id}/jobs` 已经照这个做；书库的
`/documents`、`/search`、书的元数据建议列表 2026-10-22 跟上。其余列表还在按各自的老规矩，改到哪个再把它加进下面的表
（以前列的 `/ai/conversations`、`/documents/{document_id}/agent-versions` 2026-11-03 跟 AI 服务一起删了）。
书架 `/library/books` 2026-10-22 删了（见表下说明）。

## 规矩

1. 列表回显**实际生效**的 `limit` 和 `offset`，并给 `has_more`：这一页之后还有没有。客户端用
   `has_more` 判断有没有下一页，不要用"这一页条数等于 `limit`"猜。
2. `limit` 越界（0，或大于上限）一律返回 **400**，不静默夹成上限。所以回显的 `limit` 总等于请求的值
   （没传就是默认值）。
3. `offset` 是非负整数，超过总数返回空列表，`has_more` 为 `false`。
4. 只加字段，不改旧字段：以前就有的 `total`、`limit`、`offset` 照旧。
5. 不认识的查询参数返回 400：译文列表、事件、数据、质量条目、书的任务列表、书库的 `/documents`、`/search`、
   元数据建议列表都是。message 写出参数名（``unknown field `tag`, expected one of ... in the query string``，
   只有名字、不带值）。任务列表（`GET /jobs`）暂时忽略，等前端核对完再收紧。

`has_more` 不需要 `COUNT`：任务列表、书的任务列表、搜索、元数据建议多取一条判断；`/documents` 的页和
`total` 读自同一个快照、不跳过行，直接用 `offset + 这一页条数 < total`；其余列表本来就在内存里。

## 各列表的 `limit`

| 接口 | 默认 | 范围 | 翻页方式 | 返回 |
|---|---|---|---|---|
| `GET /jobs` | 20 | 1..=500 | `limit` / `offset` | `items`、`invocation_summary`、`limit`、`offset`、`has_more` |
| `GET /documents/{document_id}/jobs` | 20 | 1..=500 | `limit` / `offset` | 上面的，加 `total` |
| `GET /documents` | 50 | 1..=500 | `limit` / `offset` | `documents`、`total`、`limit`、`offset`、`has_more` |
| `GET /search` | 20 | 1..=100 | 只有 `limit`（没有 `offset`） | `query`、`hits`、`limit`、`has_more` |
| `GET /documents/{document_id}/metadata-suggestions` | 20 | 1..=100 | 只有 `limit`（没有 `offset`） | `suggestions`、`limit`、`has_more` |
| `GET /jobs/{job_id}/translations` | 20 | 1..=500 | `limit` / `offset` | `items`、`total`、`limit`、`offset`、`has_more` |
| `GET /jobs/{job_id}/reports/quality/items` | 200 | 1..=1000 | `limit` / `offset` | `kind`、`items`、`total`、`limit`、`offset`、`has_more` |
| `GET /jobs/{job_id}/data/{dataset}` | 200 | 1..=1000 | `limit` / `offset` | `rows` 或 `groups`、`total`、`limit`、`offset`、`has_more`，`group_by` 时多 `group_total` |
| `GET /jobs/{job_id}/progress/events` | 500 | 1..=500 | `cursor`（不认 `offset`） | `items`、`next_cursor`、`has_more`、`limit` |

说明：

- `data` 带 `group_by` 时，`total` 仍是**筛选后的行数**，`offset` / `limit` 翻的是**分组**；分组的个数在
  `group_total`，`has_more` 按分组算。不带 `group_by` 时没有 `group_total`。单对象数据集（`kind=object`）
  `has_more` 恒为 `false`。
- 事件的 `has_more` 是游标语义：初始的 tail 页恒为 `false`（只往后读到快照上界），见
  [事件总览](../02-进度事件/01-事件总览.md) 和 `docs/core/api/event-feed-v2.md`。
- `GET /documents` 带 `job_id` 时是按任务查书，不是翻页：`reading_status`、`collection_id`、`q`、`offset`
  都不起作用，最多返回 1 条；`limit` 照样校验（越界 400），`limit`、`offset` 照请求回显，`has_more` 恒为
  `false`。排序是 `added_at DESC, document_id DESC`，同一秒入库的书翻页不重复、不漏。
- `GET /documents/{document_id}/jobs` 的 `has_more` 2026-10-22 起多取一条判断：`total` 是 `COUNT(*)`，
  列表会跳过读不出来的行，以前用 `total` 算时最后一页会误报还有下一页。`total` 照旧。
- 书架 `GET /library/books` 以前静默夹、带 `job_ids` 时不按 `limit` 截断；2026-10-19 冻结，前端改调 `GET /jobs?job_ids=` 以后 2026-10-22 删了（现在 404）。`GET /jobs` 带 `job_ids` 时照样校验 `limit`（1..=500，越界 400），名单超过 500 个要分批。
- 以前还没跟上的 `GET /ai/conversations`、`GET /documents/{document_id}/agent-versions` 2026-11-03 删了。`GET /collections` 不分页（合集数量小，一次全给）。
- `GET /providers/ocr` 不分页：OCR 提供方就几个，一次全给（2026-10-22 写明，契约 `ocr-providers.v1`）。
- 备份和同步不分页（2026-10-22 写明）：`GET /backups` 的 `items` 一次全给（受保留规则限制，最多约 27 份）；`GET /sync` 的
  `pending` 最多列 20 条、总数看 `pending_total`，`peers` 是同步文件夹里的其它设备，一次全给。都不收 `limit`/`offset`。
- `GET /glossaries` 不分页（术语表数量小，一次全给）；不认识的查询参数 `400`，空的 `q` 不过滤。2026-10-22 写明。

## 错误

`limit` 越界的响应：

```json
{
  "code": 40000,
  "message": "limit must be 1..=500",
  "error": { "code": "BAD_REQUEST" }
}
```
