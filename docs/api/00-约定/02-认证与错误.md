# 认证与错误

## 认证

除下面这些外，接口都需要请求头：

```http
X-API-Key: your-api-key
```

- `GET /health`、`GET /ready`（第二个端口上也有）；
- 登录注册：`GET /api/v1/auth/session`、`POST /api/v1/auth/login`、`POST /api/v1/auth/register`；
- 模型执行器的三个内部接口 `/api/v1/internal/model/jobs/{job_id}/requests…`：凭只对一个任务有效的能力令牌
  （`Authorization: Bearer …`），不收 API 密钥。

认证失败通常返回 `401` 或 `403`。

比较 key 时每一把都逐字节比完，耗时不随猜对了几个字节而变（2026-10-24 起；rust_api、retain-jobsd
共用 `retainpdf-core` 的 `api_key_matches`；以前还有助手终端握手，2026-11-03 跟 AI 服务一起删了）。请求日志只记方法和路径，不记查询串。

## 请求编号

2026-10-24 起，每个回应（成功、出错、未登记的地址，两个端口都一样）都带回应头 `X-Request-ID`。请求自己带了
`X-Request-ID`、而且是 1～64 个字母、数字或 `-_.:` 就原样沿用（nginx 可以传 `$request_id`），没带或不像样就由后端生成
16 位十六进制。后端这个请求的日志都带着它，报问题时把它一起给出来就能在日志里找到那个请求。

单机模式下来源和主机不对时也是 `403`（`error.code = "FORBIDDEN"`，2026-10-22 起）：

| 情况 | `message` |
| --- | --- |
| 后端监听回环地址，`Host` 不是 `localhost`、IP 字面量或 `RUST_API_ALLOWED_HOSTS` 里的主机名（防 DNS rebinding；监听非回环地址时配了名单才查） | `request host is not allowed` |

普通 HTTP 请求的来源不在名单里**不报错**，只是不回 CORS 头。规则见
[API 总入口 1.1](../../core/api/index.md#11-单机模式的来源和主机)。

## 凭据字段

任务请求里可能包含下游 provider 凭据，例如：

- `ocr.mineru_token`
- `ocr.paddle_token`
- `translation.api_key`
- command provider 的 `ocr.options.credential`

后端响应不会回显这些明文。前端只能通过类似 `*_configured` 的布尔字段判断是否已配置。
凭据库（`/api/v1/credentials`）也一样：只回元数据；以前 `GET /credentials?include_values=true` 会回全部明文，
2026-10-22 删了，现在带任何查询参数都是 `400`。

## 错误处理原则

- HTTP status 表示请求级错误，例如认证失败、参数非法、资源不存在。
- job 的 `status=failed` 表示任务运行失败。
- 任务失败原因优先读 `failure` 或 diagnostics 接口，不要从 `stage_detail` 反推。

常用状态：

- `400`: 请求本身写错了：字段不合法、组合不支持、请求体里有不认识的字段。和任务现在是什么状态无关，同样的请求换个状态还是 400。
- `401`: 缺少或错误的 API key。
- `404`: job、书、合集或 artifact 不存在。只有数据库里确实没有这条记录才是 404；有记录但读不出来（行解码失败、库被锁……）是 `500`，不会说成 "job not found" / "document not found"。书库接口（`/documents`、`/collections`、书的文件、阅读、覆盖、用量、元数据建议）2026-10-19 起也照这条（以前库读错一律报 404）。
  任务在、原始文件或报告还没产出也是 `404`，但带 `error.details.reason = "not_ready"`，见下面的「还没产出」。
- `409`: 请求没问题，但任务或产物的当前状态不允许该操作（任务在跑、产物不在、请求结果不确定……）。任务操作的 409 都带 `error.details.reason`，见下面的「机器可读原因」。
- `500`: 后端内部错误。响应里不带原因，只带编号：`message` 是 `internal server error (ref <编号>)`，
  `error.details.error_id` 是同一个编号，凭它在后端日志里搜 `error_id=<编号>` 找完整原因。

## 400 和 409 的分工

2026-10-19 定下的规矩，所有接口照这个来：

- 请求本身写错了 = `400`。字段值不合法、组合不支持（例如 `create_new_job=false` 用在 `ocr`）、请求体里有不认识的字段（拼错的字段不会被悄悄忽略）。
  收紧了查询参数的接口（见[分页](03-分页.md)第 5 条，书库的书、合集、搜索 2026-10-22 起也是），查询串里不认识的参数同样 400，
  message 是 ``unknown field `<名字>`, expected one of ... in the query string``；请求体的是 ``... in the request body``。
  都只带字段名、不带值。
- 请求没问题，是任务或产物现在的状态不允许 = `409`。同一个请求等状态变了可能就成功。
- 判断顺序：先看请求写没写对（400），再看状态（409）。在跑的任务收到写错的请求，得到的是 400，不是 409。

## 机器可读原因：`error.details.reason`

4xx 可以带一个稳定的 `reason`，客户端按它分支，不要解析 `message`（`message` 是给人看的，措辞会变）。
信封和没有 reason 的同状态码错误完全一样（同样的顶层 `code`、`error.code`、`message`），只是 `error.details` 里多一个字段：

```json
{
  "code": 40900,
  "message": "job is queued or running; cancel it before retrying a stage",
  "error": {
    "code": "CONFLICT",
    "http_status": 409,
    "details": { "reason": "job_active" }
  }
}
```

没有 reason 的错误 `details` 是 `{}`。`reason` 只增不改：客户端对不认识的值按「状态不允许，看 `message`」处理。

### 任务操作的 409 原因

适用于 `POST /jobs/{job_id}/actions/` 下的 `retry-stage`、`resume`（旧名 `rerun`）、`resolve-ocr-ambiguity`、`cancel`。

| `reason` | 什么时候 | 接口 |
|---|---|---|
| `job_active` | 任务在排队或运行，先取消再操作。原地重跑（原地重渲染、精修、续跑里的原地重渲染）两个请求读到同一个终态时，后到的那个也是这个原因：前一个已经开跑 | `retry-stage`（所有阶段，含原地重渲染、精修）、`resume`/`rerun`、`resolve-ocr-ambiguity` |
| `job_not_active` | 取消一个不在排队/运行的任务 | `cancel` |
| `artifacts_missing` | 这个阶段或续跑要用的产物、原始来源（upload_id / source_url）已经不在 | `retry-stage`、`resume`/`rerun` |
| `translations_not_owned` | 精修要写回任务自己的译文目录，但这个任务渲染的是别的任务的译文，请去精修源任务 | `retry-stage stage=refine` |
| `ambiguous_ocr_dispatch` | OCR 派发的结果不确定：先 `resolve-ocr-ambiguity` 绑定已有回执，或 OCR 重试时带 `ambiguous_request_policy=accept_duplicate_risk`。不能拿「从翻译阶段重试」处理 | `retry-stage`（ocr）、`resume`/`rerun` |
| `ambiguous_translation_request` | 翻译请求的结果不确定：`retry-stage` 选 translation 并带 `ambiguous_request_policy=accept_duplicate_risk`（通用续跑一律挡住） | `retry-stage`（translation）、`resume`/`rerun` |
| `request_journal_corrupt` | 翻译请求日志损坏，接受重复风险也修不好 | `retry-stage stage=translation`、`resume`/`rerun` |
| `model_executor_unsupported` | 任务绑定了 Rust 模型执行器，这条旧路径不支持（精修，或除渲染外的重试 / 续跑） | `retry-stage`、`resume`/`rerun` |
| `stale_resolution` | OCR 歧义处理的 `resolution_revision` 过期，或已被别的请求处理；原地重跑时：读到任务之后它已经又跑过一次（运行代次变了），刷新再试 | `resolve-ocr-ambiguity`、`retry-stage`（原地 render / refine）、`resume`/`rerun`（原地重渲染） |
| `no_ocr_dispatch` | 任务没有可处理的 OCR 歧义：既不是失败也不是已取消，或没有记录在案的派发 | `resolve-ocr-ambiguity` |
| `ocr_dispatch_unsupported` | 不确定的 OCR 派发属于不支持绑定收据的服务商/操作 | `resolve-ocr-ambiguity` |
| `glossary_missing` | 出新任务的重跑要按现在的术语表重新解析，源任务用的表已经删了（2026-10-22 起，以前是 `404 glossary not found`）。`retry-stage` 可在 `overrides.translation.glossary_id` 换表或填空串；只在提交时才知道，`disabled_code` 里没有 | `resume`/`rerun`、`retry-stage`（ocr、translation 出新任务）、`resolve-ocr-ambiguity`（绑定回执） |
| `glossary_disabled` | 同上，表还在但已停用（`enabled=false`） | 同上 |

同时命中多条时 `job_active` 最先判，其余的先后不保证。

`GET /jobs/{job_id}/actions` 的每个阶段的 `disabled_code`、`GET /jobs/{job_id}/actions/resume` 的 `reason_code`
是同一套值（文字说明仍在 `disabled_reason` / `reason`），可以不发请求就知道会得到哪个原因。

### 删除的 409 原因

`DELETE /jobs/{job_id}`、`DELETE /documents/{document_id}`（书架删除的旧地址 `DELETE /library/books/{job_id}` 2026-10-22 删了）。

| `reason` | 什么时候 | 接口 |
|---|---|---|
| `job_active` | 要删的任务（书本身、`-ocr` 子任务、书名下的任一任务）在排队或运行；带 `force=true` 会先取消再删。和任务操作的 `job_active` 是同一个值 | `DELETE /jobs/{job_id}`、`DELETE /documents/{document_id}` |
| `job_has_dependents` | 删除范围之外还有别的任务在用被删任务的产物（`source.artifact_job_id` 指向它，典型是重新排版的 render 任务；或者单删 OCR 子任务 `P-ocr` 而父任务 `P` 还在）；先删依赖者，或带 `force=true` | `DELETE /jobs/{job_id}` 和它的旧地址（`DELETE /documents/{document_id}` 的依赖者在别的书里时也会触发） |

「任务在排队/运行」的 409 以前没有 `reason`，2026-10-19 起带 `job_active`。两条都命中时先报 `job_active`。见 [删除任务](../01-任务/05-删除任务.md)。

### 书的元数据建议的原因

`POST|GET /documents/{document_id}/metadata-suggestions`、`POST …/metadata-suggestions/{suggestion_id}/apply` 的错误
顶层 `code` 是字符串码（如 `DOCUMENT_TITLE_CHANGED`），`error.details.reason` 是小写的稳定原因（2026-10-19 起有，以前 `details` 是 `{}`）。
书不存在、书的原文 PDF 不在磁盘上是普通 `404`，不带 reason。

| `reason` | HTTP | 顶层 `code` | 什么时候 |
|---|---|---|---|
| `field_unsupported` | 400 | `DOCUMENT_METADATA_FIELD_UNSUPPORTED` | `fields` 要了 `title` 以外的字段 |
| `job_not_found` | 404 | `OCR_JOB_NOT_FOUND`（`error.code` 是 `DOCUMENT_METADATA_JOB_NOT_FOUND`） | 点名的 `job_id` 不存在 |
| `job_mismatch` | 409 | `DOCUMENT_METADATA_JOB_MISMATCH` | 点名的任务不属于这本书 |
| `source_not_ready` | 409 | `DOCUMENT_METADATA_SOURCE_NOT_READY` | 点名的任务还没有可读的规范化 OCR 文档 |
| `source_invalid` | 409 | `DOCUMENT_METADATA_SOURCE_INVALID` | 规范化 OCR 文档坏了（以前 422） |
| `title_candidate_not_found` | 409 | `DOCUMENT_TITLE_CANDIDATE_NOT_FOUND` | 原文 Info 和 OCR 里都还没有可用的书名（以前 422） |
| `source_too_large` | 413 | `DOCUMENT_METADATA_SOURCE_TOO_LARGE` | 规范化 OCR 文档超过 256MB |
| `suggestion_not_found` | 404 | `DOCUMENT_METADATA_SUGGESTION_NOT_FOUND` | 这本书没有这条建议 |
| `title_changed` | 409 | `DOCUMENT_TITLE_CHANGED` | 书名被用户锁定，或来源已经不是文件名 |
| `revision_conflict` | 409 | `DOCUMENT_REVISION_CONFLICT` | `expected_document_updated_at` 过期 |

`OCR_JOB_NOT_FOUND` 这个顶层码建任务复用 OCR 时也在用（那边多带顶层 `reason`、`can_fallback_to_ocr`），所以元数据接口的
`error.code` 换成了 `DOCUMENT_METADATA_JOB_NOT_FOUND`，两边 `error.details.reason` 都是 `job_not_found`。
细节见 [元数据建议](../../../backend/api/docs/api-spec/document-metadata.md#stable-errors)。

### 还没产出（404）

2026-10-19 定下的规矩（[规矩和删留](../../ops/planning/api-reorg/20261019-任务接口规矩和删留.md) 第 2 条），所有接口照这个来：

- **任务（或书）本身不存在**：普通 `404`，`error.details` 是 `{}`，提示 `job not found: …`（书是 `document not found: …`）。
  书的用量 `GET /documents/{document_id}/usage` 也是：书不存在 `404`（2026-10-19 以前给 `200` 和全零汇总）；有书没任务照旧 `200` 空汇总。
- **原始文件和报告**：任务在、要的东西还没产出，返回 `404` + `error.details.reason = "not_ready"`，提示统一是 `<名字> not ready`
  （`<名字>` 是缺的那个文件或报告，如 `translated.pdf not ready`、`all.zip not ready`、`refine report not ready`）。
  等任务往下跑、这一步做完，同一个请求就能成功。
- **摘要类**（质量摘要、用量、失败诊断、各种列表、取数目录、阅读区块和元信息）：照旧 `200`，没有的部分给 `null`、空列表、`0`
  或 `available: false`，不报 404。
- 名字本身写错（没有这个文件名、这个数据集、这个条目、这一页）是普通 `404`，不带 `reason`：那不是"还没好"，是"没有"。

```json
{
  "code": 40400,
  "message": "all.zip not ready",
  "error": {
    "code": "NOT_FOUND",
    "http_status": 404,
    "details": { "reason": "not_ready" }
  }
}
```

客户端分「任务没了」和「还没好」只看 `reason`，不要解析 `message`。

| 接口 | 还没产出时 |
|---|---|
| `GET /jobs/{job_id}/files/output/{name}`、`files/pages/{page}.jpg`、`files/internal/{name}` | `404` + `not_ready`，`<名字>` 见 [下载总览](../07-产物下载/01-下载总览.md#通用约定)。`all.zip` 以前是 `409`，现在也是这个 |
| `GET /jobs/{job_id}/reader/markdown` | `404` + `not_ready`（`markdown not ready`） |
| `GET /jobs/{job_id}/reports/translation`、`translation-qa`、`layout-fit`、`refine` | `404` + `not_ready`（`translation report not ready` 等） |
| `GET /jobs/{job_id}/translations/{item_id}`、`…/revisions`，`PATCH …/translations/{item_id}`，`POST …/replay` | 还没有翻译清单：`404` + `not_ready`（`translation manifest not ready`）；清单在、条目不在是普通 `404` |
| `GET /jobs/{job_id}/translations` | `200`，空列表（以前是 `404`） |
| `GET /jobs/{job_id}/reports/quality`、`reports/quality/items` | `200`，各段 `null` / 空清单（任务还没有输出目录时以前是 `404`） |
| `GET /jobs/{job_id}/data`、`data/{dataset}` | `200`，`available: false`（任务还没有输出目录时以前是 `404`） |
| `GET /jobs/{job_id}/reports/usage`、`reports/failure`、`files`、`reader/regions`、`reader/metadata` | `200`，空值（没变） |

暂时不在这条规矩里的：

- 边翻边看 `GET /jobs/{job_id}/progress/layout` 还没就绪是 `409` + `error.code = "LIVE_TRANSLATION_LAYOUT_NOT_READY"`，
  `progress/pages/{page}` 还没提交是 `404` + `LIVE_TRANSLATION_PAGE_NOT_COMMITTED`。前端按这两个 `error.code` 决定要不要重试，保持不动。
- 书的原文 PDF 不在磁盘上（`/documents/{document_id}/files/…`、`/documents/{document_id}/reading`）是普通 `404`：原文随上传就有，不在就是丢了，不会"过一会儿产出"。

### 合并阅读过期（404 `merged_reading_expired`）

一本书翻译过好几次、每次只翻几页时，`GET /documents/{document_id}/reading` 返回合并结果的虚拟任务 id
`merged-<书的编号>-<指纹>`，阅读器按普通任务读它（`/jobs/{job_id}`、`files/…`、`reader/…`）。合并目录超过一天**没人读**、
而这本书又生成了新的合并时，旧目录会被清理（按最后一次被读的时间算，不是按生成时间；阅读入口现在指向的那个不删）。

之后拿着旧 id 的读请求返回 `404`，`message` 和任务不存在一样（`job not found: merged-…`），但带
`error.details.reason = "merged_reading_expired"`：

```json
{
  "code": 40400,
  "message": "job not found: merged-…-0123456789abcdef",
  "error": {
    "code": "NOT_FOUND",
    "http_status": 404,
    "details": { "reason": "merged_reading_expired" }
  }
}
```

客户端看到它就重新调一次 `GET /documents/{document_id}/reading`（书的编号就是 id 中间那 64 位），换成新 id 接着读。
id 本身格式不对（不是 `merged-<64 位十六进制>-<16 位十六进制>`）仍是不带 reason 的普通 `404`。2026-10-19 加入。

### 只能服务器定的 OCR 选项（400）

建任务请求的 `ocr.options` 里带了只能服务器定的选项——本地 / 命令型 OCR 要执行的 `command`、原始结果的转换器名
`raw_provider`、`ocr_providers.json` 里带 `env` 的——返回 `400`，`message` 以 `ocr.options.<键> is server-owned` 开头
（几个键一起带时是 `ocr.options.command, ocr.options.raw_provider are server-owned`），不带 `reason`：是请求写错了，换个状态也一样。
`POST /jobs`、`POST /documents/{document_id}/translate`、`/ocr`、`retry-stage` 的 `overrides.ocr.options` 都是。
老任务请求里存着的这些键，重跑、阶段重试复制请求时去掉，不会因此 400。哪些选项属于这类看 `GET /providers/ocr` 的
`client_settable`。2026-10-22 加入，见 [OCR 提供方列表](../03-OCR/01-provider列表.md)。

### 凭据的 409 原因

`POST|PUT|DELETE /api/v1/credentials…` 的 `409`。顶层 `code` 和 `error.code` 照旧是大写码，`error.details.reason`
是小写的稳定原因（2026-10-22 起有，以前 `details` 是 `{}`）。其余凭据错误不带 reason。

| `reason` | `error.code` | 什么时候 | 接口 |
|---|---|---|---|
| `credential_in_use` | `CREDENTIAL_IN_USE` | 还有任务（含已结束的）引用这条凭据（2026-11-03 起不再查 AI 运行时配置）；确认影响后带 `force=true` | `DELETE /credentials/{credential_ref}` |
| `credential_revision_conflict` | `CREDENTIAL_REVISION_CONFLICT` | `expected_credential_revision` 过期：这条凭据在别处改过 | `PUT /credentials/{credential_ref}` |
| `credential_vault_revision_conflict` | `CREDENTIAL_VAULT_REVISION_CONFLICT` | 凭据库级的 `expected_revision` 过期（旧客户端写法） | `POST`、`PUT`、`DELETE` |

`PUT` 换 `kind` 是 `400`（请求写错了），先于这两种修订号的 `409`。

### 服务没就绪（503）

`GET /ready` 不就绪时 HTTP `503`，信封 `code: 50300`、`message: "not ready"`，`error.code = "SERVICE_UNAVAILABLE"`，
`error.details.reasons` 列出原因（`db_unavailable`、`jobsd_not_healthy`；AI 服务 2026-11-03 删了，`ai_service_not_healthy` 不会再出现）；`data` 照旧是整份就绪视图。
2026-10-22 以前 503 时信封仍是 `code: 0`、`message: "ok"`。判断就绪看 HTTP 状态码。字段见
[接口总览](../../core/api/index.md#健康和就绪)。

### 磁盘快满了（503 `insufficient_storage`）

2026-10-24 起。数据目录所在磁盘的剩余空间低于下限（`RUST_API_MIN_FREE_DISK_MB`，默认 1024，`0` 不查）时，新上传、
建任务（`POST /jobs`、书的翻译和 OCR、重试、续跑……所有新建任务的入口）、原地重跑返回 HTTP `503`，信封 `code: 50300`、
`error.code = "SERVICE_UNAVAILABLE"`、`error.details.reason = "insufficient_storage"`，`message` 写着还剩多少、要多少（MiB）。
被拒时什么都没写：上传目录、任务行、任务目录都没有新东西。已经在跑的任务不管。上传在读请求体之前先查一次下限，
收完文件再按「下限 + 两倍文件大小」查一次（原文要落两份）。拿不到剩余空间（Windows）时不拦。`GET /health` 的 `disk` 报当前剩余空间。

### 排队的任务满了（429 `queue_full`）

2026-10-24 起。排队（还没开跑）的任务已经有上限那么多（`RUST_API_MAX_QUEUED_JOBS`，默认 1000，`0` 不限）时，建任务
（所有新建任务的入口，同上）、原地重跑返回 HTTP `429`，信封 `code: 42900`、`error.code = "TOO_MANY_REQUESTS"`、
`error.details.reason = "queue_full"`，`message` 写着现在排着几个、上限是多少。在跑的任务不算。被拒时什么都没写。
等前面的任务开跑以后再交。两个请求同时卡在差一个满时会一起进去，多出一两个，这个上限是挡跑飞的脚本的，不是精确配额。

### 正在恢复备份（409 `restore_in_progress`）

2026-10-28 起。恢复数据库备份（`POST /backups/{id}/restore`）从检查备份到换库的那几秒里，上传（`POST /uploads`）、建任务
（所有新建任务的入口，同上）、原地重跑返回 HTTP `409`，`error.code = "CONFLICT"`、`error.details.reason = "restore_in_progress"`，
`message` 是英文的「a database backup is being restored; try again in a moment」。被拒时什么都没写（这期间建出来的东西会被换库
盖掉，任务目录、上传文件却留着，所以干脆不建）。恢复开始前已经在建的会先做完，恢复再开始。等恢复结束（`GET /backups` 的
`running` 变回 `false`）再交。

### 备份和同步的 409 原因

2026-10-22 起有（以前 `details` 是 `{}`）。见 [数据库备份](../10-备份/01-数据库备份.md)、[多设备同步](../09-同步/01-多设备同步.md)。

| `reason` | 什么时候 | 接口 |
|---|---|---|
| `restore_blocked` | 有任务在排队或运行、AI 正在改文档、AI 有计算没算完；恢复开头和换库前各查一次 | `POST /backups/{id}/restore` |
| `backup_damaged` | 备份文件坏了。以前是 `400`：请求没写错，是那份文件的状态不允许 | `POST /backups/{id}/restore` |
| `backup_newer` | 备份来自更新版本的程序。以前是 `400` | `POST /backups/{id}/restore` |
| `sync_disabled` | 同步没开启 | `POST /sync/run` |
| `sync_not_configured` | 同步开着，但同步位置被清空了 | `POST /sync/run` |
| `restore_in_progress` | 正在恢复备份（见上一节），2026-10-28 加入 | `POST /uploads`、建任务的入口、原地重跑 |

### 术语表的 409 原因

| `reason` | 什么时候 | 接口 |
|---|---|---|
| `glossary_changed` | `PUT` 带的 `expected_updated_at` 和表现在的 `updated_at` 不一样：表在读完之后被别处（界面、AI 终端）改过。重新读一次再改；不带 `expected_updated_at` 照旧后写覆盖。2026-10-22 加入 | `PUT /glossaries/{glossary_id}` |

建任务时 `translation.glossary_id` 指向不存在或停用的表是 `400`（请求写错了；以前不存在是 `404`）。术语表读不出来（库被锁、词条坏了）是 `500`，不再说成 `404` 或空表。见 [术语表](../04-翻译/03-术语表.md)。
