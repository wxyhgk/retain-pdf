# 防重复提交

2026-11-24 起。建任务、续跑、重试都会建要花钱的任务（调 OCR、调翻译模型），双击按钮、网络超时后重发不能建出两个。
后端有两道防线，方案和取舍见 [防重复提交](../../ops/planning/api-reorg/20261124-防重复提交.md)。

## 1. 续跑、重试的查重（不用改调用方）

续跑（`POST /jobs/{job_id}/actions/resume`，旧名 `rerun`）、重试阶段（`POST /jobs/{job_id}/actions/retry-stage`）、
OCR 歧义处理（`POST /jobs/{job_id}/actions/resolve-ocr-ambiguity`）**出新任务**时：如果这个源任务已经续跑 / 重试出一个
还在排队或在跑的新任务，回 `409`，`error.details.reason = "derived_job_active"`，`error.details.active_job_id` 是那个任务的编号。
等它结束（成功、失败、取消都算）或先取消它，再续跑、重试就可以了。

- 「查有没有在跑的派生任务」和「落库」在同一个数据库事务里，两个请求同时到也只建成一个。
- 只看从**这个源任务**派生的任务：别的源任务、`POST /jobs` 新建的任务不算。
- 原地执行（续跑里的原地重渲染、`retry-stage` 的原地 render / refine）不经这里：源任务自己就是那个任务，
  它在排队 / 运行时是 `job_active`，两个请求读到同一个终态时后到的也是 `job_active`（原有的防并发）。
- 只在提交时才知道，`GET /jobs/{job_id}/actions` 的 `disabled_code`、`GET .../actions/resume` 的 `reason_code` 里没有这个值。
- 2026-11-24 以前建的派生任务没有记录，升级那一刻还在跑的那几个查不到。

## 2. `Idempotency-Key` 请求头（调用方带上才生效）

语义照 IETF 草案 [draft-ietf-httpapi-idempotency-key-header](https://datatracker.ietf.org/doc/draft-ietf-httpapi-idempotency-key-header/)。

### 哪些接口接受

接口登记表里行尾标了 `[idempotent]` 的（`backend/api/src/app/router/`），现在是这 7 个，别的接口带了这个头也不管：

| 接口 | 说明 |
|---|---|
| `POST /jobs` | 新建任务 |
| `POST /documents/{document_id}/translate` | 翻译这本书 |
| `POST /documents/{document_id}/ocr` | 给这本书做 OCR |
| `POST /jobs/{job_id}/actions/resume` | 续跑 |
| `POST /jobs/{job_id}/actions/rerun` | 续跑的旧名 |
| `POST /jobs/{job_id}/actions/retry-stage` | 重试某个阶段 |
| `POST /jobs/{job_id}/actions/resolve-ocr-ambiguity` | OCR 歧义处理（成功后建恢复任务） |

### 怎么用

用户每点一次「翻译 / 续跑 / 重试」生成一个新的 key（UUID 就行），放进请求头；**这一次点击的网络重试复用同一个 key**，
下一次点击换新的。

```http
POST /api/v1/jobs/20261124093000-a1b2c3/actions/resume HTTP/1.1
X-API-Key: ...
Idempotency-Key: 8e03978e-40d5-43e8-bc93-6894a57f9324
```

- key：1–255 个可见 ASCII 字符（`0x21`–`0x7E`，不能有空格）。也接受草案里结构化字段的写法 `"8e03…"`，外面一对引号去掉后是同一把 key。
  不合法、同一个头发了两次：`400`。
- 不带这个头：和以前完全一样。

### 语义

key 按（用户，方法 + 路由模板，key）认：同一把 key 用在不同接口上互不相干；多用户模式下各用户的 key 互不相干（单机模式都是本机用户）。
每条记录带请求指纹：方法、实际路径（含查询串）、请求体的 sha256。

| 情形 | 回应 |
|---|---|
| 第一次见这把 key | 照常处理。成功（2xx）就存下状态码和响应体；不成功（4xx、5xx）不存、删掉记录，可以带同一把 key 重试 |
| 同一把 key、同一个请求、已经处理完 | **不再执行**，原样回存下的状态码和响应体，多一个响应头 `Idempotent-Replayed: true` |
| 同一把 key、上一个请求还在处理 | `409`，`error.details.reason = "idempotency_key_in_flight"`：稍后用同一把 key 再试 |
| 同一把 key、请求不一样（方法、路径或请求体变了） | `409`，`error.details.reason = "idempotency_key_reused"`：换一把新 key |
| 记录过了 24 小时 | 当新请求（过期的记录在同一把 key 再来时删掉，定期清理也删） |

- 只有成功会被记住：第一次 `429 queue_full`、`409 derived_job_active` 之类，用同一把 key 重试会真的再执行一次。
- 重放的是第一次的响应体原样，里面的链接（`links`、`actions`）是第一次请求时按那时的地址生成的。
- 客户端断开（网络重试的典型情形）时后端照样处理完、把结果记下，重试拿到的是那次的结果。
- 不合规矩的 key 是 `400`；`idempotency_key_reused` 用 `409` 而不是草案建议的 `422`：全站 422 正在统一成 400 / 409。

### 和续跑查重的关系

两者互补：`Idempotency-Key` 管「同一次点击的重发」（重放第一次的结果，不报错）；续跑查重管「已经有一个在跑了又点了一次」
（409 `derived_job_active`，带在跑任务的编号）。续跑带同一把 key 重发，得到的是第一次的 200 重放，不是 409。

## 实现位置

- 续跑查重：`backend/packages/retainpdf-jobs/src/lifecycle/creation/submit.rs`（`NewJob::derived_run_of`），
  派生关系表 `job_derivations`（`database/retainpdf-db/src/db/job_derivations.rs`，迁移 v38）。
- `Idempotency-Key`：中间层 `backend/api/src/app/idempotency.rs`，记录表 `idempotency_keys`
  （`database/retainpdf-db/src/db/idempotency_keys.rs`，迁移 v38），过期清理挂在 `backend/api/src/app/cleanup.rs`。
- CORS：单机模式请求头照预检回显、响应头全部暴露（`Idempotent-Replayed` 读得到）；多用户模式（已停）没暴露响应头。
