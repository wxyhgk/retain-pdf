# 响应格式

除文件下载接口外，后端 JSON 响应统一使用包装对象。

## 成功响应

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

字段说明：

- `code`: 业务状态码。`0` 表示成功。
- `message`: 面向人类的短消息。
- `data`: 具体响应体。

## 错误响应

所有出错的回应（含未登记的地址 `404`、方法不对 `405`、请求体太大 `413`）都是同一个信封，由
`backend/packages/retainpdf-api-base/src/error.rs` 的 `AppError` 生成：

```http
HTTP/1.1 409 Conflict
Content-Type: application/json
X-Request-ID: 3f9c2a7d1b4e8a60
```

```json
{
  "code": 40900,
  "message": "job is queued or running; cancel it before retrying a stage",
  "error": {
    "code": "CONFLICT",
    "http_status": 409,
    "details": { "reason": "job_active" }
  }
}
```

- `code`：顶层码。一般是「HTTP 状态 × 100」的数字（`40000`、`40100`、`40400`、`40900`、`41300`、`42200`、`42900`、`50000`……）；
  少数接口是字符串（见下）。
- `message`：给人看的一句话（英文），不要拿它做判断，以后可能改写。
- `error.code`：稳定的字符串码，大写下划线：`BAD_REQUEST`、`UNAUTHORIZED`、`FORBIDDEN`、`NOT_FOUND`、`METHOD_NOT_ALLOWED`、
  `CONFLICT`、`EVENT_CURSOR_EXPIRED`（`410`）、`PAYLOAD_TOO_LARGE`、`UNSUPPORTED_MEDIA_TYPE`、`UNPROCESSABLE_ENTITY`、
  `TOO_MANY_REQUESTS`、`BAD_GATEWAY`、`SERVICE_UNAVAILABLE`、`INTERNAL`，以及各接口自己的码（`CREDENTIAL_IN_USE`、
  `DOCUMENT_TITLE_CHANGED`、`TRANSLATION_REVISION_CONFLICT`……）。
- `error.http_status`：和 HTTP 状态码相同。
- `error.details`：附加信息，没有时是 `{}`。最常见的是 `reason`——同一个 `error.code` 下的稳定小写原因（`job_active`、
  `not_ready`、`queue_full`、`restore_in_progress`……），各接口的取值见 [认证与错误](02-认证与错误.md#机器可读原因errordetailsreason)。
- 错误信封里**没有** `data`（`GET /ready` 不就绪的 `503` 例外：照旧带整份就绪视图，见认证与错误）。
- `500`：`message` 是 `internal server error (ref <error_id>)`，`error.details.error_id` 是同一个编号；具体原因只进服务端日志
  （日志里带着这个 `error_id`），不回给调用方。
- 每个回应（成功、出错都一样）都带回应头 `X-Request-ID`，报问题时连同 `error_id` 一起给出来，见
  [请求编号](02-认证与错误.md#请求编号)。

**客户端怎么分支**：看 `error.code`（字符串）和 `error.details.reason`。顶层 `code` 只为兼容旧调用方保留：大多数接口是数字，
凭据（`CREDENTIAL_IN_USE`……）、书的元数据建议（`DOCUMENT_TITLE_CHANGED`……）、账号登录（`INVALID_CREDENTIALS`……）、
译文修订（`TRANSLATION_REVISION_CONFLICT`……）、边翻边看这些接口是字符串，而且不一定和 `error.code` 相同（例如元数据建议的
顶层 `OCR_JOB_NOT_FOUND` 对应 `error.code = "DOCUMENT_METADATA_JOB_NOT_FOUND"`）。不要拿顶层 `code` 做判断。

各接口自己的码（凭据、边翻边看、OCR 复用……）同时出现在顶层 `code` 和 `error.code`；这些接口原来放在顶层的字段
（如 OCR 复用的 `reason`、`can_fallback_to_ocr`）照旧留在顶层，同时抄一份进 `error.details`，新代码读 `error.details`。
`error.details` 只放写进文档的、不含密钥的信息，错误信息里不会有凭据、签名地址、服务商原始请求或绝对路径；
文档没写的键不要拿来判断能不能重试、有没有权限。

### 请求本身解析不了

JSON 请求体、查询串、路径参数、multipart 解析失败，统一成上面的信封，`message` 是固定的几句，不回解析器细节、字段追踪、
请求体内容（2026-11-24 从 `backend/api/docs/api-spec/storage-and-errors.md` 合并过来，提示文字见
`backend/api/src/routes/common/extractors.rs`）：

| 情况 | HTTP | 顶层 `code` | `error.code` | `message` |
|---|---:|---:|---|---|
| JSON 语法错 | 400 | `40000` | `BAD_REQUEST` | `invalid JSON request body` |
| JSON 里有接口不认识的字段 | 400 | `40000` | `BAD_REQUEST` | ``unknown field `<名字>`, expected one of ... in the request body``（只回字段名，不回值） |
| JSON 值和请求结构对不上（类型错、缺字段、枚举值不认识） | 422 | `42200` | `UNPROCESSABLE_ENTITY` | `JSON request body does not match the expected schema` |
| 没有 JSON 的 `Content-Type` | 415 | `41500` | `UNSUPPORTED_MEDIA_TYPE` | `expected an application/json request body` |
| 请求体超过上限 | 413 | `41300` | `PAYLOAD_TOO_LARGE` | `request body is too large` |
| 查询串里有接口不认识的参数 | 400 | `40000` | `BAD_REQUEST` | ``unknown field `<名字>`, expected one of ... in the query string``（只回名字；2026-10-22 起，以前是 `invalid query parameters`） |
| 查询参数类型不对、整数越界、缺必填参数 | 400 | `40000` | `BAD_REQUEST` | `invalid query parameters` |
| 路径参数类型不对 | 400 | `40000` | `BAD_REQUEST` | `invalid path parameters` |
| multipart 请求开头就不对 | 400 | `40000` | `BAD_REQUEST` | `invalid multipart request` |

multipart 的文件字段边收边数字节，不信 `Content-Length`，超了照样是 `413` `PAYLOAD_TOO_LARGE`，上限见 [限制](04-限制.md)。

没登记的 `/api/...` 地址回 `404`（`code: 40400`、`error.code: NOT_FOUND`、`message: "route not found"`）。登记了的地址用错了方法：
先照常认证，没通过的回认证错误；通过了回 `405`（`code: 40500`、`error.code: METHOD_NOT_ALLOWED`、`message: "method not allowed"`），
带框架给的 `Allow` 头。

任务运行失败（`status=failed`）不是 HTTP 错误，失败原因看任务详情里的结构化失败信息，具体看 [失败结构](../08-调试诊断/01-失败结构.md)。

模型执行器的三个内部接口（`/api/v1/internal/model/…`）成功时回裸 JSON、不带 `{code, message, data}` 包装；出错仍是上面的信封。

## 压缩

2026-11-03 起：请求带 `Accept-Encoding: gzip` 时，8KB 以上的 JSON 响应用 gzip 压缩再发（`Content-Encoding: gzip`，
`Vary: Accept-Encoding`）。浏览器自动解压，调用方不用改；不带这个头照旧原样返回。下面的文件响应和事件流不压缩
（PDF 等文件要按段读）。

## 文件响应

这些接口直接返回文件流，不使用 JSON 包装：

- `GET /api/v1/jobs/{job_id}/files/output/{name}`（译文 PDF、双语 PDF、Word、原文 Markdown、图片、打包下载）
- `GET /api/v1/jobs/{job_id}/files/pages/{page}.jpg`
- `GET /api/v1/jobs/{job_id}/files/internal/{name}`（中间产物，多用户下只给管理员）
- `GET /api/v1/documents/{document_id}/files/{name}`（原文 PDF、封面、缩略图）
- `GET /api/v1/documents/{document_id}/files/pages/{page}.jpg`

旧地址（`/jobs/{job_id}/pdf`、`/pdf/side-by-side`、`/cover`、`/thumbnail`、`/preview/pages/{page}`、
`/markdown?raw=true`、`/markdown/images/{path}`、`/download`、`/artifacts/{artifact_key}`）已于 2026-10-18 删除；
对照见[下载总览](../07-产物下载/01-下载总览.md)。

前端下载文件时应以 HTTP status 和 `Content-Type` 为准，不要按 JSON 解析。
