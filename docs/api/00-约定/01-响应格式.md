# 响应格式

除文件下载接口外，后端 JSON 响应统一使用包装对象。

## 成功响应

```json
{
  "code": 0,
  "message": "ok",
  "data": {}
}
```

字段说明：

- `code`: 业务状态码。`0` 表示成功。
- `message`: 面向人类的短消息。
- `data`: 具体响应体。

## 错误响应

所有出错的回应（含未登记的地址 `404`、方法不对 `405`、请求体太大 `413`）都是同一个信封，由
`backend/packages/retainpdf-api-base/src/error.rs` 的 `AppError` 生成：

```http
HTTP/1.1 409 Conflict
Content-Type: application/json
X-Request-ID: 3f9c2a7d1b4e8a60
```

```json
{
  "code": 40900,
  "message": "job is queued or running; cancel it before retrying a stage",
  "error": {
    "code": "CONFLICT",
    "http_status": 409,
    "details": { "reason": "job_active" }
  }
}
```

- `code`：顶层码。一般是「HTTP 状态 × 100」的数字（`40000`、`40100`、`40400`、`40900`、`41300`、`42900`、`50000`……）；
  少数接口是字符串，见下面的「[顶层 `code` 的类型](#顶层-code-的类型)」。**不要拿它做判断。**
- `message`：给人看的一句话（英文），不要拿它做判断，以后可能改写。
- `error.code`：稳定的字符串码，大写下划线：`BAD_REQUEST`、`UNAUTHORIZED`、`FORBIDDEN`、`NOT_FOUND`、`METHOD_NOT_ALLOWED`、
  `CONFLICT`、`EVENT_CURSOR_EXPIRED`（`410`）、`PAYLOAD_TOO_LARGE`、`UNSUPPORTED_MEDIA_TYPE`、
  `TOO_MANY_REQUESTS`、`BAD_GATEWAY`、`SERVICE_UNAVAILABLE`、`INTERNAL`，以及各接口自己的码（`CREDENTIAL_IN_USE`、
  `DOCUMENT_TITLE_CHANGED`、`TRANSLATION_REVISION_CONFLICT`……）。`UNPROCESSABLE_ENTITY`（顶层 `42200`）2026-11-24 起不再出现：
  请求体类型、字段写错统一回 `400 BAD_REQUEST`，见 [请求体写错（400）](02-认证与错误.md#请求体写错400)。
- `error.http_status`：和 HTTP 状态码相同。
- `error.details`：附加信息，没有时是 `{}`。最常见的是 `reason`——同一个 `error.code` 下的稳定小写原因（`job_active`、
  `not_ready`、`queue_full`、`restore_in_progress`……），各接口的取值见 [认证与错误](02-认证与错误.md#机器可读原因errordetailsreason)。
- 错误信封里**没有** `data`（`GET /ready` 不就绪的 `503` 例外：照旧带整份就绪视图，见认证与错误）。
- `500`：`message` 是 `internal server error (ref <error_id>)`，`error.details.error_id` 是同一个编号；具体原因只进服务端日志
  （日志里带着这个 `error_id`），不回给调用方。
- 每个回应（成功、出错都一样）都带回应头 `X-Request-ID`，报问题时连同 `error_id` 一起给出来，见
  [请求编号](02-认证与错误.md#请求编号)。

**客户端怎么分支**：看 `error.code`（字符串）和 `error.details.reason`，再加上 HTTP 状态码。不要看顶层 `code`，也不要按它是数字
还是字符串分支——它只为兼容旧调用方保留。

### 顶层 `code` 的类型

2026-11-24 定（第 12 条，见 [顶层 code 的类型](../../ops/planning/api-reorg/20261124-请求体错误统一回400.md#第-12-条顶层-code-的类型)）：

- **现有行为不改。** 大多数错误的顶层 `code` 是数字（「HTTP 状态 × 100」）；下表这几类是字符串，已经在用的客户端照旧能读。
- **客户端做分支判断看 `error.code` 和 `error.details.reason`**，不要看顶层 `code`，更不要看它的类型。
- **以后新加的错误，顶层 `code` 一律用数字**（「HTTP 状态 × 100」，也就是 `AppError` 的普通变体和 `*_because` 构造方法）；
  要给机器看的区分放进 `error.code` 和 `error.details.reason`。下表只减不加。

顶层 `code` 是字符串的地方（`backend/packages/retainpdf-api-base/src/error.rs` 里带 `code: &'static str` 的变体）：

| `AppError` 变体 | 接口 | 顶层 `code` 的取值 | 和 `error.code` 的关系 |
| --- | --- | --- | --- |
| `OcrArtifactReuse` | 复用 OCR 结果建任务：`POST /jobs`、`POST /documents/{document_id}/translate`（带 `source.artifact_job_id`） | `OCR_JOB_NOT_FOUND`、`OCR_JOB_NOT_SUCCEEDED`、`OCR_ARTIFACT_MISSING`、`OCR_ARTIFACT_NOT_REUSABLE`、`OCR_PAGE_COVERAGE_MISMATCH` | 相同；另带顶层 `reason`、`can_fallback_to_ocr`（`error.details` 里也有） |
| `CredentialReference` | 凭据库 `/api/v1/credentials…`，以及建任务时按 `credential_ref` 取凭据 | `CREDENTIAL_IN_USE`、`CREDENTIAL_KIND_MISMATCH`、`CREDENTIAL_NOT_FOUND`、`CREDENTIAL_PROVIDER_MISMATCH`、`CREDENTIAL_REF_INVALID`、`CREDENTIAL_REF_NOT_FOUND`、`CREDENTIAL_REVISION_CONFLICT`、`CREDENTIAL_VAULT_REVISION_CONFLICT`、`CREDENTIAL_VAULT_UNAVAILABLE` | 相同 |
| `LiveTranslation` | 边翻边看 `GET /jobs/{job_id}/progress/layout`、`progress/pages/{page}` | `LIVE_TRANSLATION_LAYOUT_NOT_READY`、`LIVE_TRANSLATION_PAGE_NOT_COMMITTED`、`LIVE_TRANSLATION_LAYOUT_INVALID`、`LIVE_TRANSLATION_SNAPSHOT_INVALID`、`LIVE_TRANSLATION_SNAPSHOT_UNAVAILABLE`、`LIVE_TRANSLATION_EVENT_INVALID` | 相同 |
| `DocumentMetadata` | 书的元数据建议 `/documents/{document_id}/metadata-suggestions…` | `DOCUMENT_METADATA_*`、`DOCUMENT_TITLE_*`、`DOCUMENT_REVISION_CONFLICT`、`OCR_JOB_NOT_FOUND`（全表见[认证与错误](02-认证与错误.md#书的元数据建议的原因)） | 一般相同；**例外**：顶层 `OCR_JOB_NOT_FOUND` 对应 `error.code = "DOCUMENT_METADATA_JOB_NOT_FOUND"` |
| `TranslationRevision` | 改单条译文 `PATCH /jobs/{job_id}/translations/{item_id}` | `TRANSLATION_REVISION_REJECTED`（422）、`TRANSLATION_REVISION_CONFLICT`（409） | 相同 |
| `Account` | 账号、登录、邀请、管理员、平台设置、页数额度（多用户版，2026-10-16 起停止维护） | `INVALID_CREDENTIALS`、`ACCOUNT_DISABLED`、`ACCOUNT_DELETED`、`TOO_MANY_ATTEMPTS`、`USERNAME_TAKEN`、`WEAK_PASSWORD`、`INVITE_*`、`PAGE_QUOTA_EXCEEDED`、`INVALID_*`…… | 相同 |

其余错误（`AppError` 的普通变体，`*_because` 带 `reason` 的，`GET /ready` 的 `503`、事件流里的 `500`）顶层 `code` 都是数字。

任务运行失败（`status=failed`）不是 HTTP 错误，失败原因看任务详情里的结构化失败信息，具体看 [失败结构](../08-调试诊断/01-失败结构.md)。

模型执行器的三个内部接口（`/api/v1/internal/model/…`）成功时回裸 JSON、不带 `{code, message, data}` 包装；出错仍是上面的信封。

## 压缩

2026-11-03 起：请求带 `Accept-Encoding: gzip` 时，8KB 以上的 JSON 响应用 gzip 压缩再发（`Content-Encoding: gzip`，
`Vary: Accept-Encoding`）。浏览器自动解压，调用方不用改；不带这个头照旧原样返回。下面的文件响应和事件流不压缩
（PDF 等文件要按段读）。

## 文件响应

这些接口直接返回文件流，不使用 JSON 包装：

- `GET /api/v1/jobs/{job_id}/files/output/{name}`（译文 PDF、双语 PDF、Word、原文 Markdown、图片、打包下载）
- `GET /api/v1/jobs/{job_id}/files/pages/{page}.jpg`
- `GET /api/v1/jobs/{job_id}/files/internal/{name}`（中间产物，多用户下只给管理员）
- `GET /api/v1/documents/{document_id}/files/{name}`（原文 PDF、封面、缩略图）
- `GET /api/v1/documents/{document_id}/files/pages/{page}.jpg`

旧地址（`/jobs/{job_id}/pdf`、`/pdf/side-by-side`、`/cover`、`/thumbnail`、`/preview/pages/{page}`、
`/markdown?raw=true`、`/markdown/images/{path}`、`/download`、`/artifacts/{artifact_key}`）已于 2026-10-18 删除；
对照见[下载总览](../07-产物下载/01-下载总览.md)。

前端下载文件时应以 HTTP status 和 `Content-Type` 为准，不要按 JSON 解析。
