# 事件总览

> 地址已按 8 类整理（新地址如 `/jobs/{job_id}/progress/events`）。对应的旧地址已于 2026-10-18 删除（返回 404）。新旧对照见 [任务接口分类](../01-任务/04-任务接口分类.md)。

## 接口

```http
GET /api/v1/jobs/{job_id}/progress/events
```

事件流用于展示任务历史和细分进度。**当前阶段和进度以任务详情、列表里的 `stage_snapshot` 为准**，不要从事件里推算当前阶段
（见 [查询任务详情](../01-任务/02-查询任务详情.md)）。只做 OCR 的任务也用这个地址。契约 `contracts/job-events.v2.schema.json`。

2026-11-24 起这一篇合并了 `docs/core/api/index.md` 第 6 节「事件」和 `backend/api/docs/api-spec/runtime-and-events.md`
「Job Events」里的对外用法；事件怎么存、怎么从几处来源合并、怎么重建，见 [事件游标 v2 的设计](../../core/api/event-feed-v2.md)。

## 翻页：游标

| 参数 | 说明 |
|---|---|
| `start` | 第一页从哪头取：`tail`（默认，最近的一页）或 `head`（从最早开始，取全部历史用） |
| `cursor` | 续读：上一次返回的 `next_cursor`，原样带回来。不能和 `start` 一起给 |
| `limit` | 1..=500，默认 500；越界 400（不静默夹） |

不认 `offset`，别的参数也 400。回包 `data`：

```json
{ "protocol_version": 2, "items": [ … ], "next_cursor": "…", "has_more": false, "limit": 500 }
```

- 页面上：先取一页 tail，之后一直用 `next_cursor` 增量取新事件；任务结束时、或者要看完整历史时，从 `start=head` 起一直取到
  `has_more` 为 `false`。
- 每页在开始时钉住一个上界：这一页里不会混进请求开始之后才到的事件，下一次请求再带上；晚到的事件即使时间戳更早，
  也在下一批里出现。初始的 tail 页 `has_more` 恒为 `false`（只读到快照上界）。
- 每条有稳定的 `event_id`；`seq` 是投递位置。显示按时间、去重按 `event_id`，不要拿 `event_id` 或 `seq` 自己拼游标。
- `410`，`error.code = "EVENT_CURSOR_EXPIRED"`：事件历史重建过（来源文件被换、截断、保留期清理……），这个任务的事件窗口
  要清空、重新从 head 或 tail 取。游标格式不对、超过当前上界是 400。任务不存在等原有的 404 / 409 排在解析游标之前。

## 事件结构

```json
{
  "created_at": "2026-06-16T12:00:00Z",
  "seq": 1234,
  "display_stage": "translation",
  "stage": "translating",
  "substage": "translation_batches",
  "lane": "main",
  "event_type": "progress",
  "stage_detail": "正在翻译第 789 / 5216 批",
  "message": "translation batch progress",
  "progress": {
    "unit": "batch",
    "current": 789,
    "total": 5216,
    "percent": 15.1
  }
}
```

## 字段说明

以 `backend/packages/retainpdf-core/src/models/view.rs` 的 `JobEventRecord` 和
`backend/packages/retainpdf-jobs/src/progress/live_stage/canonical_events.rs` 为准：

- `event_id`: 稳定的事件身份，去重用。
- `job_id`、`seq`、`ts`、`created_at`、`level`。`seq` 是这个任务里的投递位置，排序用它，没有时再用 `created_at`。
- `display_stage`: 用户看到的大阶段，事件里只有 `ocr`、`translation`、`render` 三种；算不出来时**没有这个键**（事件里不会出现 `done`）。
- `stage`: 后端内部阶段，如 `ocr_processing`、`translating`、`rendering`，用于诊断，不直接当 UI 大阶段。
- `substage`: 机器可读小阶段（见 [display_stage 与 lane](02-display-stage与lane.md)）。
- `lane`: `main`、`background`（渲染预热 `render_prewarm`）、`artifact`（产物发布）、`diagnostic`（诊断、失败分类）。主状态只认 `main`。
- `event_type`: 归一后的类型，只有 `progress`（原始的 `stage_progress`、`stage_transition`）、`artifact`（`artifact_published`）、
  `terminal`（`job_terminal`）、`error`（`failure_classified`，或级别是 `error`）、`diagnostic`（其余）。
- `raw_event_type`: worker 写的原始类型（`stage_transition`、`artifact_published`……）。`event` 是旧客户端用的别名，新代码读 `event_type`。
- `provider`、`provider_stage`: 服务商私有的进度（如 `mineru_upload`、`paddle_running`），不属于正式阶段枚举。
- `progress`: 唯一正式进度对象 `{unit, current, total, percent}`，`unit` 是 `page`、`batch`、`block`、`step`、`percent`、`none`
  之一；`percent` 只在有 `total` 时给。顶层的 `progress_current` / `progress_total` / `progress_unit`、`user_stage` 不序列化，
  原始值看 `raw`（`source_kind`、`source_seq`、`stage`、`user_stage`、`event_type`）或 `payload.raw_user_stage`。
- `message` / `stage_detail`: 人类文案，不参与判断。
- `payload`: 原样的结构化内容，出接口前脱敏。失败任务的 `failure_classified`、`job_terminal` 事件在 `payload.contracts` 里带和详情
  一样的 `job_stage_contracts.v1`，可以直接从事件流解释缺了哪些产物。

## 前端规则

- 按 `seq` 排序。
- 同一个 `display_stage + substage + progress.unit` 内，优先使用最新事件。
- 主状态选择 `lane=main`。
- 后台预处理展示在辅助区域，不覆盖主阶段。
- 不要用 `message` 关键词判断阶段。

## OCR 子任务的事件和进度快照

- 事件流合并三处来源：库里的事件、`pipeline_events.jsonl`、OCR 子任务 `{job_id}-ocr` 的事件。子任务的事件挂回父任务的
  `job_id`，`payload.source_job_id` 是子任务编号，`payload.source_event` 是子任务原来的那条事件。
- 任务完成后历史事件照旧保留，不要只等最后一条 `finished`。

- 父任务的事件流会并进它的 OCR 子任务（`artifacts.ocr_job_id` 指向的任务）的事件，OCR 期间好显示第 n/m 页。
  2026-11-20 起只并**流程是 `ocr`** 的子任务：复用 OCR 产物的任务以前会把源任务本身（渲染、书籍任务）记成 `ocr_job_id`，
  源任务从头到尾的历史都被并进来，重新翻译开头几分钟进度显示的是源任务的「209/209」。事件投影的版本升了一级，已有的投影会重建。
- 任务详情里的进度（`progress_current`、`progress_total`、`progress_unit`）三个字段取自**同一条**事件：
  当前事件带了数字就整条用它，否则整条用最近一条带数字的进度事件；不会再拿一条事件的数字配另一条事件的单位。

## 服务商限流等待事件（2026-11-23）

请求被服务商限流（429）、过载（529）、暂不可用（503）退避等待时，事件流里多两条 `event_type=progress` 的事件（只加不改）：

- 开始等：`payload.observation.upstream_wait` 是等待信息（字段见 [查询任务详情](../01-任务/02-查询任务详情.md#服务商限流等待stage_snapshotupstream_wait)），
  `payload.observation.upstream_wait_transition = "started"`，`message` 如「服务商限流，等待中（deepseek HTTP 429，约 30 秒后重试）」；
- 等完：`upstream_wait = null`，`upstream_wait_transition = "ended"`，`message` 为「服务商限流等待结束，继续请求」。

两条都照这个阶段最近一条进度原样重发：`stage`、`substage`、`progress`、`stage_detail` 和上一条一样，进度不会倒退。
同一阶段多个请求同时在等只有一对；等待期间其他进度事件的 `payload.observation` 也带 `upstream_wait`。
要显示当前是否在等，读任务详情的 `stage_snapshot.upstream_wait`，不用自己从事件里拼。
