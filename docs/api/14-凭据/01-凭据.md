# 凭据

服务商密钥（翻译模型的 API Key、OCR 服务商的 token）存在后端的凭据库里，客户端拿一个不透明的编号 `credential_ref`
去引用它。**密钥只进不出**：任何接口都不回明文，也不回能还原的打码值。

接口清单见 [接口目录 · 凭据](../00-接口目录/03-凭据.md)（多用户模式下只给管理员）。契约
[`credentials.v1.schema.json`](../../../contracts/credentials.v1.schema.json)。存储、加锁这些实现见
[书库与凭据的内部设计](../../core/api/library-internals.md#凭据库)。

## 接口

```http
GET    /api/v1/credentials
POST   /api/v1/credentials
GET    /api/v1/credentials/{credential_ref}
PUT    /api/v1/credentials/{credential_ref}
DELETE /api/v1/credentials/{credential_ref}?expected_revision=&force=
```

### 一条凭据的元数据

```json
{
  "credential_ref": "cred_0123456789abcdef",
  "kind": "translation_api_key",
  "provider": "deepseek",
  "label": "主力翻译",
  "configured": true,
  "revision": 3,
  "created_at": "…",
  "updated_at": "…"
}
```

没有 `secret` 这个键。

- `credential_ref`：`cred_` 开头，1–64 个小写字母、数字、`_`、`-`。形状不对 `400`。
- `kind`：建任务认两种——`translation_api_key`（`translation.credential_ref`）、`ocr_provider_token`（`ocr.credential_ref`，
  `provider` 要和 `ocr.provider` 对上，比较时去空白、不分大小写）。接口本身只要求它是 1–64 个小写字母、数字、`_`、`-`（会先转小写）。
- `provider` 最多 128 字节，`label` 最多 256 字节，不能有控制字符；`secret` 去掉首尾空白后非空、最多 8192 字节、不能有 NUL。不合规 `400`。

### 列表、读一条

- `GET /credentials` 返回 `{credentials: [...], revision}`，`revision` 是整个凭据库的修订号。**不收任何查询参数**：以前的
  `?include_values=true` 会回全部明文，2026-10-22 删了，现在带它（或别的参数）都是 `400`（``unknown field `include_values`, … in the query string``）。
- `GET /credentials/{credential_ref}` 返回 `{credential, revision}`；没有这条 `404`。

### 新建

```json
{ "kind": "translation_api_key", "provider": "deepseek", "label": "…", "secret": "sk-…", "expected_revision": 12 }
```

返回 `{credential, revision}`。`expected_revision`（可选）是凭据库级的比较交换，过期 `409 CREDENTIAL_VAULT_REVISION_CONFLICT`。

### 更新

```json
{ "provider": "…", "label": "…", "secret": "…", "kind": "translation_api_key", "expected_credential_revision": 3 }
```

- 字段都可选，一个都不给 `400`（`credential update is empty`）。`provider`、`label`、`secret` 能改。
- **`kind` 建了就不能改**：带同样的值可以（去空白、转小写后比，方便前端整份载荷带着），换成别的 `400`，记录不动。
  被任务引用的凭据改了种类，重试时会 `CREDENTIAL_KIND_MISMATCH`；要换种类就新建一条。
- 并发保护：新客户端带 `expected_credential_revision`（这一条的 `revision`），只挡这一条被别处改过，别的凭据变了不算冲突；
  过期 `409 CREDENTIAL_REVISION_CONFLICT`。旧客户端用凭据库级的 `expected_revision`；两个都带时只看 `expected_credential_revision`。
- 判断顺序：没有这条 `404` → 改种类 `400` → 库级修订过期 `409` → 这一条的修订过期 `409`。

### 删除

`DELETE /credentials/{credential_ref}`，查询串只认 `expected_revision`、`force`。返回 `{credential_ref, deleted, revision}`。

- 默认：还有任何已落库的任务请求引用它（**含已结束的**，重试、续跑还要用）就拒绝，`409 CREDENTIAL_IN_USE`。
  回应不透露是哪些任务、有几个。2026-11-03 起不再查 AI 运行时配置里的引用（AI 服务删了）。
- 确认影响后带 `force=true` 照删；那些任务之后就不能重试了。

## 建任务时怎么用

- 新客户端：先 `POST /credentials` 建一条，再在任务里放 `translation.credential_ref` / `ocr.credential_ref`。
  内联的 `translation.api_key`、`ocr.mineru_token`、`ocr.paddle_token`、命令型服务商的 `ocr.options.credential|token|api_key`
  只是兼容输入，不要当长期方案。
- 同一处的内联密钥和 `credential_ref` 不能同时给（`400`）。
- 建任务时校验引用：形状不对 `400 CREDENTIAL_REF_INVALID`、不存在 `404 CREDENTIAL_REF_NOT_FOUND`、种类不对
  `400 CREDENTIAL_KIND_MISMATCH`、OCR 凭据的服务商不对 `400 CREDENTIAL_PROVIDER_MISMATCH`、凭据库读不了 `500 CREDENTIAL_VAULT_UNAVAILABLE`。
- 复用已有 OCR 产物、不用真跑 OCR 的请求不需要 OCR 凭据；带了的内联 OCR 密钥直接丢掉。
- 任务详情、事件、诊断里只有脱敏后的请求：`request_payload` 里内联密钥字段恒为空串，有没有配看 `*_configured`
  （`translation.api_key_configured`、`ocr.mineru_token_configured`、`ocr.paddle_token_configured`）；`credential_ref` 本身不是秘密，会原样返回。
- `GET /providers/ocr` 每个服务商的 `credential` 说明该怎么传：`credential_kind`、`reference_field`（`credential_ref`）、
  `legacy_inline_field`（兼容的内联字段名；旧字段 `field` 同值）、`env`、`required_for`；不需要凭据的服务商是 `credential: null`。
  客户端不要按服务商名字去猜，见 [OCR Provider 列表](../03-OCR/01-provider列表.md)。
- 重试的 `overrides` 可以在内联密钥和 `credential_ref` 之间换，被换下来的那一种在落库前清掉。

## 建任务时内联的密钥

还在发内联密钥的客户端（网页端用浏览器里存的 Key 就是这样），密钥不会留在任务里：落库前后端把它导入凭据库，成为一条
**托管凭据**（响应里看不出来），任务里只存引用。同种类、同服务商、同值的托管凭据复用，不重复建。

托管凭据只在**没有任何已落库任务再引用它**时自动删掉，时机是：

- 删任务（`DELETE /jobs/{job_id}`）之后；
- 删书（`DELETE /documents/{document_id}`，覆盖书名下全部任务）之后；
- 重跑丢掉引用它的旧 `<job_id>-ocr` 子任务之后。

重试的 `overrides` 带了新的内联密钥也会导入；被它替换下来的那条不会因为这次重试就删，要等引用它的任务都删了，或者手动 `DELETE`。

在那之前，即使用户在浏览器里删了 Key，密钥仍留在服务器上——这些任务的重试、续跑还要用它。想不删任务就把密钥从机器上清掉：
`GET /credentials` 列出来，`DELETE /credentials/{credential_ref}`（还有任务引用就带 `force=true`，那些任务之后不能重试）。
对托管凭据显式 `PUT` 一次就转成用户的，以后不再自动删；用户自己建的凭据从不自动删。

## 错误

| `error.code` | HTTP | 什么时候 |
|---|---:|---|
| `CREDENTIAL_REF_INVALID` | 400 | 引用形状不对 |
| `CREDENTIAL_REF_NOT_FOUND` | 404 | 建任务时引用的凭据不存在 |
| `CREDENTIAL_KIND_MISMATCH` | 400 | 凭据存在，但种类不能用在这里 |
| `CREDENTIAL_PROVIDER_MISMATCH` | 400 | OCR 凭据的服务商和 `ocr.provider` 不一致 |
| `CREDENTIAL_IN_USE` | 409 | 还有任务引用，删除要 `force=true` |
| `CREDENTIAL_REVISION_CONFLICT` | 409 | 这一条在你读到之后被改过 |
| `CREDENTIAL_VAULT_REVISION_CONFLICT` | 409 | 库级 `expected_revision` 过期（旧客户端写法） |
| `CREDENTIAL_VAULT_UNAVAILABLE` | 500 | 后端没法安全地读、校验凭据库 |

- 三个 `409` 另带小写的 `error.details.reason`（`credential_in_use`、`credential_revision_conflict`、`credential_vault_revision_conflict`，
  2026-10-22 起，只增），见 [认证与错误 · 凭据的 409 原因](../00-约定/02-认证与错误.md#凭据的-409-原因)；其余凭据错误 `details` 是 `{}`。
- 顶层 `code`、`message` 是兼容字段，新客户端看 `error.code`：

  ```json
  { "code": "CREDENTIAL_REF_NOT_FOUND", "message": "credential reference not found",
    "error": { "code": "CREDENTIAL_REF_NOT_FOUND", "http_status": 404, "details": {} } }
  ```

- 凭据管理接口自己的校验仍可能用通用的 `BAD_REQUEST`、`NOT_FOUND`（例如读、改、删一条不存在的凭据是通用 `404`）。
- 请求体、路径、查询串（列表、删除）不认识的字段 `400`，报错用统一的固定文案，不回解析细节。命中了路由但方法不对，先过认证再回 `405`。
- 错误里不会出现密钥、打码值、凭据库路径或存着的记录。
