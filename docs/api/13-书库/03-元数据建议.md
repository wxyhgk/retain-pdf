# 元数据建议

从原文 PDF 的 Info 和规范化 OCR 结果里找书名候选，存成可审查、刷新后能找回的「建议」。OCR、模型都不会直接改书名，
只能经过下面带护栏的「应用」。字段以契约 [`library-documents.v1.schema.json`](../../../contracts/library-documents.v1.schema.json)
（`DocumentMetadataSuggestionView` 等）为准。

```http
POST /api/v1/documents/{document_id}/metadata-suggestions
GET  /api/v1/documents/{document_id}/metadata-suggestions?limit=20
POST /api/v1/documents/{document_id}/metadata-suggestions/{suggestion_id}/apply
```

## 生成一条建议

```json
{ "job_id": "可选，某个 OCR 任务", "fields": ["title"], "apply_if_default": true }
```

- `job_id`：必须属于这本书、并且登记过可读的规范化 OCR 文档；不给就挑这本书最新的可用任务（没登记规范化文档的任务跳过）。
- `fields`：现在只支持 `title`（默认就是它），别的 `400`。留成数组是为了以后加作者、年份、DOI。
- `apply_if_default`：只在书名还是默认来源时顺手应用——`title_source = "filename"` 且 `title_locked = false`。
  **不再拿书名和当前文件名比**（2026-10-19）：同一本书换个文件名再传，书名照旧能自动命名。用户手动改过的书名
  （`PATCH /documents/{id}` 会设 `title_source = "user"`、`title_locked = true`）不会被覆盖。
- 请求体不认识的字段 `400`（拼错的 `apply_if_default` 不会悄悄变成「不应用」）。前端发的是 `{job_id, fields: ["title"], apply_if_default: true}`。
- 候选来源：OCR 的 `structure_role=document_title`，服务商原始类型 `doc_title`，旧的 `structure_role=title + layout_role=title`，
  `layout_role=title` 且 `sub_type` 是 `title`/`doc_title`，以及 PDF Info 的 `Title`。一般的小标题、摘要不算。
  只看规范化文档的前 8 页；加密 PDF 不读 Info。

返回（建议先落库再返回，刷新或断线后用 `GET` 能找回）：

```json
{
  "suggestion_id": "meta-20260903123000-a1b2c3",
  "document_id": "…",
  "source_job_id": "…",
  "artifact_sha256": "…",
  "status": "completed",
  "fields": ["title"],
  "title_candidates": [
    {
      "value": "A Reliable Paper Title",
      "source": "ocr_structure",
      "confidence": 0.99,
      "evidence": [
        { "source": "normalized_document", "page_idx": 0, "block_id": "p001-b0001",
          "structure_role": "document_title", "layout_role": "title" }
      ]
    }
  ],
  "selected_title": "A Reliable Paper Title",
  "generation_method": "ocr_structure",
  "needs_ai_review": false,
  "applied": false,
  "can_apply": true,
  "created_at": "2026-09-03T12:30:00Z",
  "updated_at": "2026-09-03T12:30:00Z"
}
```

- `source_job_id` 和证据里的可选项（`page_idx`、`block_id`、`structure_role`、`layout_role`）没有时整个键不出现。
- 候选的 `source`（按可信度从高到低）：`ocr_structure`（0.99）、`ocr_provider_label`（服务商的 `doc_title`，0.97）、
  `ocr_legacy_structure`（0.94）、`ocr_layout`（0.84）、`pdf_metadata`；第 2 页以后的候选每往后一页减 0.03（最多减 5 页）。
  证据的 `source`：`normalized_document`、`pdf_info_title`。
- `can_apply`：已经应用过，或者书名还是默认来源（没锁定、来源是文件名）。

## 列出建议

`GET …/metadata-suggestions?limit=20` 返回 `{suggestions, limit, has_more}`，新的在前（`created_at DESC, suggestion_id DESC`）。

- `limit` 默认 20，1..=100，越界 `400`（`limit must be 1..=100`；2026-10-22 以前静默夹）。
- 没有 `offset`，`has_more` 多取一条判断；要更多就加大 `limit`。别的查询参数（包括 `offset`）`400`。

## 应用一条建议

```json
{ "expected_document_updated_at": "2026-09-03T12:29:00Z" }
```

- 版本护栏可选，但建议带上界面上显示的 `updated_at`；过期 `409 revision_conflict`。请求体不认识的字段 `400`。
- 返回 `{suggestion, document}`；`document` 和 `GET`/`PATCH /documents/{id}` 同形，带 `source_pdf_url`、`cover_url`、`thumbnail_url`
  （2026-10-19 以前少这三个键）。已经应用过的再应用一次是幂等的。
- 自动应用的书名 `title_source` 是 `ocr` 或 `pdf_metadata`，和用户改的分得开。
- 前端目前只在生成时用 `apply_if_default`，不调这个接口。

## 错误

错误是结构化信封：顶层 `code` 是字符串码，`error.details.reason` 是小写的稳定原因（2026-10-19 起）。按 `reason` 分支，不要解析 `message`。
书不存在、书的原文 PDF 不在磁盘上是普通 `404`，不带 `reason`。

全部原因（`field_unsupported`、`job_not_found`、`job_mismatch`、`source_not_ready`、`source_invalid`、`title_candidate_not_found`、
`source_too_large`、`suggestion_not_found`、`title_changed`、`revision_conflict`）、各自的 HTTP 状态和顶层码列在
[认证与错误 · 书的元数据建议的原因](../00-约定/02-认证与错误.md#书的元数据建议的原因)。要点：

- 以前的两个 `422`（规范化文档坏了、还没有可用书名）是状态问题，同一个请求等 OCR 做完或换个任务就能成功，所以改成了 `409`
  （[400 和 409 的分工](../00-约定/02-认证与错误.md#400-和-409-的分工)）。
- 规范化文档超过 256 MB 是 `413 source_too_large`。
- 点名的 `job_id` 不存在：顶层 `code` 为兼容旧客户端仍是 `OCR_JOB_NOT_FOUND`，但 `error.code` 是 `DOCUMENT_METADATA_JOB_NOT_FOUND`
  （建任务复用 OCR 时也有顶层 `OCR_JOB_NOT_FOUND`，信封不一样）；两边的 `reason` 都是 `job_not_found`。
