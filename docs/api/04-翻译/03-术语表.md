# 术语表

术语表可以通过资源 ID 引用，也可以随任务请求内联传入。

## 任务字段

```json
{
  "translation": {
    "glossary_id": "glossary-xxx",
    "glossary_entries": [
      {
        "source": "bond",
        "target": "键",
        "note": ""
      }
    ]
  }
}
```

- `glossary_id`：引用一张术语表。不存在或已停用（`enabled=false`）时建任务 `400`（以前不存在是 `404`、停用的照样能用；2026-10-22 起）。
- `glossary_entries`：建任务时是用户内联的条目，覆盖在表上（同一条见下面「同一条」）。
- 下面这些是服务器写的，客户端发了也会被覆盖：
  - `glossary_name`、`glossary_resource_entry_count`、`glossary_inline_entry_count`、`glossary_overridden_entry_count`；
  - 建好的任务里 `glossary_entries` 变成和表合并后的**快照**（翻译只读它）；
  - `glossary_inline_entries`：用户真正内联的条目（规范化、去重后），空的时候不出现（2026-10-22 加）。

## 术语表接口

```http
POST /api/v1/glossaries/parse-csv
GET /api/v1/glossaries
POST /api/v1/glossaries
GET /api/v1/glossaries/{glossary_id}
PUT /api/v1/glossaries/{glossary_id}
DELETE /api/v1/glossaries/{glossary_id}
GET /api/v1/glossaries/{glossary_id}/export.csv
```

`POST /api/v1/glossaries/import` 2026-10-22 删了（收的是 JSON 不是 CSV，和 `POST`、`PUT` 重复，没有调用方）：
从 CSV 进来走 `parse-csv` → 预览 → `POST` / `PUT`。

### 列表

`GET /api/v1/glossaries` **不分页**，一次全给（术语表数量小）。可选筛选：`enabled=true|false`、`source_lang`、
`target_lang`、`q`（按名字、描述、编号找，忽略大小写；空串不过滤）。不认识的参数 `400`。
建任务的下拉用 `?enabled=true`。

### 新建、保存

`POST` 和 `PUT` 的请求体一样：

```json
{
  "name": "量子化学术语",
  "description": "",
  "source_lang": "en",
  "target_lang": "zh-CN",
  "enabled": true,
  "entries": [{"source": "DFT", "target": "密度泛函理论", "level": "canonical", "match_mode": "case_insensitive", "context": "", "note": ""}],
  "expected_updated_at": "2026-10-22T08:00:00.123Z"
}
```

- `name`、`entries` 必填（缺了是不合 schema，`422`），`entries` 整份替换。
- `description`、`source_lang`、`target_lang`、`enabled` 可以不给：新建用默认值（空串、`true`），
  **`PUT` 保留原值**（2026-10-22 起；以前会被清空、`enabled` 被重置成 `true`）。给了空串就是清空。
- 词条里的 `context`、`note` 没有这种保留：发了空串就是空。编辑时把读到的词条原样带回。
- `expected_updated_at`（可选，只对 `PUT` 有用）：给了就只在表的 `updated_at` 还是它时才保存，否则
  `409`，`error.details.reason = "glossary_changed"`，重新读一次再改。不给照旧后写覆盖。
- `PUT` 只改已有的表：表不在（包括读完之后被删）是 `404`，不会把删掉的表写回来。
- `updated_at` 精确到毫秒（2026-10-22 起，老表还是到秒），每次保存一定比上一版晚。

### 词条字段

- `level`：`preserve`（保留原文）、`canonical`（固定译法）、`preferred`（推荐译法），空串是 `preferred`。
- `match_mode`：`exact`（精确，区分大小写）、`case_insensitive`、`regex`，空串是 `exact`。
- JSON 接口（`POST`、`PUT`、建任务的 `glossary_entries`）认中英文别名，**不认识的值 `400`**，消息里带词条原词
  （以前静默改成默认值）。CSV 仍然宽松：不认识的落到默认值。
- `match_mode=regex` 的原词要能编译，编译不过 `400` 带原词。翻译用的是 Python 的 `re`，环视、反向引用这类
  Rust 不支持的写法放过。
- `level=preserve` 时 `target` 可以空，后端设成 `source`；其余缺 `source` 或 `target` 都是 `400`。
- 四项（原词、译文、备注、上下文）都空的条目跳过；CSV 也是这一条规则（以前 CSV 只看前三项）。

### 同一条

去重和内联覆盖用同一个键：**（原词，上下文）**。`match_mode=case_insensitive` 的原词按小写比，
`exact`、`regex` 区分大小写；上下文忽略大小写。同一个键后面的那条为准。

于是 `US`（美国）和 `us`（微秒）两个精确词、配了不同 `context` 的同一个词（化学的 bond、金融的 bond）各留一条。
以前只按「原词去空格、ASCII 小写」一个键，这些会被静默并成最后一条（2026-10-22 改）。

### CSV

在「设置 → 术语表 → 导入文件」中选择或拖入 CSV、TSV、TXT、XLSX（最大 2 MB），也可以直接粘贴文本。
文件在本地解码，支持自动识别 UTF-8、GBK/GB18030、带 BOM 的 UTF-16；乱码时可手动选择编码。
Excel XLSX 可直接导入并选择工作表，旧版 XLS 需另存为 XLSX 或 CSV。面板提供带完整表头的 CSV 模板。
导入前显示前 5 条预览、记录数、文件内重复数及字段校验错误；可调整首行是否为表头、分隔符和六个字段的列对应关系。
语境是原文匹配条件，若某列只表示分类，建议映射到备注或不导入。工作表最多读取 10000 行、100 列。

默认「追加合并」，按原词和语境去重，导入词条覆盖同键词条；也可选择「替换当前词条」。
导入结果先进入编辑区，显示词条数与重复数，点击「保存」后才写入术语库。
空结果、解析失败或合并后超过 1000 条均保留原草稿；未解析的导入内容需要先导入或清空才能保存。
列表可搜索术语库，编辑区可搜索原词、译文、备注或语境。切换、新建或关闭前会提示未保存修改。
编辑区支持修改语境、勾选及全选可见词条，批量删除需要确认，保存后生效。筛选隐藏的已选词条也包含在删除范围中。

`parse-csv` 只解析不保存，回 `entries`、`entry_count`，以及 `duplicate_count`（去重丢掉的行数，2026-10-22 加）。

- 有表头按表头认列（中英文别名，见 `docs/core/api/index.md` 第 10 节）；没有表头时列序是 `原词,译文,备注`，
  第 4 列以后不读，`level` 默认 `preferred`、`match_mode` 默认 `exact`。
- 自动识别逗号、制表符及分号，按 CSV 引号规则比较表头与列数一致性；TSV 单元格中的逗号不会仅因出现就触发 CSV 模式。
- 报错带行号：`row 3: glossary entry requires both source and target`（行号从 1 数，含表头）。
- 单元格是 `'` 后面跟 `=`、`+`、`-`、`@`、制表符、回车时，去掉这个 `'`（导出时加的，见下）。

`GET /glossaries/{glossary_id}/export.csv`：`text/csv; charset=utf-8`，开头带 UTF-8 BOM，
`Content-Disposition: attachment; filename*=UTF-8''<名字>.csv`（名字里的 `/`、`\` 换成 `_`）。
列是 `source,target,note,level,match_mode,context`。以 `=`、`+`、`-`、`@`、制表符、回车开头的单元格前加 `'`，
防止表格软件当公式执行；粘回 `parse-csv` 能还原。

## 上限

| 什么 | 上限 | 超了 |
|---|---|---|
| 名字 | 1..=120 字 | `400` |
| 描述 | 500 字 | `400` |
| `source_lang`、`target_lang` | 64 字 | `400` |
| 每张表的条数（去重后） | 1000 | `400` |
| 原词、译文 | 各 200 字 | `400` |
| 备注 | 500 字 | `400` |
| 上下文 | 500 字（2026-10-22 加，以前不限） | `400` |
| 建任务时表 + 内联合并后的条数 | 1000 | `400` |
| 请求体（含 `parse-csv` 的 `csv_text`） | 默认 2 MB | `413` |

## 快照与重跑

- 建任务时任务请求里存的是**快照**：`glossary_id`、`glossary_name`、合并后的 `glossary_entries` 和几个计数，
  另存用户内联的 `glossary_inline_entries`。翻译只读快照：任务建好以后改表、删表，不影响这一次翻译；
  在跑的任务不会因为删表失败。原地重渲染、原地精修不重新解析术语表。
- **重跑出新任务**（`POST /jobs/{job_id}/actions/rerun` 续跑、`retry-stage` 出新任务的 OCR / 翻译阶段、
  `resolve-ocr-ambiguity` 绑定回执）**用现在的表**，加上用户当时内联的条目：先把 `glossary_entries` 换回
  `glossary_inline_entries`，再和建任务一样解析（2026-10-22 起）。所以表里改过的译法（包括 AI 终端
  `term-set` 改的）、删掉的词，重跑时都按现在的表。
  - 2026-10-22 以前建的任务没有 `glossary_inline_entries`：`glossary_inline_entry_count` 是 0 就当没有内联；
    不是 0 时分不清快照里哪些是内联的，退回旧行为，把整份快照当内联条目。
  - 源任务用的表已经删了：`409`，`error.details.reason = "glossary_missing"`（以前是 `404 glossary not found`）；
    停用了：`409`，`glossary_disabled`。`retry-stage` 可以在 `overrides.translation.glossary_id` 换一张表或填空串接着跑；
    `rerun` 的 overrides 只收换模型 key，要换表请重新建任务。这两个原因只在提交时才知道，
    `GET /jobs/{job_id}/actions` 的 `disabled_code` 里没有。
  - 重跑出新的**渲染**任务不用术语，快照原样带过去。

## 前端规则

- 术语表资源的管理走 `/glossaries`。
- 任务创建时优先传 `glossary_id`；下拉用 `GET /glossaries?enabled=true`。
- 少量临时术语可以随任务传 `glossary_entries`。
- 编辑保存时把词条的 `context` 原样带回；带上详情里的 `updated_at` 作 `expected_updated_at`，`409 glossary_changed` 时提示刷新。
- 术语注入强度由 `translation.glossary_mode` 控制。
