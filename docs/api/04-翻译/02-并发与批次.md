# 并发与批次

翻译请求里的 `workers` 和 `batch_size` 不等于简单的“同时发 N 个请求，每个请求 M 条”。后端会根据 item 类型、风险和 provider 状态做调度。

## 请求字段

```json
{
  "translation": {
    "workers": 100,
    "batch_size": 1
  }
}
```

## 实际调度

翻译阶段会先把待翻译 item 分成几类：

- `batched_fast`: 低风险正文，可按 batch 合并。
- `single_fast`: 普通单 item 请求。
- `single_slow`: 复杂公式、重处理或高风险 item。

`workers` 按批数拆给这几类（诊断里的 `translation_queue_split`），但执行时 `batched_fast` 和 `single_fast` 合成一个线程池
（线程数是两边之和），原文长的单元先发（接续组按整组算），同样长的按页序；`single_slow` 单独一个池、限路数。
共享队列（`RETAIN_TRANSLATION_TRANSPORT=rust`）照旧所有任务一个池、按页序。

## 自适应并发怎么升降

所有队列共用一个并发上限（`adaptive_concurrency.current_limit`），从 `initial_limit`（最多 32）起步：

- 429：降到"撞上限时在跑的路数减 2"和"原来的四分之三"里小的那个；前者记成回升目标 `ceiling_limit`。
  同一次撞上限里一起挨 429 的请求（降速之前就发出去的）只算一次，不会连降几刀。
- 5xx、408：砍一半，同样一次撞上限只降一次；超时、很慢的成功照旧降。
- 成功：低于 `ceiling_limit` 时每连续成功 2 次加 1，到了以后每连续成功 12 次加 1、最多到 `configured_limit`。

以前每个 429 都砍一半、每 12 次成功才加 1：Anthropic 的组织并发上限在三十几路，开局 32 路同时撞上，几个 429 把上限
连砍到 8，一本书剩下的请求都只跑 9—16 路（2026-10-31 改，见 `docs/ops/planning/translation-package/20261031-普通翻译提速.md`）。

## 为什么高并发不一定线性提速

- provider 侧有 adaptive concurrency，真实 inflight HTTP 请求可能低于 `workers`。
- 429、5xx、超时会触发退避和重试。
- `single_slow` 有独立 worker 上限，复杂 item 不会吃满所有 worker。
- 结果 apply 和部分 flush 是主流程串行消化。
- tail retry 可能在主 batch 结束后追加工作。

## 诊断字段

翻译 diagnostics 里应重点看：

- `configured_workers`
- `configured_batch_size`
- `effective_batch_size_translation`
- `translation_queue_split`
  - `batched_fast_batches`
  - `single_fast_batches`
  - `single_slow_batches`
  - `batched_fast_workers`
  - `single_fast_workers`
  - `single_slow_workers`
- `concurrency_observed.peak_inflight_translation_requests`
- `concurrency_observed.peak_inflight_all_llm_requests`
- `adaptive_concurrency.current_limit`
- `adaptive_concurrency.cut_count`（降了几次）、`adaptive_concurrency.ceiling_limit`（最近一次 429 学到的回升目标，0 是没撞过）
- `result_apply.apply_elapsed_ms`
- `result_apply.max_result_drain_batch`
- `result_flush.flush_elapsed_ms`
- `result_flush.max_flush_pages`
- `tail_retry.tail_retry_items`
- `tail_retry.tail_retry_elapsed_ms`
- `request_counts.timeout_attempts`

## 前端规则

- 普通用户界面可以只暴露 `workers`。
- `batch_size` 更适合作为高级选项。
- 不要在 UI 上承诺 `workers=100` 就是每秒 100 个 item。
