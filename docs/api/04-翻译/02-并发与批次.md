# 并发与批次

翻译请求里的 `workers` 和 `batch_size` 不等于简单的“同时发 N 个请求，每个请求 M 条”。后端会根据 item 类型、风险和 provider 状态做调度。

## 请求字段

```json
{
  "translation": {
    "workers": 100,
    "batch_size": 1
  }
}
```

## 实际调度

翻译阶段会先把待翻译 item 分成几类：

- `batched_fast`: 低风险正文，可按 batch 合并。
- `single_fast`: 普通单 item 请求。
- `single_slow`: 复杂公式、重处理或高风险 item。

`workers` 会被拆分到这些队列，而不是变成单一线程池。

## 为什么高并发不一定线性提速

- provider 侧有 adaptive concurrency，真实 inflight HTTP 请求可能低于 `workers`。
- 429、5xx、超时会触发退避和重试。
- `single_slow` 有独立 worker 上限，复杂 item 不会吃满所有 worker。
- 结果 apply 和部分 flush 是主流程串行消化。
- tail retry 可能在主 batch 结束后追加工作。

## 诊断字段

翻译 diagnostics 里应重点看：

- `configured_workers`
- `configured_batch_size`
- `effective_batch_size_translation`
- `translation_queue_split`
  - `batched_fast_batches`
  - `single_fast_batches`
  - `single_slow_batches`
  - `batched_fast_workers`
  - `single_fast_workers`
  - `single_slow_workers`
- `concurrency_observed.peak_inflight_translation_requests`
- `concurrency_observed.peak_inflight_all_llm_requests`
- `adaptive_concurrency.current_limit`
- `result_apply.apply_elapsed_ms`
- `result_apply.max_result_drain_batch`
- `result_flush.flush_elapsed_ms`
- `result_flush.max_flush_pages`
- `tail_retry.tail_retry_items`
- `tail_retry.tail_retry_elapsed_ms`
- `request_counts.timeout_attempts`

## 前端规则

- 普通用户界面可以只暴露 `workers`。
- `batch_size` 更适合作为高级选项。
- 不要在 UI 上承诺 `workers=100` 就是每秒 100 个 item。
