# 翻译参数

翻译参数位于创建任务请求的 `translation` 对象中。

## 常用字段

```json
{
  "translation": {
    "api_key": "secret",
    "base_url": "https://api.deepseek.com/v1",
    "model": "deepseek-flash",
    "workers": 100,
    "batch_size": 1,
    "mode": "sci",
    "math_mode": "direct_typst",
    "context_mode": "needed",
    "glossary_mode": "matched",
    "memory_mode": "matched"
  }
}
```

字段说明：

- `api_key`: 下游大模型 API key，响应不会回显。
- `base_url`: 下游模型 OpenAI-compatible base URL。
- `model`: 模型名。
- `workers`: 翻译并发。
- `batch_size`: 每个请求包含的翻译 item 数。
- `mode`: 翻译模式。
- `math_mode`: 公式处理模式，当前默认 `direct_typst`。
- `context_mode`: 上下文注入策略。
- `glossary_mode`: 术语注入策略。
- `memory_mode`: 翻译记忆注入策略。

## 译前准备（`preparation`）

可选，默认 `off`。在初翻之前一次性生成全书术语库和风格指南，生成后冻结，并进入翻译 checkpoint 的输入指纹。

| 取值 | 行为 |
| --- | --- |
| `off`（默认） | 不生成产物；prompt 与单元缓存 key 和不带该字段时逐字节一致。 |
| `artifacts_only` | 只生成并冻结 `translated/term-base.v1.json`、`translated/style-guide.v1.json`，不注入 prompt。 |
| `terms` | 生成产物，并把术语库按块命中注入（沿用术语表的命中注入，用户术语表条目优先）。 |
| `terms+style` | 在 `terms` 基础上，再把风格指南放进 system 前缀。 |

开启注入后，注入的内容会进入单元缓存 key，开关切换不会命中旧缓存。其他取值会被拒绝（400），不会被静默改成默认值。

## 精修（`refine` / `refine_max_items` / `refine_max_tokens`）

可选，默认 `refine=off`。精修 = 在已提交的译文之上「挑错 + 定点修改」，跑在渲染阶段、真正渲染之前；每个被接受的修改都走修订历史（`source=refine`），原译可回退。报告写到 `artifacts/refine_report.v1.json`，读取接口 `GET /api/v1/jobs/{job_id}/translation/refine-report`。

| 字段 | 取值 | 默认 | 说明 |
| --- | --- | --- | --- |
| `refine` | `off` / `review_only` / `review_and_fix` | `off` | `off`：渲染行为与不带该字段时一致；`review_only`：只挑错出报告；`review_and_fix`：再对 critical / major 做定点修改。其他取值会被拒绝（400）。 |
| `refine_max_items` | 整数 ≥ 0 | `0` | 最多挑错多少块；`0` = 不限（默认审全书）。 |
| `refine_max_tokens` | 整数 ≥ 0 | `0` | 挑错 + 修改的总 token 上限；`0` = 不限（默认）。挑错约每块 330 token，要控制花费可以按块数估。 |

只在「翻译之后紧接着的那次渲染」里自动跑（`trigger=auto`）；之后的普通重新渲染一律不精修。已完成的旧任务用 `retry-stage` 的 `stage=refine` 原地精修（见「阶段操作 / retry-stage」），那是一次性的，不改任务的 `refine`。挑错用 `reviewer_*`，留空回退到翻译模型。

## 接口协议与思考深度（`api_protocol` / `thinking`）

| 字段 | 取值 | 默认 | 说明 |
|---|---|---|---|
| `api_protocol` | `openai` / `anthropic` | `openai` | `openai`：`POST {base_url}/chat/completions`，`Authorization: Bearer`；`anthropic`：`POST {base_url}/messages`，`x-api-key` + `anthropic-version`（Anthropic Messages API）。 |
| `thinking` | `auto` / `off` / `low` / `medium` / `high` / `max` | `auto` | 翻译模型的思考深度。 |
| `reviewer_api_protocol` | 空 / 同上 | 空 | 审校模型的协议；空 = 沿用 `api_protocol`。 |
| `reviewer_thinking` | 空 / 同上 | 空 | 审校模型的思考深度；空 = 沿用 `thinking`。 |

`thinking` 怎么落到请求上：

- `auto`：和以前一样，只对实测过的模型关掉或压低思考（DashScope 的 qwen3.8-flash 关闭，智谱 glm-5.3-flash 压到 low），其余不加字段、由服务商默认。
- 其余档位按协议和服务商换字段：DashScope 用 `enable_thinking` + `thinking_budget`；智谱用 `reasoning_effort` / `thinking`；OpenAI 用 `reasoning_effort`（`off` → `none`，`max` → `xhigh`）；其它 OpenAI 格式接口用 `reasoning_effort`；Anthropic 先用自适应思考 + `output_config.effort`，不支持时改用 `thinking.budget_tokens`。
- 服务商以 400 拒绝这组字段时自动退到下一组，最后一组是不加思考字段，不会因为思考设置让翻译失败。
- Anthropic 协议下，结构化输出改成 system 里的「只输出 JSON」要求；开思考时不传 temperature。

## 审校模型配置位（`reviewer_*`）

本期只留配置位、透传到 worker，还不发审校请求。全部可选，默认空串。

- `reviewer_model`: 审校模型名；留空回退到 `model`。
- `reviewer_base_url`: 审校模型 endpoint，必须以 `http://` 或 `https://` 开头；留空回退到 `base_url`。
- `reviewer_api_key`: 内联 key。处理方式与 `api_key` 完全一致：创建任务时导入凭据库换成 `reviewer_credential_ref` 并清空，不明文落库，响应只回显 `reviewer_api_key_configured`。
- `reviewer_credential_ref`: 凭据引用（kind 为 `translation_api_key`），与 `reviewer_api_key` 互斥。

两者都没给时：`reviewer_base_url` 为空或与 `base_url` 相同则回退到翻译 key；`reviewer_base_url` 指向另一家时不回退，避免把翻译 key 发给另一家服务。

## 前端规则

- 普通用户界面只展示模型、并发、术语表等核心选项。
- `context_mode`、`glossary_mode`、`memory_mode` 更适合作为高级选项。
- `preparation`、`refine`、`reviewer_*` 同样放在高级选项里；不提交时行为与之前完全一致。
- `api_protocol`、`thinking` 跟着服务商设置走（设置页「接口协议」「思考深度」）；不提交时是 `openai` / `auto`，与之前完全一致。
- 不要把 `api_key`、`reviewer_api_key` 存进可见日志或事件。
