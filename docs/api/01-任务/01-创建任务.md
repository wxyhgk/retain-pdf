# 创建任务

先上传 PDF 拿 `upload_id`，再建任务。2026-11-24 起这一篇合并了 `backend/api/docs/api-spec/jobs-submission.md` 和
`docs/core/api/index.md` 第 4、5 节里的对外用法（上传、完整请求、上限、超时、凭据、OCR 复用、返回）；上传怎么排队、内存怎么管
这些实现细节在 [运行时与实现备忘](../../core/api/runtime.md#上传的处理)。

## 上传

```http
POST /api/v1/uploads
Content-Type: multipart/form-data
```

- `file`：必填，PDF。没有这个字段 `400 missing multipart field: file`，给了两个也 400。
- `developer_mode`：可选，`1` / `true` 算开。别的字段忽略。

返回（契约 `contracts/uploads.v1.schema.json`）：

```json
{
  "upload_id": "20260327190000-ab12cd",
  "document_id": "<文件字节的 sha256>",
  "filename": "paper.pdf",
  "bytes": 1234567,
  "page_count": 18,
  "uploaded_at": "2026-03-27T11:00:00Z"
}
```

上传即建档：`document_id` 是书的编号，前端可以直接打开书的详情。
不是 PDF、修不好 `400`；超过 `RUST_API_UPLOAD_MAX_BYTES`（不设或 `0` 是 512 MiB）`413` `PAYLOAD_TOO_LARGE`（边收边数，
不等收完）；页数超过 `RUST_API_UPLOAD_MAX_PAGES`（`0` 不限）`400`；解析、修复排不上队或超时 `503`；磁盘剩余低于下限
`503` `insufficient_storage`。上限汇总见 [限制](../00-约定/04-限制.md)。

## 接口

```http
POST /api/v1/jobs
```

用于创建 `book`、`translate`、`render` 或只做 OCR 的 `ocr` 任务。

## workflow

- `book`: OCR -> Normalize -> Translate -> Render。
- `translate`: OCR -> Normalize -> Translate，不渲染 PDF。
- `render`: 复用已有产物，只重新渲染。
- `ocr`: 只做 OCR 和 normalize，不翻译、不渲染，见 [OCR-only 任务](../03-OCR/02-OCR-only任务.md)。
  原来的 `POST /api/v1/ocr/jobs` 已于 2026-10-18 删除：先 `POST /api/v1/uploads` 拿 `upload_id`，再用 `workflow: "ocr"` 调本接口。

## JSON 请求示例

```json
{
  "workflow": "book",
  "source": {
    "upload_id": "upload-xxx"
  },
  "ocr": {
    "provider": "paddle",
    "paddle_token": "secret",
    "options": {
      "paddle_model": "PaddleOCR-VL-1.6"
    }
  },
  "translation": {
    "api_key": "secret",
    "base_url": "https://api.deepseek.com/v1",
    "model": "deepseek-flash",
    "workers": 100,
    "batch_size": 1
  },
  "render": {
    "render_mode": "auto",
    "source_cleanup_strategy": "pikepdf_text_strip"
  }
}
```

## 关键字段

- `source.upload_id`: 由上传接口返回。
- `source.source_url`: 远程 PDF URL，取决于 provider 是否支持 URL。
- `ocr.provider`: `mineru`、`paddle`、`local` 或配置型 command provider。
- `ocr.options`: provider-specific 参数，优先放非密钥配置。只能放客户端可填的选项（`GET /api/v1/providers/ocr`
  里 `client_settable: true` 的，或者那里没列出的）；只能服务器定的——本地 OCR 要执行的 `command`、
  `raw_provider`、配置里带 `env` 的——带了返回 400（`ocr.options.command is server-owned; …`，2026-10-22）。
  书的 `/translate`、`/ocr` 和重试的 `overrides.ocr.options` 同样。以前建的任务请求里存着这些键的，
  重跑、阶段重试复制请求时去掉，不报错；它们的值以服务器配置为准。
- `translation`: 翻译模型、并发、术语表和上下文配置。
- `render`: 渲染参数。
- `runtime.job_id`: 任务编号由服务器分配，不要发（留空或不带）。非空会返回 400（`runtime.job_id is set by the server; do not send it`），
  `POST /api/v1/documents/{document_id}/translate`、`/ocr` 同样。
- 书上的两个入口 `POST /api/v1/documents/{document_id}/translate`、`/ocr` 和 `POST /api/v1/jobs` 一样严格（2026-10-19）：
  和入口矛盾的字段直接 400、提示里写着字段名，不再悄悄改掉——`/ocr` 的 `workflow` 只能是 `ocr` 或不写，
  不收 `source.artifact_job_id`、`source.source_url`；`/translate` 的 `workflow` 不能是 `ocr`/`render`，不收 `source.source_url`。
  原文由书自己的上传提供。请求写错先报 400，书不在（404）、要复用的 OCR 不能用（404/409）排在后面。
  以前这个字段可以指定编号，但落库是覆盖式的，传已有编号会冲掉那个任务，带 `..` 还会跑出输出目录。
  服务器兜底：新建任务的编号必须是 `[A-Za-z0-9_-]{1,128}`（不合法 400），库里已有同编号时返回 409。

## 完整请求结构

只收分组的 JSON（`workflow`、`source`、`ocr`、`translation`、`render`、`runtime`），旧的扁平字段（顶层 `upload_id`、`model`、
`api_key`……）一律 400。字段全集以契约 `contracts/create-job.v1.schema.json` 为准，翻译、渲染参数的含义见
[翻译参数](../04-翻译/01-翻译参数.md)、[渲染参数](../05-渲染/01-渲染参数.md)。

```json
{
  "workflow": "book",
  "source": { "upload_id": "20260327190000-ab12cd", "source_url": "", "artifact_job_id": "" },
  "ocr": {
    "provider": "mineru",
    "credential_ref": "cred_ocr_0123456789abcdef",
    "model_version": "vlm",
    "is_ocr": false,
    "disable_formula": false,
    "disable_table": false,
    "language": "ch",
    "page_ranges": "",
    "data_id": "",
    "no_cache": false,
    "cache_tolerance": 900,
    "extra_formats": "",
    "poll_interval": 5,
    "poll_timeout": 1800,
    "options": {}
  },
  "translation": {
    "mode": "sci",
    "math_mode": "direct_typst",
    "model": "deepseek-flash",
    "base_url": "https://api.deepseek.com/v1",
    "credential_ref": "cred_0123456789abcdef",
    "glossary_id": "",
    "glossary_entries": [],
    "start_page": 0,
    "end_page": -1,
    "batch_size": 1,
    "workers": 0
  },
  "render": { "render_mode": "auto", "compile_workers": 0, "engine": "rpr_fit" },
  "runtime": { "timeout_seconds": 1800, "no_output_timeout_seconds": 0 }
}
```

- `ocr.provider` 只管选哪家 OCR；`workflow = "book"` 是协议里的固定名字，不代表某一家服务商。
- `translation.page_ranges` 非空时用它（页码从 1 起），优先于旧的 `start_page` / `end_page`（从 0 起、含两端）。
- `ocr.mineru_token`、`translation.api_key` 不能长得像 URL；`translation.base_url` 必须 `http://` 或 `https://` 开头。
- 渲染里的枚举（`render_mode`、`font_unify_mode`、`source_cleanup_strategy`、`engine`）不认识的值 400，重试的
  `overrides.render.engine` 也一样。
- 各家 OCR 的页数、大小上限只对选中的那家生效，见 [限制](../00-约定/04-限制.md)。

### 上限

2026-10-24 起，超了 400 `"<字段> must be at most <上限>"`（下限照旧）：

| 字段 | 上限 |
|---|---|
| `translation.workers` | 256 |
| `translation.batch_size`、`translation.classify_batch_size` | 1000 |
| `render.compile_workers` | 64 |
| `render.pdf_compress_dpi` | 1200 |
| `runtime.timeout_seconds`、`runtime.no_output_timeout_seconds` | 604800（一周；提示里的字段名是 `timeout_seconds`、`no_output_timeout_seconds`） |

### 超时

`timeout_seconds` 和 `no_output_timeout_seconds` 是两条独立的限制：

- `timeout_seconds` 是**多久没有进展**就判卡住（2026-10-31 起；以前是从阶段进程启动算的整段上限，前端默认的 1800 秒让
  一百多页的翻译 agent 任务在半路被杀）。进展指 worker 报出新的阶段或进度（完成一页、一批）、提交检查点、发布产物；
  只换说明文字、反复报同一个进度不算。必须是正整数。一直有进展就一直跑，另有绝对上限防死循环：服务端
  `RUST_API_WORKER_MAX_RUNTIME_SECS`（默认 24 小时，`0` 不限），`timeout_seconds` 比它大时以 `timeout_seconds` 为准。
- `no_output_timeout_seconds` 是空闲检测：每收到一行 stdout 就重新计时，只有 worker 彻底不出声才触发。默认 `0` 关闭——
  各阶段正常静默的时长差别很大（等服务商回应、OCR 一页），没有安全的统一默认值，按工作流自己设。

三种都判为 `failed`，`return_code: -1`，失败码 `process_timeout`；`stage_detail` 分别是 `no progress for {N}s`、
`max runtime {N}s exceeded`、`no output for {N}s`（以前没有进展那一种写 `provider timeout` / `normalization timeout`）。
卡住之前已经产出的东西留着。

## 凭据

- 推荐先 `POST /api/v1/credentials` 建凭据（翻译用 `translation_api_key`，OCR 用 `ocr_provider_token` 且带对应服务商），
  再把返回的 `credential_ref` 放进 `translation.credential_ref`、`ocr.credential_ref`。凭据接口见 [凭据](../14-凭据/01-凭据.md)。
- 内联的 `translation.api_key`、`ocr.mineru_token`、`ocr.paddle_token`、配置型服务商的 `ocr.options.credential` /
  `token` / `api_key` 仍是兼容输入：建任务时导入成托管凭据，落库前清掉。内联密钥和对应的 `credential_ref` 不能同时给。
- 要跑远程 OCR 时，`ocr.credential_ref` 和所选服务商的内联 token 必须给且只给一个；要翻译时，`translation.base_url`、
  `translation.model` 必填，`translation.credential_ref` 和 `translation.api_key` 必须给且只给一个。复用 OCR 产物
  （见下）不会去调 OCR 服务商，所以不要 OCR 的 token，只查翻译凭据。
- `credential_ref` 不存在、种类不对、服务商对不上、凭据库不可用，返回结构化的 `CREDENTIAL_*` 错误，不带凭据值。
- 后端不再替 `create_job` 补默认的 OCR / 模型凭据。

返回里一律不回明文：`request_payload.ocr.mineru_token`、`paddle_token`、`translation.api_key` 恒为空串，
`*_configured`（`mineru_token_configured`、`paddle_token_configured`、`api_key_configured`）告诉有没有配；
`credential_ref` 是不透明的编号，可以原样返回。`error`、`log_tail`、事件的 `message` / `payload`、翻译诊断、译文条目和重放的内容
出 rust_api 之前都脱敏。

## 复用 OCR 产物：`source.artifact_job_id`

`book`、`translate` 都可以带 `source.artifact_job_id` 指向一个 OCR 已成功的任务。后端先核对：那个任务有可复用的成功 OCR 阶段，
原文、规范化文档、版面数据都在，服务商兼容，OCR 页覆盖要翻译的页范围。通过就不再建 OCR 子任务，直接翻译；
`POST /jobs` 不带书的范围，查不了「是不是这本书的」，书上的 `/translate` 入口会再查归属。`render` 必须带它（复用翻译产物只重渲染）。

复用不了**不会悄悄改成重新 OCR**，返回：

| `error.code` | HTTP | 含义 |
|---|---:|---|
| `OCR_JOB_NOT_FOUND` | 404 | 指的任务不存在 |
| `OCR_JOB_NOT_SUCCEEDED` | 409 | 那个任务没有成功的、可复用的 OCR 阶段 |
| `OCR_ARTIFACT_MISSING` | 409 | 需要的 OCR 产物不在或过期了 |
| `OCR_ARTIFACT_NOT_REUSABLE` | 409 | 归属、版面或服务商兼容性没通过 |
| `OCR_PAGE_COVERAGE_MISMATCH` | 409 | OCR 的页没盖住要翻译的页范围 |

```json
{
  "code": "OCR_PAGE_COVERAGE_MISMATCH",
  "message": "OCR pages do not cover the requested translation range",
  "reason": "page_coverage_mismatch",
  "can_fallback_to_ocr": true,
  "error": {
    "code": "OCR_PAGE_COVERAGE_MISMATCH",
    "http_status": 409,
    "details": { "reason": "page_coverage_mismatch", "can_fallback_to_ocr": true }
  }
}
```

按 `error.code` 分支；`reason` 只是细分。`can_fallback_to_ocr=true` 表示界面可以给一个「重新 OCR」的按钮，
不等于后端会自动退回去——要重新 OCR，调用方得去掉 `source.artifact_job_id` 再交一次。错误里不带产物路径、服务商请求、凭据、签名地址。

## 执行顺序

1. 建主任务，存下解析后的请求；
2. 没有 `source.artifact_job_id` 时建 OCR 子任务 `{job_id}-ocr`，它负责调服务商和规范化；
3. 主任务接过 OCR 子任务的规范化文档、规范化报告、版面数据和服务商原始产物；
4. 进入翻译和（或）渲染。

带了能用的 `source.artifact_job_id` 时，2、3 步换成把源任务的 OCR 产物引用抄过来，不建子任务。

前端拿到 `job_id` 后应开始轮询：

- `GET /api/v1/jobs/{job_id}`
- `GET /api/v1/jobs/{job_id}/progress/events`

## 防重复提交

`POST /jobs`（以及书的 `POST /documents/{document_id}/translate`、`/ocr`）接受 `Idempotency-Key` 请求头（2026-11-24 起）：
用户每点一次生成一个新的 key（UUID），这一次点击的网络重试复用同一把 key；同一把 key、同一个请求第二次来不再建任务，
原样回第一次的结果并带响应头 `Idempotent-Replayed: true`。不带这个头行为不变。详见 [防重复提交](../00-约定/06-防重复提交.md)。
