# 查询任务详情

## 接口

```http
GET /api/v1/jobs/{job_id}
```

用于获取任务当前快照。页面首屏应优先读取这个接口，再接入 events。字段形状见契约
[`job-status.v1.schema.json`](../../../contracts/job-status.v1.schema.json)（`JobDetailView`）。

## 当前阶段：`stage_snapshot`

当前阶段和进度**只在 `stage_snapshot` 里**，顶层没有 `display_stage`、`stage`、`substage`、`lane`、`stage_detail`、
`progress`、`background_stages` 这些键（后端测试钉着它们不许回到顶层；早先的文档把它们写在顶层，是错的）。

```json
{
  "job_id": "20260616120000-abcdef",
  "workflow": "book",
  "status": "running",
  "ocr_reused": false,
  "source_artifact_job_id": null,
  "stage_snapshot": {
    "display_stage": "translation",
    "stage": "translating",
    "substage": "translation_batches",
    "lane": "main",
    "stage_detail": "正在翻译第 789 / 5216 批",
    "progress": {"unit": "batch", "current": 789, "total": 5216, "percent": 15.1}
  },
  "background_snapshots": [
    {
      "display_stage": "render",
      "stage": "rendering",
      "substage": "render_prewarm",
      "lane": "background",
      "stage_detail": "渲染预热完成",
      "progress": {"unit": "step", "current": 2, "total": 3, "percent": 66.7}
    }
  ],
  "stages": {
    "ocr": {"state": "completed", "progress": {"current": null, "total": null, "percent": null}},
    "translation": {"state": "in_progress", "progress": {"unit": "batch", "current": 789, "total": 5216, "percent": 15.1}},
    "render": {"state": "pending", "progress": {"current": null, "total": null, "percent": null}}
  },
  "completion_note": null
}
```

字段说明：

- `status`：`queued`、`running`、`succeeded`、`failed`、`canceled`。
- `stage_snapshot`：当前主线阶段，是当前阶段和进度的权威来源；**终态任务（成功、失败、取消）是 `null`**，终态看 `status`，
  不要把 `done` 当成一个阶段。里面：
  - `display_stage`：前端展示大阶段，`ocr | translation | render`；
  - `stage`：后端内部阶段名，只用于诊断；
  - `substage`：机器可读子阶段；
  - `lane`：`main`；
  - `stage_detail`：人类文案，不参与逻辑判断；
  - `progress`：`{unit, current, total, percent}`，当前最可信的进度；
  - `upstream_wait`：只在等服务商限流时出现，见下文。
- `background_snapshots`：同时在跑的后台阶段（例如 `render_prewarm` 渲染预热），`lane` 是 `background`，形状同 `stage_snapshot`。
- `stages`：三段（`ocr`、`translation`、`render`）各自的 `state` 和 `progress`。`state` 取值：`pending`、`queued`、
  `in_progress`、`completed`、`failed`、`skipped`、`reused`。
- `completion_note`：终态任务有额外说明时才有值（例如成功收尾但「有 N 个内容块保留原文未翻译」），正常完成是 `null`。它不是阶段字段。

### OCR 复用和 OCR 子任务

- 详情总带 `ocr_reused` 和 `source_artifact_job_id`。复用了别的任务的 OCR 时 `ocr_reused=true`、`stages.ocr.state="reused"`；
  不要从「没有 OCR 事件」或当前阶段去猜是否复用。
- OCR 在子任务 `<job_id>-ocr` 里跑时（例如 GLM-OCR 边识别边把页送去翻译），`stages.ocr.state` 跟着子任务走：子任务在跑就是
  `in_progress`（哪怕翻译已经开始），成功是 `completed`，失败、取消或随父任务停下是 `failed`。只有 `completed`（或 `reused`）
  表示这个任务的 OCR 能拿去做别的翻译；OCR 子任务成功、翻译失败的父任务仍是 `completed`。2026-11-02 以前按阶段顺序推断，
  翻译一开始就显示 `completed`。
- `ocr_job`：OCR 子任务的摘要（`job_id`、`status`、`trace_id`、`provider_trace_id`、`detail_path`、`detail_url`），没有子任务为 `null`。

## 其余字段

| 字段 | 说明 |
|---|---|
| `request_payload` | 解析后的请求，已脱敏：内联密钥（`ocr.mineru_token`、`ocr.paddle_token`、`translation.api_key`）总是空串，是否配置看 `*_configured`；`credential_ref` 是不透明编号，可以回显 |
| `trace_id`、`provider_trace_id` | 追踪编号 |
| `timestamps` | `created_at`、`updated_at`、`started_at`、`finished_at`、`duration_seconds` |
| `links` | `self_*`、`artifacts_*` 和 `artifacts_manifest_*`（都指向 `/jobs/{job_id}/files`）、`events_*`、`cancel_*`，`*_path` 是相对地址，`*_url` 是绝对地址 |
| `actions` | 按钮链接：`open_job`、`open_artifacts`、`cancel`、`download_pdf`、`open_markdown`、`open_markdown_raw`、`download_bundle`、`resume`（续跑 `actions/resume`；旧名 `rerun` 的地址和这个字段 2026-11-25 都删了），每个是 `{enabled, method, path, url}` |
| `artifacts` | 产物链接和就绪状态：`pdf_ready`、`markdown_ready`、`bundle_ready`、`pdf_url`、`markdown_url`、`markdown_images_base_url`、`bundle_url`、`normalized_document_url`、`normalization_report_url`，以及 `pdf`、`markdown`、`bundle`、`normalized_document`、`normalization_report` 几个对象（`ready`、`path`、`url`、`content_type`、`file_name`、`size_bytes`）。地址规则见 [下载总览](../07-产物下载/01-下载总览.md) |
| `artifacts_display` | 给界面直接列的产物清单：`key`、`label`、`ready`、`kind`、`file_name`、`size_bytes`、`download_url`（没就绪为 `null`） |
| `book_summary` | 书的摘要：`title`、`authors`、`page_count`、`source_language`、`target_language`、`source_file_name`、`cover_url`、`thumbnail_url`、`file_size_bytes`、`document_id`（书的编号，原文、封面在 `/documents/{document_id}/files/` 下；查不到书时是 `null`，`cover_url`、`thumbnail_url` 也是 `null`） |
| `contracts` | 阶段边界的产物就绪检查，见下文 |
| `ocr_provider_diagnostics` | OCR 服务商诊断（最后一次错误的分类、HTTP 状态、业务码等），没有为 `null` |
| `runtime` | 运行时投影（重试时间线等） |
| `failure` | 正式的失败对象，见 [失败结构](../08-调试诊断/01-失败结构.md)；没失败为 `null` |
| `failure_diagnostic` | 给老客户端的兼容投影，有正式字段时从 `failure` 推出来；新代码读 `failure` |
| `error` | 原始错误文字（已脱敏） |
| `normalization_summary` | 从 `document.v1.report.json` 取的轻量摘要：`provider`、`detected_provider`、`provider_was_explicit`、`pages_seen`、`blocks_seen`、`document_defaults`、`page_defaults`、`block_defaults`、`schema`、`schema_version`、`page_count`、`block_count`。要完整报告就下载 `artifacts.normalization_report` |
| `glossary_summary` | 这次任务实际用了哪张术语表、多少条（`enabled`、`glossary_id`、`glossary_name`、`entry_count`、`resource_entry_count`、`inline_entry_count`、`overridden_entry_count`、`source_hit_entry_count`、`target_hit_entry_count`、`unused_entry_count`、`unapplied_source_hit_entry_count`）。从 `translation-manifest.json` 读，没有时退回流水线摘要；只重渲染的任务只要译文产物还在也有。是任务侧的使用快照，不是术语表本身 |
| `invocation` | worker 的调用方式：`stage`、`input_protocol`（现在都是 `stage_spec`）、`stage_spec_schema_version`（如 `translate.stage.v1`） |
| `translation_request_recovery` | 翻译请求日志的状态（`status`、`journal_ready`、`unresolved_dispatches`、`active_ambiguous_request_keys`、`historical_ambiguous_request_keys`、`requires_confirmation`、`supported_retry_policies`、`detail`）；`requires_confirmation=true` 时重试翻译要带 `ambiguous_request_policy=accept_duplicate_risk`，见 [阶段重试](../06-阶段操作/02-retry-stage.md) |
| `log_tail` | 最近几行日志（已脱敏） |

### 阶段就绪检查：`contracts`

`contracts.schema_version` 现在是 `job_stage_contracts.v1`，`contracts.stages[]` 是 Rust 对几个阶段边界做的产物检查，
前端可以拿它解释「为什么不能继续」「为什么 worker 说成功了却被判失败」：

| `stage` | 要求 |
|---|---|
| `ocr_ready_for_translation` | `source_pdf`、`normalized_document_json` 必须有；`layout_json` 可选，但发布了就得在 |
| `translation_ready_for_render` | `source_pdf`、`translations_dir`、`translation_manifest_json`；带检查点的任务还要求 `translation_checkpoint_json` 是完成 / 已提交状态（`in_progress` 的检查点不能渲染），检查点 v1 以前的老任务照旧兼容 |
| `render_complete` | `output_pdf`、`summary` |

每个产物项：`artifact_key`、`required`、`ready`、`relative_path`、`detail`（没就绪时的原因）。失败事件
（`failure_classified`、`job_terminal`）的 `payload.contracts` 也是这个形状。

## 前端规则

- 状态卡主阶段读 `stage_snapshot.display_stage`（`lane=main`）；`stage_snapshot` 为 `null` 时按 `status` 显示终态。
- 进度条读 `stage_snapshot.progress.unit/current/total/percent`。
- `stage_detail` 只显示，不用于判断。
- 当前阶段以详情 / 列表的 `stage_snapshot` 为准，不要从事件流（`progress/events`）里推算当前阶段。
- 页面刷新后不要只依赖 events 重放，先用详情快照恢复状态。
- 按钮是否可用读 `actions.*.enabled`、`artifacts.*.ready`、`artifacts_display[].ready`；能做哪些阶段操作读
  [`GET /jobs/{job_id}/actions`](../06-阶段操作/01-stage-actions.md)。

## 服务商限流等待：`stage_snapshot.upstream_wait`

2026-11-23 起（只加不改）。翻译或 OCR 的请求被服务商限流（HTTP 429）、过载（529）、暂不可用（503），正在按 Retry-After
或退避等待时，`stage_snapshot` 多一个 `upstream_wait`；所有在等的请求都等完，字段消失。进度数字、`stage_detail` 不变。
任务列表（`include_live_stage` 时）的 `stage_snapshot` 同样带它。

```json
"stage_snapshot": {
  "display_stage": "translation",
  "stage": "translating",
  "substage": "translation_batches",
  "lane": "main",
  "stage_detail": "已翻译 96/408 块 · 已完成 9/48 页",
  "progress": {"unit": "block", "current": 96, "total": 408, "percent": 23.5},
  "upstream_wait": {
    "provider": "deepseek",
    "http_status": 429,
    "reason": "rate_limited",
    "code": "rate_limit_exceeded",
    "retry_after_s": 30.0,
    "wait_source": "retry_after",
    "attempt": 1,
    "max_attempts": 2,
    "started_at": "2026-11-23T00:00:00.000Z",
    "until": "2026-11-23T00:00:30.000Z"
  }
}
```

- `provider`：翻译 `openai` / `anthropic` / `deepseek` / `zhipu` / `qwen` / `opencode` / `custom`（按 base_url 的域名认），
  OCR `paddle` / `mineru` / `glm_ocr`。
- `reason`：`rate_limited`（429）、`overloaded`（529）、`unavailable`（503）。`code` 是上游错误码，没有为 `null`。
- `retry_after_s`、`wait_source`（`retry_after` 照响应头 / `backoff` 自己退避）、`attempt` / `max_attempts`、`until`（预计等到）。
  同一阶段好几个请求同时在等时是最近一次等待的信息。
- 别的 5xx、超时、连不上照旧重试，但不报等待。契约：`job-status.v1` 的 `UpstreamWaitView`。

前端规则：字段在就显示「服务商限流，等待中」（可以带服务商名和 `until` 倒计时），不在就照常显示进度；`until` 已过、字段还在
（下一次请求还没回来）时照样显示等待中，不要据此判断卡死。
