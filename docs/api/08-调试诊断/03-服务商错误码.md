# 服务商错误码

（2026-11-23 新增）各家 OCR 服务商（PaddleOCR、MinerU、GLM-OCR）和翻译模型服务商（OpenAI、Anthropic、DeepSeek、智谱、阿里云百炼、OpenCode）
官方文档里的错误码目录：每条带含义、给用户的提示、RetainPDF 现在怎么处理（和官方说法对不对得上），
以及上游错误大类 → RetainPDF 失败码（`failure_code`）的对照。打算给前端在任务失败时显示更具体的提示用；前端还没接（`by(none)`）。

- 契约：[`provider-error-codes.v1`](../../../contracts/provider-error-codes.v1.schema.json)（前端类型从 `@retainpdf/contracts/provider-error-codes` 导入，函数名 `listProviderErrorCodes`）。
- 数据：`backend/packages/retainpdf-providers/error-codes/`（每家一个文件，分 `ocr/`、`llm/`），编译时嵌入，不碰数据库。
- 逐家的表、缺口汇总：[服务商错误码（参考）](../../reference/error-codes/README.md)，和接口读同一份数据生成。

```http
GET /api/v1/providers/error-codes
GET /api/v1/providers/error-codes?kind=ocr
GET /api/v1/providers/error-codes?provider=glm_ocr&code=1113
GET /api/v1/providers/error-codes?provider=deepseek&http_status=402
```

多用户模式下登录即可（`signed`）。不分页（9 家、两百多条，一次给完）。

## 筛选

| 参数 | 说明 |
|---|---|
| `kind` | `ocr` 或 `llm`；别的值 400 |
| `provider` | 厂商编号：`paddle`、`mineru`、`glm_ocr`、`openai`、`anthropic`、`deepseek`、`zhipu`、`qwen`、`opencode`。OCR 的编号和建任务时的 `ocr.provider` 一致。不认识的编号返回 200、`vendors` 为空 |
| `code` | 精确匹配条目的 `code`、`aliases` 或 `id`（区分大小写）；任务失败里的 `provider_code` 可以直接填 |
| `http_status` | 只要 `http_status` 里含这个状态码的条目；没有业务码的厂商（DeepSeek）用它查 |

- 不认识的参数 400。
- 筛选只作用于 `vendors` 和 `vendors[].entries`；`categories`、`failure_codes` 总是全量。
- 带了 `code` 或 `http_status` 时，没有命中条目的厂商不返回；所以查不到就是 `vendors: []`。

## 返回

`data` 是 `ProviderErrorCatalogueView`：

| 字段 | 说明 |
|---|---|
| `schema` | 固定 `provider-error-codes.v1` |
| `categories[]` | 16 个上游错误大类：`id`、`label_zh`、`description_zh`、`retryable`、通用提示 `user_hint_zh`、对照的失败码 `failure_codes`（第一个是主名）、`note_zh` |
| `failure_codes[]` | RetainPDF 自己的失败码：`failure_code`、产生方 `producer`、`summary_zh`、`retryable`、`issues`、`note_zh`，以及恢复目录里的 `resume_from`、`recovery_hint` |
| `vendors[]` | 厂商，先 OCR 后翻译模型，顺序固定：`id`、`label`、`kind`、主机名 `hosts`、出处 `sources`、错误形状 `error_shape_zh`、歧义规则 `how_to_distinguish_zh`、整体处理 `handling_summary_zh`、`notes_zh`、`issues`、`related_docs`、`entries` |
| `vendors[].entries[]` | `id`（厂商内唯一）、`code`（没有码时 `null`）、`aliases`、`http_status`、`type`、`category`、`retryable`、`meaning_zh`、`meaning_en`、给用户的提示 `user_hint_zh`、`source_url`、`retainpdf_handling` |
| `retainpdf_handling` | `status`（`ok` / `gap` / `fixing` / `not_applicable`）、`action`（`retry` / `fail_fast` / `stop_translation` / `auto_adjust` / `fail_block` / `not_applicable`）、最后落到的 `failure_code`、`summary_zh`、缺口 `gap_zh`、`priority`（`high` / `medium` / `low`）、`code_paths`、`issues` |

## 任务失败怎么对到一条

任务失败（[失败结构](./01-失败结构.md)）里有 `failure_code`、`failed_stage`、`provider`、`provider_code`、`upstream_host`：

1. OCR 阶段：厂商编号用任务详情的 `request_payload.ocr.provider`（`paddle` / `mineru` / `glm_ocr`）——失败里的 `provider` 只有 Rust 认出的
   Paddle、MinerU 失败才是厂商名，Python worker 报的是 `ocr`；再加失败里的 `provider_code` → `?provider=…&code=…`，显示条目的 `user_hint_zh`。
2. 翻译阶段：失败里的 `provider` 是 `translation`，现在多数不带服务商的码和 HTTP 状态；`upstream_host` 有值时对各家的 `hosts` 找厂商
   （`open.bigmodel.cn` 在 OCR 阶段是 `glm_ocr`，翻译阶段是 `zhipu`）。以后失败里会不会加上 HTTP 状态见交接记录。
3. 查不到条目：用 `failure_code` 找 `failure_codes[].recovery_hint`，或者大类的 `user_hint_zh`。
