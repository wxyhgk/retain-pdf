# 失败结构

> 地址已按 8 类整理（新地址如 `/jobs/{job_id}/reports/failure`）。对应的旧地址已于 2026-10-18 删除（返回 404）。新旧对照见 [任务接口分类](../01-任务/04-任务接口分类.md)。

任务失败时，优先读取 job detail 的 `failure` 和 diagnostics 接口。

各服务商的错误码（含义、给用户的提示、我们怎么处理）和这里的 `failure_code` 怎么对应，见 [服务商错误码](../../reference/error-codes/README.md)
（每家一个文件；全部失败码见 [RetainPDF 失败码](../../reference/error-codes/retainpdf/失败码.md)），接口见 [服务商错误码接口](./03-服务商错误码.md)。
用户在 issue 里实际碰到的错误码见 [错误码汇总](../../ops/planning/error-codes/20261123-错误码汇总.md)。

## 任务诊断

契约：[`job-reports.v1`](../../../contracts/job-reports.v1.schema.json)（返回 `JobDiagnosticsView`，前端类型从 `@retainpdf/contracts/job-reports` 导入；质量体检卡、质量清单、翻译诊断也在这份契约里）。

```http
GET /api/v1/jobs/{job_id}/reports/failure
```

## 失败字段示例

```json
{
  "failed_stage": "translation",
  "failure_code": "python_unhandled_exception",
  "failure_category": "translation",
  "summary": "任务失败，但暂未识别出明确根因",
  "detail": "translation review gate blocked",
  "retryable": true,
  "provider": "translation",
  "raw_exception_type": "RuntimeError"
}
```

翻译 429（OpenAI 额度用完）、GLM-OCR 余额不足、Paddle 失败时的 `upstream`（见下一节）：

```json
{ "failure_code": "upstream_rate_limited", "provider": "translation",
  "upstream": { "provider": "openai", "http_status": 429, "code": "insufficient_quota" } }
{ "failure_code": "upstream_quota_exhausted", "provider": "glm_ocr",
  "upstream": { "provider": "glm_ocr", "http_status": 429, "code": "1113" } }
{ "failure_code": "unknown", "provider": "paddle",
  "upstream": { "provider": "paddle", "http_status": 403, "code": "12001" } }
```

## 上游信息 `upstream` 和 OCR 失败的 `provider`

（2026-11-23 新增，只增不改）失败时上游服务商回的是什么，写在 `upstream` 里，前端拿它去错误码目录
（`GET /api/v1/providers/error-codes`，数据在 `backend/packages/retainpdf-providers/error-codes/{ocr,llm}/*.json`）查条目、给出对应的提示：

```json
"upstream": { "provider": "openai", "http_status": 429, "code": "insufficient_quota" }
```

- 出现在：任务详情 `failure.upstream`（`JobFailureInfo`）、任务列表和书的任务列表的 `failure.upstream`（`JobFailureBriefView`）、
  `GET /jobs/{job_id}/reports/failure` 的 `upstream`（`JobDiagnosticsView`），以及失败事件（`failure_classified` / `job_terminal`）的 `payload.upstream`。
  契约定义都叫 `JobFailureUpstream`（`job-status.v1`、`job-reports.v1`、`library-documents.v1`）。
- 有上游信息时三个键都在，不知道的是 `null`；HTTP 状态和错误码都不知道（超时、连不上、本地异常）时整个 `upstream` 键不出现。
  2026-11-23 以前失败的任务没有这个键。
- `provider` 是错误码目录里的服务商编号：
  - 翻译按配置的接口地址认：`openai`（api.openai.com）、`anthropic`（api.anthropic.com）、`deepseek`（api.deepseek.com）、
    `zhipu`（open.bigmodel.cn、api.z.ai）、`qwen`（dashscope.aliyuncs.com、dashscope-intl.aliyuncs.com）、`opencode`（opencode.ai），
    子域名也算；认不出的地址（自建代理、其他兼容接口）是 `custom`。
  - OCR：`paddle`、`mineru`、`glm_ocr`（本地 OCR 写它自己的名字，例如 `local`）。
- `http_status` 是上游回的 HTTP 状态；业务码随 HTTP 200 回来的（MinerU、Paddle 同步接口）可能是 `200` 或 `null`。
- `code` 是服务商响应体里自己的错误码，原样写成字符串：OpenAI `error.code`（没有时 `error.type`）、Anthropic `error.details.error_code`
  （没有时 `error.type`）、智谱业务码（`1113`）、DashScope `code`、Paddle `errorCode` / `code`、MinerU `code`（`-60018`）、GLM-OCR `error.code` 或顶层 `code`。
  成功码 `0` 不算。

**查目录**：`upstream.provider` 对目录里服务商的 `id`；条目先按 `upstream.code` 对 `entries[].code`（再看 `aliases`），
对不上再按 `upstream.http_status` 对 `entries[].http_status`。`upstream.provider` 是 `custom` 或 `null` 时没有对应的服务商，按 `failure_code` 给通用提示。

**哪里填**：

| 来源 | 填法 |
|---|---|
| 翻译请求（Python 请求层，三种协议） | 请求失败时在异常上记下按 base_url 认出的服务商；状态码、错误码从响应读。Key 被拒后整份停下的错误、限流等待超时的错误都接着带 |
| 翻译「一个块都没译成」 | 从报错文字里最常见那次上游错误读（`429 Client Error … for url: … \| response_body={…}`） |
| GLM-OCR | 余额不足、限流（已有 `status_code` / `provider_code`），以及「请求被拒」、5xx（另写 `upstream_*`，不改分类） |
| Paddle、MinerU（Python 那条路） | HTTP 错误读响应体；Paddle `errorCode`、MinerU HTTP 200 + `code` 不为 0 时写业务码 |
| Paddle、MinerU（Rust 那条路） | OCR 阶段失败、worker 没带上游信息时，取 OCR 诊断 `ocr_provider_diagnostics.last_error` 的 `http_status`、`provider_code`。翻译、排版、标准化阶段的失败不取（那条可能是早先恢复了的错） |
| OCR 和翻译并行（流式） | OCR 失败时把上游信息写进流式清单（`ocr/stream/manifest.json` 的 `upstream`），翻译那边抛出的 `OcrStreamFailed` 带着它 |
| 翻译请求（Rust 模型执行器，任务绑了 `translation.execution_connection`） | Python 拿不到上游响应：执行器的操作回执带 `upstream_provider`（按接口地址认的服务商编号）、`upstream_status`（上游最后一次回的非 2xx，重试成功了就没有）、`upstream_code`（按业务码停下时的码），worker 把它们写到报错上。连不上、本地超时这类没收到上游回应的没有 `upstream` |

**OCR 失败的 `provider`**：Python OCR worker（`provider-ocr`、`normalize-ocr`）以前写泛称 `ocr`，现在写服务商编号
（`paddle` / `mineru` / `glm_ocr` / `local` …，读 stage spec 里的 `ocr.provider`），前端不用再读 `request_payload.ocr.provider`。
Rust 跑的 Paddle、MinerU 本来就写服务商编号。一个进程跑全流程（`provider-case`）时翻译、排版阶段的失败照旧。
`failure_code`、`failure_category`、`retryable`、`summary`、`suggestion` 都不变。

## 重启后的自动续跑与 `translation_request_ambiguous`

API / 任务服务重启时，停在翻译阶段的运行中任务默认自动续跑。但如果翻译请求日志里有「已发出、没有终态」的请求（结果不明，续跑会把它们原样再发一遍），不自动续跑：任务落成 `failed`，
`failure_code` 为 `translation_request_ambiguous`（`failure_category=translation`，`resume_from=translation`，`retryable=true`），
`reports/failure` 和任务详情里的 `translation_request_recovery.requires_confirmation` 为 `true`。
用户确认重复风险后，走 `retry-stage`（`stage=translation`，`ambiguous_request_policy=accept_duplicate_risk`）——这条路径和手动重试的歧义闸门完全一致，不需要新接口。
日志干净（每个请求都有终态）或还没有日志时，照旧自动续跑。渲染 / 精修阶段不看这份日志。

## `resume_from` 按失败阶段区分（`auth_failed`）

（2026-11-12 新增）`resume_from` 和 `recovery_hint` 由恢复目录 `backend/packages/retainpdf-core/src/job_failure_catalogue.rs`
按 `failure_code` 查；个别分类再按 `failed_stage` 细分（同一文件的 `STAGE_OVERRIDES`）。现在只有一条：

| `failure_code` | `failed_stage` | `resume_from` | `recovery_hint` |
|---|---|---|---|
| `auth_failed` | `translation` | `translation` | 翻译 API Key 无效或没有权限。OCR 产物完好，在设置里换 Key 后从翻译阶段续跑，不会重复调用 OCR。 |
| `auth_failed` | 其他（OCR 阶段等） | `null` | 凭据无效或已过期。请在设置里更新后重试。 |

翻译 Key 被上游 401/403 拒绝时，翻译会在第一次被拒后整份停下（`failed_stage=translation`），这时 OCR 已经做完。
注意 `retryable` 仍是 `false`：意思是「原样重试没用，先换 Key」；换好 Key 之后按 `resume_from` 从翻译续跑
（`retry-stage`，`stage=translation`）。接口字段没变。

## 本机环境类失败码与 OCR 额度用完

（2026-11-23 新增，分支 `fix/failure-fallback-classes`）以前这几类不是落成「任务失败，但暂未识别出明确根因」，就是被认错
（#81 路径过长被说成鉴权失败，#135 OCR worker import 期崩溃被说成渲染失败，Paddle 12001 当日额度用完被说成鉴权失败）。
Python 的 `structured_errors.py` 按异常类型认，Rust 的文字兜底（`job_failure_fallback.rs`）在没有结构化失败时按同样的判据认，两边的码、`summary` 一致。
四个本机环境码的 `failure_category` 都是新值 `environment`，`retryable=false`（原样重试多半还会失败，先按提示处理），`resume_from=null`：

| `failure_code` | 什么时候 | `summary` | `recovery_hint`（恢复目录） | issue |
|---|---|---|---|---|
| `out_of_memory` | 异常链里有 `MemoryError`，或 `Cannot allocate memory` | 内存不足，处理中断 | 关掉其他占内存的程序，或把 PDF 拆成页数更少的几份 | #80 |
| `runtime_environment_broken` | `ImportError` / `ModuleNotFoundError`、`undefined symbol`、`DLL load failed`、`Library not loaded`，或安装包（`site-packages`、`retainpdf_*` 包目录）里的文件缺失 | 运行环境不完整：缺少模块、依赖库或安装文件 | 升级到最新版或重新安装（Docker 拉最新镜像），重试不会好转 | #7 #135 #143 #162 |
| `path_too_long` | `WinError 206`、`ENAMETOOLONG`，或 Windows 上「找不到文件」而路径已有 248 个字符以上 | 文件路径过长，超出系统限制 | 把 PDF 改短文件名或放到层级浅的目录后重新上传，或开启 Windows 长路径支持 | #79 #81 |
| `local_permission_denied` | 异常链里有 `PermissionError`，或 `WinError 32`（文件被别的程序占用） | 本机权限不足，文件或网络访问被拒绝 | 查杀毒 / 安全软件拦截、文件占用、目录可写，Windows 可试管理员身份运行 | #38 |

判据只认异常类型名和系统错误码，不认裸的「permission denied」「403」——那可能是上游鉴权失败，照旧归 `auth_failed`。
`WinError 5`（拒绝访问）和 typst 一起出现时照旧是 `typst_runtime_failed`（续跑起点 `render`），别的文件拒绝访问归 `local_permission_denied`。

**import 期崩溃也有结构化失败了**：`python -m retainpdf_pipeline.ocr|translate|render` 和 `retainpdf-pipeline` 的各个 worker 命令，
worker 模块改在 `run_with_structured_failure` 的包装里面 import（`structured_errors.run_imported_main`），
缺模块、动态库加载失败、安装包缺数据文件都会打出 `runtime_environment_broken` 的结构化失败，不再只剩一段 traceback 给 Rust 猜。

**渲染失败的文字兜底收紧了**：Rust 兜底以前只要「找不到文件」加上全文出现 typst / font 就判 `render_failed`；现在要求缺的就是 typst / 字体本身
（同一行里），或者 traceback 走在渲染模块里（`retainpdf_pipeline/render/`、`render_stage.py` 等）。OCR worker 的 traceback 里出现
`direct_typst_math.py` 不再算。

**OCR 额度用完**：PaddleOCR 官方异步接口当日解析页数额度用完是 HTTP 403 + `code=12001`。

- Rust（整份提交、轮询）：`12001` 归 OCR 分类 `quota_exceeded`（以前按 403 归 `permission_denied`，任务落 `unknown`）；任务失败按 OCR 诊断里的
  额度类（`quota_exceeded`、`html_quota_exceeded`，含 MinerU `-60018`/`-60019`）给 `upstream_quota_exhausted`，`failure_category=billing`，
  `summary` 带服务商和业务码，例如「PaddleOCR 今日解析页数额度已用完（12001）」「MinerU 今日解析额度已用完（-60018）」，`provider_code` 是业务码。
  设置页的 Paddle Token 检测（`POST /api/v1/providers/paddle/validate-token`）碰到 12001 也不再说「Token 无效」（`status=provider_error`）。
- Python（OCR 和翻译并行、分片上传时）：Paddle 返回包按官方字段 `code` / `msg` / `traceId` 读，旧写法 `errorCode` / `errorMsg` / `logId` 也认；
  不重试的 4xx 也读返回体，报错文字带业务码和服务商原话（不带请求地址）。12001 → `upstream_quota_exhausted`「PaddleOCR 今日解析页数额度已用完（12001）」，
  `suggestion`「…次日恢复：明天再试，或换一个 Token、换用其他 OCR」，不可重试。
- `upstream_quota_exhausted` 的 `recovery_hint` 没改（恢复目录里那一条讲充值），额度类的具体说法在 `summary`、`suggestion` 里。

**`auth_failed` 的建议按服务商出**：以前写死「检查 MinerU Token、模型 API Key 或后端 X-API-Key 配置」，PaddleOCR 用户也看到 MinerU。
现在 Rust 给的 `suggestion`：翻译阶段「检查翻译模型的 API Key…」，Paddle「检查 PaddleOCR Token 是否有效、是否与接口地址匹配」，
MinerU「检查 MinerU Token 是否有效或已过期」，认不出服务商时「检查 OCR 服务的 Token、翻译模型的 API Key 或后端 X-API-Key 配置」。
`recovery_hint`（恢复目录）本来就不点名服务商，没改。

前端不用改：按已有规则显示 `summary`、`recovery_hint`；`failure_category` 多了取值 `environment`。

## 自动续跑次数上限与 `auto_resume_limit_exceeded`

（2026-10-19 新增）启动恢复和运行期巡检把「运行中却没人在跑」、又有可续断点的任务放回排队自动续跑。
同一次运行（同一个 pipeline attempt）**连续 3 次**自动续跑、每次都没有新进度（没有提交新的单元、没有完成新的阶段）
就又中断了，多半是这份输入每次都让任务运行时崩溃；第 4 次发现它中断时不再续跑，任务落成 `failed`：

- `failure_code` / `category`：`auto_resume_limit_exceeded`，`failure_category=internal`，`failed_stage=startup_recovery`，
  `retryable=true`，`resume_from=null`；
- `summary`：「自动续跑次数超过上限，疑似导致运行时崩溃」，`detail`（`root_cause`）写明连续续跑了几次、上限多少；
- `recovery_hint` 来自恢复目录：先看日志排查，再手动重试。

两次中断之间有新进度就从头数，正常的反复重启（桌面端关了又开）不会把长任务判死。
用户手动重试 / 续跑是新的一次运行（新 attempt），计数从 0 开始。数据库从备份恢复后的那次续跑也计入。
上限是 runner 里的常量 `MAX_AUTO_RESUMES_WITHOUT_PROGRESS`，计数存在 `pipeline_attempts.auto_resume_count`（迁移 v27）。
前端不用改：按已有规则显示 `summary`、`recovery_hint` 即可。

## 前端规则

- 错误标题优先用 `summary`。
- 有 `upstream` 时可以拿它查错误码目录，给出服务商对这个码的说明（见上文「上游信息」）。
- 展开详情使用 `detail`。
- 是否展示重试按钮参考 `retryable` 和 `GET /jobs/{job_id}/actions`。
- 不要直接把完整 traceback 默认展示给普通用户。
- `raw_excerpt`、`traceback`、诊断 payload 可能已做脱敏。

## 翻译调试

GET /api/v1/jobs/{job_id}/translations/{item_id}
