# rust_api 耦合与边界调研

日期：2026-06-15

目标：找出 `backend/rust_api` 里目前最容易导致后续反复补丁、职责打架、难以扩展的耦合点。本文只记录当前代码证据和拆分方向，不要求一次性重构。

## 当前基线

已有架构文档定义的目标分层：

```text
app -> routes -> application services -> internal services -> job_runner / ocr_provider
```

已有硬门禁：

```bash
python3 backend/rust_api/scripts/check_architecture.py
```

当前检查结果：

```text
rust_api architecture check passed
```

阶段性结论：

- 当前硬门禁通过。
- `routes / services / job_runner / ocr_provider / db / storage_paths / job_events` 这些主要生产区已经收敛到 `models::api` / `models::domain` / `models::request` 窄 facade。
- 过滤掉 `models/**` 自身实现和 `api_tests/**` 后，生产源码已没有顶层 `use crate::models::{...}` 穿透导入。
- 剩余顶层 `crate::models` 自引用主要在 `models/input/**`、`models/job/**`、`models/view/**` 内部，属于模型模块内部实现细节，不再代表外层边界穿透。
- 本文后续章节保留历史问题、已完成收口和仍值得后续拆分的软耦合点。

## 1. 下载 API 同时承担派生产物生成职责

代表文件：

- `backend/rust_api/src/services/jobs/downloads/previews.rs`
- `backend/rust_api/src/services/jobs/downloads/side_by_side.rs`
- `backend/rust_api/src/services/jobs/downloads/pdf.rs`

现状：

- `downloads/previews.rs` 既负责下载前的业务判断，也内嵌 Python 代码生成封面、缩略图、页面预览。
- `downloads/side_by_side.rs` 负责下载接口，同时直接调用 Python 脚本生成左右对照 PDF。
- `downloads/pdf.rs` 调用 `qpdf` 做 linearize。

问题：

- `download API` 原本应该偏 HTTP 文件出口，但现在变成了“文件出口 + artifact 派生构建器 + 外部进程编排”。
- 后续如果增加更多派生产物，例如对照 PDF、双语版、带水印 PDF、阅读器预览缓存，`downloads/*` 会继续膨胀。
- 这些派生产物的缓存策略、锁、mtime 判断、临时文件 rename 会重复出现。

建议边界：

```text
routes/download_response
  -> services/jobs/downloads       只决定下载什么
  -> services/derived_artifacts    负责生成/缓存派生产物
      -> Python/qpdf/PyMuPDF 调用
```

优先级：高。

推荐第一步：

- 新建 `services/derived_artifacts`。
- 把 `side_by_side`、`preview/cover/thumbnail`、`linearize` 的“生成与缓存”下沉过去。
- `downloads/*` 只调用 `ensure_*_artifact(...) -> PathBuf`。

当前推进状态：

- 已建立 `backend/rust_api/src/services/derived_artifacts.rs`
- 已拆出：
  - `services/derived_artifacts/pdf.rs`
  - `services/derived_artifacts/preview.rs`
  - `services/derived_artifacts/side_by_side.rs`
- `services/derived_artifacts/**` 的职责限定为“生成/缓存派生产物并返回路径”：
  - `pdf.rs` 负责 qpdf linearize 缓存。
  - `preview.rs` 负责 cover、thumbnail、page preview 图片生成。
  - `side_by_side.rs` 负责原文/译文左右对照 PDF 生成。
  - 不在这里组装 `FileDownload`，也不决定 HTTP 响应。
- 已把 `services/jobs/downloads.rs` 收成薄 facade：
  - `downloads/previews.rs` 负责 cover、thumbnail、page preview 下载决策。
  - `downloads/artifact_deps.rs` 负责把 job query deps 转成 derived artifact deps。
  - `downloads.rs` 不再直接解析源/译文 PDF 路径，也不再直接依赖 derived artifact 生成模块。
- `services/jobs/downloads/*` 保留下载决策和 `FileDownload` 组装，不再直接 `std::process::Command` 启动 PyMuPDF/qpdf 生成器。
- 架构检查已增加门禁：
  - `services/jobs/downloads/**` 禁止直接 `std::process::Command`
  - `services/jobs/downloads/**` 禁止内嵌 `import fitz` / `qpdf`
  - `services/jobs/downloads.rs` facade 禁止重新引入 storage path resolver、artifact generator 或 job loading 业务逻辑。

## 2. `worker_command` 同时承担旧 CLI 和新 stage spec

代表文件：

- `backend/rust_api/src/worker_command.rs`
- `backend/rust_api/src/worker_command/legacy_ocr.rs`
- `backend/rust_api/src/worker_command/stage_commands.rs`
- `backend/rust_api/src/worker_command/stage_specs.rs`
- `backend/rust_api/src/services/job_snapshot_factory.rs`
- `backend/rust_api/src/job_runner/*`

现状：

- `worker_command.rs` 已变成薄 facade，向外 re-export OCR/provider 命令和 stage 命令。
- `legacy_ocr.rs` 负责旧 OCR/provider CLI 参数拼接，包括 `JOB_PATH_ARGS`、`OCR_ARGS`。
- `stage_commands.rs` 负责 `WorkerStageCommand` 到具体 stage spec + entrypoint command 的转换。
- `stage_specs.rs` 只负责 stage spec JSON 契约落盘。
- `job_snapshot_factory.rs` 创建 job snapshot 时只写 placeholder command，不再直接调用 `build_ocr_command(...)`。
- `translation_flow_child.rs` 创建 OCR 子任务时也只写 placeholder command。
- `ocr_flow::execute_ocr_job(...)` 在真正执行 OCR 时统一生成 provider OCR command。
- `job_runner` 后续按阶段重写 `job.command`，但现在只通过 `build_worker_stage_command(...)` 和 `WorkerStageCommand` 表达阶段意图。

问题：

- “创建 job 时的 placeholder command”和“运行阶段的 worker command”职责混在一起。
- 当前生产主链已经是 Rust orchestrated stage spec，但代码里仍有 legacy/provider CLI 入口残留在同一个 facade。
- 后续要接本地 OCR、其他翻译引擎、更多 stage 时，容易继续往 `worker_command.rs` 里塞参数。

建议边界：

```text
worker_command/
  legacy_ocr.rs          旧 OCR/provider CLI 参数组装
  stage_specs.rs         写 stage spec JSON
  stage_commands.rs      WorkerStageCommand -> stage spec -> entrypoint command
  entrypoints.rs         Python script/console entrypoint 映射
  command_builder.rs     Vec<String> 命令构造小工具
job_snapshot_factory
  只写 placeholder，不直接知道 provider CLI 参数
job_runner
  运行阶段按 StagePlan 请求 command
```

优先级：高。

推荐第一步：

- 已把 `worker_command.rs` 里的 legacy OCR CLI 参数构建拆到 `legacy_ocr.rs`。
- 已把 `translate/render/normalize` stage command 组装拆到 `stage_commands.rs`。
- 已新增 `WorkerStageCommand` 和 `build_worker_stage_command(...)`，`job_runner` 不再直接调用 `build_translate_only_command(...)` / `build_render_only_command(...)` / `build_normalize_ocr_command(...)`。
- 已让 `job_snapshot_factory` 和 OCR child 创建逻辑只写 placeholder command，真实 OCR/provider command 统一在 `execute_ocr_job(...)` 执行时生成。
- `worker_command.rs` 和 `worker_command/**` 已迁移到模型 facade：
  - 生产代码只从 `models::domain` 取 `ResolvedJobSpec`。
  - 测试构造 `CreateJobInput` / `GlossaryEntryInput` 走 `models::request`，provider/workflow 枚举走 `models::domain`。
- 已在 `backend/rust_api/scripts/check_architecture.py` 加门禁：
  - 禁止 `worker_command.rs` facade 重新出现 `OcrArg` / `JobPathArg` / OCR 参数表。
  - 禁止 `worker_command.rs` facade 直接写 `translate/render/normalize` stage spec。
  - 要求 `legacy_ocr.rs`、`stage_commands.rs`、`stage_specs.rs` 这些边界模块存在。
  - `worker_command.rs` 和 `worker_command/**` 必须通过 `models::domain` / `models::request` 导入模型。
  - 禁止 `job_runner/**` 直接调用具体 `build_*_command(...)` stage command。
  - 禁止 `job_snapshot_factory.rs` 直接依赖 `worker_command`。
  - 禁止 `translation_flow_child.rs` 创建 OCR 子任务时直接拼 `build_ocr_command(...)`。

## 3. `models` 同时承载内部运行契约和外部 API view

代表文件：

- `backend/rust_api/src/models.rs`
- `backend/rust_api/src/models/input/**`
- `backend/rust_api/src/models/job/**`
- `backend/rust_api/src/models/view/**`
- `backend/rust_api/src/services/jobs/presentation/**`

现状：

- `models.rs` 统一 `pub use` 了 input、job、view、redaction、public_contract 等多类对象。
- 很多业务模块直接 `use crate::models::{...}`，看不出拿的是内部运行模型还是对外 view。
- 文档已经强调：
  - `CreateJobInput / ResolvedJobSpec / JobSnapshot` 是内部运行契约。
  - `JobDetailView / JobEventListView / TranslationDiagnosticsView` 是外部 API 契约。

问题：

- Rust 类型层没有强制体现“内部契约 vs 外部契约”。
- 新人或 AI 修改时容易把内部字段直接带到 response。
- `models/view/job_builders.rs`、`models/view/job_types.rs` 和 `services/jobs/presentation/*` 存在职责重叠：到底谁负责 view 组装不够直观。

建议边界：

```text
models/
  domain/      内部运行模型：JobSnapshot、ResolvedJobSpec、JobArtifacts
  api/         对外 API view：JobDetailView、JobEventListView
  request/     外部 request -> 内部 spec 的输入结构
  security/    redaction/public projection
```

短期不建议大搬目录。先做两件小事：

- 在 `models.rs` 降低全量 facade 的使用，新增更窄的 re-export 模块。
- 在架构检查里禁止 route 直接使用内部敏感模型做 JSON response。

优先级：中高。

当前推进状态：

- 已新增窄 facade：
  - `backend/rust_api/src/models/api.rs`：对外 API view、query、response DTO。
  - `backend/rust_api/src/models/domain.rs`：内部运行模型、状态枚举、stage helper。
  - `backend/rust_api/src/models/request.rs`：外部请求输入结构。
- `backend/rust_api/src/routes/**` 已迁移到 `models::api` / `models::domain` / `models::request`，不再使用顶层 `use crate::models::{...}`。
- 已扫描 `backend/rust_api/src/routes/**`，直接引用内部 job 模型的点只剩下载响应层曾经为了路径 resolver 闭包引用 `JobSnapshot`。
- 已新增 `DocumentDownloadKind`：
  - `OutputPdf`
  - `NormalizedDocument`
  - `NormalizationReport`
- `routes/jobs/download.rs` 现在只表达“下载哪类文档”，不再 import `storage_paths::resolve_*`。
- `routes/download_response/files.rs` 不再引用 `JobSnapshot`，也不再接收 `impl Fn(&JobSnapshot, ...)`。
- `backend/rust_api/src/services/jobs/downloads/**` 已迁移到 `models::api` / `models::domain`，作为 service 层第一块模型 facade 试点。
- `backend/rust_api/src/services/jobs/presentation/**` 已迁移到 `models::api` / `models::domain`，包含对外 view DTO、event record、redaction helper 和内部 job snapshot 的边界区分。
- `backend/rust_api/src/services/jobs/creation/**` 生产代码已迁移到 `models::request` / `models::domain`：

- `stage_retry_request.rs` 根据重试阶段复制 request，并决定复用哪个 artifact。
- `stage_retry_overrides.rs` 处理前端传入的 stage retry overrides。
- `stage_retry_view.rs` 组装 `stage-actions` 和 `retry-stage` 的 API response。
- `stage_retry.rs` 是命令编排入口，负责 load source job、校验 mode、创建新 job 或 in-place render retry。

问题：

- 这块同时碰到外部 API DTO、内部 job/artifact、request input、workflow 和 command 编排。
- 如果类型导入不分层，容易把内部 `JobSnapshot` / `ResolvedJobSpec` 泄到 API view 组装，或者把 API DTO 当内部运行模型用。

建议边界：

```text
stage_plan.rs                 内部 artifact 可用性 -> retry/resume plan
facade/command/stage_retry.rs command orchestration
stage_retry_request.rs        source JobSnapshot -> CreateJobInput
stage_retry_overrides.rs      overrides JSON -> request/spec patch
stage_retry_view.rs           internal result -> API DTO
```

当前推进状态：

- `stage_plan.rs` 已迁移到 `models::api` / `models::domain` facade：
  - `RetryStageKind` 走 `models::api`。
  - `JobSnapshot` / `JobArtifacts` / `JobStatusKind` / `WorkflowKind` 走 `models::domain`。
- `stage_retry*.rs` 已迁移到 `models::api` / `models::domain` / `models::request` facade：
  - API DTO：`RetryStageRequest`、`RetryStageSubmissionView`、`StageActionsView`、`StageRetryAction*`。
  - 内部运行模型：`CreateJobInput`、`ResolvedJobSpec`、`JobSnapshot`、`WorkflowKind`。
  - request 输入结构：`JobSourceInput`。
- `models::api` 已补齐 stage retry DTO：
  - `RetryStageKind`
  - `StageRetryActionLinkView`
  - `StageRetryActionView`
- 架构检查已把 `stage_plan.rs` 和 `facade/command/stage_retry*.rs` 纳入模型 facade 门禁。

后续可选收口：

- 如果 stage retry 后续继续复杂化，可以把 in-place render retry 编排从 `stage_retry.rs` 拆成 `stage_retry_in_place.rs`，但当前已有文件边界和测试覆盖，暂不急着拆。

当前推进状态：

- 已建立 `backend/rust_api/src/services/jobs/stage_view.rs`
- `stage_view` 现在集中负责：
  - `display_stage`
  - `stage`

## 5. `services/jobs/query::load_supported_job` 被多个内部模块直接绕用

代表文件：

- `backend/rust_api/src/services/jobs/downloads/previews.rs`
- `backend/rust_api/src/services/jobs/downloads/side_by_side.rs`
- `backend/rust_api/src/services/jobs/facade/query/downloads.rs`

现状：

- `JobsFacade` 已经是对外 service 门面。
- 但 downloads 子模块内部仍然直接 `load_supported_job(...)`。

问题：

- facade 负责的权限/工作流过滤、OCR-only 语义、supported-job 判断容易被子模块各自复制。
- 现在代码还能接受，但随着 OCR job、book job、library job、derived artifact 入口增多，这类直接 query 会让边界散掉。

建议：

- downloads service 接收已加载的 `JobSnapshot`，由 facade 统一加载。
- 或者建立 `JobReadContext { job, data_root, deps }`，让所有下载/派生 artifact 共享。

优先级：中。

## 7. `job_runner` provider transport 和 stage orchestration 仍然贴得较近


## 建议拆分顺序

第一轮：低风险边界收口。

1. `derived_artifacts`：把 preview/cover/thumbnail/side-by-side/linearize 的生成和缓存从 downloads 拆出去。
2. `stage_view`：统一 events/detail/list 的 progress snapshot 投影入口。
3. `worker_command`：拆 legacy CLI 和 stage spec command。

第二轮：模型边界收口。

1. 收窄 `models.rs` facade。
2. 将 API view builder 和 domain model builder 文档化/拆目录。
3. 增加架构检查：route JSON response 不直接暴露内部运行模型。

第三轮：provider lifecycle 收口。

1. 给 `ocr_provider` 增加 provider lifecycle trait。
2. `job_runner/ocr_flow` 从 provider-specific orchestration 改为消费统一 lifecycle。
3. 本地 OCR API 接入走同一生命周期。

## 可以加入架构门禁的检查

短期建议新增这些非侵入检查：

- `routes/**` 禁止 `use crate::worker_command`。
- `routes/**` 禁止 `use crate::job_runner`，已有。
- `services/jobs/downloads/**` 禁止直接 `std::process::Command`，改由 `services/derived_artifacts/**` 统一调用。
- `services/jobs/downloads/**` 禁止内嵌 Python 多行脚本。当前已经覆盖 `import fitz` / `qpdf`。
- `routes/jobs/**` 禁止重复 `route_deps`，已有。
- `services/jobs/presentation/**` 和 `services/book_projection/**` 使用同一 artifact/readiness projection helper。
- `models/view/**` 不允许引用 `AppState`、`Db`、`storage_paths`。
