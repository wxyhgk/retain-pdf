## 1. 这一期做了什么（分支 `refactor/api-client-phase2`）

| 第 6 节的条目 | 现在 |
|---|---|
| 生成层已有、还有地方手写：终端作用域的 `GET /collections` | 走 `@/platform/api` 的 `listCollections`（底下是生成的函数） |
| 同上：阅读包的 `GET /documents/:document_id`、`GET /jobs/:job_id/data/revisions` | 阅读包不自己拼地址了。会话数据端口 `ReaderSessionDataPort` 加两个可选方法 `fetchDocument`、`fetchRevisionGroups`，web 宿主用 `fetchDocument`、`fetchJobData`（生成的 `getDocument`、`getJobDataset`）实现；宿主不提供就当没有 |
| 文件地址各处拼一遍（原文 PDF、`translated.pdf`、`side-by-side.pdf`、`ocr.md`） | 收进 `@retainpdf/domain/job` 的 `documentSourcePdfPath`、`jobOutputFilePath`，返回从 `/api/v1` 开始的路径，调用方照旧用自己的 `resolveResourceUrl` 补服务器。`tests/jobs/file-paths.test.mjs` 扫源码，再手拼就红 |
| 重复实现：`fetchJobMarkdown` / `fetchJobMarkdownDocument` | 后者没人调，删了 |
| 重复实现：web 的 `buildApiUrl` 和 `packages/api` 的同名函数 | web 那份唯一的调用方（上传地址）改用 `packages/api`，web 那份删了 |
| 重复实现：上传地址两份 | 都从 `packages/api` 的 `buildUploadsEndpoint` 取 |
| 不走 `apiFetch`：终端作用域的 `/collections`、`agent-workspace`，画板的 `ai/board`，ingest 的 `/health` | 都走 `apiFetch`（多用户模式带登录 Cookie、401 进统一处理）。`agent-workspace` 和画板列表契约里还没有，在 `packages/api` 里借生成层的 `request()` 发（`materializeCollectionWorkspace`、`listJobBoard`），不另手写请求；画板文件是二进制出口，只给地址 `jobBoardFileUrl`，用 `fetchProtected` 取 |

`packages/api` 里手写发请求的棘轮（`tests/contracts/api-client-codegen.test.mjs`）从 36 拧到 34。
