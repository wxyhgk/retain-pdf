## 并行时数据长什么样

- 翻译任务 `{id}`：ocr_submitting →（OCR 子任务一拉起就）translating → rendering → finished，自己的阶段里没有 ocr_processing。
  translating 期间 substage 按轮换：continuation_review → page_policies → ocr_stream → translation_batches。
  ocr_stream 的进度是「OCR 已交出、能翻的页 / 全书页数」；translation_batches 每轮从 0 数，不是全书进度。
- OCR 子任务 `{id}-ocr`：ocr_upload → ocr_processing（substage glm_ocr，进度是已识别页 / 总页）→ normalizing → finished。

## 前端怎么画

- **OCR 站跟 OCR 任务**：OCR 任务在跑，OCR 站就亮（assemblyStations），不管翻译任务走到哪；以前只看翻译任务，并行时 OCR 站会被画成已完成。
  百分比用 OCR 任务的进度，用时用 OCR 子任务自己的分段计时（多读一次 GET /jobs/{id}-ocr），两站时间可以重叠。
- **翻译站跟 ocr_stream**：百分比用最近一条 ocr_stream 的页数（`use-stream-progress.ts` 记住上一条，快照换到别的 substage 时不跳回每轮的批次数）。
- 两站的实时说明各写各的（悬停里）。
- 标题「识别和翻译中」；HUD 的进度环看翻译跟到哪了（「10 / 34 页」），还没收到 ocr_stream 时先看 OCR。
- 并行时不单独给「取消 OCR」：取消翻译任务就够了（原来的规则：翻译在跑时不单独动 OCR）。

串行的老服务商（Paddle、MinerU）不受影响：OCR 子任务在跑时翻译任务也停在 OCR 阶段，两边说法一致。
