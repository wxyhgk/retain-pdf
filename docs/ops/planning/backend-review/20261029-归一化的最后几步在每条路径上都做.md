# 归一化的最后几步在每条路径上都做（2026-10-29）

OCR 归一化审查（2026-10-29）里两条同类问题，用户让"先修 bug"：

- MinerU 有两条归一化路径：Rust 调的 normalize worker（`build_normalized_artifacts`）做"缩放到原文 PDF → 重建行 → 按最终文档刷新报告"；
  Python 直跑 MinerU（`mineru_provider/job_flow.py`）只做适配，同样的输入出来的文档不一样。
- 命令型 OCR（`local_command` / `remote_command`）交回原始输出（raw payload）时也只做适配：坐标留在 OCR 自己的单位里（Paddle 是像素），
  却标着 `pt`；校验按页面自己的宽高查，查不出来。

## 影响到谁

查了 Rust 那边的分流（`retainpdf-runner` 的 `ocr_flow/mod.rs`）：内置的 MinerU、Paddle 网络接口走 Rust 传输，之后跑 normalize worker；
**命令型 OCR 和 Paddle 官方命令行走 Python 的 provider 进程**，归一化在那个进程里做完，不再跑 normalize worker。所以：

- 命令型 OCR 交回原始输出：正式任务会碰到（配了命令型 OCR 的用户；以后接 GLM-OCR 多半也走这条）。
- `job_flow`：正式任务里 MinerU 从来不走它（只在不经过 Rust、直接用 Python 命令跑 OCR 时用到），修它是为了三条路一致。

## 做法

- 新模块 `document_schema/finalize.py`：`finalize_normalized_document(document, report, source_pdf)` 依次缩放到原文 PDF、重建没有真实行的块的行、
  按最终文档重新校验并刷新报告；`refresh_report_for_final_document` 从 `normalize_pipeline.py` 挪过来（那边照旧以旧名字导出）。单独成模块是为了
  避免循环导入：`normalize_pipeline` 会导入 MinerU 的模块，而 `ocr_provider` 包会一路导入到 `job_flow`。
- normalize worker、命令型 OCR 的原始输出、`job_flow` 三处都调它；后两处在函数里导入（原因同上）。
- 命令自己写好的 `document.v1.json` 不动：契约要求它已经是 PDF 点。
- 两个模拟"远程命令"的测试原来往原文目录里写一个只有文件头的假 PDF（`%PDF-1.4`），以前没人读；现在缩放要读页面尺寸，改成写一份真的 320×480 的 PDF。
  文档补上"远程命令交出的原文必须是能打开的真 PDF"。

## 验证

- 新测试 `test_raw_payload_from_a_command_is_scaled_to_the_source_pdf`：命令交回一页 640×960 的原始输出、原文 PDF 是 320×480，归一化后页面是
  320×480、块框缩一半、报告 `coordinate_space=pdf_point`。去掉命令型 OCR 里的这一步，测试红。
- `document_schema` 测试 281 个全过；管线架构检查过；全套合并前检查和管线、翻译测试见合并说明。

## 没做

- `job_flow` 把 `--model-version`（比如 `vlm`）当成服务商版本，盖掉 MinerU 自己的 `_version_name`：只影响 Python 直跑，没改。
