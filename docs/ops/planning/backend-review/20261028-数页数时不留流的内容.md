# 数页数时不留流的内容（2026-10-28）

[上传边收边写到磁盘](./20261024-上传边收边写到磁盘.md)留下的尾巴："lopdf 解析照旧整份读进内存，内存预算照旧按文件大小"。

## 问题

上传收完以后要数页数（`retainpdf-ingest` 的 `uploads/pdf.rs`）。原来是 `lopdf::Document::load`：先把整份文件读进一个
`Vec`，再把每个对象解析出来，**每个流（图片、页面内容、字体）的内容各复制一份留在 `Document` 里**。所以峰值是文件大小的
两倍多，而内存预算（`RUST_API_UPLOAD_BUFFER_MIB`，默认 512）只按文件大小算一份，几个大文件同时上传时预算是少算的。

数页数只要页面树（目录 → 页面树节点 → 页），这些流一个都用不到。

## 做法

- 改用 `Document::load_filtered`，过滤函数 `keep_page_tree_objects`：普通的流读到就扔（返回 `None`），字典、数组这些
  照留；对象流（`ObjStm`）要留着，页面树的字典可能装在里面，lopdf 读完再拆开。
- lopdf 0.32 的过滤函数有个细节写在注释里：最外层的对象留下的是传进去的那个（返回值只看是不是 `None`），对象流里拆出来的
  对象留下的是返回值。流不会装在对象流里，所以对象流自己返回什么都行。
- 峰值变成：整份文件读进来的那一份，加上正在读的那一个流，加上页面树和对象流。内存预算还是按文件大小占，现在和实际对得上。
- 没加新依赖。没做 mmap（文件映射进来就不用再读一份）：要加 `memmap2`，Windows 上映射着的文件不能改名，上传收尾正要改名，
  收益不值这个麻烦。

## 量出来的

仓库里的 9 份真实论文（`tests/fixtures/pdfs/`，0.6 MB 到 20 MB，有对象流、交叉引用流、166 页的）：

| 文件 | 文件大小 | 原来留下的流 | 现在留下的流 |
|---|---|---|---|
| d3cs00837a-69p.pdf | 20.1 MB | 19.8 MB | 0 |
| yakubenko-halogen-lithium-10p.pdf | 9.3 MB | 9.3 MB | 25 KB |
| cr5c00021-55p.pdf | 5.7 MB | 5.9 MB | 254 KB |
| navier-stokes-166p.pdf | 3.0 MB | 3.2 MB | 474 KB |
| 1.pdf | 2.2 MB | 2.2 MB | 81 KB |
| 其余 4 份 | 0.6–2.7 MB | 和文件差不多大 | 0 |

现在留下的都是对象流。

## 验证

- 新测试 `uploads::pdf::tests::page_counts_match_a_full_load_without_keeping_the_streams`：9 份论文逐份比，过滤后数的页数和
  完整读的一样，也和文件名里写的页数一样；留下的流只有对象流，字节数等于完整读出来的对象流。
- 去掉修正（改回 `Document::load`）这个测试红，放回来绿。
- `retainpdf-ingest` 全部测试，全套合并前检查见合并说明。

## 没做

- 文件本身还是整份读进内存一次（见上面 mmap 那条）。
- 修复坏 PDF 走 PyMuPDF 子进程，那边的内存不归这里管，照旧。
