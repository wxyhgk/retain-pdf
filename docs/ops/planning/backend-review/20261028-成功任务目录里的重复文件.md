# 成功任务目录里的重复文件（2026-10-28）

数据目录自动清理的主体。用户 2026-10-28 定的四条规则：

| 东西 | 用户定的 |
|---|---|
| 成功任务里纯重复的中间文件（OCR 原始压缩包、解包里的原 PDF 和图片副本、`rendered/` 下多复制的 zip、重渲染成功后的 `.previous.pdf`） | 成功后马上删 |
| 渲染准备的中间件（`artifacts/render_prepare/`、`render_prewarm/`） | 并进派生缓存的天数（`RUST_API_DERIVED_CACHE_RETENTION_DAYS`，默认不清） |
| 失败、取消的整个任务目录 | 不自动删 |
| 重复上传 | 硬链接复用（另一个分支，[重复上传用硬链接共用一份](./20261028-重复上传用硬链接共用一份.md)） |

成功任务的译文、规范化文档、翻译清单、Markdown 这些阅读器、书库、重渲染真正要读的，一个都不动。

## 先查清楚的

两个只读子代理逐条查过谁读这些文件、缺了会怎样（代码位置记在它们的报告里，结论如下）：

- 一本书从上传到翻译完，原 PDF 在盘上有 3 份完整的加压缩包里 1 份：`uploads/` 一份、任务 `source/` 一份、MinerU 解包的
  `*_origin.pdf` 一份、OCR 压缩包里一份。`documents/<书>/` 里不存原文。
- **OCR 原始压缩包**：解开以后没人读；复用 OCR、续跑、重渲染只要规范化文档、原文、布局。文件列表里它是只给管理员看的
  `ocr-provider/raw.zip`，列表的"有没有、多大"是存任务时记进 `job_artifact_entries` 的，**删了要清字段重存**，不然列表还说它在。
- **MinerU 解包目录**：`source_pdf` 从来不指进这里（Rust、Python 都复制进 `source/`）；阅读器只读 `md/`，没有退回读解包目录的
  兜底（有测试专门断言原始 Markdown 不对外）；`md/` 从 2026-04-05 起每次 MinerU OCR 都复制。规范化以后解包目录只有布局
  `layout.json` 还有人读（复用 OCR 时缺了报错）。`md/images` 里被引用的图是解包图片的硬链接，所以删解包的 `images/` 腾出的
  只是没被引用的那些。
- **`rendered/<任务>.zip`**：只写不读，同步还特意排除它，不在文件列表里。
- **`.previous.pdf`**：只在排队期间（书库合并读）和这次失败时（接回来当 `output_pdf`）用；成功以后不再读，下次重渲染会覆盖。
- **渲染准备、预热**：按指纹找缓存，缺了重新准备（预热缺了退回同步准备）。预热清单 `render_source_prewarm_manifest.json`
  阅读器排版接口要读（缺了返回空、字号适配变差），同步也保留它，所以留着。`pipeline_summary.json` 里记的
  `render_prewarm/visual_profile.v1.json` 路径只是记录，只有管线读，准备时重新生成。
- **`downloads/<任务>.zip`**：每次请求都重新生成（临时文件加换名），生成完到打开发送之间有一小段，所以只删一小时以前的。
- **共享目录**：OCR 子任务的产物写在父任务目录里，复用 OCR 或译文的任务指进别人的目录。所以排队、在跑的任务引用着的
  目录一律不碰。

## 做法

- 文件包 `retainpdf-files` 新模块 `artifacts/intermediates.rs`：
  - `prune_succeeded_job_intermediates(data_root, job)`：只删任务自己目录 `jobs/<任务>/` 里的；任务编号不是普通名字的什么都不删；
    不跟符号链接。解包目录只认 MinerU 的（`provider_artifact_layout(Mineru)` 的 `unpacked`），要 `md/full.md` 在；记录里任何字段
    指着的文件都留着。上一份译文要名字是 `.previous.pdf`、不是 `output_pdf`、`output_pdf` 还在才删（`output_pdf` 不在可能是
    正好又开了一次重渲染，刚挪过去）。
  - `clear_pruned_record_fields(data_root, job)`：记录里指向任务自己目录里、已经不在的原始压缩包（`provider_zip`、诊断里的
    `provider_bundle_zip`）和上一份译文（`previous_output_pdf`、`previous_finished_at`）的字段清掉。指到别人目录的不归它管。
  - `job_dirs_referenced_by(data_root, job)`：任务自己的、`source.artifact_job_id` 的、OCR 子任务的、各个产物路径落在的任务目录。
- 打包下载不再复制 `rendered/<任务>.zip`（`bundle.rs` 去掉 `persist_bundle_copy`）。
- 派生缓存的回收（`derived_artifacts/retention.rs`）加上 `render_prepare/`、`render_prewarm/`：里面每一项（子目录看里面最新的文件）
  超过天数删，预热清单不删；新加 `prune_stale_download_bundles`。
- 数据库加 `succeeded_job_ids`、`unfinished_job_ids`。
- rust_api 的整轮清理（`app/cleanup.rs`，启动时一轮、之后每 `RUST_API_CLEANUP_INTERVAL_SECS` 一轮，默认 6 小时）：
  1. 先算排队、在跑的任务引用着的目录；
  2. 每个成功任务（目录不在上面那堆里）删重复文件，再对它和它的 OCR 子任务清字段，有改动用 `cas_save_job` 只认 `succeeded`
     存回去（这期间被重跑了就不存，下一轮再说），存的时候文件列表跟着重算；
  3. 删 `downloads/` 里一小时以前的 zip；
  4. 设了天数时回收派生缓存，同样跳过上面那堆目录。

## 和用户定的"成功后马上删"的差别

删是在下一轮定期清理时做的：启动时一轮，之后默认每 6 小时一轮，不是任务一成功就删。任务跑完的那个时点在 runner 包里，
runner 在文件包下面一层、用不到它，挂过去要动包的依赖方向；等 6 小时以内不影响什么（多占的盘空间是暂时的）。要更快可以把
`RUST_API_CLEANUP_INTERVAL_SECS` 调小，每轮只是对成功任务的目录做几次 `stat`。

## 没做

- 复用了别人 OCR 的任务，记录里抄过去的 `provider_zip` 路径不清：清理只改任务自己目录的记录和它的 OCR 子任务。那些任务的文件
  列表里 `ocr-provider/raw.zip` 会显示还在，下载时 404 `not_ready`（下载前本来就查文件在不在），只给管理员看。
- 失败、取消的任务目录不自动删（用户定）。
- 检查和删除之间有一小段（毫秒级）：这期间正好有人开重渲染，上一份译文可能被删掉，那次重渲染排队期间阅读退回更旧的版本、
  失败了接不回上一份；渲染缓存被删的话 render 照常现做。
- 管线在 `artifacts/render_prepare/source_base/base.pdf`、`text_strip/stripped.pdf` 里存的近乎整份的 PDF，只按派生缓存天数删。
