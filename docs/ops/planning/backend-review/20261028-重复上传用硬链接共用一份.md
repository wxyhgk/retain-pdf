# 重复上传用硬链接共用一份（2026-10-28）

数据目录自动清理的一部分（用户 2026-10-28 定的规则：重复上传"复用，用硬链接"）。同一批里另两件——任务成功后删纯重复的
中间文件、渲染准备的中间件并进派生缓存天数——在别的分支；失败和取消的任务目录不自动删（用户定）。

## 问题

每次上传都新建一个 `uploads/<upload_id>/` 存一整份。同一本书传两次（换了设备、重新导入、多建一个任务时又传了一遍），
盘上就是两份一模一样的 PDF。书（`documents`）的编号就是 sha256，同一本书只有一行，但上传记录和文件各是各的。

## 做法

`retainpdf-ingest` 的 `uploads/staging.rs`，`publish_upload` 落库之前调 `share_existing_copy`：

- 用 `db.upload_with_content_hash` 找同样编号、最早的那条上传。编号是**同一所有者范围里**原样字节的 sha256（多用户时
  各账号分开算，`scoped_content_hash`），所以只会和自己传过的那份共用。
- 那份文件还在，就在新目录里建一个指向它的硬链接（先建成 `.<文件名>.link`，再换名盖掉刚收的那份），刚收的那份随之删掉。
- 建不了硬链接（跨盘、FAT 之类不支持）或者换名失败：留着刚收的那份，上传照常成功，不报错。
- 上传记录照旧各有各的目录和编号，接口返回不变。删其中一个（孤儿上传清理、删书都是整个目录删）只删自己这个名字，另一个照样能读。

已有的那份可能修复过（PyMuPDF 重写，字节和原样不同）：原样字节一样，修复出来的是同一份文档，用哪份都行。上传目录里的文件
只会整份换名替换（修复就是这样），不会原地改写，查过代码没有原地写 `stored_path` 的地方，所以共用一份是安全的。

## 没做

- 建任务时把上传复制进 `jobs/<任务>/source/`（`page_subset.rs` 的 `std::fs::copy`）没改成硬链接：管线会不会原地改那份
  没逐个查清，改了万一改坏上传就是丢原文。macOS 上 `std::fs::copy` 本来就是 APFS 的写时复制，不占第二份空间；
  Windows、Linux 上照旧占。
- 没登记上传的老任务补成书时（`source_document.rs`）照旧另存一份，不过它本来就先查同样内容的上传，有就直接归属过去。
- 已经存在的重复上传不回头合并。
- 备份整份拷数据目录时，硬链接会被拷成两份文件，恢复后照常能用，只是不再共用。

## 验证

- 新测试 `uploads::tests::uploading_the_same_pdf_again_shares_one_file_and_either_can_be_deleted`：同一份传两次，编号、
  目录不同，后一份是硬链接（Unix 上链接数 2），目录里不留临时文件；内容不同的另存（链接数 1）；删掉先传的那个目录，
  后传的照样能读；已有那份文件不在了（记录还在）照常另存。
- 去掉 `share_existing_copy` 的调用，测试红在"the second upload links to the first copy"，放回来绿。
- 全套合并前检查见合并说明。Windows 上的硬链接本机没跑。
