# 阶段超时按进展计时

2026-10-31。用户："貌似最大的执行时间是 30 分钟，这样肯定不行啊，agent 翻译，如果是 100 页就超过了 30 分钟。"

## 问题

- `runtime.timeout_seconds` 以前从阶段进程启动开始算整段时长，到点就杀（`retainpdf-runner` 的
  `process_runner/execution.rs`）。后端默认 1800 秒，前端开发者设置也默认 1800 并显式发上来，所以改后端默认值没用。
- 翻译 agent 按页顺序翻（要带术语记忆），low 档实测每页约 14.5 秒，加上开头通读、最后审校，一百二三十页就过 30 分钟。
- 空闲检测 `no_output_timeout_seconds` 默认关、前端发 0，真正兜底的只有这 30 分钟。
- 顺带：走模型执行器的任务，模型会话有效期按 `timeout_seconds + 600`（至少 1 小时）算，翻过一小时模型请求会因会话过期失败。

## 决定

- `timeout_seconds` 改成**多久没有进展**：从最近一次进展算起。进展是阶段事件的（阶段, 子阶段, 进度, 总数）和上一条不同，
  或者提交了检查点、发布了产物；只换说明文字、反复报同一个进度不算（不然原地打转、不停打印的 worker 永远不会被判卡住）。
  前端发的 1800 正好变成"半小时一页都没出来才算卡住"，前端不用改。
- 绝对上限 `RUST_API_WORKER_MAX_RUNTIME_SECS`，默认 24 小时，`0` 不限；请求的 `timeout_seconds` 更大时以请求为准。防死循环一直烧钱。
- 模型会话有效期改成绝对上限 + 600 秒（至少 1 小时）。
- `stage_detail`：`no progress for {N}s`、`max runtime {N}s exceeded`、`no output for {N}s`。以前没有进展那种写
  `provider timeout` / `normalization timeout`；前端没有按这两个字符串判断（全仓搜过）。
- 不报进度事件的阶段，"最近一次进展"就停在启动时刻，行为和以前一样，不会更差。
- Paddle、MinerU 轮询自己的 `ocr.poll_timeout`（默认 1800 秒）按"服务商多久没返回"算，这次不动。

## 验证

- 新加 3 个 Rust 用例：一直出页的 worker 跑过 `timeout_seconds` 不被杀（阈值 2 秒、跑 5 秒）；反复报同一个进度照样被判没有进展；
  一直有进展也会撞上绝对上限。原有超时用例改成新文案。
