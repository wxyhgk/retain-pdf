# 数据库整理

2026-11-20。用户：「看看我们现在的数据库，我感觉现在比较乱了」；同意从第 1 步开始，也同意只读查真实库（只看行数、大小，不看内容）。

## 盘点

表结构看的是代码（`database/retainpdf-db`：`db.rs` 的初始建表、`ensure_legacy_columns` 补列、v01–v30 编号迁移），
真实库（`data/db/jobs.db`，user_version 30）只读查了行数和各表占的空间。

| 分组 | 表 | 真实库 |
|---|---|---|
| 任务 | `jobs`、`artifacts`（旧，一整坨 JSON）、`job_artifact_entries`、`events`、`pipeline_attempts`/`dispatches`/`stages`/`units`、`model_sessions`/`model_operations` | 148 个任务 |
| 进度事件 | `event_feeds`、`event_feed_items`、`event_source_versions`、`event_feed_retention` | 40 万条 |
| 书库 | `uploads`、`documents`、`document_title_state`、`document_metadata_suggestions`、`collections`、`collection_documents`、`blocks_fts`、`translation_versions`/`_jobs`/`_choices`、`glossaries` | 43 本书 |
| 同步 | `sync_*` 11 张 | 在用（`/api/v1/sync`） |
| 账号（多用户，10-16 停了） | `users`、`sessions`、`invite_codes`、`page_ledger`、`job_page_charges`、`platform_settings` | 都是 0 行 |
| 死表 | `ai_conversations`、`ai_messages`、`assets`、`agent_calculation_runs`、`agent_calculation_artifacts`、`document_operations`、`document_operation_attempts`、`document_operation_events`、`document_versions`、`favorites` | 都是 0 行 |

**库有 1.4GB**（148 个任务、43 本书），空间几乎都在三处：

- 进度事件存了两份：`event_feed_items` 536MB（加索引约 97MB）、`events` 201MB（加索引约 60MB），合计约 900MB；
- `jobs` 195MB，几乎全在 `result_json`：worker 的完整 stdout 存了进去，11-03 的一个任务一行 177MB（stdout 171MB）。
  11-03 以后的任务都在 0.2MB 以内，已经截断了，老行还在；
- 全文搜索 `blocks_fts` 约 216MB（14.7 万个块，正常）。空闲页约 28MB。

## 乱在哪

1. 10 张死表：RetainPDF 自己的 AI（11-03 去掉）留下的对话、消息、截图、AI 计算、AI 改写文档，收藏（接口、前端早没了），
   读写代码、备份检查、同步还都带着；
2. 任务产物记两份：旧 `artifacts` 表（`artifacts_json`）和 `job_artifact_entries`，保存时两边都写；
3. `jobs` 一半是 JSON：`status_json`、`command_json`、`request_json`、`log_tail_json`、`result_json`、`runtime_json`、`failure_json`，
   旁边又有从 JSON 抄出来的 `stage`、`progress_*`；
4. 建表三套写法：`db.rs` 初始建表、启动时补列、编号迁移，看一张表要三处拼；
5. 进度事件两份（`events` 原始、`event_feed_items` 整理后给接口），各自留到什么时候没有统一；
6. 多用户的归属列（v22 `owner_user_id`）单机也带着。`documents.active_version_id` 是 AI 改写文档留下的列，
   一直是空的，但还在书的接口契约里（可选字段）。

## 第 1 步（分支 `refactor/db-drop-dead-tables`）

- 迁移 v31 `drop_dead_tables`：先删引用别人的表再删被引用的；表上的索引、同步触发器（v17、v19）随表删；
  同步记账里这几类（`favorite`、`asset`、`conversation`、`calculation`、`operation`）的待发、已知实体、待定、自己的记录一起清。
  `documents.active_version_id` 没有外键，不受影响。
- 删的代码：db 包的 `conversations.rs`、`agent_calculations.rs`、`document_operations/`；core 的 `models/document_operation.rs`、
  对话和消息的记录类型、对话列表上限；备份恢复前不再查「AI 正在改文档、AI 计算没算完」；书的孤儿回填不再看收藏；
  同步的种类、表、文件路径列、「没结束不发」里这几类都去掉；账号参数归类去掉 `conversation_id`、`calculation_id`。
- 同步兼容：旧版本设备还会发这几类，新加 `RETIRED_SYNC_KINDS`，收到当过时改动忽略。以前不认识的种类一律当「新版本才有的」存着等升级，
  这几类永远等不到，会一直挂在待定里。
- 测试：同步测试里专测这几类的删掉，收敛测试的「收藏」换成术语表，第三期补登记改测术语表，新加「旧设备发来已删种类直接忽略」；
  db 加「迁移后这 10 张表和它们的索引、触发器都不在、书照常能写」；事件流回退到 v13 重跑迁移的测试，回退时补这几张表的骨架
  （已上线的迁移不能改，v16、v17、v19 重跑要用到）。
- 真实库副本上跑 v31：58 张表 → 48 张，外键检查、完整性检查都过，约 10 秒。
