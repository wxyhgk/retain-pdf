# OCR 和翻译并行

2026-10-31。GLM-OCR 端到端实测 34 页论文 74 秒：OCR 33 秒（智谱按 key 排队，每页约 0.9 秒，2 路并发不变快）、翻译 26 秒、渲染 9 秒，
三段严格串行。用户选了"OCR 和翻译并行"（"我觉得用 3 是最好的，这样速度能达到极限"）。

## 用户的决定

- 跨栏、跨页拼接单独做成一个**监控**环节："只要 ocr 过了两页，我们就开始监控，进行拼接，然后同步交给翻译……这样就能不用等最后的时候了"。
  监控跟着 OCR 一对页一对页地判断（规则找候选，模型复核），拼好、确认独立的段落马上进翻译；翻译拿到的已经是拼好的单元，不事后重翻。
  一页里只有最后一段要等下一页到了才定；跨栏拼接只看本页，页一到就能定。
- 只对 GLM-OCR（能流式公布）和 legacy 翻译引擎；翻译 agent 要先通读全书，照旧等 OCR 做完。渲染这次不并行（约 9 秒）。

## 分三步

1. **OCR 流式公布**（`feat/ocr-stream-manifest`）：GLM 驱动每做完一片，把前面连着做完的页归一化写到 `ocr/stream/document.v1.json`，
   就绪清单 `ocr/stream/manifest.json`（`ocr_stream_v1`：`seq`、`ready_pages`、`total_pages`、`done`、`failed`、`error`，先写文档后写清单，都原子写）。
   契约在 `retainpdf_pipeline/foundation/shared/ocr_stream.py`。
2. **监控 + 翻译**：翻译 worker 的流式模式。跟着清单按轮做：新到的页做页面策略；监控在已知页上重算接续（瞬时），只把新出现的候选对送模型复核；
   拼接已定的单元进翻译池跑完，再等下一版清单。等待时定时报进度（防"多久没有进展"超时）；断点按页校验（现在按整份文档哈希 + 页范围，文档一变就失效）。
   OCR 结束后最后一页的末段定下来、翻完，做收尾（乱码修复、漏翻补救、质检、清单）。
3. **Rust**：book 任务的 OCR 支持流式时，OCR 子任务和翻译阶段同时拉起；OCR 失败或任务取消时翻译跟着停；别的情况照旧串行。

## 第 1 步的验证

- 量过：100 页归一化 0.44 秒（适配 0.29 + 缩放 0.15），所以每片都把前缀整个重做，不做拼接；对着整本原文 PDF 按位置对得上。
- 前缀页和最后整份的同一页逐字节一致（真实结果 50 页前缀对 100 页整份，没有一页不同），翻译按前缀先做的块编号、内容都稳定。
- 单测：每片公布一次（2、4、5 页）、最后一版就是整份且标 `done`；前缀里的图片已经裁好挂上；续跑时断点里的页在请求之前就公布；
  请求失败时标 `failed`、`error` 写原因、`ready_pages` 停在已公布的页数。公布在主线程做，下一片的请求同时在跑，不互相等。
