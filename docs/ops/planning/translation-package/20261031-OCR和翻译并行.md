# OCR 和翻译并行

2026-10-31。GLM-OCR 端到端实测 34 页论文 74 秒：OCR 33 秒（智谱按 key 排队，每页约 0.9 秒，2 路并发不变快）、翻译 26 秒、渲染 9 秒，
三段严格串行。用户选了"OCR 和翻译并行"（"我觉得用 3 是最好的，这样速度能达到极限"）。

## 用户的决定

- 跨栏、跨页拼接单独做成一个**监控**环节："只要 ocr 过了两页，我们就开始监控，进行拼接，然后同步交给翻译……这样就能不用等最后的时候了"。
  监控跟着 OCR 一对页一对页地判断（规则找候选，模型复核），拼好、确认独立的段落马上进翻译；翻译拿到的已经是拼好的单元，不事后重翻。
  一页里只有最后一段要等下一页到了才定；跨栏拼接只看本页，页一到就能定。
- 只对 GLM-OCR（能流式公布）和 legacy 翻译引擎；翻译 agent 要先通读全书，照旧等 OCR 做完。渲染这次不并行（约 9 秒）。

## 分三步

1. **OCR 流式公布**（`feat/ocr-stream-manifest`）：GLM 驱动每做完一片，把前面连着做完的页归一化写到 `ocr/stream/document.v1.json`，
   就绪清单 `ocr/stream/manifest.json`（`ocr_stream_v1`：`seq`、`ready_pages`、`total_pages`、`done`、`failed`、`error`，先写文档后写清单，都原子写）。
   契约在 `retainpdf_base/ocr_stream.py`（第 2 步从 pipeline 挪到底座包：翻译包也要读，它不能依赖 pipeline）。
2. **监控 + 翻译**：翻译 worker 的流式模式。跟着清单按轮做：新到的页做页面策略；监控在已知页上重算接续（瞬时），只把新出现的候选对送模型复核；
   拼接已定的单元进翻译池跑完，再等下一版清单。等待时定时报进度（防"多久没有进展"超时）；断点按页校验（现在按整份文档哈希 + 页范围，文档一变就失效）。
   OCR 结束后最后一页的末段定下来、翻完，做收尾（乱码修复、漏翻补救、质检、清单）。
3. **Rust**：book 任务的 OCR 支持流式时，OCR 子任务和翻译阶段同时拉起；OCR 失败或任务取消时翻译跟着停；别的情况照旧串行。

## 第 1 步的验证

- 量过：100 页归一化 0.44 秒（适配 0.29 + 缩放 0.15），所以每片都把前缀整个重做，不做拼接；对着整本原文 PDF 按位置对得上。
- 前缀页和最后整份的同一页逐字节一致（真实结果 50 页前缀对 100 页整份，没有一页不同），翻译按前缀先做的块编号、内容都稳定。
- 单测：每片公布一次（2、4、5 页）、最后一版就是整份且标 `done`；前缀里的图片已经裁好挂上；续跑时断点里的页在请求之前就公布；
  请求失败时标 `failed`、`error` 写原因、`ready_pages` 停在已公布的页数。公布在主线程做，下一片的请求同时在跑，不互相等。

## 第 2 步：监控 + 翻译（`feat/translation-stream`）

- 跟着 OCR 的流程放在 `workflow/streaming_flow.py`（和 `book_flow.py` 同一层，架构规则登记了）；批量翻译之后的收尾从
  `book_flow.py` 抽成 `finish_book_translation`，两种跑法共用。流式只对 legacy、不做译前准备；agent 和译前准备等 OCR 做完按整本翻。
- **扣住哪一块**：跨页拼接只发生在"上一页最后一个能接的块"（`continuation.rules.eligible`）和"下一页第一个能接的块"之间，
  所以每轮只扣最新一页最后一个能接的块，它已经在拼接组里就整组扣（`pending_translation_items(deferred_item_ids=…)`）。
- **监控**：规则那一遍每轮在已知页上重算（会先清掉上一轮的拼接），模型复核的结论按（前块, 后块）记住，判过的不再送模型。
- **断点**：阶段只能往前走，第二轮起监控记在 translating 下，新页做完页面策略再记进断点；"已完成又变回待翻"的门禁只看断点里已有的页；
  指纹按原文 PDF 的 sha256。诊断里阶段耗时改成累加（每轮进出一次）。
- 契约从 pipeline 挪到底座包 `retainpdf_base/ocr_stream.py`（翻译包不能依赖 pipeline），加了 `wait_for_ocr_stream`、`OcrStreamFailed`。
- 翻译阶段 spec 的 `inputs.ocr_stream_dir`（可选，旧 spec 没有）：给了就不要求 `source_json` 开始时存在。

验证：
- 等价性：人造三页两栏论文（有跨栏、跨页段落），假模型（只换 HTTP），整本一次翻和一页一页流式翻，逐块译文、拼接组完全一样，
  流式里每块只翻一次、总翻译次数一样、判过的拼接对不再送模型；前两轮各扣了一块，最后一轮不扣。
- 反证：把扣留关掉，第 1 页最后一块第一轮就翻了，第二轮和第 2 页拼成组，断点门禁当场报"已完成又变回待翻"——这就是要避免的重翻。
- 集成测试（假传输跑真实翻译入口）在 worktree 里要让子进程用 worktree 的翻译包（它们的 PYTHONPATH 只有 pipeline，翻译包从虚拟环境
  装的主检出导入），临时加 sitecustomize 跑了 206 个全过，跑完删掉。

## 第 3 步：Rust 同时拉起（`feat/ocr-translate-parallel`）

- `JobRecord::ocr_streams_pages()`（现在只有 `glm_ocr`）为真、OCR 之后接着翻译时，`run_job_with_ocr` 走
  `run_ocr_and_translation_together`：OCR 子任务和翻译阶段 `tokio::join!` 同时跑。翻译阶段用事先知道的路径
  （整份文档 `ocr/normalized/document.v1.json`、上传的原文、`ocr/` 当流目录），stage spec 写 `inputs.ocr_stream_dir`；
  渲染准备要整份文档，这时不和翻译并行拉起。
- 两边不写同一行：OCR worker 跑起来以后只写子任务的行（`save_ocr_job` 的父任务镜像只在拉起进程之前那几次）。
- OCR 没做成（失败、取消、进程被杀、超时）：driver 补标清单 `failed`（`job_runner/ocr_stream.rs`），等着的翻译马上退出；
  父任务按 OCR 的结果收尾。OCR 在 Python 里失败时自己已经标过，已经 done / failed 的不再动。
- 两边都成：OCR 产物并回父任务（CAS），渲染用 OCR 落在任务目录的那份原文（选页时是切出来的子 PDF）。
- OCR 子任务结果的 CAS 收尾抽成 `persist_ocr_child_result`，串行、并行两条路共用；扫源码的守卫测试改成两条路都要走它、它里面必须是 CAS。
- 前端：父任务在 OCR 还在跑时就是 translating，翻译多了 `substage=ocr_stream` 的进度（OCR 已到的页数），已通知前端会话。

## 合并后开发栈实测（2026-10-31）发现的问题

34 页论文端到端：翻译跟着 OCR 跑了 4 轮，OCR 交出最后一页后 4.4 秒翻译就完成（串行时 OCR 完了再翻要 26 秒）——并行生效。
但任务没渲染就"成功"了：第 3 步把 OCR 产物并回父任务后多写了一次库，翻译是中间阶段、内存里 status 已是 Succeeded，写下去父任务成了终态，
渲染阶段启动时的 CAS 被拒。修：不在那里写库，产物随渲染阶段启动一起写（`fix/parallel-render`），加了扫源码的守卫测试。
这次 OCR 本身也慢（四片 77、14、12、26 秒，上午同一篇 8、12、5、3 秒；第一片时翻译还在等、没有别的请求），是智谱服务端的波动。

## 修好以后再测，渲染准备提前（2026-11-01）

修好渲染以后同一篇 34 页论文 55 秒（上午串行 74 秒）：OCR 31 秒（智谱恢复正常），OCR 交出最后一片后 3.4 秒翻译完成，渲染 16 秒。
渲染比串行时（9 秒）慢，是因为串行时"渲染准备"（页面分析、去文字层这类不看译文的活）和整个翻译阶段重叠，并行时它要整份文档，
第 3 步干脆没拉起。用户："可以，接着做渲染准备提前"。现在 OCR 一做完就拉起（`perf/render-prepare-after-ocr`），
和翻译最后一轮重叠，翻译成了再限时等它收尾；翻译失败或取消就丢弃句柄（kill_on_drop）。
同时父任务进 translating 时的说明在并行模式下改成"OCR 进行中，翻译跟着 OCR 开始"（以前写"OCR 完成，开始翻译"）。
