# 翻译包拆成底座和两个引擎

2026-11-20，方案，还没动手。包名同日定了（见文末「已定」）。

## 起因

用户：「翻译包得分成两个，一个是普通翻译，一个是 agent 翻译。」

现在翻译包 `backend/translation`（`retainpdf-translation`）里两种引擎混在一起：304 个模块、约 4.8 万行、35 个提示词文件。
任务的 `translation.engine` 选 `legacy`（普通翻译，批量逐块翻）或 `agent`（翻译 agent）。agent 的核心早就独立成
`backend/translation-agent`（`retainpdf-translation-agent`，只用标准库），但把它接进流水线的一层
（`workflow/agent_flow.py`、`workflow/agent_openai.py`）还在翻译包里，而且两种引擎共用翻译包的前后半段：

```
document.v1.json
  ├─ 前半段（共用）：读每页模板、接续段、页面策略
  ├─ 中段（二选一）：legacy 批量逐块翻 ／ agent（通读 → 按节或逐页 → 审校）
  └─ 后半段（共用）：回填、断点、清单、诊断、质检
```

只切成「普通翻译」「agent 翻译」两半，共用的前后半段放哪边都不对：放普通翻译，agent 就得依赖普通翻译；两边各抄一份，
断点、清单这些协议会走样，排版那边要兼容两套。所以切成**三块：共用的底座、两个引擎**。

## 目标结构

| 包 | 目录 | 放什么 | 以后 |
|---|---|---|---|
| 翻译底座 `retainpdf-translation`（名字不变） | `backend/translation` | 读文档、接续段、页面策略、回填、断点、清单、诊断、质检、请求日志、模型请求层、用量；引擎分派入口；`public` 门面 | 稳定 |
| 普通翻译 `retainpdf-translation-classic`（新，import 名 `retainpdf_translation_classic`） | `backend/translation-classic` | 批量逐块翻、乱码重构、修复兜底、空译收口、译前准备、领域判断、可疑块分类、精修、编辑部、表格翻译、上下文窗口、任务记忆，以及它们的提示词 | 冻结：只修 bug，不加功能（11-18 用户：精修、编辑部别删） |
| agent 翻译 `retainpdf-translation-agent`（已有） | `backend/translation-agent` | 核心 `retainpdf_translation_agent`（照旧只用标准库）+ 接线 `retainpdf_translation_agent_engine`（从翻译包挪来的 `agent_flow`、`agent_openai`，依赖底座） | 主力，提示词整理在这里做 |

任务请求里的引擎名照旧是 `translation.engine = "legacy"`（接口、前端、库里的旧任务都用它），只是代码搬进 classic 包；
引擎登记表里 `legacy` 指向 classic 包。

依赖方向（架构检查卡住，两头都查）：

```
流水线 retainpdf_pipeline.translate（worker 外壳）
  ├─> 翻译底座（引擎分派：按名字延迟加载引擎，不静态 import 引擎）
  ├─> 普通翻译 ──> 底座
  └─> agent 接线 ──> 底座、agent 核心（标准库）
两个引擎之间互不 import；底座不 import 任何一个引擎。
```

底座名字不变，好处是流水线、渲染、OCR 现在走的 `retainpdf_translation.public` 大部分不用改。

另外 agent 接线 `agent_flow` 只用了普通翻译的一个函数 `book_flow.prepare_book_payloads`（前半段：读模板、接续段、页面策略）。
它本来就是共用的前半段，只是写在普通翻译的文件里：挪进底座的 `workflow/prepare.py`；里面给普通翻译加上下文窗口的那一步
（`annotate_translation_context_windows`）改成钩子。

## 三个要特别小心的地方

1. **断点指纹不能变。** `core.engine_identity` 读普通翻译的提示词（`translation_*.txt`）算提示词哈希，写进断点指纹；
   指纹变了，正在跑、等着续跑的任务会整份重来。挪走时指纹的算法和内容一字不改，加一条测试：拆前拆后同一个请求算出同一个指纹。
2. **`public` 门面导出了普通翻译的东西。** 渲染前精修 `run_refine_for_render` 和表格翻译 `TableContext` 等共 8 个名字，
   流水线的 `render_only_pipeline.py`、`translate/tables_stage.py` 在用。底座的 `public` 不能再导出它们
   （否则底座依赖普通翻译）：普通翻译包出一个自己的 `public`，流水线这几处改从那里取。精修、表格翻译对 agent 任务照样能用，
   因为流水线三个包都依赖。
3. **前端和别处的测试会读后端路径。** 2026-10-16、10-17 搬文件时，前端测试和别的包的测试读 Rust 源码路径，CI 红过。
   每次搬家前对整个仓库 `git grep` 一遍要搬的路径，包括 `frontend/`（只读，不改；要改的写进交接文档）。

## 不变的东西

- 产物协议：逐页译文、`translation-manifest.json`、`translation-checkpoint.v1.json`、请求日志，字段和文件名都不变；排版不用动。
- Rust 拉起翻译的方式（`python -m retainpdf_pipeline.translate --spec …`）、stage spec、任务请求里的 `translation.engine`。
- 两种引擎的行为、提示词内容、断点指纹。这次只搬家、切依赖，不改行为；提示词整理另做。
- `retainpdf_translation.public` 里底座那部分的名字。

## 分几步做

每一步一个分支，做完跑全套合并前检查（两份架构检查、依赖清单、requirements 同步、`.github`、接口脚本、
`cargo test --workspace`、翻译单测正序和倒序、翻译 agent 和 agent_lab），等用户说「合」。

| 步 | 分支 | 做什么 | 怎么验 |
|---|---|---|---|
| 1 | `refactor/translation-engine-seams` | 在原地切开上面 20 处依赖：引擎登记表、执行计划拆两层、策略里的三个钩子、`prepare_book_payloads` 挪进底座、`deepseek` 传输和翻译客户端拆开。**不搬文件** | 架构检查加一条：底座清单里的模块不许 import 普通翻译清单里的模块（清单先写在检查脚本里）；翻译测试不改一个断言照样过 |
| 2 | `refactor/translation-classic-package` | 新建 `backend/translation-classic`，把 138 个模块和它们的提示词搬过去，改 import；普通翻译出自己的 `public` | 测试里 75 个文件、流水线 devtools 和入口 8 个文件改 import（机械替换）；登记新包：`backend/pyproject.toml`、`uv.lock`、`backend/translation-classic/pyproject.toml`、`.github/workflows/tests.yml`、`ops/deployment/docker/backend/Dockerfile.app`、`ops/development/dev.sh`、`ops/release/build_source_archive.py`、依赖清单和 requirements 同步脚本、`stage_specs.py`；断点指纹测试 |

| 4 | `chore/translation-split-docs` | 文档：三个包的 README、`backend/pipeline/README.md`、`CLAUDE.md` 里的检查清单（翻译测试套件路径、新包要跑的测试）、`docs/core/contributing/backend.md` 的包对照表 | `.github` 文档链接测试 |
| 5 | — | 实测：开发栈各跑一本短书，普通翻译、agent 各一次；再拿一个跑到一半的任务续跑，确认断点接得上 | 要花钱（Haiku、qwen3.8-flash 各几页），跑前确认 |

第 1 步最难，也最值钱：切完以后两个引擎在代码上已经分开，后面几步都是搬家。第 1 步之后如果要停，也不留半成品。

## 风险

- **测试量大**：翻译测试 2045 个，第 2 步要改 75 个测试文件的 import。机械替换，但量大，要防漏改；倒序跑一遍查模块之间互相污染。
- **钩子写错，普通翻译悄悄少一步**：领域判断、可疑块分类、任务记忆改成钩子后，普通翻译漏注入不会报错，只会翻得差一点。
  第 1 步给普通翻译加一条测试，钉住这三个钩子都注入了。
- **并行开发冲突**：搬家期间别的分支改翻译包会大面积冲突。第 2 步动手前确认没有在做的翻译包分支，做得越快越好。

## 已定（2026-11-20）

- **包名**：普通翻译叫 `retainpdf-translation-classic`（目录 `backend/translation-classic`，import 名 `retainpdf_translation_classic`）。
  用户先提过 `-base`：仓库里已经有底座包 `retainpdf-base`，而方案里的「底座」是继续叫 `retainpdf-translation` 的共用部分，
  叫 base 正好说反；`-legacy` 带「要淘汰」的意思，所以用 classic（经典版）。
  底座留 `retainpdf-translation`，agent 留 `retainpdf-translation-agent`，都不改名。
- **连字符还是下划线**：照仓库的规矩，包名和目录用连字符、import 用下划线（pip、uv 把 `-` 和 `_` 当同一个字；
  `retainpdf-math`、`retainpdf-pipeline`、`retainpdf-base` 和 Rust 的 `retainpdf-*` 都这么写，`CLAUDE.md` 写明了）。

## 也定了（2026-11-20 晚些）

- **agent 接线放哪**：放进 `backend/translation-agent`，作为单独的接线模块 `retainpdf_translation_agent_engine`（依赖底座），
  和只用标准库的核心 `retainpdf_translation_agent` 并列；agent 翻译的东西都在一个目录。
- **先做哪件**：先整理了 agent 的提示词（第二批、第三批，已合并），拆包在后面做。

## 第 1 步做完（2026-11-20，分支 `refactor/translation-engine-seams`）

先把归类做准再切：`tail_retry_queue`、`classification.rule_engine`、`services.context`、`core.context`、`llm.domain_context`
（领域判断两种引擎都跑，行为不变就先归底座）其实是两边共用的，归底座以后要切的从 20 处降到 13 处。实际切法：

| 依赖 | 怎么切 |
|---|---|
| `deepseek` 请求层顺带导出拼提示词的函数 | 不再导出，测试改从 `prompt_building` 取 |
| 调模型的可疑块分类（开关从没打开过） | `TranslationPolicyConfig.page_classifier` 由引擎传入；`classification` 包不再转发 |
| 回填更新任务记忆 | 只用协议 `services.memory.updater`（归底座） |
| 审校汇总经过带调模型修复的协调器 | 直接用规则审查器 `ConsistencyReviewerAgent`，结果一样 |
| `provider_registry` 捆着旧引擎的批量翻译函数 | 运行时只留发请求的部分；编排代码从 `translation_client` 直接取（只有 DeepSeek 一家，行为一样） |
| 执行入口 import 两个旧引擎流程 | 引擎登记表 `workflow/engines.py` |
| 执行计划里的译前准备、批大小 | 译前准备挪到 `workflow/preparation_step.py`，批大小按引擎登记的函数算（agent 引擎照请求里的 batch_size 写诊断，以前也走旧引擎的算法，只影响诊断数字） |
| agent 接线借 `book_flow.prepare_book_payloads` | 挪进 `workflow/prepare.py` |

新加架构检查 `devtools/architecture_checks/translation_engines.py`：普通翻译模块按前缀列清单（`CLASSIC_MODULES`），
同目录里留在底座的列 `BASE_EXCEPTIONS`（规则审查器、审校汇总、记忆更新器协议、并发参数）；底座、agent 接线 import 它们
（含函数里的延迟 import、`from 包 import 子模块`）就报错。按这份清单：底座 180 个模块约 2.6 万行，普通翻译 124 个约 2.1 万行。

第 2 步搬家要注意：`BASE_EXCEPTIONS` 里的模块在普通翻译的目录下，搬的时候要挪到底座自己的目录；
`services/agents/__init__.py` 会把协调器、修复这些普通翻译的东西全带进来，审校汇总搬走后才真正断开运行时依赖。

## 第 3 步做完（2026-11-20，分支 `refactor/translation-agent-engine`）

agent 接线 `agent_flow.py`、`agent_openai.py` 从翻译包的 `workflow/` 挪进 `backend/translation-agent` 的新 Python 包
`retainpdf_translation_agent_engine`，行为不变。

- **依赖方向反过来**：以前翻译包依赖 agent 包；现在翻译包不依赖 agent 包，接线依赖翻译包。agent 包的 `pyproject.toml`
  加了 extra `engine`（翻译包 + requests），核心照旧 `dependencies = []`、只用标准库；流水线依赖 `retainpdf-translation-agent[engine]`。
- **断点身份**：底座的 `checkpoint/identity.py` 以前直接 import agent 包的版本号，现在经引擎登记表的新字段
  `EngineSpec.checkpoint_identity` 取（agent 是 `retainpdf_translation_agent_engine.identity:agent_engine_identity`，普通翻译没有，身份不变）。
