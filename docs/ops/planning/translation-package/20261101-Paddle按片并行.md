# Paddle 按片并行提交

2026-11-01。用户："如果是这样,我们的 paddleocr 是不是也可以一页一页的翻译?" → 实验 → "可以"。

## 为什么不能照搬 GLM

Paddle 官方接口是"提交任务 → 轮询 → 全部做完才给结果下载地址"，轮询能看到已识别几页，但拿不到已做完的页。所以由我们切片，各自提交成一个任务。

## 实验（34 页论文，每次文件内容不同以避开服务端缓存）

| 轮 | 整份一个任务 | 切 4 份同时提交 |
|---|---|---|
| 1 | 42.8 秒 | 79.6 秒（一份 4 页的排了 79 秒才开始） |
| 3 | 46.1 秒 | 10.9 秒 |
| 4 | 94.1 秒 | 23.8 秒 |

- 同一个 token 的几个任务是真并行的（GLM 按 key 排队，不是）。
- 排队时间波动很大，单份有时几秒、有时一分多钟才开始。
- 同一份文件重复提交，服务端直接回缓存结果（第 2 轮整份 0.4 秒，不算）。

## 决定

- `paddle_chunked.py`：每份 10 页、最多同时 4 份；没有等着提交的份了、某份交上去 15 秒还一页没识别就再交一份，谁先完用谁
  （真实跑那次正好触发：第 1 份排了 20 秒，再交的一份很快做完，34 页共 33 秒）；失败重交最多 3 次；按原文 sha256 续跑。
- 拼接时各份的全局编号加偏移：Paddle 适配器按 `global_group_id` 认接续组，各份都从 0 编，不偏移就会把不同份的块拼成一组。
- 只在 OCR 和翻译并行时用（Rust `execute_ocr_job_streaming`）：官方云服务、官方 HTTP、上传的文件。自建服务（`paddle_api_url`）
  没量过并发、远程地址、官方命令行照旧由 Rust 整份提交——Rust 那条路有派发意向记录（进程死在提交途中重启后不重复提交），
  切片这条没有，进程死掉时在途的几份会再交一次；再交一份防卡住本来也是有意多花一小份。
- OCR 成了而清单没标完成时，Rust 补一版 done 指向最后整份文档（`ensure_ocr_stream_done`），翻译不会干等。
- 只在 OCR 并行流程里调的入口单独一个（`execute_ocr_job_streaming`，写的 provider spec 带 `ocr.stream_pages: true`，Python 只在这时按片；
  Python 整份提交的老路径照旧，有测试钉着）：一开始按"有父任务就走"判断，把守 Rust 传输取消语义和派发记录的
  三个测试也改道了，收窄成显式入口；外面多包一层后 future 太大，测试线程栈溢出，装箱。

## 验证

- 假接口单测 6 个（并行、前缀公布、卡住再交、失败重交和放弃、续跑、编号偏移）；core 单测钉住哪些 OCR 能流式；清单补 done 的单测。
- 真实 Paddle 跑完整驱动：34 页 33.4 秒（含一次再交），243 块、16 张图全挂上，清单最后标 done。
