## 1. 剩下的 409 全部带 `reason`

上次审计范围外、`details` 还是 `{}` 的 409：

| 地方 | `reason` |
|---|---|
| `job_loading` 读老版本布局的任务（`retainpdf-api-base/src/job_loading/mod.rs`） | `legacy_job_unsupported` |
| 事件文件那个位置不是普通文件（`retainpdf-jobs/src/progress/event_feed/files.rs`） | `event_source_not_file` |
| 建任务指定的 `job_id` 已存在（`retainpdf-jobs/src/lifecycle/creation/submit.rs`） | `job_exists` |
| 改标签名撞上别的标签（`retainpdf-library/src/tags.rs`） | `tag_name_taken`，另带 `existing_tag_id` |
| 模型执行器内部接口：任务不在跑（`retainpdf-providers/src/model_requests_api.rs`） | `job_not_active`（沿用任务操作已有的值） |
| 模型执行器：冻结的模型连接变了、同一个 `operation_id` 换了内容、任务暂停等人工处理、单块请求次数超了 | `model_connection_changed`、`operation_content_changed`、`job_paused`、`unit_budget_exceeded` |

`ModelExecutorError::Conflict` 从一句话改成 `{ reason, message }`，`message` 原样不变（Python `rust_executor.py` 只看状态码，
把 409 都当「要人工处理」，不受影响）。

补完以后生产代码里没有不带原因的 409 了。`AppError::conflict`（不带原因）改成只在 `retainpdf-api-base` 自己的测试里能用
（`#[cfg(test)]`），以后新写 409 只能用 `conflict_because` / `conflict_because_with`，忘了写原因编译不过。

## 2. `GET /jobs` 不认识的查询参数 400

`ListJobsQuery` 加 `deny_unknown_fields`。核对过调用方：前端 `frontend/packages/api/src/jobs.ts` 只带 `limit`、`offset`、`status`、
`workflow`、`provider`、`q`、`include_live_stage`、`job_ids`（`scope` 在前端函数里换成 `workflow`，不上传）；桌面壳
`backend-http.js` 只带 `limit`、`offset`；`query_acceptance.py` 带 `limit`、`q`。`owner` 是路由按当前用户填的，查询串里带算不认识。
契约 `job-status.v1` 的 `ListJobsQuery` 加 `additionalProperties: false`，重新生成（类型只多一段说明）。

## 3. 改单条译文内容没过检查：422 → 400

`PATCH /jobs/{job_id}/translations/{item_id}` 新译文内容没通过检查（`validation_failed`、`item_not_translatable`）以前回 422，
是全站最后一个 422。改成 400，`error.code` 和顶层 `code` 照旧 `TRANSLATION_REVISION_REJECTED`，`details`（`reason`、`validation`）不变。
和请求体写错的 400 靠 `error.code`（`BAD_REQUEST`）区分。

为什么选 400 不留 422：11-24 起全站请求有问题都是 400（请求体写错）或 409（状态不允许），客户端按 `error.code` + `reason` 判断；
留一个 422 要客户端单独记。前端 `reviseTranslationItem` 按 `details.reason` 出提示、不看状态码，不用改；Python 修订是本地预检，不调这个接口。

`AppError::translation_revision` 按状态码选 `error.code` 的写法改成「409 是 CONFLICT，其它是 REJECTED」。
