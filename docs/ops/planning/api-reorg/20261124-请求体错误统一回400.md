# 请求体错误统一回 400

> 日期：2026-11-24
> 分支：`fix/api-error-format`
> 起因：[规矩漏网补齐](./20261124-规矩漏网补齐.md) 留下的两条，用户定了：
> 第 13 条（请求体类型、字段写错时有的接口回 422、有的回 400）统一成 400；第 12 条（错误的顶层 `code` 有时是数字、有时是字符串）
> 现有行为不改，只在文档里写清楚怎么用。

## 第 13 条：请求体写错一律 400

### 422 原来出在哪

先把后端所有会回 422 的地方都找了一遍（`UNPROCESSABLE_ENTITY`、`unprocessable_entity`、`42200`、axum 的
`Json`/`Query`/`Path`/`Form` 提取器）：

| 地方 | 什么时候 | 这次 |
| --- | --- | --- |
| `backend/api/src/routes/common/extractors.rs` 的 `safe_json_rejection`（`ApiJson` 提取器） | `JsonDataError`：字段类型不对、缺必填字段、枚举值不认识。axum 的 `Json` 默认对它回 422，这里照搬了 | **改 400** |
| 同文件的 `parse_json_body`（模型执行器内部接口 `POST /api/v1/internal/model/jobs/{job_id}/requests` 验完令牌再解析） | 同上 | **改 400** |
| `retainpdf-jobs/src/translations/revision.rs` 的 `outcome_from_payload` | 改单条译文 `PATCH /jobs/{job_id}/translations/{item_id}`：新译文**内容**没通过检查（`TRANSLATION_REVISION_REJECTED`，`validation_failed` / `item_not_translatable`） | **不动**，见下 |
| `retainpdf-data` 的 PaddleOCR 错误分类、`retainpdf-providers` 的 DeepSeek 探测 | 上游服务回的 422，不是我们回给调用方的 | 不相关 |

其余提取器本来就不回 422：`ApiQuery`、`ApiPath`、`ApiMultipart` 的拒绝都是 400；路由文件里不许直接用 axum 的原生提取器
（`check_architecture.py` 的 `check_route_input_extractors` 钉着），`Form` 没人用。`retain-jobsd`（`backend/jobs/src/main.rs`）用原生
`Path`，写错是 axum 的纯文本 400，它是内部进程间协议、没有统一信封，不在这次范围。先收成 JSON 再按类型解析的入口
（`POST /jobs`、书的 `/translate`、`/ocr`、续跑 `resume`/`rerun`，走 `AppError::invalid_json_body`）本来就是 400。

### 怎么改的

一处统一转换，不逐个接口改：

- `retainpdf-api-base` 的 `AppError` 加 `bad_request_because(reason, message)`（400 的 `Reasoned`，信封和普通 400 一样：顶层
  `code: 40000`、`error.code = "BAD_REQUEST"`，`error.details` 多一个 `reason`），以及两个构造方法：
  - `request_body_syntax_error(prefix)`：不是合法 JSON，reason `invalid_json`；
  - `request_body_data_error(prefix, serde 原文, 固定文案)`：认出「不认识的字段」那句就回字段名、reason `unknown_field`，
    其余（类型不对、缺字段、枚举值不认识）回固定文案、reason `schema_mismatch`。serde 原文只用来认那一句，不回给调用方。
- `ApiJson`、`parse_json_body`、`invalid_json_body` 三处都改成调这两个方法。`message` 一个字都没变，只有状态码（422 → 400）和
  `error.details`（`{}` → `{"reason": …}`）变了。
- `AppError::UnprocessableEntity` 变体留着（公开的构造方法，删了是破坏性改动），注释写明请求体写错不要用它；现在后端没有地方再用它，
  顶层 `42200`、`error.code = "UNPROCESSABLE_ENTITY"` 不会再出现。

### 为什么带 reason

用户要求「带 reason」。三种写错以前在 `message` 上能区分，但约定是客户端不解析 `message`；带上 `invalid_json`、`unknown_field`、
`schema_mismatch` 以后，客户端（尤其是 agent）能按 `reason` 判断是 JSON 坏了、字段名拼错还是值的类型不对。只增：以前 `details`
是 `{}` 的两种（语法错、不认识的字段）现在多一个键，状态码不变。

查询串、路径参数写错（`invalid query parameters`、`invalid path parameters`）这次没加 reason：不是这条决定的范围，需要时另加。

### 改单条译文的 422 为什么不动

`TRANSLATION_REVISION_REJECTED` 是请求体**写对了**、但新译文内容没过检查（公式定界符不配对、这一块按策略保留原文），带
`details.validation.issues` 告诉调用方怎么改。它不是「类型、字段写错」，不在第 13 条里；契约（`translation-revisions.v1`）、
前端（`frontend/packages/api/src/translation-debug.ts` 按 `details.reason` 说人话）都按它现在的样子用着。这个接口请求体写错
（缺 `source`、`source` 不认识）以前也是 422（`UNPROCESSABLE_ENTITY`），现在是 400，和内容没过检查的 422 用状态码和
`error.code` 都能分开。要不要也改成 400，等用户另定。

### 前端

`git grep` 过 `frontend/`：源码里没有按 422 / `42200` / `UNPROCESSABLE_ENTITY` 判断的地方。测试里出现的 422 都是
`TRANSLATION_REVISION_REJECTED`（`tests/shared/translation-debug-client.test.mjs`、`tests/book-detail/edit-translation.test.mjs`、
`tests/reader/reader-block-edit.test.mjs`）或自己造的假回应（`tests/shared/document-ocr-client.test.mjs` 的 OCR 复用错误，
后端实际是 404 / 409），都不受影响。**前端不用改**，交接记录里写了一节。

### 测试

- `retainpdf-api-base`：`request_body_errors_are_400_with_reason` 钉三种情况的状态码、顶层 `code`、`error.code`、`reason`，且不回显值。
- `extractors.rs`：`ApiJson` 类型写错、缺字段都是 400 + `schema_mismatch`，语法错 `invalid_json`，不认识的字段 `unknown_field`。
- rust_api：`http_contract::json_data_mismatch_is_400_and_redacts_parser_details`（以前钉的是 422）、
  `invalid_job_payload_uses_json_bad_request_envelope`、`malformed_axum_json_rejection_uses_unified_error_envelope`；
  术语表 PUT 缺字段、译文修订请求体写错、模型执行器内部接口类型写错，都从 422 改成 400。
- 接口快照（`routes.txt`、`file-responses.txt`、`submissions.txt`）不涉及，没变。

## 第 12 条：顶层 `code` 的类型

现有行为不改。文档（[响应格式](../../../api/00-约定/01-响应格式.md#顶层-code-的类型)）写明：

- 客户端做分支判断看 `error.code` 和 `error.details.reason`，不要看顶层 `code`，更不要按它是数字还是字符串分支；
- 以后新加的错误，顶层 `code` 一律用数字（「HTTP 状态 × 100」）；字符串顶层 `code` 的清单只减不加。

查清楚的、顶层 `code` 是字符串的地方都是 `backend/packages/retainpdf-api-base/src/error.rs` 里带 `code: &'static str` 的变体：

| 变体 | 接口 | 取值 |
| --- | --- | --- |
| `OcrArtifactReuse` | 复用 OCR 结果建任务（`POST /jobs`、书的 `/translate`） | `OCR_JOB_NOT_FOUND`、`OCR_JOB_NOT_SUCCEEDED`、`OCR_ARTIFACT_MISSING`、`OCR_ARTIFACT_NOT_REUSABLE`、`OCR_PAGE_COVERAGE_MISMATCH` |
| `CredentialReference` | 凭据库、建任务按 `credential_ref` 取凭据 | `CREDENTIAL_*`（9 个） |
| `LiveTranslation` | 边翻边看 `progress/layout`、`progress/pages/{page}` | `LIVE_TRANSLATION_*`（6 个） |
| `DocumentMetadata` | 书的元数据建议 | `DOCUMENT_METADATA_*`、`DOCUMENT_TITLE_*`、`DOCUMENT_REVISION_CONFLICT`、`OCR_JOB_NOT_FOUND`（`error.code` 是 `DOCUMENT_METADATA_JOB_NOT_FOUND`） |
| `TranslationRevision` | 改单条译文 | `TRANSLATION_REVISION_REJECTED`、`TRANSLATION_REVISION_CONFLICT` |
| `Account` | 账号、登录、邀请、管理员、平台设置、页数额度（多用户版，已停止维护） | `INVALID_CREDENTIALS`、`TOO_MANY_ATTEMPTS`、`INVITE_*`、`PAGE_QUOTA_EXCEEDED`、`INVALID_*` 等 |

手写的错误信封（`GET /ready` 的 503、事件流里的 500）顶层 `code` 都是数字。除元数据建议的 `OCR_JOB_NOT_FOUND` 外，字符串顶层
`code` 都和 `error.code` 相同。
