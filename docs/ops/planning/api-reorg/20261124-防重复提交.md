# 防重复提交

> 日期：2026-11-24
> 分支：`feat/job-idempotency`
> 起因：建任务、续跑、重试都不防重复提交，双击按钮或网络超时后重发会建出两个要花钱的任务（各调一次 OCR、翻译模型）。
> 用户定了两件都做：续跑查重（后端自己挡，前端不用改）和 `Idempotency-Key` 请求头（前端带上才生效）。

## 问题

- `POST /jobs`、书的 `/translate`、`/ocr` 每来一次就建一个新任务；客户端超时重发、双击都会多建。
- 续跑、重试出新任务（`actions/resume`、`retry-stage` 出新任务、`resolve-ocr-ambiguity`）也一样：源任务是失败的终态，
  两次请求都过得了「任务在跑」那一关（在跑的是派生出的新任务，不是源任务）。
- 原地重跑（续跑里的原地重渲染、`retry-stage` 原地 render / refine）**已经防住了**：落库是 CAS（`relaunch_in_place` +
  `RunFence`，`cas_save_job_as_new_run` 在 `BEGIN IMMEDIATE` 里比状态和运行代次），两个请求读到同一个终态只有先到的写得进去，
  后到的 409 `job_active`（或 `stale_resolution`）；顺序第二次时源任务已经是 queued，`resume_plan` 直接 409 `job_active`。
  现有测试 `rerender_keeps_pdf.rs`、`retry_refine.rs` 钉着。这次不动。

## 做法一：续跑、重试的查重（`derived_job_active`）

- 新表 `job_derivations(job_id → jobs ON DELETE CASCADE, source_job_id, created_at)`（迁移 v38）：续跑、重试阶段、OCR 歧义恢复
  建的新任务各记一行「从哪个源任务派生」。
- 为什么不直接用 `request_json` 的 `source.artifact_job_id`：OCR 重试的新任务只带 `upload_id`、不带 `artifact_job_id`；
  反过来书库「只翻一部分页」、`POST /jobs` 复用别的任务 OCR 的新任务也带 `artifact_job_id`，那些不是续跑。单独一张表最准。
- `submit_job` 的 `NewJob::derived_run_of(源任务)`：
  1. 最前面先看一眼（`Db::active_derived_job`）：有在跑的就 409，不建目录、不导凭据，没有副作用；
  2. 落库时 `Db::save_derived_job_as_new_run` 在同一个 `BEGIN IMMEDIATE` 事务里再查一次、写任务行、记派生关系。两个请求同时
     过了第 1 步，也只有一个写得进去，另一个 409（页数预扣跟着退回）。OCR 歧义恢复的事务（`create_ocr_recovery_job_state`）
     里也记一行，它本身已经靠派发记录的 CAS 只建一个。
- 「在跑」= 派生任务的状态是 `queued` / `running`；结束了（成功、失败、取消）就能再续跑。
- 409 `error.details` 带 `active_job_id`：`AppError::Reasoned` 加了 `extra`（并进 `details`，和 `reason` 并列），构造用
  `AppError::conflict_because_with`。以前带 reason 的错误都不受影响（`extra` 是 `Null`）。
- 不回填升级前的派生任务：升级那一刻还在跑的几个查不到，影响很小。
- 没放进 `GET /actions` 的 `disabled_code`、`GET .../actions/resume` 的 `reason_code`：那两处是只看任务本身的纯函数，
  要查库才知道；按钮照样能点，点了 409 带编号，前端跳过去就行。以后要显示可以再加（只增不改）。

## 做法二：`Idempotency-Key` 请求头

照 IETF 草案 draft-ietf-httpapi-idempotency-key-header。

- 哪些接口：会建付费任务的 7 个——`POST /jobs`、`POST /documents/:id/translate`、`/ocr`、`POST /jobs/:id/actions/resume`、
  旧名 `rerun`、`retry-stage`、`resolve-ocr-ambiguity`（`git grep submit_job` 核对过，对外调到 `submit_job` 的就这些；
  OCR 歧义处理本身靠 `resolution_revision` 防重，但网络重试时第二次会是 409 `stale_resolution`，带 key 能拿回第一次的结果，所以也加）。
  接口登记表里行尾标 `[idempotent]`（`endpoints!` 宏的新选项），中间层按登记表判断，测试钉着这 7 个。
- 位置：中间层 `backend/api/src/app/idempotency.rs`，挂在认证、访问控制里层（`route_layer`，要知道是哪个用户）；存取在
  `retainpdf-db` 的 `idempotency_keys.rs`（新表 `idempotency_keys`，迁移 v38）。是 HTTP 协议层的事，不放进 8 个业务领域包。
- key：1–255 个可见 ASCII 字符；也收草案的结构化字段写法 `"…"`（去掉引号算同一把）。不合法、发了两次：400。
- 记录按（`owner_user_id`，方法 + 路由模板，key）认，存请求指纹（方法、实际路径含查询串、请求体 sha256）：
  - 第一次：`BEGIN IMMEDIATE` 里查没有就写「处理中」占位；处理完 2xx 存状态码、`Content-Type`、响应体，不是 2xx 删掉占位；
  - 同 key 同指纹已完成：不执行，原样回，加 `Idempotent-Replayed: true`；
  - 同 key 处理中：409 `idempotency_key_in_flight`；同 key 指纹不同：409 `idempotency_key_reused`；
  - 保留 24 小时：同一把 key 再来时先删过期的那条（当新请求），定期清理（`app/cleanup.rs`，每 6 小时）删全部过期的。
- 处理函数放在单独的 tokio 任务里跑：客户端断开（网络重试最常见的情形）时 axum 会丢掉请求的 future，放在单独任务里才能照样
  跑完、把结果记下；否则会留下一个永远「处理中」的占位，重试一直 409。
- 结果存不下来（库出错）时照样回成功的响应，占位留在「处理中」直到过期：宁可让重试 409，也不再建一次。
- 进程崩溃留下的「处理中」占位也要等 24 小时过期；前端每次点击用新 key，不受影响。

### 为什么 409 不用 422

草案建议同 key 不同请求回 422。项目正在把 422 统一成 400 / 409（「请求本身写错 400，状态不允许 409」，见
[认证与错误](../../../api/00-约定/02-认证与错误.md#400-和-409-的分工)），而「这把 key 已经被另一个请求用过」是服务端记录的状态
和这次请求冲突，归 409，用 `reason` 区分。处理中按草案就是 409。

## 两者的关系

`Idempotency-Key` 管「同一次点击的重发」（重放第一次的结果，不报错）；续跑查重管「已经有一个在跑了又点了一次」（409，带在跑任务的编号）。
续跑带同一把 key 重发，拿到的是第一次的 200 重放，不是 409（测试钉着）。

## 对前端

只增不改。续跑查重前端不改就生效（新的 409 reason）；`Idempotency-Key` 要前端每次点击生成 UUID 带上，见
[后端改动交接](../../../core/frontend/backend-changes-handoff.md)。契约 `job-actions.v1` 的 `ActionBlockReason` 加 `derived_job_active`。
CORS 单机模式请求头照回显、响应头全暴露，nginx、桌面端局域网转发都不拦这个头，不用改。
