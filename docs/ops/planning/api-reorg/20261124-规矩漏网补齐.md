# 规矩漏网补齐

> 日期：2026-11-24
> 分支：`fix/api-rule-gaps`
> 起因：[任务接口的规矩和删留](./20261019-任务接口规矩和删留.md) 定的四条规矩（状态不允许 409 带 `reason`、没产出 404 + `not_ready`、
> 列表回显 `limit` 越界 400、不认识的字段 400），审计又找出几处没跟上的。这次补齐，只增不改。

## 改了什么

### 1. 409 补 `reason`

| 地方 | 以前 | 现在 |
|---|---|---|
| `PUT /documents/{document_id}/translation-version` 选了已隐藏的版本（`retainpdf-library/src/versions.rs`） | 409，`details` 是 `{}` | 409 + `version_hidden` |
| `GET /jobs/{job_id}/files/internal/{name}` 登记的产物是个目录（`retainpdf-jobs/src/files/downloads/files.rs`） | 409，`details` 是 `{}` | 409 + `artifact_is_directory`。现在开放的 `internal/` 名字都是文件，正常碰不到，是兜底 |
| `retry-stage stage=translation` 给失败的书补回 OCR 子任务产物，写回时 CAS 没过（`retainpdf-jobs/src/actions/streamed_ocr_artifacts.rs`） | 409，`details` 是 `{}` | 和原地重跑的 CAS 一样分两种：任务已经排上队 / 在跑 → `job_active`；还是终态但不是读到的那一次 → `stale_resolution`。沿用现有的两个值，前端 `ACTION_CONFLICT_MESSAGES` 已经认识 |

原因表写进 [认证与错误](../../../api/00-约定/02-认证与错误.md)（任务操作表两行补说明，新加「其它 409 原因」一节）。

审计范围外、这次没动的、`details` 仍是 `{}` 的 409（留给以后，不在本次任务里）：`job_loading` 的老任务不支持、
`progress/event_feed/files.rs` 事件源不是文件、建任务指定的 `job_id` 已存在（`submit.rs`）、模型请求接口的几处
（`model_requests_api.rs`）、标签重名（`library/src/tags.rs`）。

### 2. 解析请求体的报错不再回显值

`POST /jobs`（`routes/jobs/lifecycle.rs`）、续跑 `resume`/`rerun`（`routes/jobs/actions.rs`）先收 `Value` / 原始字节再按类型解析，
以前报错是 `invalid job payload: {serde 原文}`，serde 原文会带出提交的值（`invalid type: string "…"`、`unknown variant `…``）。
书的 `/translate`、`/ocr`（`retainpdf-library/src/views.rs`）是同一段代码的另一份，一起改了。

现在统一走 `AppError::invalid_json_body(前缀, &serde 错误)`（`retainpdf-api-base`），和 `ApiJson` 提取器同一套说法：

- 不认识的字段：``<前缀>: unknown field `x`, expected ... in the request body``（只有名字）；
- 类型不对、枚举值不认识、缺字段：`<前缀>: request body does not match the expected schema`；
- 不是 JSON：`<前缀>: invalid JSON request body`。

提取器里找「unknown field」那一句的函数挪到 `retainpdf-api-base` 的 `unknown_field_detail`，两边共用。
**状态码没动**：这几处照旧 400，提取器同类情况是 422，统一状态码是还没定的第 13 条，不在这次做。

### 3. 查询串不认识的参数 400

加 `deny_unknown_fields`：

| 查询类型 | 用在哪 | 认的参数 |
|---|---|---|
| `JobFilesQuery` | `/jobs/{job_id}/files/` 下的 `output/…`、`pages/…`、`internal/…`，`/documents/{document_id}/files/{name}`、`/documents/{document_id}/files/pages/{page}` | `download`、`dpi`、`width`、`watermark`，新登记 `version` |
| `DeleteJobQuery` | `DELETE /jobs/{job_id}` | `force` |
| `LiveTranslationEventsQuery` | `GET /jobs/{job_id}/progress/stream` | `after_seq` |

`ListJobsQuery`（`GET /jobs`）照旧不收紧（文档写着暂缓）。

**收紧前核对的调用方**（2026-11-24，读 `frontend/web/src`、`frontend/packages/*/src`、`frontend/desktop`、Python worker、CLI）：

- 文件出口：
  - `frontend/packages/domain/src/job/file-paths.ts`：`jobOutputFilePath` 带 `?download=1`；`documentSourcePdfPath` 带
    **`?version=<原文版本>`**（阅读器 `session-helpers.ts`、`host/data.ts` 在用），后端以前不认、悄悄忽略，只起浏览器缓存分版本的作用
    （`retainpdf-library/src/media.rs` 的注释也这么写）。直接收紧会把阅读器读原文打成 400，所以把 `version` 登记成认识的参数
    （后端照旧不看它）。
  - `frontend/web/src/features/book-detail/domain/word-export-settings.ts` 带 `dpi`，`artifact-resources.ts` 带 `download=1`。
  - `frontend/packages/domain/src/job/actions.ts` 的 `resolveJobMarkdownBundleAction`（状态卡片 `status-card-result-actions-view-model.ts`
    在调）会给 Markdown 打包地址加 `?include_job_dir=true`，但它找地址的那些字段（`markdown_bundle_zip` 的清单项、
    `actions.download_markdown_bundle`、`artifacts.markdown_bundle_zip`……）现在的后端一个都不返回，地址总是空串，空串不加参数，
    请求发不出去；带任务号目录的变体随旧地址 `/artifacts/{key}` 2026-10-18 就删了。不登记，交接里提醒前端这段是死路。
  - 后端自己拼的地址只带 `download=1`（`retainpdf-files/src/links.rs`、`retainpdf-library/src/documents.rs`）。
  - 桌面壳局域网共享的 `?k=` 在代理层就摘掉了（`frontend/desktop/src/main/lan-share.js`），到不了后端。
  - Python worker、CLI 不调文件出口。
- 删任务：只有生成的客户端 `deleteJob`（`frontend/packages/api/src/generated/library-books.ts`），查询类型 `LibraryDeleteQuery` 只有 `force`。
  契约的 `LibraryDeleteQuery` 补 `additionalProperties: false`。
- 边翻边看的流：只有 `frontend/packages/api/src/live-translation.ts`，只带 `after_seq`（续读另用 `Last-Event-ID` 请求头）。

### 4. 边翻边看的流出错先说一声再关

`progress/stream`（`routes/jobs/progress.rs`）流开着时后端查询出错，以前只打日志、直接断开。现在先发一条

```text
event: error
data: <错误信封 JSON>
```

再关。data 就是这个错误当普通接口返回时的信封（`code`、`message`、`error.code`、`error.http_status`、`error.details`，有 reason 就带）；
500 照旧只给 `error_id`，原因只进日志。没有 `id` 行，不动客户端续读的位置。

前端 `streamLiveTranslationEvents`（`frontend/packages/api/src/live-translation.ts`）的 `normalizeCommitEvent` 只认
`translation_units_committed`，别的事件名返回 `null` 跳过；流随后结束，`use-live-translation.ts` 的循环照旧重连。所以前端不改也不会出错；
想把原因显示出来可以接（见交接）。

### 5. 编辑部事件的 `limit`

`GET /jobs/{job_id}/progress/editorial` 以前把 `limit` 静默夹到 1..=2000、不回显。现在：越界（0 或大于 2000）400
`limit must be 1..=2000`（用共用的 `checked_limit`），先查请求再读任务；返回多一个 `limit`（实际生效的值，默认 500）。
翻页照旧 `after` / `next_after`，不改（前端在用）。

核对：前端只有 `useEditorialLive.ts` 调，经 `fetchEditorialEvents` 只带 `after`，从不带 `limit`，不受影响。
契约 `job-events.v2`：`EditorialEventListView` 加必填的 `limit`，`EditorialEventsQuery.limit` 范围改成 1..=2000。前端自己的
`EditorialEventPage` 类型只读三个旧字段，多一个字段不影响。
