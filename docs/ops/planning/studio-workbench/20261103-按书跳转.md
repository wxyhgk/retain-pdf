# 按书跳转（studio-bridge.v1 的 navigate 加 document_id）

2026-11-03。Studio 会话检查嵌入时提的：合并任务的编号（`merged-<书>-<指纹>`）在多翻几页后就变了，Studio 笔记里存的
`retainpdf:` 链接、「读原书」、上次读到哪页都是按任务记的，会指向旧任务。用户定：加。

## 定了什么

- `navigate` 加可选的 `document_id`。只在 RetainPDF 的 `ready.features` 有 `navigate-document` 时发。`navigate-document`
  不是一种新消息，是 navigate 的一种用法，所以放在 features 里，不在 `messages` 表里。
- **`job_id` 照旧必填**。它是按书找不到时的后备（书删了、还没有可读的译文、请求失败），也让没有这项能力的 RetainPDF
  照旧能用。契约「只加不改」：旧字段不动。
- 有 `document_id` 时，RetainPDF 调 `GET /api/v1/documents/:document_id/reading` 拿到这本书现在该打开的任务，打开它。
- **页号**：按书打开的任务只有两种，从第 1 页起覆盖整本的任务，或者合并任务，都按整本书编页。所以这时 `page_idx`
  就是整本书的页序号（0 起），不用换算。Studio 手里的整本书页号有两个来源：全文检索命中的 `document_page` 减 1
  （同一天加的），或者在按书打开的任务上收到的 `reading`、`quote` 的 `page_idx`。
- `block_id` 在打开的任务里找，找不到就只翻到那一页（和 navigate 平常一样，不回消息）。

## 没做的

- 嵌入方只认 http 回环来源，从 iPad 网关（https）打开时不握手。用户定先不做。
- Studio 在一个单独打开的范围任务（不是按书打开的那个）上收到的 `page_idx` 是那个任务自己的页号，不能直接当整本书的页号
  用。要的话以后给 `reading`、`quote` 加整本书的页号。

## 谁做什么

- 契约：后端会话（这次改的 `contracts/studio-bridge.v1.schema.json`、`contracts/tests/studio-bridge-contract.test.mjs`）。
- RetainPDF 阅读页认 `document_id`、`ready` 里报 `navigate-document`：前端会话（`frontend/web/src/platform/studio-bridge/`）。
- Studio 看到 `navigate-document` 改用 `document_id`：Studio 那边。
