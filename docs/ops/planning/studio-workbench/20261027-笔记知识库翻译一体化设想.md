# 笔记、知识库、翻译一体化设想（2026-10-27）

状态：**只是讨论，没开工**。用户原话"我们现在只是讨论一些，具体的以后再搞"。这里记下想法和讨论时的判断，动手前再逐条确认。

## 想法

用户想做一个研究工作台，把这几样放在一起：

- **动态笔记**：像 Notion 一样写，内容是纯 Markdown。
- **知识库**：笔记和书库里的书放在一起，可以一起搜、互相引用。
- **PDF 翻译**：沿用 RetainPDF 的保版式翻译。
- **AI agent**：能读笔记和书，能动手做事。
- **书自动转成笔记**：一本书按章节变成一棵笔记树。
- **AI 跑模型计算并画出结果**：计算化学（xtb、Gaussian、ORCA……），结果、结构、谱图直接放在笔记里，可以交互。

做法：把 RetainPDF 全部迁进「计算化学手记」仓库（`notion2gitub_blog`）的 Studio，在 Studio 里单独开一个 RetainPDF 页面，
放 RetainPDF 自己的组件和包。这样可以直接用 Studio 已有的功能（编辑器、AI 面板、终端、资料库……），前端少做很多东西，
笔记里也能引用 PDF。

用户的判断：做成了会特别好用。读、译、记、问、算现在要好几个软件拼（文献管理、翻译、笔记、终端、可视化），能一条线走到底、
又懂公式和化学的工具基本没有；而且用户自己就是天天用它的人。

## 两个项目现在有什么（2026-10-27）

| | Studio（计算化学手记） | RetainPDF（本仓库） |
|---|---|---|
| 做什么 | 本机的 Notion 式写作工具，加一个发布出去的博客 | PDF 保版式翻译、书库、阅读器 |
| 数据 | `blog/` 下一篇一个文件夹的纯 Markdown，文件就是数据 | SQLite 加数据目录 |
| 技术 | Node、Astro、React、Milkdown（fork）；Mac 应用是 Tauri | Rust（axum）、Python 管线；桌面是 Electron，三个平台都打包 |
| 规模（不含第三方代码） | 约 7.3 万行 | 约 62 万行：`frontend/web` 16 万、`backend/pipeline` 14 万、`backend/packages` 9.9 万、`backend/translation` 4.5 万、`backend/api` 4.3 万、`frontend/packages` 3.6 万、`backend/ai` 2.6 万…… |

| 要的东西 | 已经有的 | 还缺的 |
|---|---|---|
| 动态笔记 | Studio：编辑器、页面树、公式编号和引用、版本历史、插件框架 | 基本齐了（Studio 自己的待办见它的 `docs/notion-gaps.md`） |
| 知识库 | RetainPDF 书库：文档、合集、阅读进度、搜索；Studio：反向链接、资料库 | 笔记和书没打通：不能一起搜，没有"这条出自哪本书第几页" |
| PDF 翻译 | RetainPDF：保版式、公式不丢、OCR、术语表 | 齐了 |
| AI agent | Studio：AI 面板通过 ACP 接 Claude / Codex / pi，有 MCP 服务和 `studio` 命令，AI 能建页、改页、搜资料库 | AI 看不到 RetainPDF 书库；RetainPDF 自己的 AI（`backend/ai`）暂停中 |
| 书转笔记 | RetainPDF 能把 PDF 转成 Markdown（`services/jobs/reader/markdown.rs`）；Studio 有"拆分"，做过 500 页长文不卡 | 中间那一步：按目录或标题层级拆成笔记树，图片、公式、编号、出处带过去。Studio 的差距清单里正好有"从 Word、PDF 导入成 Markdown" |
| AI 计算和可视化 | Studio：`job`、`xtb`、`crest`、`qc`、`energy` 插件，Gaussian / ORCA 输出解析，3D 分子；联动可视化有分期计划（Studio 的 `docs/plans/interactive-chemistry.md`） | AI 通过工具提交计算、读结果、插进笔记要确认或补上；路径播放、谱图联动还在计划里 |

RetainPDF 书库里已经有"批注、跨书笔记"的口子（`retainpdf-library` 的 `collection_workspace.rs`），但没有像样的编辑器。

## 讨论时的判断

### 前端迁，后端不迁

- **前端迁进 Studio**。两边都用 React、radix-ui、tailwind、lucide、xterm，组件能直接搬。`frontend/web` 里很多是外壳
  （侧栏、设置、AI 聊天、终端、列表页），Studio 都有，不用搬。要搬的是 RetainPDF 独有的：阅读器（`frontend/packages/reader`，
  原文和译文对照）、翻译任务的参数和进度、书库详情。
- **后端留作引擎**。Rust 接口加 Python 管线约 35 万行，保版式翻译全在这里，不用 Node 重写。Studio 起它当子进程，
  通过 HTTP 接口和 MCP 工具调它。

### 翻译走管线，AI 调度和校对

不让 Claude、Codex 这类 agent 一段一段翻整本书：慢、贵、不稳定、保不住版式。分工是：

- 翻译照旧走 RetainPDF 的管线：便宜模型批量翻、术语表、保版式。
- AI agent 做调度和校对：替用户开任务、选参数、盯进度；挑出译得差的段落重翻；从笔记里整理术语表；翻完把书转成笔记。

### 数据守住纯 Markdown

- 笔记（包括书转出来的）是 Studio 格式的文件夹，不进数据库。AI 直接读文件，git 能管。
- 书本身（PDF、译文、页面图）留在 RetainPDF 的数据目录，笔记里引用到具体页。
- 知识库先不上向量检索：笔记加书的全文索引，加"出处"关联，AI 用工具自己搜、自己读。不够了再加。

### AI 只留一套

用 Studio 的 AI 面板（ACP）。RetainPDF 的 `backend/ai` 和阅读器里的 AI 聊天不再恢复，迁完冻结、以后删。

## 百万行规模下要守的规矩

用户估计做成以后代码会过 100 万行。到这个规模，卡人的不是写，是验证和理解：人和 AI 每次都只能看清一小块。所以：

1. **两边只通过合约说话**：Studio 调 RetainPDF 只走 HTTP 和 MCP，格式写在 `contracts/`，不互相引用代码。
2. **垂直功能做成插件**：化学、计算、可视化进 Studio 的 `plugins/` 或 RetainPDF 的领域包，核心保持小。
3. **边加边删**：行数是成本。眼下能减的：暂停的 `backend/ai`（2.6 万行）、冻结的多用户代码（约 5.3k 行，还在编译和测试）、
   标着 `old` 的旧地址（先看 `route_usage` 的统计）。
4. **测试能只跑改到的部分**：现在 CI 一次 8 到 12 分钟，规模翻倍以后要按改动选包跑。
5. **先不合仓库**：两个仓库靠合约连，到统一桌面壳那一步再定要不要合。

## 迁移顺序（草案）

每一步做完都能单独用上；老前端在 Studio 全部接上之前一直能用。

| 步 | 做什么 | 在哪边 |
|---|---|---|
| 1 | Studio 能用上引擎：Studio 起、管 rust_api；来源校验放行 Studio 的地址；key 怎么传；给 agent 的 MCP 工具（开翻译任务、查进度、读译文、搜书库） | RetainPDF 后端 |
| 2 | Studio 里加 RetainPDF 页面，先放阅读器和书库列表 | Studio |
| 3 | 引用 PDF：笔记里的论文块（显示书的某页、点开阅读器）、阅读器"摘到笔记"、书转笔记 | 两边 |
| 4 | 迁翻译任务界面和设置，然后冻结 `frontend/web` | Studio |
| 5 | 统一桌面打包 | 两边 |

每一步先做到自己真在用，确认离不开了再做下一步。

## 还没定的问题

- **网页版和 Docker 部署还留不留？** Studio 只接受本机访问；要留就得让 Studio 能脱离开发服务器部署。这也决定后端的来源校验和
  key 怎么设计。
- **打包**：Studio 现在只在 `npm run dev` 里有，Mac 应用是 Tauri、只有 Mac。迁过去要变成能发的应用，带上 Rust 服务、
  Python 运行时、OCR 依赖。RetainPDF 的 Electron 已经在三个平台做通，经验要搬过去。桌面壳选哪个：讨论时倾向 Electron，没定。
- **Studio 插件不能注册单独的页面**：现在能加面板、命令、块，要在 Studio 核心加一个页面注册的接口。
- **书转出来的笔记放哪**：直接写进 Studio 的 `blog/`，还是先导出到单独的文件夹让用户挑。
- **博客发布**（Astro、GitHub Pages）不进主线，保留但不牵着核心走。
- Studio 仓库有它自己的规矩：可以提交，不推送；不写本机路径、用户名、主机名。
