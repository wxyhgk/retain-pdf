# Studio 不用填 RetainPDF 的接口地址和密钥

2026-11-02。接着 [以笔记为根](./20261102-以笔记为根.md)。

## 为什么

书的 ＋（从书库挑书）、AI 读书，都要 Studio 的服务器去问 RetainPDF 的接口，原来要在设置 › RetainPDF 里填接口地址和 API 密钥。
用户：「建议都整合在一起，而不需要自己填入」。

## 怎么做

Studio 的服务器从 RetainPDF 自己的页面找，和「翻译」里的阅读页拿到的是同一份（`server/retainpdf-settings.mjs`）：

- 依次读 `runtime-config.js`、`runtime-config.local.js`、页面本身，后说的算，取 `apiBase`、`xApiKey`。
  - 开发栈的 `serve_static.py` 把后端的密钥写进 `runtime-config.local.js`。
  - 桌面版把配置写在页面末尾。
  - Docker 版密钥由 nginx 转发时加上，页面里没有。
- 配置只读不执行。`apiBase` 不是写死的字符串时（开发栈写的是按页面主机现算的代码），照 RetainPDF 前端 `apiBase()` 的做法：
  http 的页面用同一台机器的 41000 端口，https 用页面自己的地址。
- 找到的记 30 秒；接口说密钥不对或者连不上时立刻再找一次、再问一次，先开 Studio、后开 RetainPDF 也行。
- 设置里填了的优先。设置页写出找到的接口地址、有没有找到密钥。
- 密钥只在 Studio 的服务器里用，不发给页面，也不写进文件。

只改 Studio，RetainPDF 和后端都不动。

## 验过的

隔离的 Studio 什么都不填，对着开发栈：接口地址找到 `http://127.0.0.1:41000/`、找到密钥，书库列出 28 本书。
单元测试：三种写法（对象里、事后赋值、桌面版的 JSON）、后说的算、没写死时用 41000、填了的优先、过一会儿重找；
密钥不对时重找一次再问。浏览器测试：假的 RetainPDF 在页面配置里给出密钥，只设了页面地址，＋ 就能从书库挑书。
