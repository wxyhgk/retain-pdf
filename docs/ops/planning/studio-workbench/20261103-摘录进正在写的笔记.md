# 摘录进正在写的笔记

2026-11-03。

## 用户说的

> 此外前端部分还是不是以笔记为主要啊，还有就是我们现在默认是在某个笔记页面里面记录笔记的，很明显不符合我们的使用的实际情况，实际情况是，一个笔记里面可能还有多个 pdf 的文字

（用户在 Studio 会话里说的，转给前端会话。）

## 以前怎么走

[以笔记为根](./20261102-以笔记为根.md) 那次只改了「笔记旁边开书」这条路：书在笔记旁边以标签打开，摘录进这篇笔记。

从「书库」整页读书的那条路没改，还是默认的：阅读页上点「笔记」或「摘到笔记」，Studio 在「读书笔记」下面给这本书找或建一页（页面属性 `retainpdf: {document, job}`），打开在旁边，摘录放进那一页。一本书一页笔记，正是用户说的「默认在某个笔记页面里记」。

## 现在怎么走

- **笔记 = 正在写的那篇**：Studio 里打开着的页面（书库后面一直开着一篇）。阅读页的「笔记」把它打开在书旁边；「摘到笔记」放进它（在里面放过光标就放在光标处，不然放在最后）。一篇页面都没开着时新建一篇。
- **一篇笔记摘几本书**：摘录带着书的链接。回到这篇笔记、点「书」，摘过的每本书都是旁边的一个标签。
- **中途换了一篇**：在书库外打开另一篇页面再回书库，旁边就是那一篇，摘录进那一篇。
- **不再建「读书笔记/书名」**：以前建的那些页照旧是普通页面，属性和按书找回的接口（`POST /api/studio/retainpdf/notes`）都留着，界面不再调它。
- **离开阅读页（回到 RetainPDF 的书库）时**：不再把「笔记对应的那本书」告诉 AI，因为笔记不属于某一本书。

## 没改的

- 书库里点一本书还是整页读。Studio 会话提过「点书 = 在当前笔记旁边打开」，这改的是挑书的方式，要先问用户。

## 验过的

- `tests/e2e/translate-view.spec.ts` 改了四条：
  - 摘录进打开着的页面，不建页；回到笔记，书出现在旁边的标签里。
  - 「笔记」打开的是正在写的那篇；中途换一篇，旁边就是那篇，摘录也进那篇。
  - 告诉 AI 的笔记是这一篇。
  - 离开阅读页后不再提这本书。
- 这个文件的 12 条都过；Studio 单测都过。整套浏览器测试见合并说明。

## 打开书时右栏先不收

用户在 Studio 会话里答了[界面整理](./20261102-界面整理.md)留下的问题：「先不收」。笔记旁边开书时右栏（AI）照旧在，不再自动收起。书库整页读、笔记在旁边时照旧收起，那是更早就有的，用户没提。Studio 会话提过「地方不够时自动收左边页面树」，用户没表态，没做。
