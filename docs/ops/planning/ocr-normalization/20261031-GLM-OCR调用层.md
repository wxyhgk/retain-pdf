# GLM-OCR 调用层

2026-10-31，接入 GLM-OCR 的第 2 步（第 1 步见 [GLM-OCR 适配器](./20261031-GLM-OCR适配器.md)）。用户："继续推进"。

## 决定

- **在 provider worker 里跑**：和命令型 OCR、Paddle 官方 CLI 一样，调接口、裁图、归一化都在 Python 进程里，Rust 只拉起进程、注入凭据。
  不学 Paddle HTTP 那样在 Rust 里轮询：GLM-OCR 是同步接口，没有任务号可轮询，第 3 步的 Rust 改动也最小。
- **分片 10 页、串行**（都可调，服务端上限 100 页）：见下面的实测，片小不多花钱、进度和断点更细；并发不变快。
- **断点按原文 sha256 + 分片页数**：两者对得上的片重跑时不再请求（不再花钱）；换了分片大小就全部重来，不拼两种切法的结果。
- **每片报进度**：任务"多久没有进展"的超时（同日的阶段超时改动）按它算，一本大书只要一直出片就不会被杀。
- **选页**：先切出子 PDF 当原文，和 Rust 那边 Paddle 的做法一致，下游页号对得上。
- **图片**：GLM 不回传图片，按块的框从原文 200 dpi 裁，放到 `md/images/page-<N>/imgs/…`（和 Paddle 一处，阅读页、AI 工具照原样找得到）。
  图片表的键带页前缀：不同页同样的框不会串（写的时候查出来的问题）。
- **只支持上传的本地文件**：网页上传都是本地文件；`source.file_url` 第 3 步在能力声明里标不支持。
- 用 `import fitz`：写成 `import pymupdf` 依赖报告会把同一个包记两遍。

## 验证

- 假接口单测 8 个：分片和拼接、断点（删掉一片只重请求那一片、换片大小全部重来）、选页、裁图并挂到块上（三页同样的框各放各的）、
  `full.md` 占位换成本地图（第二片的页号要加偏移）、页数不对时报错而不是错位、4xx 报服务端原因且不带 key。
- 用外部 CLI 缓存的真实结果（34 页论文）当假接口跑完整驱动：4 片、重跑 0 次请求、16 张图全部裁出并挂上（看过 Fig.1 的裁图）、
  `full.md` 没有剩下占位。真实结果不进仓库。
- 真实付费调用（用户选的方案：34 页论文测分片和并发，约 0.06 元）：
  - 10 页一片、串行：48.7 秒，4 片每片约 12 秒，193 块、16 张图全部裁出挂上，109802 tokens（外部 CLI 一次交 34 页是 109799）。
  - 10 页一片、2 路并发：50.6 秒，没变快，没遇到 429。
  - 据此默认 10 页一片、串行。
