# GLM-OCR 适配器

2026-10-31。用户："下一步我们可以接入 glm_ocr api 了，接入这个还有一个好处就是可以只用一个 api key，因为 glm5.3-flash 也可以一起用。"

## 接入分四步（每步一个分支）

1. **适配器**（本分支）：GLM-OCR 原始结果 → `document.v1`，离线。
2. **调用层**：按页分片提交 `POST /paas/v4/layout_parsing`（一次 ≤100 页、≤50MB，base64 要带 `data:application/pdf;base64,` 前缀），
   每片报进度、写检查点，429/5xx 退避、4xx 直接失败，从原文 PDF 按框裁图填 `_images`。分片大小、能不能 2 路并发要实测
   （外部 CLI 的经验：3 路并发 × 100 页必吃 429）。
3. **Rust 接入**：`OcrProviderKind` 加 `glm_ocr`、能力声明、凭据、探测；OCR 没给凭据而翻译也接智谱时复用翻译的 key。
4. **前端**：设置页选项，交接说明给前端会话。

## 适配器的决定

- 看了外部 CLI 存下的两份真实结果（34 页论文、533 页教材的前 100 页）：`layout_details` 逐页逐块给框（模型像素，`data_info.pages`
  给宽高）、`label`、`native_label`、`content`。`native_label` 就是 PaddleOCR-VL 的官方标签，块内容写法也和 Paddle 一样。
- 所以不另写块解析：每页改成 Paddle `parsing_res_list` 的样子，走 Paddle 的页、块解析（分类、图注挂图、栏信号、补行都复用），
  再把每块的来源改回 GLM（`provider=glm_ocr`、`raw_path=/layout_details/<页>/<数组下标>`）。
- GLM 总是出排版好的 markdown；我们请求 Paddle 时块里是纯文字（看了真实 Paddle 任务的 document.v1）。不洗的话翻译会收到
  `## Abstract`、`<div align="center">`。洗：去 `<div>`、标题类块的 `#`、表格标签的属性；行间公式 `$$…$$` 两边一样，不动。
- 块按 GLM 的 `index` 排（阅读顺序），数组顺序不一定一致。
- 没有分组号：不出服务商接续提示，跨页接续交给翻译那边自己判断。
- 图片块没有内容：文字留空，按框挂进图片表（键 `imgs/img_in_<标签>_box_<x1>_<y1>_<x2>_<y2>.jpg`，Paddle 按文件名里的框对回块），
  值由调用层裁好图后填（`_images`）；没裁的标成图片未就绪。
- 多次请求由调用层拼成一份同样形状的结果，`_meta.chunks` 记每次的页范围。

## 验证

- 两份真实结果本地走完整归一化（适配 → 缩放到原文 PDF → 补行 → 校验）都通过：34 页 193 块、100 页 1429 块；
  页面尺寸缩放到原文（595×842、252×323 点）；洗完没有一块还带 `#`、`<div>`、表格属性；翻不翻和块类型一致（正文、标题、图表注翻，
  参考文献、公式不翻）。真实结果不进仓库。
- 快照守卫加人造样例 `glm_ocr_english_paper`；新单测钉住洗排版、来源全是 GLM、按 index 排、图片挂到本地裁的文件。
