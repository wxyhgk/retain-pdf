# OCR 归一化拆分方案（2026-10-29，待定）

状态：**方案，没开工**。用户 2026-10-29："得重点看看归一化部分的耦合情况，得拆分很细才行，这点对我们后续很重要，如果数据错误就会非常麻烦。"
归一化（OCR 原始输出 → `document.v1.json`）是翻译、渲染、阅读器、书库、AI 的唯一数据源头，这里错了下游全错、而且很难查。

## 一、现状（2026-10-29 量的）

`backend/pipeline/retainpdf_pipeline/ocr/`：95 个模块、15288 行。按语法树统计模块间的导入（脚本只读，不进 `devtools/`）：

**1. 子包之间 16 个环，全部经过 `document_schema`。** 它本该是最底层的"数据结构"，却往上导入了：

| `document_schema` 里的模块 | 往上导入了 | 为什么 |
|---|---|---|
| `normalize_pipeline.py` | `ocr_provider.paddle_normalize`、`mineru_provider.artifacts` | 归一化的流程编排（读文件、缩放、写盘、素材）放在了数据结构包里 |
| `adapters.py` | 四个适配器 | 分派表 |

而 `ocr_provider`（调 OCR 服务的那层）、`mineru_provider`、各家适配器又都导入 `document_schema` → 环。2026-10-29 修 bug 时就撞上了：
把"缩放、重建行"收成一个公共函数，`job_flow` 一导入就循环。

**2. 通用逻辑放在某一家的模块里。**
- `ocr_provider/paddle_normalize.py` 装着所有服务商都要用的"缩放到原文 PDF"（`rescale_document_geometry_to_pdf`）和"重建行"
  （`post_rescale_rebuild_paddle_text_geometry`）。后者以前对所有服务商都跑，把 MinerU 的原生行压成了一行（2026-10-29 修，见
  `backend-review/20261029-OCR归一化原生行被覆盖和选页错位.md`）。
- 判断"这个块要不要翻译"分散在三层：核心默认值（`contract_v1.py`）、各家适配器的白名单（`mineru/projection.py`、`paddle/translation_policy.py`）、
  翻译包抽取时的兜底（`json_extractor.py` 自己一份角色清单）。

**3. 适配器之间互相引用。** 新版 MinerU 的 v2 适配器导入旧版 MinerU 适配器，还导入 MinerU 的传输层（`mineru_provider`）。

**4. 同一份文档有三份读取代码。** `ocr/document_schema/consumer_reader.py`、翻译包的 `normalized_reader.py`、渲染的
`render/semantics/document_reader.py`，都先读旧字段（`bbox`、`text`）再读新字段（`geometry`、`content`）。原因是 OCR / 翻译 / 渲染三个阶段之间
**禁止互相导入**（`architecture_tasks.csv` 的 DEC-001，有意的设计），共享的读写契约只能照抄，由 `devtools/architecture_checks/stage_contract_duplicates.py`
盯住抄本里同名符号的键集合是否一致。

**5. 几个阶段原地改同一份文档。** 适配器出来以后，补默认值（`apply_document_defaults_with_report(in_place=True)`）、补契约字段、缩放、重建行都在
同一个 dict 上原地改，前一步写的东西后一步可以悄悄覆盖（原生行被覆盖就是这样发生的），出了错也分不清是哪一步改的。

**6. 测试接不住"数据错了"。** 现有测试大多是人造的小样例、断言个别字段；所谓 golden 文件是**输入**不是期望的输出；没有用真实 OCR 原始输出
端到端跑、把整份 `document.v1.json` 钉住的测试。原生行被压成一行这种问题，从适配器到最终文档全程没有测试发现。

## 二、目标结构

从下往上一层只依赖下面的层，同层之间不互相导入：

| 层 | 放什么 | 能依赖 |
|---|---|---|
| L0 文档模型 | `document.v1` 的词表、版本、JSON Schema、校验器、**唯一的读取器** | 什么都不依赖 |
| L1 规范语义 | 角色、分类、翻不翻（**唯一的策略模块**）、默认值、接续提示的公共写法 | L0 |
| L2 适配器（每家一个） | 原始输出 → 规范文档，纯函数：不读写文件、不碰 PDF、不调网络 | L0、L1；**互不导入**，几家共用的放进 L1 或"某家公共"子包 |
| L3 几何 | 缩放到原文 PDF、补行（按数据里有没有真实行决定，**不按服务商名字**）、目录条目 | L0 |
| L4 归一化流程 | 适配 → 几何 → 校验 → 写盘；**所有路径的唯一入口**（normalize worker、命令型 OCR、MinerU Python 直跑） | L0–L3 |
| L5 传输（每家一个） | 调 MinerU / Paddle 接口、官方命令行、本地命令；只负责拿到原始文件，然后调 L4 | L4 |

**数据安全的规矩：**
1. 每一层的入口拷一份、出口交一份新的，不原地改调用方的文档；
2. 每一层之间跑一遍不变量检查（框在页内、行在块内、编号唯一、页数对得上……），出错时报"哪一层、哪一页、哪个块"；
3. 用架构检查把分层钉死：L0 不许导入任何 `ocr` 子包、适配器之间不许互相导入、只有 L4 能写盘，违反就让 CI 红。

## 三、怎么拆（每一步都不改输出）

**最重要的前提：先建"快照守卫"，再动结构。** 拆分是纯重构，每一步的输出都必须和拆之前**逐字节一样**；有意改行为的修复单独开分支、单独说明。

| 步 | 做什么 | 怎么验 |
|---|---|---|
| 0 | 快照守卫：一组原始输出（现有的人造样例 + 真实的 MinerU、Paddle 原始输出）跑完整归一化，把整份 `document.v1.json` 存成期望文件；改了输出就红，确实要改时重新生成、看 diff | 新测试本身 |
| 1 | 几何搬出 Paddle 模块：缩放、补行、目录条目挪到 L3，补行改成按"有没有真实行"决定 | 快照不变 |
| 2 | 流程编排搬出 `document_schema`：`normalize_pipeline` 挪到 L4，三条路径都只调它；加架构规则"`document_schema` 不许导入 `ocr_provider`、`mineru_provider`"，环全部消掉 | 快照不变；架构检查 |
| 3 | 适配器互相隔离：v2 适配器不再导入旧版适配器和传输层，共用的挪进 MinerU 公共子包 | 快照不变；架构检查 |
| 4 | 阶段之间不原地改：每层入口拷一份，补一组层间不变量检查 | 快照不变；新的不变量测试 |
| 5 | 翻不翻只在一个地方定：适配器只给事实（原始标签、关系），策略模块统一决定；翻译包的兜底清单删掉 | 快照不变；翻译测试正反两遍 |
| 6 | 读取器只留一份：见下面"要你定的"第 2 条 | 渲染、翻译测试；抄本检查 |
| 7 | JSON Schema 真正用起来：测试里用它校验快照，补上缺的字段定义，核心对象收紧 `additionalProperties` | 快照全部过 Schema |

步 1–4 只动 `ocr/` 包内部；步 5 碰翻译包；步 6 跨阶段。每一步一个分支，合并前跑全套检查加管线、翻译测试。

## 四、要你定的

1. **快照守卫要真实的原始输出。** 我按约定不读 `data/` 下的任务，需要你提供 1–2 篇不涉密论文的原始输出（MinerU 的 `layout.json` 或 middle.json、
   Paddle 的原始 JSON），或者同意我用仓库里的 `tests/fixtures/pdfs/` 跑一次 OCR（要用你的 OCR 额度）。
2. **读取器只留一份，要不要推翻 DEC-001？** 两条路：
   - A. 把 L0 文档模型（词表、校验器、读取器）放进三个阶段都能依赖的底层包（比如 `backend/base` 的 `retainpdf_base`，或者新建一个
     `retainpdf_document`），三个阶段都从那里读，删掉手抄的副本。改动跨阶段，但从根上消掉"抄本漂移"。
   - B. 维持 DEC-001，只把 `ocr/` 内部拆干净，三份读取器继续由抄本检查盯着。改动小，但"读到的和写的不一样"这类风险还在。
3. **目录名要不要跟着改。** 按层改目录（比如 `ocr/model`、`ocr/geometry`、`ocr/normalize`）最清楚，但要同步改测试、文档、架构检查里写死的路径；
   也可以先不改目录、只改依赖方向。
