# 扫描件的行间公式编号：CPU 小模型截图识别

2026-11-26。分支 `feat/formula-number-ocr-crop`，接着 [行间公式编号](./20261126-行间公式编号.md)。上一步的三种来源（编号块、LaTeX 的 `\tag`、
原文文字层）在扫描件上几乎都用不上：GLM 没有编号块、`\tag` 很少，扫描件又没有文字层——本机两本扫描件 2008 个公式只配上 18 个。
用户定（2026-11-26）：没有文字层时，用 **CPU 就能跑的小模型**截图识别公式编号，**做成正式功能**。

## 怎么做（`ocr/document_schema/formula_number_ocr.py`，来源 `ocr_crop`）

**在哪一步**：缩放到 PDF 的点之后，紧跟文字层兜底（`pdf_geometry.rescale_document_geometry_to_pdf` 里：恢复乱码 → `pdf_text_layer` →
`ocr_crop` → 补分隔符）。这里能拿到原文 PDF，坐标已经是点。

**只做哪些**：

- 页上 `get_text("words")` 一个字都取不出来（和 `pdf_text_layer` 判断扫描件同一个口径），而且渲染出来不是空白页（空白页不加载引擎，
  人造测试的空白 PDF 也不受影响）；
- 只做前三种来源都没配上的公式。

**步骤**（和实验一致）：

1. 每页只渲染一次，按页宽约 2000 像素、灰度。不按固定 dpi：开本小的书按 110 dpi 渲染字太小，检测不到（实验里召回只有 45%）。
2. 公式框右边、同一行截一条窄图：上下各放宽公式高度的 15%（至少 4 像素），横向从公式右边缘 +4 像素到页宽的 97%。只做检测
   （`use_det=True, use_rec=False, use_cls=False`），取离公式最近（最左边）的字框。
3. 这个字框四边各扩 6 像素，从整页图上切出来，只做识别（`use_det=False, use_rec=True, use_cls=False`）。识别置信度 ≥ 0.5、
   整段像编号才收：带圆括号（全角也认），`(1.2)`、`(1.3a)`、`(A.1)`、`(5-37)`；`·`、`．` 当点，`–`、`—` 当连字符。
4. 右边一个字框都没有，才用同样的办法看左边（离公式最近的是最右边那个）。这和文字层兜底「左边的编号要求公式右边同一行没有字」是一个意思：
   右边有字时，左边的 `(1)` 多半是列表序号。

**宁可不配也不配错**：

- 离公式最近的字框和别的字框挨着（纵向叠过一半、横向间隔不到 1.5 倍字高）：是一行正文（`(2) where x is …`），不收（`crowded`）。
- 字框换回 PDF 的点、四边收进 0.2 倍字高（检测框按 unclip 往外扩了一圈）后，照文字层兜底的规则排除（抽成共用的
  `formula_numbers.number_position_blocked`）：被编号块框着、落在别的块里（整块就是这个编号的除外）、和公式之间隔着别的块、跨栏（`other_block`）。
  收进去那一步是真实数据逼出来的：第一版 (5.8) 的检测框蹭到上一段落块下沿 1 个点，被当成落在段落里，连带它前后三个丢了点的编号都补不回来。
- 两个公式认到同一个字框（编号在两行公式中间）：都不收（`contested`）。

**RapidOCR 的坑**：`use_det`、`use_rec`、`use_cls` 上一次调用传的值会被沿用，每次调用三个都写全；检测要设 `Det.limit_type = max`、
`Det.limit_side_len = 960`，不然窄条会被放大到短边 736 像素，一个公式 2 秒。日志级别设成 `error`（检测为空时它每次打一行 warning）。

## 补回丢了的点（`formula_numbers.repair_formula_number_separators`）

扫描件上编号里的小数点常常印得很淡，认成 `(57)`、`(510)`，或者点认成空格 / 逗号的 `(5 20)`、`(5,20)`（截图识别把后两种记成标签 `5 20`）。
写成通用函数，对认出来的来源都做（`layout_block`、`latex_tag`、`ocr_crop`；`pdf_text_layer` 是原文的字，不动）：

- 按全书阅读顺序（页序、页内 `reading_order`）排出所有带编号的公式。连着的一段「丢了点」的编号（一串 2–5 位数字，或者两段数字中间一个空格），
  前后紧挨着的编号都得是「章.序」（`5.6`、`5-36`、`6.46b`）、分隔符一样。
- 每个丢了点的编号列出所有拆法（`510` → 5|10、51|0；序号不许是 0、不许以 0 开头），找让「前一个 → 这几个 → 后一个」一个接一个的拆法：
  同章序号加一（`5.6 → 5.7`，带字母的 `5.6b → 5.7`、`5.6 → 5.7a`）、同号字母往后一个（`5.6a → 5.6b`）、下一章从 1 开始（`5.54 → 6.1`）。
- **只有一种**拆法才补，分隔符用前后编号的，括号照原样；记 `repaired: true` 和 `repaired_from`（补之前读到的样子）。一段最多 12 个。
- 接不上（前后不是「章.序」、中间少了号、拆法不唯一）：
  - 截图识别读出的、中间是空格的（`(5 20)`）不是能印出来的编号，去掉；
  - 截图识别读出的一串数字（`(58)`）夹在同一章的两个「章.序」编号中间，肯定丢了点又补不回来，去掉；
  - 别的照原样留着：只有一边有「章.序」，或者全书本来就是 `(1)`、`(2)` 这样编的；编号块、`\tag` 读出的也照原样留着（只补、不去掉）。
  - 去掉的记进 `ocr_crop.rejected.unrepaired`，`numbered.ocr_crop` 减掉。

## 模型从哪来、怎么跳过

- 引擎：RapidOCR（Apache-2.0）3.10.0 + onnxruntime 1.32.0，CPU。实验里 PP-OCRv5 移动版、服务器版的识别都更差，用 rapidocr 默认那套：
  **包里自带的 PP-OCRv6 small 检测（9.9 MB）和识别（21 MB）模型**。
- **不联网**：选「用包里自带的」，不选「钉地址下载到数据目录」——自带的不联网就能用，Docker、离线机器、桌面都不用多一步下载和缓存目录。
  代码把 `Det.model_path`、`Rec.model_path` 直接指向包里的文件（不走 rapidocr 按 `model_root_dir` 校验、缺了去 modelscope 下载那条路），
  先核对钉住的 sha256（`RAPIDOCR_MODELS`），不对就不用。方向分类模型不用（`use_cls=False`，不加载）。识别模型的字表在 ONNX 元数据里，也不下载。
  真引擎的测试把 `socket.connect` 换成直接报错，钉着「不碰网络」。
- 加载：进程里第一次要用时加载一次（失败也只试一次），先各跑一次空白小图，模型加载失败在这里就知道。本机加载约 2 秒。
- **跳过**（这一步不做，归一化、翻译照常；`derived.formula_numbers.ocr_crop.skipped` 记原因，worker 日志打一行）：
  `ocr_engine_unavailable`（没装 rapidocr / onnxruntime，或者 import 失败）、`ocr_model_unavailable`（包里没有钉住的模型、sha256 对不上）、
  `ocr_engine_failed`（模型加载失败）、`disabled`（环境变量 `RETAINPDF_FORMULA_NUMBER_OCR=0` / `off` / `false` / `no`）。
  知道做不了以后只计页数、公式数，不再渲染。单个公式识别出错记 `ocr_error`，不影响别的公式。

  `retainpdf-pipeline[scan-ocr]`，`uv.lock` 重新锁（新增 numpy 2.4.6、opencv-python-headless 5.1.0.95、shapely、pyclipper、omegaconf、PyYAML、
  tqdm、colorlog、six、protobuf、flatbuffers）。开发环境、CI（`uv sync --all-extras`）、Docker（`uv export` 工作区）、独立后端源码包
  （打的就是工作区和 `uv.lock`）都自动带上。

  pipeline 的必装依赖生成，后端不改前端的文件；做成 extra，桌面清单这次不变，桌面没装时这一步自己跳过。Docker 的两份清单
  （`ops/deployment/docker/requirements-{app,test}.txt`）改成「必装 + `scan-ocr`」。桌面要做的写在
  [后端改动交接](../../../core/frontend/backend-changes-handoff.md)（哪个文件、旧写法、新写法、体积）。
- `ops/release/desktop_python_check.py` 把 `rapidocr` 登记成可选 import（没装时跳过这项功能），不然桌面包检查会因为源码里 import 了没装的库报错。
- 依赖报告（`docs/core/python/pipeline_dependencies.*`、`pipeline_runtime_requirements.in`）重新生成，多了 `rapidocr`。
- 体积（新增的包）：Linux x86_64 轮子约 138 MB、解开约 350 MB（opencv 63.7、onnxruntime 27.8、rapidocr 27.3 含 31 MB 模型、numpy 16.9）；
  macOS arm64 本机装好约 215 MB。Docker 镜像会大约 350 MB，大头是 opencv（rapidocr 预处理要它）。
- 平台：onnxruntime 1.32.0 没有 macOS x86_64 轮子；opencv 5.1 的 macOS 轮子要 macOS 15 起。后端工作区的开发机是 macOS 15 arm64、
  Docker 和 CI 是 Linux，不受影响；桌面要支持 Intel Mac、老 macOS 时另钉（见交接）。

## 记录格式

沿用 `content.formula_number`：`source` 多一个取值 `ocr_crop`，可选 `repaired: true`、`repaired_from`。schema（`$defs/formula_number`）、
`validator.py`（`source` 四个取值、`repaired` 是布尔、`repaired_from` 只在补过的上有）、`document_schema/README.md`「行间公式编号」一起改。

```json
{"text": "(5.7)", "label": "5.7", "source": "ocr_crop", "in_latex": false, "repaired": true, "repaired_from": "(57)"}
```

文档 `derived.formula_numbers`（报告同名一份）：`numbered` 多 `ocr_crop`，多 `repaired`（补了几个）；截图识别要做的时候另有
`ocr_crop: {pages, formulas, rejected: {no_text, crowded, not_a_number, other_block, contested, ocr_error, unrepaired}, skipped?}`。
耗时不写进文档（不稳定），只打在 worker 日志里。快照样例重新生成：8 份样例的文档和报告只多了 `"ocr_crop": 0` 和 `"repaired": 0`。

## 真实数据（本机 `data/jobs` 两个扫描件 GLM 任务，只读）

用本分支的代码对原始分片重跑完整归一化（适配 → 缩放 → 文字层 → 截图识别 → 补分隔符 → 补行 → 校验），原文 PDF 用任务自己的；没有改 `data/`。

| 任务 | 行间公式 | 截图识别补上 | 补小数点 | 去掉（补不上） | 没收的原因 | 截图识别耗时 |
|---|---|---|---|---|---|---|
| `20261031160024-08f6e5`（一章，21 页有公式） | 55 | 53 | 14 | 0 | 两边没字 1、不像编号 1 | 44.3 秒，0.81 秒 / 公式 |
| `20261101154521-25e53c`（481 页，351 页有没配上的公式） | 1953（`\tag` 18） | 1417 | 0 | 0 | 两边没字 446、不像编号 70、两个公式抢同一个 2 | 400.6 秒，0.21 秒 / 公式 |

- 第一本：丢了点的 14 个（`(57)`、`(59)`、`(5 10)`、`(5 19)` … `(5 54)`）全部按前后补上，53 个编号从 5.1 到 5.59 一个不重、顺序不倒
  （缺的 5.34、5.43–5.47 实验里也没认到）。
- 第二本：比实验多 84 个，主要是附录的 `(A.1)`、`(C.3)` 这种（实验的正则不认字母后面带点）；按每章编号连续推算缺 60 个，召回约 95.5%；
  一个重复的标签都没有（实验里有一个 `(6.46b)` 重复，这次被「两个公式认到同一个字框」挡掉）。少数是 `(1)`、`(1a)` 这样另起编号的一节，照原样留着。
- 耗时：跑的时候机器负载很高（10 核，load average 160–240，别的会话在编译），比实验时慢；实验在负载低时第一本 0.28 秒 / 公式、第二本 0.11 秒（全书约 3.6 分钟）。
  每页渲染约 0.1 秒、模型加载约 2 秒；检测、识别单次 0.1–0.2 秒。
- 抽查：每本随机抽 20 个截图识别的结果，把公式那一行和认出来的编号画在一起逐个看（截图只放在会话临时目录，不进仓库），**40 个全对**，
  包括第一本补了点的 `(5 9)→(5.9)`、`(5 38)→(5.38)`、`(57)→(5.7)`、`(5 49)→(5.49)`、`(5 52)→(5.52)` 和第二本的 `(A.3)`、`(1.132b)`、`(5.149a)`、多行公式末行的编号。
- 顺带看到（不是这次的改动）：第二本 GLM 的 `\tag` 有 8 个只认出了章号（`\tag{2}`、`\tag{3.}`），`latex_tag` 照收；这是上一步的规则，没动。

## 没做的、待定

- 补点只认「正好接上」：中间少了一个号（`5.6, (58), 5.9`）就补不上、截图识别的去掉。要不要放宽成「同章、在前后之间、拆法唯一」，看以后的数据。
- Docker 镜像多约 350 MB（opencv 占一半多，rapidocr 的图像预处理要它）。要压体积得换掉 rapidocr、自己接 onnxruntime 写预处理，没做。
- 桌面安装包要不要带（体积、Intel Mac、老 macOS），交给前端；不带时这一步跳过。
- 线程：onnxruntime 默认用满所有核；归一化和别的任务并行跑时可能要限线程，等实际遇到再加。
- 已经跑完的任务要重跑归一化才有这些编号。
