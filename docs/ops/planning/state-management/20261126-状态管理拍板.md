# 后端状态管理：用户拍板（2026-11-26）

[后端状态管理设计](./20261126-后端状态管理设计.md) 末尾列了 8 件要拍板的事。用户说「一次要考虑到事情太多了，我有点考虑不过来，一个个来」，
于是逐个问了。技术项也要求逐个问（「逐个问我」）。下面记录结论；有 3 件和设计里的推荐不同，最后一节写它们对路线图的影响。

| 编号 | 问题 | 用户的选择 | 和推荐比 |
|---|---|---|---|
| Q4 | 模型的决定（领域识别、目录 agent 的定译……）第一次就失败了，要不要也冻结 | **失败也冻结**：续跑一律沿用，不再问模型；用户点「重新识别」才重做 | 同推荐 A |
| Q5 | 手改译文进不进库 | **进库**（`translation_edits`，叠在模型译文上，以库为正本） | 同推荐 A |

已经定了、不再问的：结果不明的请求不自动续跑、等用户确认（11-26）；启动时不硬删书（已修）；多用户不做新功能。

## 三处不同于推荐的选择对设计的影响

### Q3：新增任务状态「待确认」

- 任务状态从 5 个变 6 个：`awaiting_confirmation`。进入条件：有结果不明的上游请求，任务停下等用户确认。出口：用户确认继续 → `queued`；用户放弃 → `canceled`（或 `failed`，确认时让用户选）。
- 这是**对外的枚举新增值**，按「对前端只增不改」的约定要先做好兼容：
  - 契约（`contracts/` 和 `backend/contracts/` 里任务状态的枚举）加值，前端生成客户端重新生成；前端所有按状态分支的地方（列表筛选、进度、桌面通知、统计）要认它。旧前端不认识时按「失败」显示，所以后端在过渡期同时给 `status_compat: "failed"` 一类的兜底字段，前端接完再去掉。
  - 数据库 `jobs.status` 的 CHECK（如有）、统计查询、启动对账、巡检、重试入口都要认它：`awaiting_confirmation` 不算「在跑」，巡检不碰；重试接口在这个状态下就是「确认继续」。
  - 显式状态转换表（第 1 步）里写进这个状态的进出边。
- 放进路线图第 1 步（任务运行收尾一致、集中对账）一起做：转换表、对账规则 `decide(facts)` 本来就要处理「结果不明」。前端改动写进交接。

### Q2：块状态记在数据库里

设计原来推荐放页文件，理由是「放在别处又多一份真相」。用户选了数据库，那就要让数据库成为块状态的**唯一正本**，页文件只放内容（原文、译文、排版字段），不再从页文件字段推断「翻完没有」：

- 新表（草案）`translation_block_states`：`job_id`、`run_generation`、`item_id`、`state`（pending / translated / kept / dead_letter）、`kept_owner`（document / policy / engine / model / user）、`basis_source_sha`、`basis_unit`（成员和序号）、`page_hash`、`failure`、`updated_at`；主键 `(job_id, item_id)`。
- **写入路径**：Python worker 不直接连库（Rust 是库的唯一写者）。现有的 `pipeline_checkpoint_v1` stdout 事件和 `commit_pipeline_units` 已经按页、带 `page_hash` 和 `producer_generation` 提交；在这条提交里带上这一页每块的状态，Rust 在**同一个事务**里写 `pipeline_units` 和 `translation_block_states`。这样「译文写盘」和「状态入库」靠 `page_hash` 绑在一起：库里的状态只对那一版页文件成立。
- **断点和续跑**：断点不再存待办名单当真相；续跑时从库里读块状态（Rust 在起 worker 时交给它一份，或 worker 经内部只读接口取），调和入口按 `page_hash` 和原文 sha 核对页文件与库是否一致，不一致的页按页文件内容重算状态并写回库（调和，不判整本失败）。
- **跨任务续跑**：拷断点时连同这本书的块状态一起拷到新任务（库里复制行），不再靠拷文件推断。
- **代价**：多一条「状态在库、内容在文件」的接缝，靠 `page_hash` 守住；Python 单测里要有一个假的「状态存储」接口。旧任务没有库里的状态时，按固定推断表从页文件旧字段推出一次，写进库，标 `inferred`。
- 路线图第 2 步（翻译块状态）里的「2b 统一读口」「2c 写口收敛」「2d 断点 v2」按这个落地；「块 state 放页文件」的草案作废。

### Q8：请求账直接写数据库

- 所有上游请求（翻译、OCR、问答、领域识别、复核……）都要经过 Rust 的模型执行器，由执行器在发请求前后写库：`upstream_requests` 表，状态 `intent → sent → succeeded | failed_not_sent | failed_sent | ambiguous`，和用量、花费在同一行。
- **前提**：模型执行器全面上线。现在执行器默认关着，大部分请求是 Python 直接发的（`docs/ops/planning/model-executor-rollout.md`）。所以第 6 步（请求账）改成**排在执行器推开之后**；执行器没覆盖到的路径（OCR 的 Python 驱动、问答的自带 agent、领域识别）要一并迁到执行器，或给它们一个经 Rust 写账的内部接口。
- 过渡期：第 0 步 Z1 的小修（「连接没建成」记 `failed_not_sent`、退出时排空在途请求）照做，记在现有的请求日志里；等请求账上线后由它取代请求日志和用量台账两份。
