## 2. 崩溃矩阵

以 Book 任务为例：OCR → 翻译 → 渲染，翻译走默认的 legacy 直连。「死」分三种：
- **K**：后端整个被杀，或者断电；
- **Q**：桌面正常退出。进程内模式下会终止 worker；打包的桌面版是 jobsd + 监督，**不终止 worker**（J-E1）；
- **W**：只有 worker 死。

| # | 时刻 | 死后各处状态 | 重启后会发生什么 | 对不对 |
|---|---|---|---|---|
| 1 | 提交后，driver 没起来 | 库：`queued`，没有 attempt。文件：上传件 | `requeue_stuck_queued_jobs` 重新发射（`startup_recovery.rs:478-523`） | 对（整行覆盖的问题上一份已提） |
| 2 | driver 已 CAS 成 running，worker 还没 spawn，或 spawn 了但 pid 还没落库（`process_runner/startup.rs:44-79`） | 库：`running`，没有 pid，没有 attempt。可能有一个**没登记的 worker 在跑** | NoPid 加上没有 attempt，任务判失败 `worker_process_missing`；那个没登记的 worker 不会被杀，要等它写 stdout 报 EPIPE 才死 | 基本对。窗口很小 |
| 3 | **串行 OCR 中**，Rust 原生 MinerU/Paddle 已提交、拿到回执、正在轮询 | 父任务：`running`，没有 pid，**没有 attempt**（父任务的 attempt 只在翻译、渲染 worker 的 `read_stdout` 里建，`io_support.rs:164`）。子任务：`running`，有 attempt，`dispatches` 里有回执 | 父任务判失败（不可续）；子任务先被改回 `queued`，随后 `settle_orphaned_ocr_children` 收尾成失败（`:411-467`）。回执只在同一个 attempt 里被认，**不会被重试复用**。重试会重新提交、重新付 OCR 费 | **不对**，见 N3 |
| 3' | 同上，但 OCR 走 Python worker（GLM-OCR、Paddle 官方 CLI、命令型 provider、全部流式 OCR） | 没有 dispatch intent（`ocr_flow/mod.rs:127-129` 直接 `execute_process_job`） | 同上判失败。**不会被 `ocr_request_ambiguous` 挡住**，重试静默重发 | **不对**，见 N4 |
| 4 | 并行 OCR + 翻译（流式）中 | 父任务的 attempt 已建，`current_stage` 被翻译 worker 推到 translate。子任务有自己的 attempt。清单停在 `done=false` | 父任务自动续跑，走 `resume_translation_stage_from_durable_state`，它不走流式，要找完整的规范化文档，**找不到就失败**（`translation_flow_stage.rs:76-85`）。子任务在父任务终态后的下一次启动才被收尾 | 不对。上一份已推测，这次读码确认：父任务 attempt 的 stage 来自翻译 worker 的观察 |

## 4. 新发现的问题

按严重程度排。前缀 J、L、G 的条目来自子代理，我抽查过的标了 ✓。

### 一级：整本失败、白花钱、违背已定策略

**N2. 每次退出 app（或 Docker stop）时翻译有在途请求，下次启动这个任务就判失败，不会自动续跑。（读码 + 现有单测）**
- 证据：
  - Python 翻译期间不处理 SIGTERM，在途请求的 dispatch 已经 fsync（`request_journal.py:24-26`），但没有 terminal；
  - Rust 把没配对的 dispatch 当结果不明（`translation_request_journal.rs:104-114`；单测 `unmatched_dispatch_requires_confirmation…`，`:259`）；
  - 启动对账因此不续跑，落 `translation_request_ambiguous`（`startup_recovery.rs:160,203-244`）。
- 并发通常是 8 到 32 路，退出时几乎一定有在途请求。
- 和 `shutdown_workers.rs:16-17` 写的「下次启动由对账照常接手（有检查点的自动续跑）」直接矛盾。
- 打包桌面版退出时根本不停 worker（J-E1 ✓）：worker 写 stdout 报 EPIPE 后退出，或者下次启动被杀，在途请求一样没有 terminal，结果相同。
- L-D2 ✓ 会放大它：断网时「连接被拒」也记成 ambiguous（`client.py:94-99`）。

**N3. 串行 OCR 期间重启，已付费的 OCR 结果被丢弃，重试重新付费。（读码）**
- 原因：父任务在 OCR 阶段没有 attempt（attempt 只在 `io_support.rs:164` 建），重启时直接判失败（`startup_recovery.rs:155-157`）。
- 子任务收尾时只把**没有回执**的 intent 标成 ambiguous（`:449-460`、`db/pipeline/dispatches.rs:241`）。已经拿到回执（服务商任务 id）的那次提交，不会被任何路径复用：
  - `rerun` 和 `stage_retry` 开的是新任务或新 attempt；
  - 只有 `ocr_ambiguity.rs` 能手动绑定回执，而且只针对 ambiguous 的 dispatch。
- 触发场景：几百页的 MinerU/Paddle OCR 要跑好几分钟，用户这时退出桌面版，或服务器重启。
- 说明：「没有复用路径」是我在 `retainpdf-jobs/src/actions` 里没找到，不是证明了不存在。

**N4. 走 Python worker 的 OCR（GLM-OCR、Paddle 流式和官方 CLI、命令型 provider）完全不过 dispatch 闸门。（读码）**
- `ocr_flow/mod.rs:82,127-129`：`run_provider_worker` 为真时直接 `execute_process_job`，不调 `begin_ocr_dispatch`。
- 崩溃后：
  - `mark_open_dispatch_intents_ambiguous` 没东西可标；
  - `rerun` 的 `ambiguous_ocr_dispatch` 闸门（`rerun.rs`）拦不住；
  - 重试静默重发，GLM-OCR 按页计费。
- 和 N3 合起来看：「OCR 不重付」只对 Rust 原生的 MinerU/Paddle 首次提交成立。

**J-E1 ✓. 打包桌面版（mac、Linux）和开发栈退出时不停 worker，继续花模型的钱。（读码）**
- 位置：`app/jobs.rs:37`（远端模式直接 return）、`jobs/src/main.rs:290-300`（jobsd 没有 SIGTERM 处理，壳一死就 `exit(0)`）、桌面 `backend.js:295`（打包默认 remote）。
- 违背 2026-10-24 定的「退出时停掉」。

**L-D1 ✓. 执行器任务的用量恒为 0。（复现）**
- 回执里的 token 存进了 `model_operations.result_json`，但台账只读 jsonl。执行器默认关着。

### 二级：整个任务失败，但触发需要条件

**N1. `pipeline_events.jsonl` 末尾留半行后，同一 attempt 的第二次续跑必然判 seq 倒退，任务失败。（复现）**
- 机理：
  - Python 的 seq 来自「文件里的非空行数」（`base/events.py:184`）；
  - 追加时不检查末尾有没有换行（`:290`）；
  - 半行和下一条记录粘成一行，于是行数比已用的 seq 少 1，而且以后一直少 1；
  - Rust 要求同一（任务, attempt, 阶段）内 `seq` 严格递增，否则 bail（`db/pipeline/stages.rs:88`）；
  - bail 让读取任务出错，worker 被杀，任务失败（`io_support.rs:222-226`、`execution.rs:202-207`）。
- 复现：临时复现脚本 `seq_partial_line.py`（没进仓库）。
  - A 发出 seq 1–5；
  - 模拟 A 在写第 6 行时被杀；
  - B 发出 7–9；
  - C 的第一条是 9，`9 <= 9` 判倒退；
  - 文件 9 行，其中 1 行坏。
- 触发：SIGKILL 或断电正好落在写这一行时（`terminate_*` 宽限期后的 SIGKILL、桌面强退），随后在**同一个 attempt** 里还要再续跑两次。概率低，但一旦发生，那个 attempt 就再也续不了。
- 对照：请求日志写入时会截掉半行（`request_journal.py:75,54-56`），事件文件没有。
- 附注：并行 OCR 时，OCR 子进程的 workspace 用父任务目录（`ocr_flow/mod.rs:100-105`、`workspace.rs:27-28`），两个进程用各自的计数器追加同一个事件文件。
  - 目前行数只会多不会少，不会倒退；
  - 但文件里的 seq 会重复；
  - Python 文本模式的两次 `write` 在一条记录超过缓冲区时可能交错（推测）。

**N5. stdout 投影上的任何不一致，都按「整本失败」处理。（读码）**
- 涉及：`apply_durable_stage_observation`、`apply_durable_checkpoint`、`apply_durable_artifact_commit` 的所有 bail（seq 倒退、stage 不符、generation 冲突、job_id 不符、cursor 过期、`output_pdf` 不是常规文件），都经 `?` 让读取任务出错，worker 被杀（`io_support.rs:218-235`）。
- 这些错多半说明「Rust 这边的投影和 worker 对不上」，不说明译文坏了；断点文件是权威，可以重放。
- 现在没有「丢掉这条投影、记一笔诊断、继续跑」的降级，也没有「下一次启动从文件重建投影」的路径。
- 另外，检查点的 `stage` 必须等于 cursor 的 stage（`checkpoint_commit.rs:14`），而 cursor 的初值取自 `job.stage`（`io_support.rs:156`）。这依赖 worker「先发一条带 user_stage 的阶段观察，再发检查点」这个**没写进契约**的顺序。

**L-D3 ✓（L 读码）. 执行器任务的启动对账只读 Python 请求日志。**
- 执行器任务不写这个日志，于是被当成干净的、自动续跑。会话却已经被暂停，第一笔新请求就 409，整份失败。

**L-D4（L 读码）. 执行器客户端一次本地超时（`timeout=(2,5)`，不重试）就锁存失败，整本失败。**

**J-E2（J 读码）. jobsd 探活连续失败约 15 秒，监督器就杀掉重启 jobsd，所有在跑的任务被对账杀掉。**
- 再叠加 N2，翻译中的任务全部判失败。

### 三级：漏计、错计，或者是隐患

- **L-D5 ✓.** 领域预热（`domain_prewarm.rs:96-103`）和单块重放（`replay.rs:37-62`）不传 `RETAIN_USAGE_LEDGER`，模型调用不入账。重放对执行器任务还会直连。
- **G-D1 ✓（复现）.** 问答出错、取消时，已累计的用量不带出去（`server.py:373-379`），断线、关页面也不保存。模型那边已扣费的 token 在 RetainPDF 里查不到。
- **L-D7 ✓.** 台账行没有请求身份，所以台账、请求日志、执行器回执三份记录没法互相对账。
- **L-D6（推测）.** Windows 上多个线程用 `O_APPEND` 并发追加台账会互相覆盖。
- **N6. 旁路进程不在任何台账、pid 记录或 Job Object 之外的清理里。（读码）**
  - 领域预热、渲染准备只靠 `kill_on_drop`（`domain_prewarm.rs:107`、`render_prepare.rs:100`），而且没设进程组（不调 `configure_child_process`）。
  - 后端被 SIGKILL 时它们成孤儿；对账只看任务行上的 pid，看不到它们。
  - 预热会调付费模型（一次请求），影响小。
  - 同类的还有 ACP 桥的 agent 子进程（G-D4：只杀直接子进程，没有进程组）。
- **N7. OCR 流式清单的写的一方每个进程从 `seq=0` 开始（`ocr_stream.py:70`），`ocr/stream/` 目录也没人清。（读码，现在不可达）**
  - 现在只有新任务目录会走流式，原地重跑只给渲染用（`rerun.rs`），所以碰不到。
  - 以后一旦有「原地重跑 OCR」或流式续跑，旧清单的 `failed=true` 会让翻译立刻退出，`done=true` 会让翻译读到旧文档。
  - Rust 的 `mark_ocr_stream_failed` 是读-改-写，和写的一方没有互斥，靠「子进程已死」这个前提。
- **N8. 阶段 spec 用 `fs::write` 原地覆盖（`stage_specs.rs:106,185,…`），不是原子写。（读码）**
  - 崩溃时会留下半个 spec，下次同一阶段启动前会被整份重写，所以只影响诊断和重放，影响小。
  - 它和 W5 合起来说明：**一次阶段运行的真实输入（spec + 环境变量）没有被完整、不可变地记录下来**。
- **J-E3、J-E4（推测）.** 重复的 launch 会先清掉取消标记再去重（`lifecycle.rs:64` 对 `:91-101`）；远端模式下 `fail_unlaunched_job` 查的是壳自己那张空的登记表。
- **J-E5（读码）.** 控制面没有握手，`/healthz` 不报库路径。数据目录写成相对路径时，两边可能打开两个库，任务永远停在 queued。
- **G-D2（读码）.** `retainpdf mcp` 靠全局 `backend.json` 找后端，同一 HOME 下多个后端时会串。
- **G-D7（读码）.** 问答记录 PATCH 是整份删了重插，没有版本号，乱序到达时旧的覆盖新的。
- **N9. `attach_untranslated_content_warning` 自己拼了 `data_root/jobs/<id>/artifacts/translation_diagnostics.json`（`completion_pipeline.rs:96-101`）。**
  - 绕过了 `storage_paths::resolve_translation_diagnostics`，`KNOWN_ARTIFACT_PATH_READERS` 那条规则没拦住。
  - 现在 `output_root` 固定是 `data_root/jobs`（`config/paths.rs:79`），结果一致，是隐患。

## 5. 设计建议

### 5.1 协议：要不要一份 schema、带版本、两边生成代码或做一致性测试

**要。但先做「一份 schema + 共享 golden 样例 + 两边都读样例的测试」，不急着做代码生成。**
- 理由：现在漂移的主要是**语义和字段**，不是类型。
- 例子：
  - 阶段 spec 只钉了 translate 的 params 键；
  - 请求日志的判据有两份；
  - 环境变量名有四份拷贝。
- 代码生成要给 Rust、Python、TS 三边配工具链，收益低于「每个契约一个 `contracts/<名字>.vN.schema.json` + `contracts/fixtures/<名字>/*.json`，Rust 和 Python 测试都读同一批样例」。`pipeline-stdout.v1` 已经是这种做法，照搬就行。

**按收益排的先后：**
1. **环境变量和运行时输入**（W3–W6、A3）。
   - 定一份 `worker-runtime-env.v1`，列出 Rust 注入的每个变量、谁读、是不是秘密。
   - 所有子进程（阶段 worker、预热、渲染准备、重放、AI 诊断、问答 agent）都通过**同一个启动帮助函数**拿环境，正好修 L-D5、N6。
   - 继承来的 `RETAIN_*` 行为开关（W5）在 spawn 时拍成快照，写进 spec 或 attempt 记录，不再静默继承。
2. **请求日志 + 台账**（W18、W19）。见 5.4。
3. **阶段 spec**（W1）。
   - 6 种 spec 都进 schema，覆盖全部字段；
   - spec 改成原子写，并带上 `attempt` 和 `generation`；
   - 每个 attempt 留一份不可变的副本（N8）。
4. **结构化失败**（W12、W13）。
   - 给 `StructuredFailure` 一个 schema 和版本；
   - 从 stderr 文本改成写一个文件 `logs/failure.v1.json`（原子写），stderr 那行留作兼容。
   - 这样不怕 stderr 收尾被丢。
5. **版本号写法统一成 `schema` + 整数 `schema_version`**。读的一方遇到**更新**的版本要报「请升级」，不要当作没有。现在 OCR 清单和事件观察遇到新版本都静默当作不存在。

### 5.2 对账：要不要集中成一个模块

**要**，但集中的是**规则和顺序**，不是把代码挪到一个文件里。

现在至少 7 处对账（见第 2 节末尾），互相有顺序依赖，例如「OCR 子任务收尾必须在父任务判定之后」靠代码顺序保证。建议在 runner 里加一个 `reconcile` 模块：

1. **输入**：一张「任务的可观测事实」表，每个任务一份，只读：
   - 任务行；
   - attempt、stage、units、dispatches；
   - worker 身份和存活；
   - 断点文件摘要（generation、完成页数）；
   - 请求日志摘要；
   - 执行器操作摘要；
   - OCR 子任务；
   - 渲染产物。
2. **规则**：一个纯函数 `decide(facts) -> Action`。Action 是：续跑（从哪个阶段，带什么输入）、成功、失败（哪个失败码）、需要用户确认、收尾子任务、杀进程。
   - 规则写成表，每一行都有单测；
   - 现在散在各处的规则全部搬进来；
   - 补上 N2、N3、N4、L-D3 的那几行。
3. **执行**：按 Action 逐条 CAS 落库。启动对账、运行期巡检、手动「重试」入口（`resume_plan`）都调同一个 `decide`。
   - 现在 `resume_plan`（API）和 `startup_recovery`（runner）对「能不能续」的判据不同，L-D3 就是一例。
4. **N2 需要先定一个产品规则**：结果不明的请求不超过 K 个（例如 ≤ 并发数），而且是正常退出引起的，就自动续跑，并在任务上记「可能重复计费 ≤ K 次」。超过 K 或者原因不明时，才要用户确认。
   - Python 侧收到 SIGTERM 时停止派发新请求，在宽限期内等在途请求回来、写 terminal。这样大多数退出可以做到 0 歧义。

### 5.3 事件溯源和快照怎么取舍

现在的结构是：
- 文件是权威：断点、页文件、修订、请求日志、台账；
- 库是投影：`pipeline_units`、事件流、`model_operations`；
- 两者靠 stdout 连接，靠「生产方 outbox + 消费方幂等」对齐。

这个方向是对的，W10' 的 outbox 是好例子。建议：

- **不做全量事件溯源。** 页文件和断点是体积大的快照，用事件重放重建代价太高，模型产出的东西也不确定。
- **做「带回执的快照 + 小事件日志」：**
  1. 每个权威快照（断点、页文件）带 `generation` 和内容 hash。
  2. 只有「跨进程的事实变化」写成事件，事件带生产方身份（attempt, generation）和**单调序号**。
     - 序号由**一个**写的一方用文件记住，参照请求日志的截半行写法，修 N1；
     - 或者由 Rust 在 spawn 时传入起始序号，不再数行。
  3. Rust 的投影要**能从快照重建**：
     - 投影对不上时，记诊断、标「投影需要重建」，不让任务失败（修 N5）；
     - 下一次启动、或读的时候，从文件重建。
     - 修订那条已经这样做了（`revision_publication.rs` + 读时自愈），推广到 `pipeline_units`。
- **库里该有、现在没有的状态**：取消意图（`cancel_requested_at`）、运行时身份和租约（`runtime_id` + heartbeat）、旁路进程登记。理由是它们必须在进程死后仍然可读。（同 J 的建议）
- **stdout 降级成通知通道，不再是唯一真相通道。** 进度改成可以重连：worker 把事件写进带序号的文件，stdout 只发「有新东西」。新的 runner 可以从文件续读，才谈得上「改壳不杀任务」和「重启接管还活着的 worker」。

### 5.4 计费：怎样做到不重不漏

- **一张请求账作为唯一真相**（同 L 的建议 1）：
  - 每个上游请求一行，身份是「稳定单元 id + 用途 + 次数」；
  - 状态：`intent → sent → succeeded | failed_not_sent | failed_sent | ambiguous`；
  - usage 和回执挂在同一行。
- 台账、请求日志、`model_operations`、OCR 的 `pipeline_dispatches`、问答用量都从它投影出来，或者用同一个身份互相引用。
- 现在 OCR（Rust、库）、翻译（Python、文件）、执行器（Rust、库）是三套写法：
  - 先统一**身份和状态集合**；
  - 存储可以暂时不统一。
- 「发没发出去」只用一张判定表，两种语言共用 golden 样例（修 L-D2，并统一 `transport.rs:136` 和 `client.py:94-99`）。

### 5.5 迁移分几步，先做哪一步

| 步 | 内容 | 为什么 |
|---|---|---|
| 0（马上，小改动） | ① 事件写入时截掉半行（照请求日志的 `_load_existing_state`），修 N1。② 远端 jobsd 退出时照进程内的规矩停 worker（J-E1）。③ 旁路进程补台账环境变量（L-D5）。④ `client.py` 把「新连接没建成」记成 `failed_not_sent`（L-D2） | 每条都是几行，直接止住白花钱和整本失败 |
| 1 | **对账规则集中**：`decide(facts)` 纯函数 + 规则表 + 单测；把 N2（有界歧义自动续跑 + SIGTERM 时排空在途请求）、N3（父任务在 OCR 阶段也建 attempt，或者回执跨 attempt 复用）、N4（Python OCR 也写 dispatch intent）、L-D3（执行器任务读库）作为新规则加进去 | **收益最大**：桌面用户「退出再打开」的主路径从「失败、要确认」变成「自动续跑」，OCR 不再重付 |
| 2 | **契约补齐**：`worker-runtime-env.v1` + 唯一的子进程启动帮助函数；请求日志和台账共用 schema + golden 样例；6 种 spec 全进 schema；结构化失败改文件 | 堵住现在静默漂移的通道，为第 3 步打底 |
| 3 | **投影可重建**：stdout 投影出错降级而不是整本失败（N5）；`pipeline_units` 能从断点重建；事件序号由单一来源分配 | 去掉一大类「状态对不上就整本失败」 |
| 4 | **归属入库，进度通道可重连**：`runtime_id` + 租约、`cancel_requested_at`、旁路进程登记；进度改走文件 + 通知 | 这时 jobsd 才有意义（改壳不杀任务、接管还活着的 worker）。否则建议承认现状，打包版回到进程内模式，少一种形态 |
| 5 | **请求账统一**（5.4） | 最大的一步，等前几步稳定后按领域分批做 |

第 1 步和上一份审查的「冻结模型产出的决定、调和入口」可以合并成一个方案文档：那份的调和入口管的是 Python 进程内的页状态，这里的 `decide` 管的是跨进程的任务状态，两层接口在「续跑从哪儿开始、带什么输入」处对接。
