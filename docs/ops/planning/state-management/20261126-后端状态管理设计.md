## 一页结论

**现在最大的六类问题**

1. **同一件事存了好几份，各写各的，也各读各的。**
   - 一个块「翻完没有」有 6 套判定。
   - 译文存了三层字段，渲染和阅读页取字段的优先级相反；`final_status` 的两份，Python 和 Rust 也读反了。
   - 任务「在哪个阶段」有 6 份记录。
   - 书的「当前译文」有三种口径。

   几份对不上时，轻的显示错，重的让守卫误报、整本失败。
2. **派生值被当成真相存下来，再拿来做守卫或判断新鲜。** 例如：
   - 断点里的待办名单；
   - 产物登记表写入那一刻的 `ready`；
   - 合并阅读只看文件戳；
   - Word 导出只看两个 PDF。

   后果是续跑报 regressed、整本失败，手改过的译文在合并阅读、Word 导出里还是旧的。
3. **模型做出的决定没有冻结，每次续跑都重算。** 包括领域识别、目录定译、接续复核、分组、引擎的 skip、去重副本的结论。模型每次给的结果不一定一样，所以要么指纹对不上、整本重翻，要么块状态自相矛盾。
4. **没有显式的状态机，也没有「一次运行」这个实体。**
   - `jobs.status` 在十几个文件里直接赋值。
   - 任务落终态和 attempt 收尾分在两个事务里。
   - 事件不区分是哪一次运行的。
   - 取消只记在内存里。

   后果：attempt 卡在 running 以后，手改的译文永远登记不进去；重启后用户的取消会丢。
5. **跨进程协议和对账都是散的。**
   - 对账规则散在 7 处，没有一张总表。
   - 有 7 种协议靠两份或多份手抄维持。
   - stdout 投影上任何一处对不上，都按整本失败处理。
   - 打包的桌面版退出时不停 worker。
   - OCR 已经拿到回执，重启后却不复用。

   最后两条都在白花钱。
6. **写盘缺保证，用户数据混在任务产物里，计费没有统一的账本。**
   - 写盘：规范化文档有 4 条写入路径不是原子写；事件文件末尾的半行会让任务失败。
   - 用户数据：手改译文放在可以重跑的任务目录里；问答的会话文件从不清理；删书时不删书的目录。
   - 计费：用量台账里没有请求身份，执行器的用量恒为 0，旁路进程不入账，连接被拒也被记成「结果不明」。

**目标模型，一句话**：每个状态只有一个属主、一个正本。模型做出的决定和用户写下的东西，一落盘就冻结；其余一律是能从正本重算出来的派生。状态只能按转换表改，跨进程只能走带版本的协议。重启时由一个对账入口把派生对齐到正本，而不是把任务判死。

**先做什么**

1. **第 0 步：止损小修**，共 18 条，分 7 个分支，每条都小，不动结构。按收益排在最前面的四条：
   - 打包的桌面版退出时停掉 worker；
   - 请求日志把「没发出去」和「结果不明」分开，退出时先把在途请求排空；
   - 选页时切出的子 PDF 每次生成的字节一样，不再让 OCR 缓存失效、重新付费；
   - agent 引擎续跑时不再必报 regressed。
2. 然后两条线并行：
   - **第 1 步**（Rust）：运行收尾放进一个事务，并集中对账；
   - **第 2 步**（Python）：冻结模型做出的决定，加一个调和入口，统一块状态的读法。

## 设计原则

每一条都写明在本项目里具体指什么。

| # | 原则 | 在本项目里指 |
|---|---|---|
| P1 | **每个状态只有一个属主** | 一个字段、一列、一个文件只有一个模块能写，其余只读。<br>例：`jobs.status` 只由 `jobs/lifecycle/transitions.rs` 写；`artifacts.ocr_status` 只由 OCR 子任务收尾写，或者干脆不存、读的时候去 join；块的 `state` 只由 `transition()` 写；页文件只由断点会话和修订入口写，`reclassify --apply` 这类旁路一律不许写。<br>架构检查照 `check_job_entry_ownership` 的写法加规则 |
| P2 | **真相和派生分开** | 真相是没法从别处重算的东西：上传、OCR 原始结果、模型的回答、用户写的东西、断点里已提交的页。<br>其余都是派生：待办名单、进度、`ready`、书卡指针、合并目录、全文索引、`pipeline_units`。<br>派生不能拿来做守卫；对不上时重建派生，不判任务失败 |
| P3 | **模型的决定第一次产生就冻结** | 领域识别、目录定译、术语和风格准备、接续复核的结论、已译单元的分组、引擎和模型判的「保留原文」。<br>这些写进 `translated/decisions.v1.json`，跟着断点跨任务走；续跑只读不重算。<br>**失败也冻结**（见拍板 Q4），只有用户明确要求才重做 |
| P4 | **显式状态机，加一张转换表** | 任务、运行、attempt、阶段、派发、块，每种状态都有一张 `(从, 事件, 到, 条件, 顺带做的事)` 表；表外的转换一律拒绝，并记一笔违规。<br>`cas_save_job` 只核对「从哪来」不够，还要核对「到哪去」 |
| P5 | **先调和，再守卫** | 重启、续跑、导入断点之后，先走一个调和入口：原文变了的作废，策略重算，冻结的组不拆，把结果写成新的基线，再让守卫生效。<br>守卫只检查不变量（「对同一份原文已经有结果的块，不能丢掉结果」），不比较两份派生名单 |
| P6 | **持久化要有保证** | 全仓一个 `atomic_write`（临时文件、fsync、改名，Windows 上退避重试），Python 和 Rust 各一份，同一张测试表。<br>追加写的日志在打开时截掉末尾的半行。<br>加载路径只读，绝不顺手改写磁盘上的文件 |
| P7 | **协议只有一份定义，并且带版本** | 每个跨进程、跨语言的东西，都是 `backend/contracts/<名字>.vN.schema.json` 加 `contracts/fixtures/<名字>/` 下的共享样例，Rust 和 Python 的测试读同一批样例。<br>读的一方遇到**更新**的版本，报「请升级」，不当作没有。<br>版本号统一写成 `schema` + 整数 `schema_version` |
| P8 | **用户数据和任务产物分层** | 用户数据包括：条目、书目、标签、合集、笔记、批注、问答、译文版本和当前选择、手改译文、术语表。这些只能由用户动作删除，先进回收站。<br>派生缓存可以随时删、随时重建，但要登记属于哪本书。<br>任务产物可以按保留期清，**不承载用户写的东西** |
| P9 | **计费只有一本账** | 每个上游请求（翻译、OCR、领域识别、目录、表格、问答、预热）一行，身份稳定，状态集合是 `intent → sent → succeeded / failed_not_sent / failed_sent / ambiguous`。<br>用量和回执都挂在这一行上。台账、请求日志、`model_operations`、`pipeline_dispatches`、问答用量都是它的投影 |
| P10 | **部分结果不能冒充完整结果** | OCR 有页没认出来、流式公布的前缀页、手改译文以后没有重排的 PDF，都要显式标出完整性或者「已过期」，不能悄悄当成完整的用 |

## 目标模型

### 1. 任务和运行

**要不要 `job_runs` 表**

数据库重做的第 1c 步，11-21 已经定了不做：不把 pid、命令这些搬进每次运行的表。这里不推翻那个决定，推荐**方案 A：不建 `job_runs` 表，把运行代次放到现有的表上**。选项见拍板 Q1。

- **运行身份**：一次运行就是 `(job_id, run_generation)`。
- `jobs` 继续当「当前这次运行的快照」，但写法改掉：
  - 不再整行覆盖，改成按列窄写；
  - 加 `row_version` 列。
- 下面几张表各加一列可空的 `run_generation`：`pipeline_attempts`、`events`、`job_stage_history`。旧数据是 NULL，当作第 0 次运行。

数据结构草案（迁移只增列，迁移号到时再排）：

```sql
-- 运行代次放到现有表上
ALTER TABLE pipeline_attempts ADD COLUMN run_generation INTEGER;   -- 认领时写 jobs.run_generation
ALTER TABLE events            ADD COLUMN run_generation INTEGER;   -- 追加时写
ALTER TABLE job_stage_history ADD COLUMN run_generation INTEGER;   -- 只追加，不再 DELETE seq >= len

-- 行版本、持久化的取消意图、建任务时的类型
ALTER TABLE jobs ADD COLUMN row_version INTEGER NOT NULL DEFAULT 0;   -- 每次窄写 +1
ALTER TABLE jobs ADD COLUMN cancel_requested_at TEXT;                 -- API 取消一律写；driver、对账都读
ALTER TABLE jobs ADD COLUMN kind TEXT;                                -- 建任务时的 workflow，原地重渲染不改（N10）

-- 血缘：不新建表，扩 job_derivations
ALTER TABLE job_derivations ADD COLUMN kind TEXT;                     -- retry | continue | ocr_recovery | rerender | partial
ALTER TABLE job_derivations ADD COLUMN resume_from_job_id TEXT;       -- 沿重试链找到的、最近一个有断点的祖先
```

`parent_job_id` 在 v32 已经有了。之后恢复查询、巡检、事件投影都改用这一列，不再拼 `{父}-ocr` 字符串。

**`jobs` 各列由谁写**

| 列 | 唯一写入方 | 写法 |
|---|---|---|
| `status`、`finished_at`、`failure_json`、`error` | `jobs/lifecycle/transitions.rs` 的 `transition_run()` | `UPDATE … WHERE job_id=? AND run_generation=? AND status IN (从) AND row_version=?` |
| `stage`、`stage_detail`、`progress_*` | `update_progress()`（stdout 读循环、driver 推进阶段） | 窄写；OCR 子任务**不再镜像**到父任务（修 N3），视图读的时候 join 子任务 |
| `artifacts.ocr_status` 等 `ocr_*` | 不再存在父任务行上 | 视图从子任务行读；旧字段为了兼容，读的时候填 |
| `pid`、`worker_identity` | `set_worker()`（spawn） | 两列放在同一条语句里写 |
| `log_tail_json` | `append_log_tail()` | 窄写 |
| `artifacts_json` 的路径 | `set_artifact(key, path)` | 窄写，同时写 `job_artifact_entries` |
| `request_json`、`kind` | 建任务；原地重跑时只改 `request_json` 里属于这次运行的参数 | `kind` 写一次就不变 |
| `cancel_requested_at` | API 取消、jobsd `/cancel` | 内存里的标记只用来尽快通知 |

**任务状态转换表**：只有 `transition_run()` 能改状态。

| 从 | 到 | 唯一入口 | 同一事务里顺带做 |
|---|---|---|---|
| (无) | queued | `submit_job`、`relaunch_in_place`（代次 +1） | 记 `job_created` 事件 |
| queued | running | `start_run` | 事件 |
| running | queued | `requeue_for_resume`，只有对账能调 | attempt 保持 running；事件 |
| queued / running | canceled | `cancel_run`（API、driver 检查点） | 收尾 attempt 和 running 的阶段；写 `cancel_requested_at`；事件 |
| queued / running | failed | `fail_run` | 收尾 attempt；写失败信息（失败码查 `job_failure_catalogue`，不再手拼四套）；事件 |
| running | succeeded | `finish_run` | 收尾 attempt；登记译文修订；事件 |
| 终态 | queued | `relaunch_in_place` | 代次 +1；新 attempt |
| 其余 | — | 拒绝，记违规 | — |

- **终态和 attempt 收尾放进同一个 IMMEDIATE 事务**（修 N1）。书卡、全文索引这些派生仍然在事务外，但由对账兜底。
- 中间阶段的结果改成返回 `StageOutcome::{Done, Failed, Canceled}`，不再借内存里的 `status=Succeeded` 表示「这一阶段成了」（`runner/process_runner/completion.rs:65-80`）。
- 架构检查加一条：`transitions.rs` 以外不许出现 `.status = JobStatusKind::`。

**attempt、阶段、派发**

- attempt 只有一条路：running → succeeded / failed / canceled，并且只和 run 的终态一起写。
- `acquire_pipeline_attempt` 只续用 `run_generation` 相同的 running attempt；不同代次的，先按行上的状态收尾，再新开一个。
- 阶段：running → completed / failed / canceled。**completed 不能回到 running**；要重跑就新开 attempt。现在 `db/pipeline/attempts.rs:132-152` 和 `stages.rs:153-166` 的 upsert 都会把已完成的阶段改回 running。
- 派发表已经接近状态机，只补两处：
  - 顶层任务死在 `intent` 时，启动就把它标成 ambiguous；
  - 走 Python worker 的 OCR 也写 intent 和回执（修 S09）。

**事件和投影**

- 事件只在改状态的同一个事务里写，相当于 outbox；废掉「事务外读 previous、拿内存快照 diff、派生事件」这条路（`retainpdf-data/src/job_events.rs:140-241`）。
- live stage 和进度流只看当前这次运行的事件；`event_feeds.context` 去掉 `status`，状态变化不再触发整份重建（修 N2）。
- 接口上**新加** `run_generation`、`execution_attempt` 两个字段；旧的 `attempt` 字段保留（N6）。

### 2. 翻译块状态

**存放位置**：仍然在页文件 `page-NNN.json` 里。页文件已经有快照、哈希、发布协议，不另起一套。每块新增 `state`，旧的约 80 个字段降为投影，供 Rust、渲染、前端过渡使用。

```jsonc
"state": {
  "v": 1,
  "status": "pending",                 // pending | translated | kept | dead_letter
  "kept": {                            // 只在 status=kept 时有
    "owner": "engine",                 // document | policy | engine | model | user
    "reason": "skip_back_matter_index",
    "attempt_id": "…", "at": "…"
  },
  "result": {                          // translated 时有；dead_letter 时若有旧结果也留着
    "unit": {"id": "__cg__:cg-12", "members": ["p027-b011", "p028-b003"], "index": 1},
    "basis": {                         // 这份结果依据的东西；调和时逐项比对
      "source_sha": "…",               // 本块原文规范化空白后的 sha256
      "unit_source_sha": "…",          // 当时整组受保护原文的 sha256
      "math_mode": "direct_typst", "engine": "legacy",
      "inferred": false                // 从旧页文件推出来的为 true
    },
    "unit_text": "…",                  // 整组受保护译文；取代 translation_unit_protected_* 和 group_protected_*
    "member_text": "…",                // 本块受保护译文；取代 protected_translated_text
    "quality": "ok",                   // ok | partial | suspect（$ 不成对、JSON 壳之类，只标不删）
    "origin": "model",                 // model | fixed:toc_agent | fixed:connective | dedupe:<代表块号>
                                       // | repair:garbled | repair:agent | final_recovery | revision:user|agent|refine
    "attempt_id": "…", "revision_id": null, "at": "…"
  },
  "result_shelved": null,              // 被 kept 覆盖时挪到这里，不删
  "result_stale": null,                // 被调和作废时挪到这里，并写进调和报告
  "failure": {"count": 2, "last_code": "transport_timeout", "last_at": "…"}   // 成功后清空
}
```

- `blocked`（等同组的伙伴、流式时等下一页）不落盘，从 `pending` 加上分组现算。
- `translation_diagnostics` 只当日志用：`final_status`、`dead_letter` 从里面移出去，所有读方一律读 `state`（修 T-N7 两边读反的问题）。
- 页文件外面包一层信封 `{"schema":"translation_page_v2","items":[…]}`；读的一方看到裸数组，就按 v1 读。

**转换表**：唯一的写入口是 `transition(item, event)`。

| 从 | 事件 | 到 | 条件 | 顺带做 |
|---|---|---|---|---|
| pending | `result_applied(unit, text, origin)` | translated | 当前分组等于 `unit` | 写 `result`（含 basis），清 `failure` |
| pending | `attempt_failed(code)` | pending | — | `failure.count += 1` |
| pending | `exhausted(code)` | dead_letter | 重试和补救都用尽 | 保留 `failure` |
| dead_letter | `result_applied` | translated | 同上 | 清 `failure`（修死信标记残留） |
| pending / dead_letter | `keep(owner, reason)` | kept | owner 优先级不低于当前的：user > model > engine > policy > document | 有 `result` 就挪进 `result_shelved` |
| kept(policy / document) | `policy_recomputed(translate=true)` | pending；如果 `result_shelved` 的依据没变，直接回到 translated | 只有策略能撤销策略自己的决定 | — |
| kept(model / engine / user) | 策略重算 | **不变** | 冻结（修上一轮 #1） | — |
| translated | `revised(text, source)` | translated | — | 更新文字，`origin=revision:*` |
| translated | `invalidate(reason)` | pending | **只有调和入口能发**：依据不符，或者用户明确要求重翻 | 旧结果挪进 `result_stale` |
| translated | `attempt_failed` / `exhausted` | — | **拒绝**并记违规 | 现在 `T/core/payload/parts/final_status.py` 只观测、不拦，以后改成拦 |

现有写入点和事件的对应：

| 现有写入点 | 对应事件 |
|---|---|
| `mark_policy_skip` | `keep(policy / document / engine)` |
| `mark_keep_origin`（模型判的） | `keep(model)` |
| 编号快路径 | `keep(engine)` |
| 最终补救按策略保留 | `keep(policy)` |
| 去重副本，代表块失败时 | **副本保持 pending**（修 T-N1） |
| `apply_*` | `result_applied` |
| `_mark_dead_letter` | `exhausted` |
| `apply_revised_*` | `revised` |

**冻结的决定**：`translated/decisions.v1.json`，追加式、原子替换，每个决定产生的当下就写，不等阶段结束。

```jsonc
{
  "schema": "translation_decisions", "schema_version": 1,
  "document": {"identity": "…"},                         // 见「产物」一节的规范化文档身份
  "domain":   {"status": "ok" | "failed", "value": {…}, "model": "…", "at": "…"},
  "fixed_translations": {"status": "ok" | "failed", "source": "toc_agent", "input_sha256": "…",
                         "complete_document": true, "items": {"p003-b004": "…"}},  // 流式时按前缀算的标 false，OCR 做完后补算一次再冻结（修 T-N3）
  "preparation": {"term_base_sha256": "…", "style_guide_sha256": "…"},
  "continuation_review": {"pairs": [{"prev": "p027-b011", "next": "p028-b003", "digest": "…", "join": true}]},  // 每批判完就追加（修 T-N2）
  "frozen_units": {"__cg__:cg-12": {"members": ["p027-b011", "p028-b003"]}},
  "engine": {"agent_reading_sha256": "…"}
}
```

- 断点身份**不再包含**这些决定的哈希。它们不是输入，是冻结下来的中间结果；这样剩下的指纹问题（S05 的 ①②③）也就消失了。
- 跨任务要带走哪些文件，由 Python 维护一份清单 `translated/resume-set.v1.json`：`decisions`、`agent/`、`tables.v1.json`、`job-memory.json`、`term-base`、`style-guide`、`toc-agent`、`revisions.v1.jsonl`、memo、请求日志。Rust 照单拷，不再写死文件名（修 T-N4）。

**调和入口 `reconcile()`**

在 `TranslationCheckpointSession.acquire` 之后、第一次 `update` 之前，按整本扁平的口径跑一次：

1. **只读加载**：
   - 不清洗、不迁移、不按单页刷新（删掉 `T/core/payload/translations.py:83,144` 的刷新，以及 `template_sync.py:171-174` 每次重打 skip 的逻辑）；
   - JSON 坏了的页先从快照恢复，恢复不了再重建，并写进报告。
2. **原文绑定**：
   - 结果的 `basis.source_sha` 和现在的原文不符，就 `invalidate("source_changed")`；
   - 这是唯一一条会让译文「消失」的路径，顺带修好上一轮 #12。
3. **分组**：
   - 先套用 `frozen_units`；
   - 再用规则加 memo，只给没冻结的块分组；
   - 新分组碰到已经有结果的块，按 #224 的规矩拆开。
4. **策略**：只重算 `kept.owner ∈ {policy, document}` 的块。
5. **质量**：`$` 不成对、JSON 壳这类问题，只标 `quality=suspect`，放进低优先级的待办，**不删译文**（修上一轮 #3、T-N11）。
6. **报告**：写 `reconcile-report.v1.json`，打一行 stdout 事件，前端能显示「续跑时有 12 块原文变了，已重新排队」。
7. **提交基线**：调和后的状态作为新的基线写进断点；守卫从这之后才生效。

页面策略、agent 的 skip、流式每一轮的重新整理，都改成调用 `reconcile` 里对应的步骤，不再各改各的页。

**守卫和指纹**

- **守卫**：改成检查不变量。
  - 断点里每块存 `result_fp = sha(unit.id, basis, unit_text, member_text)`。
  - 上一代有 `result_fp` 的块，这一代要么 `result_fp` 不变，要么在调和报告里有它的 invalidate 记录。
  - 待办名单只用于显示，现算，不参与比较。
  - 投影函数必须是纯函数：`pending_translation_items` 拆成「建单元」（会写）和「列待办」（只读）两个（修 T-N6）。
- **指纹分两层**：
  - **硬输入**：文档身份、目标语言、`mode`、`math_mode`、引擎、模型、术语表。不符时隔离旧译文、提示用户，不删页文件。
  - **软输入**：`batch_size`、并发、规则文本版本，以及已经冻结的各项决定。不符时只记录（修 T-N9）。
  - 只用显式列出的字段算指纹，不再用 `vars(policy_config)`。

### 3. 产物：元数据和 `is_fresh`

每个由别的东西生成出来的产物，都带一份 `producer`：

- JSON 产物把它嵌在文件里（例如 document.v1 的 `derived.producer`）；
- PDF、docx 这类二进制产物，旁边放一个 `.<名>.producer.json`；
- 派生产物已有的 `.<名>.inputs.json` 并进这份文件。

```jsonc
"producer": {
  "kind": "normalized_document",
  "schema": "normalized_document_v1", "schema_version": "1.1",
  "steps": {"glm_adapter": 3, "formula_numbers": 5, "toc_split": 2},   // 每个改变输出的步骤一个版本常量；不用整个程序的版本号
  "inputs": {"provider_result": "sha256:…", "source_pdf": "sha256:…"}, // 写内容哈希，不写路径
  "env": {"formula_number_ocr": "on"},
  "completeness": {"pages": 620, "failed_pages": [66]},                 // 修 A-N5；流式前缀写 {"prefix_of": 620}
  "job_id": "…", "at": "…"
}
```

**`is_fresh(产物)`**：Python、Rust 各一份，照同一张表实现。

- 判定条件：有 `producer`，schema 认识，每个步骤的版本都不低于当前要求，输入哈希等于现在的输入哈希。
- 不新鲜时怎么办，按产物种类定：

| 产物 | 不新鲜时 | 理由 |
|---|---|---|
| 规范化文档 | 提示「可以重新归一化（不重新付 OCR 费）」，用户点了才重做 | 断点身份依赖它；自动重做会让续跑失配 |
| 渲染准备缓存、预热、page specs | 自动重建 | 便宜、确定（修 A-R4、R5、R6） |
| 对照版、水印、Word、预览 | 自动重建 | 同上；输入里**要有页文件或断点代次**（修 A-R1） |
| 合并阅读目录 | 自动重建 | 指纹要加上页文件或断点代次（修 A-L1） |
| 译文 PDF | 标「已过期：译文改过、还没重排」，前端提示重排 | 贵，用户决定 |
| OCR 原始结果、译文 | 不重建，只提示 | 贵，而且结果不确定 |
| 没有 `producer` 的旧产物 | 当作「版本未知」照用；用户主动重跑时补上 | 兼容 |

- **依赖关系写成数据**：每种产物声明自己的输入和重建函数，上游一变就沿依赖图往下标脏。依赖图见附录「OCR 和产物」第 2 节。
- **库里的登记**：`job_artifact_entries` 的 `ready` 改成读的时候核对（按 mtime 和大小缓存），不再固化在写入那一刻（修 J-N5）；`checksum` 从 `producer` 里填。数据库重做把 `artifacts_json` 的完整拆分并进了第 5 步，这里只增列，不提前拆。
- **身份**：
  - 复用 OCR、断点身份都比规范化文档的**身份**，即 `hash(原始结果) + 步骤版本表 + 环境`，而不是整份文件的字节哈希；
  - OCR 分片缓存的键改成「上传的 sha256 + 所选页 + 服务商 + 模型」（修 A-N1 的根子）；
  - 大文件不做全面的内容寻址存储，用硬链接去重就够了。
- 和 [书按段走](../book-segments/README.md) 的 `layout.json`、`segments.json` 一起做时，段文件直接带 `producer`，避免改两次目录结构。

### 4. 用户数据

**分三层，各层的删除规则写死**

| 层 | 内容 | 谁能删 |
|---|---|---|
| 用户数据 | 条目、书目、标签、合集、笔记、批注、问答、译文版本和当前选择、**手改译文**、术语表 | 只有用户动作；先进回收站（`library_items.deleted_at`，5b 已建列），清空回收站才真删 |
| 派生缓存 | 全文索引、合并阅读目录、书文件夹、封面、页预览 | 随时可删可重建；按书登记归属，删书时一起清 |
| 程序产物 | 任务、产物、事件、断点 | 保留期到了，或者用户删任务；不承载用户写的东西 |

**规矩**：启动、对账、同步一律不硬删用户数据。「书没有原文」是一种状态（`file_missing`），不是删除的理由。223267ee8 已经把启动清理改成只统计；之后要显示这个状态，还要让读路径过滤 `deleted_at`。

**锚点**：问答、批注、笔记、白板共用一套结构，和 [学习系统](../learning-system/README.md)「锚在原文上」的方向一致。

```jsonc
"anchor": {
  "file_id": "…", "pane": "source" | "translated", "doc_page": 28,
  "quote": {"exact": "…", "prefix": "…", "suffix": "…"},   // 原文侧的引文，定位优先用它
  "rect": [x0, y0, x1, y1],                               // 页内比例坐标，可选
  "hint": {"job_id": "…", "item_id": "p028-b003", "version_id": "…", "generation": 7}  // 只用来加速；对不上就提示「原文或译文变了」
}
```

`ask_threads` 只增列，赶在前端接上问答记录之前做：

```sql
ALTER TABLE ask_threads ADD COLUMN quote_prefix TEXT NOT NULL DEFAULT '';
```

**手改译文进库**：作为阅读时叠在任务产物上面的一层。选项见拍板 Q5。

```sql
CREATE TABLE translation_edits (
  edit_id        TEXT PRIMARY KEY,
  file_id        TEXT NOT NULL REFERENCES item_files(file_id) ON DELETE CASCADE,
  version_id     TEXT REFERENCES translation_versions(version_id) ON DELETE SET NULL,
  item_id        TEXT NOT NULL,                -- 文档坐标系下的块号
  doc_page       INTEGER NOT NULL,
  source_sha256  TEXT NOT NULL,                -- 块原文的指纹：对不上就提示「原文变了」，不静默套用
  text           TEXT NOT NULL,
```

- 页文件里的修订（`revisions.v1.jsonl`）继续保留，用来驱动重排。
- 「这块是谁定的」以库为正本：手改就是块状态里的 `revision:user` 来源。
- 这样删任务、整本重翻、恢复备份都不会丢手改。

**删除只有一个出口**：`library::delete_item(item_id, mode = trash | purge)`。

- `trash`：只写 `deleted_at`，同步发出去的是「进回收站」，不是删除。
- `purge` 按顺序做：
  1. 数据库事务；
  2. `documents/<书>/`（修 Lib-4）；
  3. 任务目录、上传目录、书文件夹；
  4. 按 `ask_threads.session_id` 删 pi 会话文件（修 Lib-6）。

**同步只发真相**：

- 书的同步文件排除 `merged/`、`pages/` 这些缓存目录（修 Lib-5）。
- 凭据库明确「不同步、不备份」；重试同步来的任务时，给出能看懂的错误（「这台设备没有这把密钥」）。
- 译文版本要不要同步，见拍板 Q6。

### 5. 跨进程协议和对账

**协议**：每份都进 `backend/contracts/`，配共享样例，两边的测试读同一批样例。

| 协议 | 现在 | 目标 |
|---|---|---|
| `pipeline-stdout.v1` | 已经是单一定义加契约锁 | 照旧；加一行 `hello`，worker 启动时报出自己支持的协议版本，不认识的版本让这次运行失败并说明原因（现在 `stdout_parser/durable_rules.rs:73,84` 悄悄丢弃） |
| `worker-runtime-env.v1` | 环境变量四处手写，约 25 个 `RETAIN_*` 原样继承 | 一份清单，列出每个变量谁写、谁读、是不是秘密。所有子进程（阶段 worker、预热、渲染准备、重放、问答 agent）都经**同一个启动函数**拿环境（修 L-D5、B-N6）；继承来的行为开关在 spawn 时拍成快照，记进 attempt |
| `stage-spec.v1`（6 种） | Rust 用 `json!`、Python 用 dataclass，各写一份，只钉了 translate 的 params 键 | 6 种都进 schema；原子写；带 `run_generation` 和 attempt；每个 attempt 留一份不可变副本 |
| `translation-checkpoint.v1` | 只有 Python 定义，Rust 三处手写校验 | schema 加样例；Rust 只留一个 `CheckpointView::load`，「能不能续」和「实际导入」用同一个判定 |
| `translation-request-journal.v1` | 两份手抄 | schema 加样例；判定表（见第 6 节）两边共用 |
| `usage-ledger.v2` | 每行没有请求身份 | 每行带 `request_id`（见第 6 节） |
| `ocr-stream.v1` | Python 加 Rust 读-改-写，各一份 | Rust 不再自己写清单，改成调用 Python 的写法；`seq` 接着旧清单往下数 |
| `structured-failure.v1` | 走 stderr，收尾超过 30 秒就整段丢掉 | 写文件 `logs/failure.v1.json`（原子写）；stderr 那行留作兼容 |
| 事件序号 | 数事件文件的行数得出 | 写的一方在打开文件时截掉半行，并把序号记在文件里；或者由 Rust 在 spawn 时通过 spec 传起始序号 |

**集中对账**：在 runner 里加一个 `reconcile` 模块，集中的是规则和顺序，不是把代码搬进一个文件。

1. **事实**：每个任务一份只读的 `JobFacts`，包括：
   - 任务行、当前运行代次、`cancel_requested_at`；
   - attempt、阶段、单元、派发；
   - worker 的身份和存活情况；
   - 断点摘要（代次、完成页数）；
   - 请求账摘要（结果不明几条、没发出去几条）；
   - 执行器操作摘要、OCR 子任务、渲染提交记录。
2. **决定**：纯函数 `decide(facts) -> Action`。Action 包括：续跑（从哪个阶段开始、带什么输入）、成功、失败（失败码）、等用户确认、收尾子任务、杀进程。
3. **执行**：按 Action 逐个任务 CAS 落库，**一个任务出错只记日志，继续处理下一个**（修 J-N4）。
4. **谁调用**：启动对账、运行期巡检、手动「重试」的 `resume_plan`，三处都调同一个 `decide`。

规则表要先写下的几行：

| 事实 | 决定 |
|---|---|
| 行是终态，attempt 还是 running | 按行上的状态收尾 attempt（修 J-N1 的遗留数据） |
| 请求账里有「结果不明」的请求 | **等用户确认**，不自动续跑（用户 11-26 定）。对外仍然是 failed，带失败码 `translation_request_ambiguous`，另加一个只增的字段 `needs_confirmation`（拍板 Q3） |
| 请求账里只有「没发出去」的请求 | 照常自动续跑 |
| 有 `cancel_requested_at` | 落 canceled，杀进程；不续跑（修 J-N12） |
| 父任务在串行 OCR 阶段，派发已经有回执 | 续跑时接着轮询这份回执，不重新提交（修 B-N3） |
| 流式 OCR 加翻译中断 | 续跑先补齐 OCR（复用分片缓存），再从断点接着翻；不走「要整份文档」的路径就失败（修 S30） |
| 父任务已终态，子任务 attempt 还开着 | 收尾子任务，把开着的 intent 标成 ambiguous（启动和巡检都做；修 J-N11） |
| 渲染提交记录在，文件也在 | 用 sha256 核对后判成功（现在只看文件在不在） |
| stdout 投影对不上（seq 倒退、generation 冲突） | 记诊断，标「投影要重建」，**不让任务失败**；从断点文件重建 `pipeline_units`（修 B-N5） |

**退出**（落实用户 11-26 的决定，并尽量少要确认）：

- Python worker 收到 SIGTERM 后，停止派发新请求，在宽限期内等在途请求回来，写上 terminal。这样大多数正常退出能做到没有歧义。
- jobsd 在监督者退出、或者自己收到 SIGTERM 时，照进程内模式的规矩终止 worker（修 J-E1）。

### 6. 请求账

**唯一真相**是表 `upstream_requests`。

- worker 进程里先写同一 schema 的 JSONL（就是现在的请求日志升级而来，写请求体之前 fsync）。
- Rust 在阶段结束、对账、读用量时导入库。
- 问答、执行器、Rust 原生的 OCR 直接写库。

```sql
CREATE TABLE upstream_requests (
  request_id     TEXT PRIMARY KEY,   -- sha(job_id, run_generation, purpose, unit_key, try_no)；问答用 thread_id + 轮次
  job_id         TEXT,               -- 问答为空
  run_generation INTEGER,
  attempt        INTEGER,
  purpose        TEXT NOT NULL CHECK (purpose IN ('translate','ocr','domain','toc','table','prepare','review','ask','prewarm','replay')),
  unit_key       TEXT,               -- 单元号、OCR 片号、问答轮次
  try_no         INTEGER NOT NULL,
  provider       TEXT NOT NULL,
  model          TEXT,
  status         TEXT NOT NULL CHECK (status IN ('intent','sent','succeeded','failed_not_sent','failed_sent','ambiguous','resolved')),
  receipt_json   TEXT,               -- 服务商任务号、回执
  input_tokens   INTEGER, output_tokens INTEGER, cached_tokens INTEGER, pages INTEGER,
  cost_micros    INTEGER,            -- 按当时的价格表算
  error_code     TEXT,
  created_at     TEXT NOT NULL, updated_at TEXT NOT NULL
);
```

**「发没发出去」只用一张判定表**，两种语言共用样例：

| 现象 | 状态 |
|---|---|
| 连接被拒、DNS 失败、TLS 握手失败、本地限流在发出前就拒了 | `failed_not_sent`（修 L-D2） |
| 请求体已经写出，之后断开或超时 | `ambiguous` |
| 有 HTTP 响应，但不是 2xx | `failed_sent` |
| 2xx，解析成功 | `succeeded` |
| 用户确认后重发，或者绑定了已有回执 | 原请求标 `resolved` |

**投影**：

| 投影 | 怎么来 |
|---|---|
| `token-usage.v1.jsonl` | 由账导出 |
| 请求日志 | 就是账在 worker 里的那一份 |
| `model_operations` | 回执写进账（修 L-D1） |
| `pipeline_dispatches` | 加一列 `request_id` |
| 问答用量 | 出错、取消时也写账（修 G-D1） |

和 [模型用量与花费](../model-usage/README.md) 的估价共用价格表。

**Q1. 「一次运行」用什么表示？**（关系到 11-21「1c 不做」的决定）

- A：不建 `job_runs` 表，在 `pipeline_attempts`、`events`、`job_stage_history` 上加 `run_generation`；`jobs` 加 `row_version`、`cancel_requested_at`、`kind`；改成窄写。

- C：都不做，只修 S09、S26。
- **推荐 A**：能修掉 S09、S26、S27、S40、S42，不动断点续跑的核心表，和 1c 的结论不冲突。B 等第 1 步做完、确实还需要时再提。

**Q2. 块状态 `state` 放在哪里？**

- A：放在页文件里，旧字段保留为投影。
- B：另起一个文件或一张表。
- **推荐 A**：页文件已经有快照、哈希、发布协议，放在别处又会多出一份真相。

**Q3. 有结果不明的请求、要等确认时，任务对外怎么显示？**

- A：仍然是 failed，带失败码 `translation_request_ambiguous`，另加只增的字段 `needs_confirmation` 和 `ambiguous_request_count`。
- B：新加一个状态 `awaiting_confirmation`。
- **推荐 A**：对前端只增不改；B 要改前端所有按状态分支的地方。

**Q4. 模型的决定第一次失败时，要不要也冻结？**（例如领域识别、目录 agent 第一次失败）

- A：失败也冻结，续跑不再问；用户点「重新识别」才重做。
- B：失败不冻结，续跑时再试一次，但成功以后不进指纹。
- **推荐 A**：和「宁可多确认，也不重复收费」一致，S05 剩下的 ①② 也就不存在了。代价是第一次失败的书会少一点领域提示。

**Q5. 手改译文进不进库？**

- A：进库（`translation_edits`），作为叠加层，以库为正本。
- B：留在任务目录，但删任务前提示、备份时带上任务目录里的修订。
- **推荐 A**：手改是用户数据，删任务、重翻、恢复备份都不该丢。时机放在第 2 步写口收敛之后。

**Q6. 译文版本要不要同步？**（书库条目模型「要定的」第 4 条）

- A：同步版本，但不同步当前选择。
- B：不同步，本机收到同步来的任务时，按建任务的同一条规则自动收编进版本。
- C：维持现状。
- **推荐 A**：版本承载着「读哪份」和「手改挂在哪」，比任务更像用户数据；现状（C）会让多设备用户读不到新译文。

**Q7. 打包桌面版的运行形态**

- A：短期修好「jobsd 退出时停 worker」，保留 remote 加监督；第 3 步做完租约和可重连的进度以后，再兑现「改壳不杀任务」。
- B：回到进程内模式，少维护一种形态。
- **推荐 A**：修起来只要几行，也不丢 ADR-002 的方向。如果第 3 步迟迟做不了，再考虑 B。

**Q8. 请求账存在哪？**

- A：worker 里写 JSONL（同一 schema），Rust 在节点上导入库表；问答、执行器、OCR 直接写库。
- B：所有上游请求都改走 Rust 执行器，只写库。
- **推荐 A**：执行器默认还关着，B 要等执行器全面上线；A 不依赖它。

**报告之间说法冲突、以代码为准的更正**

1. **流式清单 seq 从 0 数起，现在能不能碰上**：
   - 「OCR 和产物」报告说，自动续跑时 `current_stage` 为空，会落到重跑 OCR 的路径上；
   - 「进程边界」报告说，现在碰不到。
   - **代码**：流式时父任务的 attempt 在翻译 worker 读 stdout 时建，这时 `job.stage` 已经是 translating（`runner/translation_flow_stage.rs:171`），`durable_stage_key` 得出 translate（`runner/process_runner/io_support.rs:456-463`）；之后 `dispatch_workflow` 走「从翻译续」（`runner/lifecycle.rs:286-288`），不会重跑 OCR。
   - 结论：前一份报告给的触发路径**不成立**，机制本身成立，留作隐患（S46）。真正会碰上的是 S30：续跑走了非流式路径。
2. **上一轮 #5 的子结论「请求日志也在这里断掉」**：快照上，源任务没有断点时，也会先拷请求日志再返回（`runner/translation_checkpoint_resume.rs:47-49`）。所以「直接上一个任务没有断点」这种情况，请求日志**不会**断。只有链上更早的一环从没进过翻译阶段时，才会断。这条子结论只对一部分情况成立。
3. **G-D1「出错、取消时用量都丢」**：复现显示，正常取消会把用量放进结果的 `_meta` 里带出去，只有出错，或者取消时碰上异常，才会丢（`server.py:373-379`）。
