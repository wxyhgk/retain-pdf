### 5.1 OCR 和归一化

**N1. 选页的子 PDF 每次生成的字节都不一样，GLM 分片缓存对选页任务永远不命中，重试照样付费。**（复现 + 读码）
- `glm_ocr_driver.py:123-141` `prepare_source_pdf` 用 `fitz` 的 `insert_pdf` + `save` 切出子 PDF；PyMuPDF 每次写新的文件 ID 和时间戳。
  复现 `repro/subset_det.py`：同一份原文切同样的页两次，sha256 不同；加 `no_new_id=True` 并清空元数据后两次相同（`subset_det2.py`）。
- 共用缓存的键（`glm_ocr_driver.py:155-157, 197-199`）和任务内的 `chunks.json`（`:200-201`）都用这个子 PDF 的 sha256，所以：
  - 选页任务 OCR 失败后重试、新建任务：共用缓存不命中，整本重新付费；
  - 同一任务目录重跑：任务内断点也对不上；
  - 共用缓存里每次留一套没人再读的分片，直到 365 天后清。
- Paddle 分片（`paddle_chunked.py:187-194`）同理（只有任务内断点）。
- 触发：上传时选页（`ocr.page_ranges`），OCR 用 GLM 或 Paddle 官方 HTTP。整本任务不受影响（原文是上传文件本身，字节稳定）。

**N2. 跟着 OCR 翻（流式）又选了页时，翻译拿到的原文是整份上传，页号和 OCR 文档错位。**（读码）
- Rust 流式路径把 `source_pdf_path` 设成上传文件（`translation_flow.rs:296-300`，`translation_flow_stage.rs:75-77` 原样传给 worker），
  而 OCR 文档的第 n 页是子 PDF 的第 n 页（`glm_ocr_driver.py:565`、`paddle_chunked.py:294`）。`ocr_streams_pages`（`questions.rs:67-76`）不排除选页。
- 按页号读原文的地方都读错页：
  - 表格翻译 `tables_stage.py:154-165`：`build_table_model(block, pdf[page_index])` 用错页的文字层建表格结构；
  - agent 引擎 `agent_flow.py:288-305`：页码标签取错页，`skip_back_matter` 判页眉时会把不该保留的标题标成保留原文（或反过来）；
  - 领域识别读的是整本前两页，不是所选页（`domain_context.py:314`）。
- 断点的流式身份 `ocr_stream_source_pdf_sha256` 是整份上传的哈希（`identity.py:108-111`）；之后「重试翻译」用源任务记录的
  `artifacts.source_pdf`（子 PDF，`stage_contract.rs:69-70`），`resumes_streamed_attempt`（`identity.py:46-62`）永远对不上。
  上一份审查第 2 条说的是指纹里的模型产出；这里是另一条让选页流式任务的断点必然作废的原因。
- 串行（不流式）路径用的是子 PDF，没有这个问题。

**N3. 流式清单的 `seq` 每个写者进程从 0 数起，同一目录重跑流式 OCR 时，翻译会卡住或直接失败。**（机制复现，触发推测）
- `OcrStreamWriter.__init__` 把 `_seq` 设成 0（`ocr_stream.py:70`），不读已有清单；读者只认 `seq > after_seq`（`:145`），
  失败的清单一读到就抛（`:136-144`）；OCR 开跑时不清 `ocr/stream/`。
- 复现 `repro/stream_seq.py`：旧清单停在 seq=4（进程被杀，没写 done/failed），读者先拿到它；新一轮全命中缓存直接写 done（seq=1），
  读者一直等。`repro/stream_failed.py`：旧清单是 failed，新一轮还没公布，读者立刻 `OcrStreamFailed`。
  Rust 补标（`ocr_stream.rs:49-79`）看到 done 已在就不动，救不回来。
- 触发需要同一任务目录再跑一次流式 OCR + 翻译：自动续跑时 `current_stage` 为空（父任务的翻译 worker 还没打出第一行阶段观察，
  例如在等第一片 OCR 时进程被杀），`dispatch_workflow` 落到 `run_job_with_ocr`（`lifecycle.rs:276-304`）。没有实测这个窗口多大。
  卡住以后要等翻译自己的无进展超时，然后失败、再自动续跑。

**N4. 流式文档的页不再等于最后整份文档的同一页；翻译只按页第一次到达时的版本建模板。**（复现；当前后果推测为小）
- 今天合进来的公式编号补点 `repair_formula_number_separators`（`formula_numbers.py:683-733`，在 `pdf_geometry.py:102` 每次归一化都调）
  按**全书**阅读顺序看前后编号。GLM 每片把前缀重新归一化（`glm_ocr_driver.py:228-234, 577-585`），前缀末尾那串丢了点的编号没有「后一个」，补不上。
- 复现 `repro/formula_prefix.py`：三页 `5.6 / 57 / 5.8`，整份归一化第 2 页补成 `5.7`，只有前两页时仍是 `57`。
- 翻译的页模板在页第一次到达时生成，之后不刷新（`streaming_flow.py:117-121`、`pages.py:24-29`）。眼下翻译载荷里不带
  `formula_number`，阅读器读最终文档，所以影响小；但「前缀页 = 最终页」（`glm_ocr_driver.py:19-21`、`ocr_stream.py:7`）
  是流式翻译的前提，没有测试守着，以后任何一个整本视角的归一化步骤都会悄悄打破它。

**N5. GLM 认不出来的页留空、任务照样成功，这件事只记在原始结果里。**（读码）
- `_page_by_page_chunk`（`glm_ocr_driver.py:285-348`，留空在 `:327-333`）把整页、两半都认不出的页留空，记进 `_page_fallbacks`；
  这只进了 `glm_ocr_result.json._meta.page_fallbacks`（`:443, 464`）和一条进度事件（`:402-422`）。全仓再没有别处读 `page_fallbacks`。
- 规范化文档、任务行、复用校验都不知道这几页是"OCR 失败"而不是"空白页"。重试翻译、书库复用 OCR 会一直用这份缺页的文档；
  那一片不进共用缓存（好），但只有新建 OCR 任务才会再试。

**N6. Paddle 的流式文档和规范化文档格式不同，成功后的硬链接去重对 Paddle 永远不生效。**（读码，只是占盘）
- 规范化文档 compact 写（`paddle_normalize.py:97`），流式文档是缩进写（`ocr_stream.py:82` 用 `save_json_atomic` 默认缩进），
  `link_identical_copy` 先比长度（`intermediates.rs:294`）就放弃。Paddle 任务一直留两份，其中一份大 30–50%。
  `intermediates.rs:14-16` 和 `storage.md` 写的「逐字节相同」只对 GLM 成立。

**N7. 远程地址（source_url）的任务选了页，书和页号对不上，之后复用不了 OCR。**（子代理读码；我核对了 `transport.rs:54-90`）
- 原文被原地截成子 PDF，`ocr_page_numbers` 记原始页号（`ocr_flow/transport.rs:74-84`）；随后按这份子 PDF 建书
  （`ocr_flow/mod.rs:195` → `source_document.rs:26-31`），书的页数变成所选页数。之后复用时原始页号超出页数，
  报 `invalid_ocr_page_coverage`（`ocr_artifact_reuse.rs:297-305`），而且书本身也不是原书。

**N8. 复用 OCR 的任务拿不到 OCR Markdown。**（子代理读码；我核对了 `resolvers.rs:16-20`）
- `resolve_markdown_path` 只看任务自己的 `md/full.md`，不像图片（`resolve_ocr_markdown_images_dir`，`:33-40`）那样退到产出 OCR 的任务找。
  阅读页的 Markdown、下载对这类任务返回 not_ready（`jobs/reader/markdown.rs:48`、`jobs/files/downloads/files.rs:293`）。可能是有意的，但没有注释说明。

**N9. 已拿到回执、但 OCR 结果没落盘就失败的任务，重试 OCR 会重新付费。**（子代理读码，我没复核）
- 挡重试只认 ambiguous（`jobs/actions/ocr_ambiguity.rs:127-129`）；派发记录按任务和 attempt 分，retry-stage OCR 新建的任务会重新提交，
  服务商那边已经做完的任务不复用。

**N10. 规范化文档的写入五条路径里四条不是原子的。**（读码，后果推测）
- GLM `glm_ocr_driver.py:610`、Paddle `paddle_normalize.py:97`、MinerU `job_flow.py:55`、命令型 `local_command_driver.py:265` 用 `save_json`
  （`io.py:10-33`，直接 `open("w")`）；只有 normalize worker 用 `save_json_atomic`，而 `save_json_atomic` 的说明正是「规范化文档会被并发读」。
- 读的一方只看文件在不在（`stage_contract.rs:54-82`、`source_json.py:12`）。崩溃时 OCR 阶段会失败，所以眼下多半不会被下游用到；
  但成功后的硬链接（`intermediates.rs:310`）让流式文档和它共用一个 inode，以后要是有人原地重写其中一个，两个一起变。
- 上一份审查第 13 条说的是原子写在 Windows 上没有重试，这里是根本没用原子写。

## 6. 设计建议

### 6.1 现状的共同毛病

1. **过期判断五花八门，最常见的是不判。** OCR 和归一化只看文件在不在；GLM 缓存看原文哈希（还是不稳定的哈希）；渲染准备看算法版本 + 输入；
   合并目录看文件戳；派生产物看记录文件 `.inputs.json`；渲染输出的 sha256 写了没人读。同一个"这份东西还新吗"的问题，有六种答案。
2. **派生产物不知道自己是由什么生成的。** document.v1 只有 schema 版本，没有归一化代码版本、没有原始结果哈希、没有生成环境
   （公式编号截图识别装没装）；所以"归一化修了 bug，要不要对旧任务重做"无从判断，也没有"不重新付费、只重新归一化"的入口。
3. **产物的身份靠路径。** 任务行里的路径、登记表的 `ready` 快照、合并目录的文件戳、子任务和父任务两行同样的路径——
   路径在不等于内容对。复用别的任务的产物是直接读对方目录，对方被清理、重跑、手改都不会通知下游。
4. **部分结果被当成完整结果。** OCR 有页认不出来照样成功（N5）；流式前缀被当成最终页（N4）；手改译文后 PDF、manifest、合并目录不跟（L1）。
5. **写入的原子性没有统一。** 同一个产物有原子和非原子两种写法（N10）；Rust 和 Python 各写一份流式清单。

### 6.2 产物要不要统一元数据

要，而且先做这一步收益最大。建议每个"由别的东西生成的"产物旁边有一份小的旁注（或嵌在文件头），格式统一：

```json
{
  "kind": "normalized_document",
  "schema": "normalized_document_v1@1.1",
  "generator": "retainpdf-pipeline/ocr-normalize@<代码版本或步骤版本表>",
  "inputs": {"provider_result": "sha256:…", "source_pdf": "sha256:…", "env": {"formula_number_ocr": "on"}},
  "completeness": {"pages": 620, "failed_pages": [66]},
  "produced_at": "…",
  "producer_job": "<任务号>"
}
```

- `generator` 不要用整个程序的版本号（每次发版都会让所有东西过期），用**每个步骤自己的算法版本**，渲染那边的 `*_ALGORITHM_VERSION` 已经是这个思路，
  照搬到归一化（每个改变输出的步骤一个常量，合起来成一个版本表）。
- `inputs` 写哈希，不写路径；子 PDF 要先让它确定（N1 的修法：`save(no_new_id=True)` + 清元数据，或者干脆把键改成 `上传 sha256 + 所选页列表`）。
- `completeness` 把 N5、N4 这类"部分结果"显式化；书按段走方案里的 `segments.json` 的 `failed_pages` 可以就是它。
- Rust 的 `job_artifact_entries.checksum` 现在恒为空，可以从旁注里填。

### 6.3 统一的「过期判定 + 重建」

建议一个很小的接口，Python 和 Rust 各一份，按同一份表实现：

- `is_fresh(产物) = 旁注存在 && schema 认识 && generator 版本表里每一步都 ≥ 当前要求 && inputs 的哈希等于现在输入的哈希`
- 不新鲜时按产物种类决定动作：**重建**（便宜、确定：归一化、渲染准备、派生产物、合并目录）、**提示用户**（贵或不确定：OCR、翻译）、
  **照用但标注**（旧任务没旁注：当作"未知版本"，只在用户主动重跑时更新）。
- 依赖图（第 2 节）写成数据：每种产物声明自己的输入和重建函数。上游变了，沿图往下标脏，而不是靠每个下游自己去比文件戳。
  L1（手改不进合并指纹）和派生产物跟不上手改，都是"下游没声明全部输入"的同一类错误。

### 6.4 内容寻址要不要做

- **对贵的、跨任务共用的原始结果，做**：OCR 分片（GLM 已经有，修好 N1 的哈希即可；Paddle、MinerU 补上）、翻译单元缓存（已有）。
  键 = 输入内容哈希 + 服务商 + 模型 + 影响结果的参数。
- **对归一化文档，做"键"不做"存储"**：任务目录里照旧一份文件，但它的身份是 `hash(原始结果) + 归一化版本表 + 环境`。
  复用 OCR 时比这个身份，不比路径；断点身份也换成它，而不是整份文档的字节哈希（字节哈希对任何无关字段的改动都敏感）。
- **对大文件（规范化文档、译文 PDF）不建议全面内容寻址存储**：要引入引用计数和垃圾回收，而现在的清理逻辑（`intermediates.rs`、
  `retention.rs`、`job_dirs_referenced_by`）已经很复杂。硬链接去重（像流式文档那样）够用。
- 合并目录可以改成内容寻址的"计划 + 各页输入哈希"，并改用硬链接而不是 copytree。

### 6.5 迁移顺序

| 步 | 做什么 | 为什么这个顺序 |
|---|---|---|
| 0 | 修直接的错：N1（子 PDF 确定化，一行 `no_new_id`）、N2（流式传子 PDF，或流式时不允许选页）、N3（`OcrStreamWriter` 接着旧 `seq` 数，开跑时清掉旧的 failed）、L1（合并指纹加页文件戳或断点 generation） | 都是小改动，N1、N2 直接省钱和防错 |
| 1 | **归一化加步骤版本表和输入哈希**，写进 document.v1（`derived.normalizer` 或旁注）；`completeness.failed_pages`（N5）；把 N4 的不变量写成测试（整份归一化的第 n 页 == 前缀归一化的第 n 页，GLM 逐字节，或者把整本视角的步骤挪到收尾） | 收益最大：之后所有"OCR 能不能复用、断点能不能接、要不要重新归一化"都有依据；改动只在 Python 一侧，旧文档没有这个字段就当"未知版本" |
| 2 | 统一 `atomic_write`（和上一份审查的持久化建议合并）；所有产物写入换过去；Rust 不再自己写流式清单，改成调 Python 的写法或共用一份 schema | 机械改动，降低"写一半"类问题 |
| 3 | 产物旁注 + `is_fresh` 接口，先接派生产物和合并目录（便宜、可重建），再接渲染准备 | 用便宜的产物把接口磨合好 |
| 4 | 依赖图写成数据，复用 OCR / 译文时按身份比，`job_artifact_entries.checksum` 填上 | 需要 1、3 |
| 5 | 和书按段走的第 1、2 步合并：`layout.json` + `ocr/segments.json` 时，段文件直接带旁注 | 避免两次改目录结构 |

先做第 1 步的理由：现在所有跨任务复用（重试翻译、书库复用 OCR、合并阅读）的输入都是规范化文档，而它是全系统唯一一个
"没有任何版本和来源信息、却被所有人信任"的产物。
