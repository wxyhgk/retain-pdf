# 阅读页提问：主对话按书分

2026-11-27，分支 `feat/ask-main-per-book`。改的是 [主对话、副对话和记忆](./20261126-主对话副对话和记忆.md) 里用户已定的第 3 条
「主对话是全局的」；其余照旧。接口用法见 [docs/api/16-AI/02-主对话和记忆.md](../../../api/16-AI/02-主对话和记忆.md)「主对话按书分」。

## 为什么改

11-26 定的是一个全局主对话（用户当时说「每一本书一个主对话我感觉也不好」）。用了一天，用户反馈「主对话串了，好几个 pdf 打开都是同一个聊天框」。
前端会话问了用户，用户选的是「**每本书一个主对话，用户层记忆照旧所有书共用**」。

## 用户已定（2026-11-27）

1. 每本书一个主对话；没有书的照旧是全局那条。
2. 用户层记忆照旧所有书共用；书层记忆照旧按书。
3. 以前那条全局主对话**按书拆开**（后端问的，用户选「按书拆开」；另两个选项是留着不拆、旧的归档）。

## 怎么做

- 数据库 v45（`v45_ask_main_per_book.sql`）：
  - 主对话用 `ask_conversations.document_id` 记属于哪本书（这一列以前只有副对话用，记开在哪本书）。
  - 「同一时间只有一个开着的主对话」的唯一索引从 `(kind)` 换成 `(COALESCE(document_id, ''))`：每本书一个，全局那条一个。
  - 删书时这一列置空（外键 `ON DELETE SET NULL`），开着的会和全局那条撞唯一索引、书删不掉：`item_files` 上加一个删除前的触发器，
    先把这本书开着的主对话归档。归档的留着，能在归档里看。
  - 拆旧数据：带书的消息挪到那本书的主对话里（每本书一条，id 是旧 id 加书号前 12 位，状态、标题照旧，按原来的顺序从 1 重新编号，
    `message_id` 不变，所以改问的 `edited_from`、副对话的分叉点、记忆的出处消息都不用动）；没有书的消息留在原来那条（编号不动，中间空着）；
    副对话跟着它分叉的那条消息走，没有分叉消息就看它开在哪本书；它回到主对话的结论卡片（`side_summary`，本身不带书）跟着它；
    记忆的出处对话跟着出处消息；拆过的对话的压缩摘要作废（几本书混在一起），下次按剩下的消息重新压。
- 接口：`POST /ai/ask-conversations/main` 收一个可以不带的请求体 `{document_id?}`，带了取或建这本书的，不带照旧是全局那条（对前端只增不改）。
  老后端的请求体都是 `deny_unknown_fields`，带了 `document_id` 会 `400`，所以前后端要一起更新。`GET /ai/ask-conversations` 多一个 `document_id` 筛。
- 上下文、压缩、副对话、改问都是按对话算的，不用改；主对话按书分以后，上下文的最近几轮自然只有这本书的。

## 验证

- 新测试：每本书各有一个开着的主对话、和全局那条互不影响、归档和重新打开按书算、删书先归档；迁移把旧的全局主对话按书拆开
  （两本书 + 没书的消息 + 副对话和结论卡片 + 记忆 + 压缩摘要）；接口带 / 不带 `document_id`、书不在 404、不认识的字段 400、按书筛。
- 真实库副本上 `retainpdf db-snapshot dump|diff`（main 编的和分支编的各 dump 一次）：只有对话这一类变了——原来那条全局主对话的 18 条消息
  分到两本书的主对话里（16 条、2 条），原来那条剩 0 条、照旧开着；别的 872 条一样。
