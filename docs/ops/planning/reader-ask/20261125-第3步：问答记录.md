# 阅读页提问第 3 步：问答记录

2026-11-25，分支 `feat/ask-records`。接着 [后端 ACP 桥和自带 agent](./20261125-后端ACP桥和自带agent.md) 的「分步」第 3 步。
前端在书页左边白边画「?」、点了重新打开那次问答（[阅读页提问](./20261125-阅读页提问.md)「书页上的『?』」），现在只记在这次打开里；
这一步让后端按书存下来，下次打开还在。接口用法见 [docs/api/16-AI/01-阅读页提问.md](../../../api/16-AI/01-阅读页提问.md) 的「问答记录」。

## 存在哪：数据库，两张新表（v39）

和它最像的是**书上的用户数据**：标签（v37 `item_tags`）、译文版本（v30 `translation_versions`）、书名建议。它们都在数据库里，
按书的文件（`item_files.file_id` = 接口里的 `document_id`）挂、删书跟着外键级联删。批注、笔记以后也进库（[书库条目模型](../database-redesign/20261121-书库条目模型.md) 5c、5d）。
数据目录里的文件只放产物（任务目录、上传、书文件夹导出），没有存用户写的东西的先例。所以放库里：

- `ask_threads`：一次提问一行。`document_id` 外键到 `item_files(file_id)`，`ON DELETE CASCADE`（和译文版本一样）；锚点拆成列
  （`pane` 有 `CHECK`、`page >= 1`、`item_id`、`selection`、`source_text`、`translated_text`、`section`、`point_x` / `point_y`
  两个要么都有要么都空），不整块存 JSON：列表要按书、按页取，以后搜问答也方便；`agent_id`、`session_id`、`title`、两个时间。
- `ask_messages`：一条问或答一行（`thread_id`、`position`、`role` 有 `CHECK`、`text`、`thought`、`usage_json`）。用量是 agent 给什么
  存什么的一块（自带 agent 的 `_meta.retainpdf.usage`），整块存 JSON；其余是列。列表里的条数 `COUNT(*)` 现算。

不做的：

- **不进条目主表**（`library_items` 的新类型）。问答不是用户会单独整理、打标签、放文件夹的东西；要进主表得改 `item_type` 的
  `CHECK`（SQLite 只能重建表，它被一串外键指着），收益不抵风险。以后要「问答转成笔记」，用 5b 已有的 `item_relations`
  （`derived_from`）把笔记条目和书连起来就行。
- **不同步**（不加 `sync_dirty` 触发器）：第一版只在本机用；要同步时再给它一个同步种类，表结构不用动。
- **没有归属列**：多用户模式下路径里的 `document_id` 由中间件核归属，`thread_id` 归 `Nested`（处理函数按书查，不在这本书上 404）。

## 放哪个领域：书库

记录挂在书上、跟着书删，和标签、译文版本同一类，放书库包（`retainpdf-library` 的 `ask_threads.rs`，请求和返回类型在 `views.rs`），
数据库层 `database/retainpdf-db/src/db/ask_threads.rs`，处理函数 `backend/api/src/routes/ask_threads.rs`（登进
`ROUTE_SERVICE_IMPORT_ALLOWLIST`，只用 `crate::services::library`），接口登记在 `app/router/documents.rs`（`owner: library`）。
ACP 桥（providers 领域）只管转发、不碰记录，两边不互相依赖。

## 接口

都在书下面（`/api/v1/documents/:document_id/ask-threads`），signed，`by(web)`：列（不带问答正文）、建、读一次、改、删。
改用 `PATCH` 整份换掉问答：前端手里本来就是整段对话（assistant-ui 的导出），每答完一轮写一次；重发同一份结果一样，网络重试、
编辑重答都不用另外处理。另外开一个「追加一条」的接口省不了什么（一段对话最多 1 MB）。

契约 `ask-threads.v1`（两份 + 生成的 TS），端点先不写 `client_name`：前端的生成客户端（`frontend/packages/api`）有漂移检查，
等前端接的时候连同生成代码一起加（`ai-agents.v1` 当时也是这样）。

## 上限

| 什么 | 上限 | 超了 |
|---|---|---|
| 一本书的提问 | 500 | 409 `ask_thread_limit`（`details.limit`）|
| 一次提问的问答条数 | 200（一问一答两条）| 400 |
| 一条正文 / 思考摘要 | 50000 / 20000 字 | 400 |
| 一次提问的正文和思考加起来 | 1000000 字节 | 400（请求体默认上限 2 MB，留了余量） |
| 一条用量 | 对象，写成 JSON 4096 字节 | 400 |
| 锚点里的选中的字 / 那一块的原文、译文 / 章节 | 4000 / 各 8000 / 200 字 | 截断（只是出处，阅读器选中的字本来也截到 4000） |
| `agent_id` / `session_id` / `item_id` | 64（字母、数字、`-_.`）/ 256 / 200 字 | 400 |

## 验证

数据库层单测 3 个、书库包单测 4 个、`api_tests::ask_threads` 5 个（真接口走一遍并对契约核键集合、请求类型和契约字段一一对上、
不在这本书上 404、删书跟着删、校验和上限）；`schema.sql` 重新生成；真实库副本上 `db-snapshot dump|diff`：迁移前后每本书只多一个
`ask_threads: []`。具体数字见开发记录。

## 以后

- 自带 agent 的 `session/load`（`loadSession = true`，从记录重放历史）；本机 agent 支持 `session/load` 的直接用记下的 `session_id`。
- 前端接：书打开时列出来画「?」，点了 `GET` 一次再打开；答完一轮 `PATCH`；删「?」用 `DELETE`。交接写在
  [后端改动交接](../../../core/frontend/backend-changes-handoff.md)。
- 要不要同步、要不要「问答转笔记」，等用户用起来再定。
