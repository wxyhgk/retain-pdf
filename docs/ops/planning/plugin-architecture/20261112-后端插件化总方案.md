# 后端插件化总方案

**状态：** 定方案，按下面的步骤一个分支一个分支做
**日期：** 2026-11-12
**范围：** 后端（Rust 模块化单体 + Python 流水线）的扩展点；前端跟着从后端读清单的部分写进交接文档，由前端会话做

## 1. 为什么

用户看过 DeepSeek Harness（口号 "Everything is a Plugin"）后，定了：后端能做成插件的都做成插件。

盘点下来，我们的问题不是"没有插件框架"，而是**同一样东西在好几处各写一份**，加一个实现要满仓库找地方改，漏一处就出 bug：

| 扩展点 | 加一个新实现要改的文件 | 已经出过的问题 |
|---|---|---|
| OCR 服务商 | 接 GLM-OCR 实测后端 39 个、前端 25 个，共 64 个 | 服务商定义有 4～5 份；命令行至今认不出 GLM；契约 `job-status` 的枚举没有 `glm_ocr`；"会不会一片片交结果"靠 `provider == "glm_ocr"` 判断，并行那几次连出阶段显示 bug |
| 翻译接口协议和服务商预设 | 约 20 个 | 同一组协议实现了 4 遍（Python 正式调用、Rust 探针、Rust 执行器、翻译 agent）；Rust 的预设表写着"与前端一致"，实际已经分叉 |
| 流水线阶段 / 子阶段 | 新阶段 15～20 个 | 子阶段名单 Rust、Python 各一份，已经不一致 |
| 失败分类 | 4～6 个 | Rust 兜底分类没有 `billing`，限流写成 `rate_limited`（Python 是 `upstream_rate_limited`） |
| 渲染引擎 | 约 18 个 | 默认值 `rpr_fit`，Python 三个函数的默认参数还是 `"typst"` |

完整盘点见同目录的 [扩展点盘点](./20261112-扩展点盘点.md)。

## 2. 从 DeepSeek Harness 学什么、不学什么

它底下的 Cordis 只能跑在 JS 里，而且是运行时装卸插件，我们的 Rust、Python 用不上（桌面壳主进程 10-22 已经用 Cordis 试过，
见 [desktop-cordis-pilot](../desktop-cordis-pilot/README.md)）。学它的规矩，不学它的形状。

**学：**

1. **一种能力 = 一份定义 + 多个实现 + 用的人只认定义。** 消费方不知道背后是哪家。
2. **能力写进清单，代码问能力、不问名字。** 禁止在插件目录以外写 `provider == "glm_ocr"` 这种判断。
3. **有第二个实现才抽接口。** 只有一种实现、以后也不会换的，不做成插件。
4. **配置先校验再启动，错了响亮失败、带路径**；配置分层（内置 < 部署 < 单次任务），能打印最终生效的那份。
5. **错误带稳定代码跨语言传**，代码表两边用测试钉住。
6. **每个扩展点一套可复用的契约测试**，每个实现传一个工厂进去跑一遍；测试替身就是一个普通实现（回放录好的响应）。
7. **关停有顺序**：先不接新活，再等手上的做完，最后关资源（11-02 重启杀掉 620 页任务就是缺这个）。

**不学：**

- 运行时热插拔、依赖消失后自动重建：我们是批处理任务，启动时组装一次就够。
- 一切皆插件的粒度（他们 374 个包，一项能力至少 3 个包）。
- 通用事件总线（他们自己承认顺序不直观、所有权难推理）。
- 配置里嵌脚本表达式；依赖缺了静默挂起；补丁匹配不到时静默跳过。
- 插件市场、按用户装插件：多用户和商业版 10-16 已停。

## 3. 分界线

| 做成插件（会有多种实现） | 留在内核（只有一种实现） |
|---|---|
| OCR 服务商、OCR 结果转换器 | 任务的创建、排队、续跑、失败恢复 |
| 翻译接口协议、服务商预设、翻译引擎 | 存储路径、产物出口 |
| key 校验探针 | 数据库、接口路由和登记表 |
| 渲染引擎、渲染模式 | 子进程的拉起和关停 |
| 导出格式 | 账号和权限 |
| 流水线阶段和子阶段（登记，不是可插拔的进程） | |
| 失败分类、术语表来源 | |

## 4. 插件在我们这里长什么样

### 4.1 清单：每个扩展点一份，所有语言读同一份

- 位置：`backend/config/<扩展点>.json`（OCR 已经有 `ocr_providers.json`），格式由 `contracts/` 里的 JSON Schema 定。
- **Rust 编译时嵌入**（`include_str!`），不再有手写的"找不到文件时的备用定义"；部署可以放一份覆盖文件按条目叠加
  （按 key 整条替换，加新条目），启动时校验，校验不过就启动失败并说明哪一条哪个字段。
- **Python 读同一份文件**（随包发布），同样不留手写备用定义。
- **命令行**经 Rust 包读，**前端**经接口读（例如 `GET /providers/ocr`），不再自己写一份。
- 清单里写**能力**（会不会一片片交结果、页数和大小上限、要哪把 key、能不能借翻译的 key、有没有 key 检测……），
  代码问能力。

### 4.2 接口和登记表

- **Rust：** 一个 trait 一张登记表。登记写在一个文件里、显式列出（不用 `inventory` 之类的链接期魔法，好查）。
  消费方拿 `&dyn Trait`，不再对枚举 `match`。
- **Python：** 已有的 `register_ocr_provider_driver`、`register_ocr_adapter` 这种登记表，推广到别的扩展点。
- **门禁：** 架构检查加一条——插件目录以外不许出现具体实现的名字（按扩展点登记允许的位置），
  清单、契约枚举、两边登记表必须一致（测试比对）。

### 4.3 契约测试

每个扩展点在 `backend/pipeline/devtools/tests/<扩展点>/contract/`（Python）或对应 Rust 包的 `tests/`（Rust）放一套
测试，参数是"一个实现"。加实现 = 在测试的实现列表里加一行 + 给它录一份回放数据。

### 4.4 外部插件（最后一步）

跨语言唯一干净的插件形式是**进程外插件**：一个独立程序，按 JSON 契约读输入、写输出。命令型 OCR 服务商
（GLM-OCR 就是这么接的）已经是这个样子。等前面几步定型，再把它写成正式协议，推广到导出格式等。

## 5. 步骤

每一步一个或几个分支，各自合并，旧行为不变，接口只增不改。哪一步不值了可以停，做完的部分各自有用。

| 步 | 内容 | 前端配合 | 做完的标志 |
|---|---|---|---|
| P0 | 本方案 + 扩展点盘点 | — | 合并 |
| **P1** | **OCR 服务商**（下面拆成 5 个分支） | 要 | 加一个命令型服务商只改：清单一项、Python 驱动、转换器、回放数据和测试一行 |
| P2 | 翻译接口协议和服务商预设：协议表、预设表各一份，Python、Rust 探针、Rust 执行器都读它 | 要（预设从接口读） | Rust 执行器能用 `openai_responses` 预设；预设表只剩一份 |
| P3 | 流水线阶段登记：阶段输入（stage spec）进契约；子阶段名单只剩一份 | 可能（进度显示） | Rust、Python 子阶段名单由同一份清单生成或比对 |
| P4 | 失败分类：Rust、Python 共用一张失败代码表 | 否 | Rust 兜底分类和 Python 取值一致，测试比对 |
| P5 | 渲染引擎和模式、导出格式、key 校验探针 | 要 | 默认值只有一处；加一个导出格式只改登记表一行 + 实现 |
| P6 | 翻译引擎、术语表来源 | 少 | 同上 |
| P7 | 外部插件协议（进程外插件） | 否 | 一个不在仓库里的 OCR 程序按协议接进来跑通 |

### P1 OCR 服务商拆成的分支

1. **P1a 清单成为唯一来源**：`ocr_providers.json` 加能力字段（一片片交结果、分片页数、页数和大小上限、key 怎么来、
   key 检测、文档链接）并写 schema；Rust 嵌入、Python 读同一份，删掉两份手写备用定义；命令行的服务商表改读清单
   （顺带补上 GLM-OCR）。
2. **P1b 按能力判断**：`ocr_streams_pages`、借翻译 key 等按名字判断的地方改成查清单；`GET /providers/ocr` 返回能力和上限
   （也就是接口评审里的 X2）；架构检查禁止插件目录外出现服务商名字。前端改读这个接口，删掉自己那份 `providers.ts`。
3. **P1c Rust 侧收口**：Rust 自己调的服务商（MinerU、Paddle 自建服务）收进一个 trait，`OcrProviderKind` 散在约 12 个文件里的
   `match` 收到登记表里；契约 `job-status` 的服务商字段从清单生成。
4. **P1d 契约测试**：一套 OCR 驱动 + 转换器的契约测试，每家服务商用回放数据跑一遍。
5. **P1e key 检测探针登记表**：`/providers/<服务商>/validate-token` 由登记表驱动，补上 GLM-OCR（接口评审里的 X5）。

## 6. 约定

- 对前端只增不改：旧字段、旧地址保留；前端要改的写进 `docs/core/frontend/backend-changes-handoff.md`，每步合并后通知前端会话。
- 每个分支照常跑 CLAUDE.md 里的全部合并前检查；动了翻译包就跑翻译测试正反两遍。
- 每一步完成后在本目录追加一份实现记录（`YYYYMMDD-<步>实现记录.md`），不改写本文件。
