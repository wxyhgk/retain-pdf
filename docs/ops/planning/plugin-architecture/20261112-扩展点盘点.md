# RetainPDF 后端扩展点盘点（为「改成插件式」做准备）

日期：2026-11-12；基于 main `cddaf3838`。只读盘点，没改仓库。
路径都相对仓库根。「文件数」是在今天的代码上加一个同类新实现、照现在的做法要碰的文件，
只算后端 + 契约 + 文档 + 测试；前端单列（前端由前端会话改，但它确实是成本的一部分）。

---

## 0. 总的规律（先看这个）

1. **已经有「注册表」的地方都只在 Python 一侧**：OCR 驱动 `register_ocr_provider_driver`（`ocr/ocr_provider/drivers.py`）、
   归一化适配器 `register_ocr_adapter`（`ocr/document_schema/adapters.py`）、命令型 OCR 从 `backend/config/ocr_providers.json`
   自动发现。Rust 一侧几乎全是硬编码 `match` / `const &[&str]`。
2. **跨语言的「同一张表」靠三种办法保持一致**，强弱不一：
   - Rust 测试 `include_str!` 读 Python 源码里的字面量对比（`retainpdf-core/src/models/input/translation.rs` 读
     `control_context.py`、`model_wire.py`、`workflow/execution.py`）——只覆盖 preparation 模式、接口协议、翻译引擎三张表；
   - 架构门禁（`check_failure_catalogue_covers_python_codes`、`stage_contract_duplicates.py`）；
   - 什么都没有，靠注释「与 xxx 一致」——这类已经出现漂移（见各节「痛点」）。
3. **契约每张枚举至少 4 份**：`contracts/*.schema.json` + `backend/contracts/*.schema.json`（逐字节镜像，`check_parity.py`）
   + `contracts/src/*.ts` + `contracts/dist/*.d.ts`；同一个枚举又常出现在 create-job / job-status / library-documents
   三个 schema 里，所以「加一个枚举值」在契约层就是 6～12 个文件。
4. **新请求字段要手工穿过 4～6 个 Python 入口**（`provider_pipeline.py`、`mineru_pipeline.py`、`book_pipeline.py`、
   `from_ocr_pipeline.py`、`translate_only_pipeline.py`、`translation_stage.py`），每个 +2 行 `getattr(args, ...)`；
   加翻译引擎、改默认渲染引擎时都是这样，漏一个就是默认值分叉（见 §6）。

## 1. OCR 服务商

### 1.1 现有实现
| key | 类型（`kind`） | 谁去调服务商 | 归一化 |
|---|---|---|---|
| `mineru` | remote | **Rust**：`retainpdf-data/src/ocr_provider/mineru/`（client/status/errors…7 个文件）+ runner `ocr_flow/mineru*.rs`（5 个文件） | Python `provider_adapters/mineru`（+ `mineru_content_list_v2`） |
| `paddle` | remote | 两条路：自建服务 / 官方 CLI 由 **Rust** 整份提交（`ocr_provider/paddle/`、`ocr_flow/paddle*.rs`）；官方 HTTP + 上传文件由 **Python** 按片并行（`paddle_chunked.py`，2026-11-01 起） | Python `provider_adapters/paddle` |
| `glm_ocr` | remote_command | **Python** `glm_ocr_driver.py` / `glm_ocr_api.py` / `glm_ocr_repair.py` | Python `provider_adapters/glm_ocr` |
| `local` | local_command | Python `local_command_driver.py`，命令来自配置 | `generic_flat_ocr` 等（`raw_provider`） |
| 配置里另加的命令型 | remote_command / local_command | Python `drivers.py::discover_configured_ocr_provider_drivers` 自动生成驱动 | 按 `raw_provider` |

### 1.2 选哪个由什么决定
- 请求字段 `ocr.provider`（字符串）。
- Rust：`retainpdf-data/src/ocr_provider/mod.rs::parse_provider_kind` 硬编码 `"mineru"|"paddle"|"local"` → `OcrProviderKind` 枚举；
  不认识但在配置里是命令型的（`is_configured_command_provider`）**一律当成 `OcrProviderKind::Local`**——GLM-OCR 就是走这个后门进来的。
- Paddle 内部再按 `ocr.options.transport`（official_http/official_cli）、`paddle_api_url` 是否为空、是否 `source_url` 分 Rust / Python 两条路
  （`retainpdf-core/src/models/job/questions.rs::ocr_streams_pages`）。
- 能力差异按字符串硬编码：`ocr_streams_pages` 里 `provider == "glm_ocr"`；借翻译 key 在
  `retainpdf-runner/src/job_runner/worker_process.rs`（`GLM_OCR_PROVIDER`、`ZHIPU_API_HOST = "open.bigmodel.cn"`）。

## 2. 翻译模型：接口协议、服务商预设、传输方式、引擎

### 2.1 接口协议（真正的「实现」维度）
- 实现：`openai`（/chat/completions）、`openai_responses`（/responses）、`anthropic`（/messages）。
- 选择：请求字段 `translation.api_protocol`（还有 `reviewer_api_protocol`）。
- Python：`backend/translation/retainpdf_translation/llm/shared/model_wire.py`（URL、请求体、思考字段、用量解析，各协议一组函数）+
  `llm/providers/deepseek/client.py:307` 的 `if anthropic / elif responses` 分支 + `workflow/execution_plan.py`（anthropic 提示词缓存）。
  `llm/shared/provider_registry.py` 有个注册表外壳，但只有一个 `DEEPSEEK_RUNTIME`，`resolve_active_provider_runtime()` 直接返回它——协议分支其实在 deepseek client 里。
- **同一组协议在别处又实现了 3 次**：
  - Rust 探针 `retainpdf-providers/src/provider_probe/deepseek.rs`（三种都有，注释「与 Python model_wire 一致」，URL 规整函数手抄）；
  - Rust 模型执行器 `retainpdf-providers/src/model_executor/policy.rs` 只会 `/chat/completions`，`lifecycle/validation.rs` 拒掉其他协议；
  - 翻译 agent `backend/translation-agent/.../agent.py` 写死 Anthropic Messages；`workflow/agent_flow.py` 再拼一次 messages URL。
- 取值表：Rust `retainpdf-core/src/models/input/translation.rs::TRANSLATION_API_PROTOCOLS`（有 include_str 守卫对 `model_wire.PROTOCOLS`）、
  `retainpdf-config/src/providers.rs::API_PROTOCOLS`（无守卫）、`backend/cli/src/cmd/setup.rs` 选项（无守卫）、契约 3 个 schema × 4 份。
- 加一个协议：Python 2～3 + Rust 探针 1 + 取值表 3 + 校验 1 + 契约约 10 + 文档/测试 4～6 ≈ **20 个文件**；若要 Rust 执行器也支持再 +3。

### 2.2 服务商预设（DeepSeek、Qwen、OpenAI、Anthropic、智谱、OpenCode、自定义）
- 预设表 2 份：Rust `retainpdf-config/src/providers.rs::MODEL_PROVIDERS`（命令行用）和前端 `frontend/web/src/platform/config/providers.ts`，文件头写「与前端一致」。
- 按主机名的特例散在两种语言：Python `model_wire.py::_auto_openai_thinking`（qwen3.8-flash@dashscope、glm-5.3-flash@bigmodel 的思考字段）、
  `deepseek/transport.py:117` 和 Rust `model_provider_headers.rs` **各一份** opencode.ai 会话头；`provider_identity.py`、`deepseek/client.py:163` 认 api.deepseek.com；
  Rust `worker_process.rs` 认 open.bigmodel.cn（借 key）；余额接口只有 DeepSeek（`/providers/deepseek/balance`）。
- 加一个预设：2 张表 + 0～4 处主机特例；**没有任何一致性检查**。
- 痛点：前端 11-01（`f73785a0d`）把预设协议全改成 `openai_responses`，Rust `MODEL_PROVIDERS` 仍全是 `"openai"`、命令行 setup 仍列 `/chat/completions`——
  注释说一致，实际已分叉；同时 Rust 执行器只支持 `openai`，前端新预设下 Rust 传输方式等于用不上。
  devlog 该行 follow_up：「DeepSeek、智谱、Qwen 和中转站是否支持 /responses 没核实」。

### 2.3 传输方式 `RETAIN_TRANSLATION_TRANSPORT=legacy/rust`
- 实现 2 个：legacy（Python 直接发 HTTP）、rust（Python 经 `llm/shared/rust_executor.py` 调 Rust `model_executor`）。
- 选择：Rust `worker_process.rs:206` 写死 `legacy`，有 `model_binding`（任务带 `translation.execution_connection` 且灰度打开）时改成 `rust`；
  Python `core/execution_policy.py`、`deepseek/client.py` 读环境变量。
- 加一种传输：要动 Rust worker_process、Python 执行策略、客户端分支、校验（`validation.rs` 里 execution_connection 的约束）、`stage_plan.rs`（refine 不支持 Rust 执行器）≈ 6～8 个文件。
- 这是内部实现选择，不是用户面扩展点，不建议插件化；但它把「协议」的支持矩阵变成了二维（协议 × 传输），目前只有 openai×rust 一格可用。

### 2.4 翻译引擎 `translation.engine = legacy / agent`
- 选择：请求字段；Python `workflow/execution.py::TRANSLATION_ENGINES` + `execution_runner.py` 分支；Rust `TRANSLATION_ENGINES`（include_str 守卫读 execution.py）。
- 引擎特有规则散在两边：Rust `lifecycle/validation.rs:247`（agent 要求 anthropic）、`worker_command/stage_specs.rs:201`（agent 时跳过自动精修）；
  Python `execution.py:97`（只有 legacy 能跟着 OCR 流式翻）、preparation 按 off 处理。
- 加 agent 的实际成本（`099fc608d`）：**约 48 个文件**——契约 3 个 schema × 2 + ts 4、Rust core 6、jobs 3、data 1、6 个 Python 入口各 +2 行透传、
  `engine_identity.py`、`checkpoint/identity.py`、`usage_ledger.py`、`revision.py`、架构检查 2、`submissions.txt` 快照、uv.lock。
- 痛点：`fix/agent-engine-skip-extras`（10-30）——「engine=agent 时译前准备、翻译后自动精修照跑、**重复花钱**」，就是引擎的「不需要哪些步骤」没有集中声明，Rust 和 Python 各漏了一处。

### 4.2 渲染模式 `render.mode`（auto/overlay/typst/typst_visual/dual）

| 粗/细阶段名 | `retainpdf-core/src/models/job/stage.rs`：`JobStage` 枚举（含 `MineruUpload`/`MineruProcessing`）+ `public_stage_for_substage`、`public_stage_for_raw_stage`、`event_progress_unit` 三个 match 列表 |
| 解析 stdout | `job_runner/stdout_parser/stage_rules.rs` |
| 重试/续跑 | `retainpdf-jobs/src/views/job_types.rs::RetryStageKind`、`actions/stage_plan.rs`、`actions/stage_retry.rs`、`job_failure_catalogue.rs::ResumeFrom` |
| 失败归类按阶段 | `retainpdf-core/src/models/job/failure.rs::infer_failure_category`（按 stage 字符串兜底） |

### 5.3 Python 一侧
- `foundation/shared/stage_specs.py`：每种 spec 一个 dataclass + `schema_version` 校验（`domain_prewarm` 的在 `translate/entrypoints/domain_prewarm.py`）。
- `backend/base/retainpdf_base/events.py`：`_OCR_STAGES`、`_TRANSLATE_STAGES`、`_RENDER_STAGES`、`_PAGE_PROGRESS_STAGES`、`_BATCH_PROGRESS_STAGES`。
- 每个阶段的 `__main__.py` + `run_with_structured_failure(default_stage=...)`。

### 5.4 加一个阶段（或子阶段）要改
- 新阶段进程：Python `__main__`/入口 1～2、`stage_specs.py` 1、`console.py` 1；Rust `entrypoints.rs`、`stage_specs.rs`、`stage_commands.rs`、`process_contract.rs`、
  `stage.rs`、runner 编排 1～2、`stdout_parser` 视情况；若可重试再加 `job_types.rs`、`stage_plan.rs`、`stage_retry.rs`、契约 `job-actions`/`job-status` 各 4 份、
  `docs/core/rust_api/11-阶段事件与失败协议.md` → **约 15～20 个文件**。
- 只加一个子阶段（如 `garbled_repair`、`refining`）：Python `events.py` 2～3 个集合 + Rust `stage.rs` 3 个 match（+ `ocr_flow/support.rs` 的列表）≈ 3 个文件、6 处，**无守卫**。
- 跨语言重复：stage spec 是「Rust 手写 json! 写、Python dataclass 读」两份，**`contracts/` 里没有 stage spec 的 schema**；子阶段表两份且已不一致
  （Rust 有 `render_prewarm`/`render_pages`/`render_compile`/`refining`，Python 的 `_RENDER_STAGES` 没有；Rust `event_progress_unit` 把 `agent_repair`、
  `final_untranslated_recovery` 当按页，Python `_PAGE_PROGRESS_STAGES` 没有它们）。
- 痛点：`fix/parallel-render`（10-31，加并行阶段后翻译成功就写库、渲染不跑）、`fix/ocr-stage-from-child`（11-02，子任务阶段状态按先后推错）、
  `JobStage` 里服务商专属阶段（`mineru_*`）让「OCR 阶段」不中立。

## 最值得插件化的 3 个

1. **OCR 服务商**：增长最快（11 月刚接 GLM，书按段的方案还会再动），实测一家 64 个文件；定义有 4～5 份且已漏（命令行、契约枚举、探针）。
   已有命令型服务商 + Python 驱动/适配器注册表打底，只差把「能力」（流式公布、分片页数、页数/大小上限、凭据与借 key 规则、探测方式、展示名、文档链接）
   写进 `ocr_providers.json` 一份清单，Rust 内置副本/Python 内置副本/命令行表改成读它，前端改读 `GET /providers/ocr`（只增不改）。
2. **翻译接口协议（连同服务商预设）**：同一组协议实现了 4 遍（Python、Rust 探针、Rust 执行器、agent），预设表两份已分叉，Rust 执行器只支持前端已经不用的协议。
   做成一个协议适配器接口（Python 一份为准）+ 一份预设清单 JSON（含主机特例：思考字段、额外请求头、余额接口），探针改为调同一份实现或读同一份规则。
3. **流水线阶段登记**：阶段/子阶段/stage spec 在 Rust 与 Python 两边手抄，子阶段表已经不一致、stage spec 没有 schema；近一个月加了渲染准备、领域预热、
   精修、OCR 流式、并行等多次，每次都出过阶段显示或收尾 bug。一份 `contracts/stages.v1.json`（阶段、子阶段、所属大阶段、进度单位、进程入口、spec 版本、可否重试）
   生成或校验两边，收益是消掉一整类漂移；它更像「清单驱动」而非运行时插件。
