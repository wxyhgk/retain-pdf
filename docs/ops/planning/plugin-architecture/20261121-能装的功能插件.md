# 能装的功能插件

2026-11-21。用户说后面要加笔记、文献管理、划线，「还有比较重要的就是插件系统」；问是哪一种插件时，用户选了
**能装能卸的功能插件**（像 Obsidian、Zotero 的插件）。

## 和以前的决定是什么关系

- [后端插件化总方案](./20261112-后端插件化总方案.md)（11-12）只做**内部能力可替换**（OCR、翻译、渲染、导出格式按清单登记），
  并写了「不学运行时装卸、不做插件市场」。那一份照做（P1a、P1b 已合并），它是本文件的底座；**「不做运行时装卸」这一条对功能
  插件这一层改了**，对内部能力那一层不变（内置的 OCR 服务商照旧编译进去、启动时组装）。
- 前端的[功能登记表](../frontend-migration/20261112-功能登记表.md)（11-12）当时说「不做完整插件系统，它的好处要在外人写功能、
  用户自己开关功能时才兑现」，并留了后路：「真要插件化时把表里引进来换成运行时注册」。现在这两个条件成立了，登记表就是
  插件往界面里加东西的地方。前端那一半由前端会话做，这里只写后端要提供什么、以及交接给前端的约定。

## 三层

| 层 | 是什么 | 谁写 | 跑在哪 |
|---|---|---|---|
| 1. 内部能力 | OCR 服务商、翻译协议、渲染引擎、导出格式……按清单登记的多种实现 | 我们 | 编译进后端 / 流水线 |
| 2. 进程外程序 | 一个独立程序按 JSON 协议读输入写输出（11-12 方案的 P7；命令型 OCR 服务商已经是这样） | 我们或别人 | 后端拉起的子进程 |
| 3. **功能插件** | 往阅读页、书库里加面板、按钮、命令；存自己的数据；在「导入一本书」「翻译完成」「划了一条线」时做事 | 别人 | 前端（网页 / 桌面版），通过后端接口办事；可以附带一个第 2 层程序 |

功能插件是用户能装能卸的单位：一个插件 = 一个文件夹（清单 + 前端代码 + 可选的第 2 层程序）。

## 插件清单 `retainpdf-plugin.json`

```json
{
  "id": "com.example.citation-cards",
  "name": "引用卡片",
  "version": "0.3.0",
  "api": 1,
  "permissions": ["library.read", "notes.write", "annotations.read"],
  "contributes": {
    "reader.panels": [{ "id": "cards", "title": "引用卡片", "entry": "dist/panel.js" }],
    "library.commands": [{ "id": "export-cards", "title": "导出引用卡片" }],
    "settings.sections": [{ "id": "main", "entry": "dist/settings.js" }],
    "item_types": [{ "id": "card", "title": "卡片" }],
    "events": ["item.created", "annotation.created", "job.finished"],
    "data": { "sync": true }
  },
  "backend": { "command": ["bin/cards-helper"], "protocol": "retainpdf-process/1" }
}
```

- 格式由 `contracts/` 里的 JSON Schema 定，装的时候先校验，错了说清是哪一项。
- `api` 是插件接口的大版本；后端只装认得的版本，不认得就拒绝并说明。
- `contributes` 里的各项对应前端登记表的各个口子（设置分栏、书籍详情页签、阅读页面板、书库命令……），哪些口子开放由前端定，
  清单 schema 跟着加。

## 权限：后端说了算

插件的前端代码跑在沙箱里（iframe / Worker，前端定），但**不能只靠前端拦**：插件办事一律走后端接口，后端按权限放行。

- 装的时候列出插件要的权限，用户同意才装；之后在设置里能看、能收回。
- 每个启用的插件有**自己的访问令牌**，只带它被授予的权限；后端每个接口在登记表里本来就写了谁能用（`public`/`signed`/`admin`/`closed`），
  再加一列「插件要哪个权限」，没登记的接口插件一律不能调。
- 权限按「读什么 / 写什么 / 花钱的 / 碰外面的」分：

| 权限 | 能做什么 |
|---|---|
| `library.read` | 读书目、文件信息、文件夹、标签 |
| `library.write` | 改书目、标签、文件夹 |
| `notes.read` / `notes.write` | 笔记 |
| `annotations.read` / `annotations.write` | 划线和批注 |
| `files.read` | 读原文 PDF、译文、版面结果的内容 |
| `jobs.read` | 看任务和进度 |
| `jobs.create` | 发起翻译（**花用户的钱**，单独提示） |
| `network` | 插件自己的前端代码联网（沙箱默认不让） |
| `process` | 拉起插件附带的第 2 层程序（**能做任何事**，装的时候醒目提示，只建议装信得过的） |

- 插件的数据（`plugin_data`）不需要权限：只能读写自己名下的。

## 后端要提供什么

1. **插件登记**：数据库 `plugins` 表（编号、版本、启用、授予的权限、装的时间、从哪装的）；插件文件放数据目录 `plugins/<编号>/`；
   接口：列出、从本地文件夹或压缩包装、启用/停用、卸载（可选连数据一起删）、读清单。
2. **按插件的令牌和权限检查**（见上）。
3. **条目接口**：书目、文件、笔记、划线、标签、文件夹的增删改查——本来就要给前端做（[书库条目模型](../database-redesign/20261121-书库条目模型.md)
   的 5a–5e），插件用的是同一套，不另开一套。
4. **插件数据接口**：读写 `plugin_data`（按插件、按条目、按键）。
5. **事件**：插件订阅书库和任务的变化。书库加一个**变化流**（`item.created/updated/deleted`、`annotation.created`……，带序号，
   断线后从序号接着读），任务沿用现有的进度事件。**事件只通知、不拦截**：插件不能卡住或改写核心流程（导入、翻译、导出）；
   要「改写导出结果」这类能力，以后按第 1 层的扩展点（导出格式）单独开口子。
6. **第 2 层程序的协议**（11-12 方案的 P7）：插件附带的程序由后端按需拉起，按 JSON 协议收发，关停有顺序。

不做：插件直接执行 SQL、插件改别的插件的数据、插件阻塞核心流程、多用户下按用户装插件（多用户已冻结，插件按这台机器装）。

## 步骤

插件的后端几步要等书库条目模型的 5a、5b 做完（插件读写的就是条目），可以和 5c 以后穿插着做。

| 步 | 内容 | 前端配合 |
|---|---|---|
| Q0 | 本方案 + 清单 schema 草稿 | 前端看口子列表 |
| Q1 | 插件登记：`plugins` 表、装 / 卸 / 启停接口、清单校验 | 要（设置里的插件管理页） |
| Q2 | 插件令牌和权限：接口登记表加「插件权限」列、门禁测试 | 要（沙箱和令牌传递） |
| Q3 | 插件数据接口（`plugin_data`） | 少 |
| Q4 | 书库变化流 + 插件订阅事件 | 要 |
| Q5 | 第 2 层程序协议（即 P7） | 否 |
| Q6 | 一个示范插件（例如「划线导出成 Markdown 笔记」），装、用、卸、数据同步走一遍 | 要 |

## 要定的

1. **插件用什么语言写**：前端部分只能 JS/TS；附带的程序随便什么语言（按协议）。要不要另外支持 WASM 这种不用装运行环境、
   能关进沙箱的后端插件，等 Q5 时看有没有需求。
2. **从哪装**：先只支持本地文件夹 / 压缩包；插件市场、签名、自动更新以后再说。
3. **插件能不能加自己的条目类型**：清单里留了 `item_types`（条目主表的 `plugin:<编号>/<类型>`），Q3 时定要不要开放。
