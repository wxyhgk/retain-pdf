# 改译文按旧译文比对（第 3 步之一）

> 日期：2026-11-25
> 分支：`feat/revision-expected-text`
> 起因：[AI 怎么拿到书的数据](./20261124-AI怎么拿到书的数据.md) 第 3 步：`PATCH` 加 `expected_translated_text`，服务端比对旧译文，
> 关掉 agent「先读再写」之间的竞争窗口。用户 2026-11-25「开始做」。

## 为什么不用现有的 `expected_generation`

agent 读的是书文件夹里的 Markdown，只有锚点（块编号、源任务、页码），没有检查点代次；`expected_generation` 还是整份译文一个数，
别的块改了也会让这一块的写回失败。按这一块的内容比，只在这一块真被改过时才拒。

## 做法

- 请求体加可选的 `expected_translated_text`（上限和 `translated_text` 一样 20000 字）。Rust 只转给翻译包的写回进程。
- 比对在翻译包 `workflow/revision.py` 里、持着检查点锁、读出当前页之后、校验新译文之前做（`_check_expected_text`），
  和写回在同一把锁里，没有窗口。
- 比的时候去掉所有空白：书文件夹导出把多行压成一行（`one_line`），首尾空白也不算数。中文里多一个、少一个空格就当成同一句，
  这对「有没有人改过」的判断无害。
- 两种写法都认：存储形式 `protected_translated_text`（占位符模式下带占位符）和展示形式 `translated_text`；调用方读到的那句
  也按 `_protected_form` 换一次占位符再比。
- 对不上：409 `TRANSLATION_REVISION_CONFLICT`，`reason = text_mismatch`，`details.current_translated_text` 是当前的展示形式，
  agent 拿它重读再改。什么都不写。
- 不带这个字段时行为不变；前端编辑框不带（用户自己在改，不需要）。

## 改了哪些

- 翻译包 `revision.py`（`RevisionRequest.expected_translated_text`、`_check_expected_text`），流水线入口
  `entrypoints/revise_translation_item.py` 从标准输入读它；Rust `ReviseTranslationItemRequest` 加字段、冲突时带出 `current_translated_text`。
- 契约 `translation-revisions.v1` 两份副本：请求加字段、原因加 `text_mismatch`、错误详情加 `current_translated_text`，重新生成。
- 文档 `docs/api/08-调试诊断/02-translation-debug.md`。
- 测试：翻译包单测（空白不同照样对得上、被改过就拒且不写、不带不比、命令行入口），rust_api 端到端一条。
