# 表格翻译 T0：摸底

**日期：** 2026-11-12
**工具：** `backend/pipeline/devtools/table_survey.py`（只读，只出计数，不输出文档内容；同一份原文被多个任务做过 OCR 只算一次）
**数据：** 本机开发环境 `data/jobs` 下已有任务的 OCR 结果和原文 PDF（不进仓库）。39 份不同的文档、共 12746 页，其中 31 份有表格。

## 2. 表格来源：三类，不是两类

| 来源 | 张数 | 怎么判断 | 格子的位置和原文从哪来 |
|---|---|---|---|
| 有文字层 | 2494（80.7%） | 表格框里读得到 ≥3 个词 | 文字层 |
| **字转成了曲线** | 436（14.1%） | 没有文字层、没有图片，但框里有 ≥300 段矢量路径 | 只能看图或用 OCR 的行框 |
| 图片 | 147（4.8%） | 没有文字层，框里有图片 | 只能看图或用 OCR 的行框 |
| 判断不了 | 15（0.5%） | 以上都不像 | — |

"字转成曲线"是方案第一稿和第二稿都没想到的一类：看着是字，在 PDF 里是图形（集中在一本手册，横排页上尤其多）。
**将近两成的表读不到文字层**，看图这条路必须做（和用户"所有协议都要能看图"的决定一致）。

旋转页上 OCR 的框和 PDF 内容的坐标可能差一个旋转，判断时两种坐标都要看（只看一种时 301 张被误判成"判断不了"）。

## 4. 对方案的修正

1. **T1 表格模型**：来源分三类（`text_layer` / `vector_paths` / `image`）；旋转页的坐标要处理；"字转曲线"的格子位置和
   图片表一样从 OCR 行框或看图来。
2. **T5 放回**：字转曲线的表要盖掉矢量字形但**保住表格线**（表格线也是路径，要把又细又长的线段和字形分开）；图片表要
   估底色再写。三类各有一种"盖原文"的办法。
3. **续表**：比想象的集中（基本在一本手册），但那本书有 291 张；放在 T6 不变，评测集里要有。
4. **成本**：一本书上千张表时，"一张表一个 agent 任务"要配：小表打包成一次请求、按表格内容缓存、整本的预算上限和进度。
   写进 T3。
5. **评测集**要专门补：MinerU 的样本（本机没有）、字转曲线、横排页、图片表、续表。

## 5. 评测集怎么建

- **进仓库的部分**：只用仓库里已有的公开样例 PDF（`tests/fixtures/pdfs/`）。按表题找到有表格的页：
  `d3cs00837a-69p.pdf` 35 页（化学综述，表格多）、`babeldoc-10p.pdf` 4 页、`cr5c00021-55p.pdf` 4 页、`2.pdf` 3 页、
  `1.pdf` 2 页、`s41524-tibetan-plateau-21p.pdf` 2 页、`navier-stokes-166p.pdf` 1 页、`yakubenko-halogen-lithium-10p.pdf` 1 页，
  共约 52 页。这些页要先跑 OCR（GLM-OCR 和 PaddleOCR 各一遍，要花钱，跑之前先问用户），OCR 结果和人工标注进仓库。
- **合成的部分**：公开样例里没有横排页、字转曲线、图片表、续表，用脚本生成带标准答案的 PDF（格子位置、该翻 / 不翻都已知），
  结构和位置可以精确打分。T1 里做。
- **本机的部分**：本机用户的书只在本机跑评测、只出计数，不进仓库。
