# 翻译状态管理审查（2026-11-26）

## 为什么查

一位 Windows 桌面用户的 1000 多页的书续跑时整本失败，报
`Translation checkpoint completed items regressed to pending: p028-b003, …`。

- 直接原因：续跑重新拼段，把已译块和未译块拼成了一组。已在 `fix/translate-resume-regroup`（PR #224）修了。
- 这个守卫 2026-11-03 已经误报过两次，同类问题反复出现。
- 用户：「状态管理很重要，我们需要着重设计」。

## 怎么查的

5 个 Sonnet 子代理分头只读审查，用的是含 #224 修复的快照 885d8f501：

| 编号 | 方向 |
|---|---|
| A | 断点契约和会话（`workflow/checkpoint/`） |
| B | 接续段、翻译单元和组 |
| C | Rust 侧的任务状态、重试续跑、断点导入 |
| D | 块级翻译状态的生命周期：重翻、死信、定译、两个引擎 |
| E | 落盘和 Windows |

- 复现测试放在临时目录，没有进仓库。
- 汇总时我重跑了这些复现，下面标「复现」的都看过结果。
- 标「读码」的，我逐条对过代码位置。

**证据等级的含义**

| 标记 | 意思 |
|---|---|
| 复现 | 用真实函数在最小数据上跑出了错误结果；没跑真流水线，没调真模型 |
| 读码 | 读代码确定，没有单独复现 |
| 推测 | 机理成立，但触发条件没证实 |

## 发现（按严重程度）

### 一级：整本失败、整本白花钱，或者停不下来

1. **agent 引擎的任务续跑，每次都报 regressed。**（A、D 各自独立发现，复现）
   - agent 引擎在 `prepare_book_payloads` 之后，自己把三类块标成保留原文：`skip_no_prose`、`skip_running_header`、`skip_back_matter_index`。
   - 续跑时，页面策略的 `reset_policy_state` 只豁免 `skip_model_keep_origin`，其余 `skip_*` 一律打回「要翻」。
   - 于是 `update("policy_ready")` 抛 regressed。agent 的 skip 要在这之后才重新跑，所以每次重试都在同一处失败。
   - 有书后索引的书，几乎整个索引都会触发。
   - 只影响 agent 引擎，默认的 `legacy` 引擎不受影响。
   - 位置：`services/policy/payload_rules/policy_mutations.py:22`；`translation-agent/.../agent_flow.py:310-360, 746-749`。

2. **模型产出的东西进了续跑指纹，一变就整本丢弃。**（A、D、E 各自独立发现，复现）
   - `identity.py` 把下面几样放进了指纹：
     - `vars(policy_config)`，其中含领域识别结果 `domain_context`；
     - 目录 agent 的定译 `fixed_translations_sha256`。
   - 指纹翻转的两种情况：
     - 第一次识别或目录 agent 失败（结果为空，且不写缓存），重试时成功；
     - Rust 导入断点时不拷 `toc-agent.v1.json`、`style-guide.v1.json`、`term-base.v1.json`，新任务重新跑一遍，结果不逐字节一致。
   - 后果：
     - 跨任务续跑：`discard_copied_resume_candidate` 删掉所有已译页，从头翻。只打一行 stdout，用户看不到提示。
     - 同一任务内续跑：报 `fingerprint mismatch within the same attempt`，以后永远失败。
   - **和 #224 直接相关**：#224 修了 Windows 领域识别（SIGALRM）以后，Windows 上 sci 模式的旧失败任务升级后重试，领域识别第一次真正成功，指纹必变，整本重翻。那位用户的书大概率就是这个结局。

3. **加载页文件时，按「`$` 不成对」静默抹掉已完成的译文。**（D、E 各自独立发现，复现）
   - 位置：`core/payload/template_contract.py:57-83` 的 `sanitize_loaded_translation_record`，每次续跑加载每页时都会调用。
   - 它数 `$` 时不排除代码段。agent 的校验是排除代码段的，所以像 `` `echo $HOME` `` 这样的译文能通过 agent 校验。
   - 一旦判为不成对，就清空 6 个译文字段，块变回待办，报 regressed；还会落盘覆盖原文件。
   - 程序员向的书（shell、正则、Makefile）都会触发。

4. **Windows 上点取消，worker 不会停。**（C，读码）
   - `retainpdf-proc/src/lib.rs:172`：非 unix 平台上 `worker_process_exists` 恒为 false。
   - 后果：取消、jobsd 终止、启动对账、退出清理全都认为进程已死，不去杀它。
   - 数据库已经写成 Canceled，但 Python worker 可能继续调模型花钱、继续写断点，一直到写 stdout 失败或撞上 1800 秒的超时。

5. **重试链悄悄丢断点。**（C，读码）
   - `translation_checkpoint_resume.rs:47`：源任务没有断点文件时直接返回 false。重试只看「上一个任务」。
   - 链上只要有一环没留下断点（排队时取消、准备阶段出错），再重试就整本从头翻，而且不提示。
   - 「结果不明要确认」用的请求日志也在这里断掉。

6. **断点导入失败或断点内部不一致时，用户没有出路。**（C，读码）
   - 导入出错时用 `?` 直接让整个任务失败，每次重试都拷同一份，所以每次都同样失败。
   - 重试请求里没有「丢弃断点、重新翻」这个选项。
   - 这类错误落到兜底分类 `python_unhandled_exception`，提示写着「重试会从头开始」（这句是错的），而且标成可重试，诱导用户反复点。

### 二级：不报错，但译文错了或者重复了

7. **组里有不翻的成员时，写回把译文截掉一段。**（B，复现）
   - 位置：`core/payload/parts/apply.py:312-326`。发给模型的只有要翻的成员，写回时却按全部成员切分。分给不翻成员的那段被扔掉。
   - #224 新加的 `keep_translated_blocks_out_of_mixed_groups` 也把不翻的成员算进切出来的段，会出现同样的截断。**#224 要补上这一点。**

8. **被挪出组的块，成员级译文是空的，渲染时退回整组译文，同一段排两遍。**（B，复现）
   - 这是 #224 的残留：修复前这里直接报 regressed，修复后变成静默重复。

9. **跟着 OCR 翻时，扣住的「页尾那一段」不对。**（B，复现）
   - 位置：`translation-classic/.../streaming_flow.py:57-76`。
   - 两种情况：
     - 双栏页取的是载荷里最后一块，不是右栏最后一块；
     - 隔着只有图或表的页时不扣。
   - 后果：段落先被翻掉，下一页到了又要拼。修复前报 regressed，修复后变成一段话被切成两半各自翻。

10. **最终补救按单块补救接续组成员，喂给模型的却是整组原文。** 结果每块都拿到整段译文，版面上排两遍。（B，复现）

11. **agent 引擎**（B、D，复现和读码）：
    - 组里一块成了死信，它会带上同组另一块的整组译文，渲染出别人的译文。
    - 续跑时按页状态文件回放：用户手改过的译文会被盖回去；死信永远不重试。
    - 状态指纹不含术语表和定译。

12. **跟着 OCR 翻的断点，身份里不含 OCR 内容。** OCR 重做、换引擎后，旧译文会挂在变了的原文上。（A，复现）
    - `resumes_streamed_attempt` 的说明写着「按条目指纹核对」，但实际上没有核对原文。

13. **Windows 上的原子写入一律没有重试。**（E，读码；模拟了抛出 PermissionError）
    - 涉及：断点、页文件、manifest、memo、domain-context、OCR 流式清单，以及 Rust 导入时的拷贝和改名。
    - 杀毒软件或索引器短暂占用文件，就会抛 `PermissionError`，整个任务失败。
    - `prune_snapshots` 删除失败也会让任务失败。

### 三级：统计不准、偶发，或者是隐患

- 守卫把「已有页上第一次出现的新块」当成回退（A，复现）。
- 断点的页集合可以悄悄变少：进度倒退，快照被清（A，复现）。
- 单成员接续组不进待办名单，进度显示「全部完成」，实际还有一块没译（A，复现）。
- `published_page_hash` 跨任务继承，新任务的库里少登记了页（A，复现）。
- 每次 `acquire` 都把已完成的断点降成 `preparing`（A，复现）。
- 死信后来翻成功了，诊断里的死信标记却不清，导致 `dead_letter_count` 多算（D，复现）。
- 手改译文后，manifest 里的汇总不更新（D，读码）。
- 标题的 `translation_style_hint` 每次续跑追加一次，不去重（D，复现）。
- 每次提交断点的开销随全书页数线性增长：1000 页时一次约 0.85 秒，断点文件 3.2 MB（E，复现）。
- Rust 起 worker 的几处没设 `PYTHONUTF8=1`。不经桌面壳启动时，Windows 上 stdout 走 cp936（E，复现）。
- 启动对账时重新排队用的是整行覆盖，不是 CAS，可能把用户刚取消的任务改回排队（C，读码）。
- 流式 GLM 任务的自动续跑没有补回 OCR 产物（C，推测）。
- `connection_fingerprint` 含并发数、`revision`、凭据，以后启用后改并发数就会让所有断点作废（A、E，读码）。

## 根本问题（5 份报告的共识）

1. **派生值被当成真相存下来，再拿来做守卫。**
   - 断点里的 `pending_item_ids` 是 `project_progress` 按当时的分组、策略、标签算出来的。
   - 下一次续跑拿另一种口径算出的结果和它比，任何口径变化（重新分组、策略重置、版本升级、加载时清洗）都会被当成「丢了译文」。
   - 2026-11-03 和这一次的事故都是这一类。
2. **「这块翻完了没有」至少有 5 套判定。**
   - 断点、导出门禁、汇总统计、渲染、加载清洗各算各的，看的字段也不同。
   - 单看每处都对，组合起来互相矛盾。
3. **模型产出的决定每次续跑都重算。**
   - 包括：领域、目录定译、拼段复核、分组、引擎自己的 skip、分类。
   - 模型不是确定的，所以续跑时状态会变；变了以后，要么指纹不符整本作废，要么守卫报错整本失败。
4. **守卫只有两种结局：放过，或者整本失败。** 没有「调和」这一步，同一任务内也不能自愈。
5. **持久化层缺三样东西**：
   - Windows 上的统一重试；
   - 断点只有一份，没有 `.prev` 可以回退；
   - 加载路径不是只读的。
6. **Rust 和 Python 对断点各管一半，续跑协议是隐式的**：靠导入时去「上一个任务」的目录里顺手找。

## 设计方向（等用户定）

**块状态**
- 每块存一个显式的 `state`：`pending`、`translated`、`kept_origin(owner=policy|engine|model)`、`dead_letter`、`blocked`。
- 另存「译文是按哪段原文、哪个分组译出来的」的指纹。
- 所有写入都走一张转换表；转换时顺带清掉这个状态下不该留的字段。
- 断点、门禁、汇总、渲染都只读 `state`。

**守卫**
- 改成基于事实的不变量：「对同一份原文已经有结果的块，不能丢掉结果」。
- 待办名单只用于展示，现场计算，不再拿来比较。

**冻结模型产出的决定**
- 领域、定译、术语、拼段复核结论、已译块的分组归属、引擎 skip、模型判的保留原文。
- 第一次产生就写进断点目录，和断点一起带到新任务，续跑只读不重算。

**一个调和入口**
- 读盘之后、第一次提交之前，统一处理：
  - 原文变了的块清掉结果；
  - 已完成的块在策略重置后仍然保持完成；
  - 重新分组时不拆开已完成的单元。
- 所有会改页的步骤（策略、引擎 skip、分组）都从这一个入口进。
- 加载路径改成只读。

**指纹分层**
- 硬输入（原文、模型、提示词版本、模式）不符：才是真正不同的任务，走「隔离旧译文 + 提示用户」，不删。
- 软输入（并发、超时、凭据、规则版本）不符：只记录，不影响续跑。

**续跑协议（Rust）**
- 新任务里显式记 `resume_from`，重试链上沿它往回找最近一个有断点的祖先。
- 导入改成原子操作：钉住一份副本、校验、再发布。
- 重试时给用户「丢弃断点重新翻」的选项。
- 新增一类错误 `checkpoint_state_inconsistent`：不可重试，提示写对。

**取消**
- 由 runner 在 `wait_with_limits` 里自己杀进程树。
- Windows 实现 `OpenProcess`、`GetExitCodeProcess`。

**持久化**
- `retainpdf_base` 里放唯一一个 `atomic_write`：带 Windows 退避重试和 fsync。
- 断点保留 `.prev`。
- 提交只处理脏页。

**测试**
- 续跑测试要跑过页面策略阶段，两个引擎都要覆盖。
- 指纹稳定性测试：模型成功和失败两种情况下，指纹要么相同，要么被明确归类。
- Windows runner 上跑断点存取、原子写重试、进程判断这几组。
