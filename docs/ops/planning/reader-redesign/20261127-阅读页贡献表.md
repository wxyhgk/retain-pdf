# 阅读页贡献表

2026-11-27。

## 为什么

用户（2026-11-27）：「阅读页面，我觉得得重新设计，目前的这种把阅读页面写死了，想一想方案」。

看了代码，「写死」有四处：

1. 十几个功能（查找、画笔、提问、Markdown、放大、交叉引用、改译文、版本对比、实时翻译、下载、工具球、文档暗色）都直接接在
   `ReaderAppReactPdf.tsx` 里（当时 685 行），共用一个约 30 个字段的 reader context；加一个功能就要改主组件、context、根节点 class。
2. 面板、浮层的位置写死（查找在左、助手停靠在右、工具球、HUD、提问窗各一处），不能挪、不能浮出来、不能并排。
3. 整个阅读页围着「翻译任务」转：入口是 `job_id`，栏是原文 / 译文，没翻译的 PDF 走 `sourceOnly` 特例；书库要改成条目模型
   （[书库条目模型](../database-redesign/20261121-书库条目模型.md)），以后有笔记、高亮、引用管理。
4. 没有口子：右键菜单项、页边的「?」、页面叠层都只为提问写了一份，别的功能接不进来；而能装的功能插件用户 11-21 定了要做
   （[能装的功能插件](../plugin-architecture/20261121-能装的功能插件.md)）。

方案给用户看过，分三层：文档核心（不画界面，翻译只是一层数据）、页面视图（每页一叠登记进来的层）、工作台外壳（面板停靠 / 浮动）；
三层之间靠一张**贡献表**连起来，现有功能都改成用同一套接口的内置扩展。用户定先拆主组件（同日做完，`src/app/`），
再「阅读页面部分的设计先做贡献表」。

## 定了什么

和 11-12 前端的[功能登记表](../frontend-migration/20261112-功能登记表.md)同一个思路：功能写在自己的目录里，阅读页只认一张表。
不同的是阅读页的贡献跟着 React 状态变（问过哪几页、右键这一下问的是哪儿），所以**扩展是组件**，挂上以后用 hook 把贡献登记进表；
扩展本身照旧写在一个静态列表里（`extensions/builtin.ts`，一个功能一行），好查、好删、类型检查和打包照常。
将来的功能插件就是「列表里多出来的、从清单装进来的扩展」，口子不用改。

### 扩展和接口（`packages/reader/src/extensions/`）

- `ReaderExtension = { id, title, Component }`。组件挂在阅读页根节点里浮层的位置，**画出来的就是它的浮层**（浮动窗口……），没有就 `null`。
- `useReaderApi()`：扩展能看到、能用的阅读页——书（`documentId`、`jobId`、`versionId`）、块和目录（`regions`、`metadata`、`bookmarks`）、
  `pageCount`、`resetKey`（换书时变）、`hoveredItemId()`、`goToPage()`。按扩展的真实需要加，不预先铺开。
- `useReaderContribution(contribution)`：登记自己的贡献，换了就替换，扩展卸下就拿掉。

### 第一期的口子

| 口子 | 形状 | 阅读页在哪画 |
|---|---|---|
| `menuItems(context)` | 右键书页那一下同步算出菜单项（`{target, clientX, clientY, page}` → `[{key, label, hint?, onSelect}]`） | 右键菜单画笔那一排上面；key 前面加扩展名 |
| `pageLayer({page, height})` | 每一页上叠的一层 | 每页（`PdfPageSlot`），按扩展顺序 |
| `shortcuts` | `[{keys, desc}]`，只是说明；按键扩展自己监听 | 快捷键说明里单独一组，组名是扩展的 `title` |

顺序是扩展第一次登记的顺序（内置列表里的先后），之后改内容不挪位置。一个扩展渲染出错只丢掉它自己（出错边界），算右键菜单出错
就跳过它，阅读页照常。

### 第一个扩展：提问

`ask/ReaderAskExtension.tsx`：宿主给了 ACP 端口才登记。右键「在这里提问 / 问这段」走 `menuItems`（原来是右键时先存锚点、
再从状态算菜单项，现在右键那一下直接算），书页白边的「?」走 `pageLayer`，「选字 + ?」写进快捷键说明，提问窗是组件自己画的。
阅读页主组件里不再有任何提问的字样。

### 一个坑：浮层不能放进表

最初浮层也是一个口子（`overlay`，放 React 元素）。真机一开就 React #185 死循环：提问的面板元素每次渲染都是新的 →
登记 → 表变 → 阅读页重画 → 扩展跟着重画 → 又是新元素 → 再登记。即使不死循环，提问里每变一下都会经表让整个阅读页（每一页）重画。
所以：浮层由扩展自己画；挂扩展的 `ReaderExtensionOutlets` 用 `memo`，阅读页重画不带着扩展重画（扩展只跟着阅读页接口和自己的状态变）。
单测里钉住了「每次画都交新贡献对象也不转圈」。

## 接下来

按价值排，每一步阅读页照常能用：

1. 把别的功能挪成扩展：Markdown 面板、画笔（它自己的右键菜单那一排、`P` 快捷键、页面层）、交叉引用、对比版本……
   挪的时候缺什么口子再加（面板 `panels`、工具栏按钮、命令），不预先铺。
2. 页面层：画笔、悬停框、搜索命中、实时译文叠层也改成登记的层，`PdfPageSlot` 里不再写死。
3. 工作台外壳：面板能停靠、能浮动、能并排，布局按用户记住。
4. 和任务解耦：按 `document_id` 打开，翻译变成一层，对照是两个视图（要后端配合书库条目模型）。
5. 开放给能装的功能插件（沙箱、清单里的 `reader.*` 口子，见 11-21 方案的 Q1–Q6）。
