# 真实文档实测（2026-10-30）

用户："推送后续再说，你看看我最新的 pdf 的翻译任务，用这个做测试就行了"。

用的是用户本地最新的翻译任务：一本英文量子化学教科书的一章（34 页，印的页码从 402 起，公式很多：行内公式约 790 个、行间公式约 210 个）。
OCR 是 PaddleOCR，规范化后的 `document.v1.json` 直接进测试系统（新加 `devtools/agent_lab/real_doc.py`：OCR 的块类别换成我们的分类、标题按编号推级别、
取印的页码；`python -m devtools.agent_lab --document … --pdf … --baseline …`）。同一任务里正式流程（DeepSeek）的译文当基线，按页号块号对上（330 块全对上）。
文件只在本地跑，不进仓库。模型只用 Haiku 5.5（带通读和审校）。

## 第一遍暴露的问题（人造样例上都没碰到过）

| 问题 | 原因 | 怎么改的 |
|---|---|---|
| 跑到一半整个崩了 | 对方没回应就断开连接（`RemoteDisconnected`），这类网络错误没被捕获、不退避 | 网络层的错也退避重试 |
| 330 块里 29 块退回原文、64 块重翻 | 全是"公式变了"的误判：① 真实 OCR 写 `$ \hat{F} $`（带空格），模型交回 `$\hat{F}$`；② 正文的 z、n/2、x, y, z 被模型套上公式符号；③ 两个公式合成一个；④ 公式被写成普通文字（`$H_2$` → H₂、`$(14.135)$` → (14.135)） | 公式按去掉空格的内容比；多出的公式内容在原文正文里有就不算错；丢的公式被别的公式包含、或者以普通文字留在译文里，只记警告 |
| 模型顺手"修"了 OCR 认错的公式（多一撇、多一竖） | 规则是公式一个字符都不许动 | 相似度 ≥ 0.85 的一对由程序换回原文写法，记警告 `formula_restored`（OCR 本身的错留给以后的原文核对员） |
| 数字检查把套进公式的正文数字算丢了 | 先去掉公式再数 | 新套上公式符号的原文文字按普通文字数 |

## 改完的结果

| | 新 agent（Haiku 5.5，通读 + 审校） | 正式流程（DeepSeek，同一套程序检查） |
|---|---|---|
| 退回原文 | 2 块（都是真错：一个变量丢了撇、漏了一个公式） | — |
| 公式和原文不一致 | 2 | 22（多数是公式写成普通文字或多套了一个） |
| 原文 we、译文没"我们" | 35 | 53 |
| 数字可能丢了 | 1 | 6 |

抽读：两边都准确通顺、公式都保住，质量大体持平；新 agent 有的句子更顺（少翻译腔），DeepSeek 有的地方更贴原文的括号写法；标题两边几乎一字不差。
这一章约 52 万输入 token、5.6 万输出 token，按 Haiku 5.5 价格约 0.08 美元；带审校从头跑约 6 分钟。

结论：在真实教科书上，只用 Haiku 的新 agent 和现在的正式流程大体持平；真实文档的主要难点在公式的写法和 OCR 噪声，检查要按真实写法放宽，
人造样例看不出这些。下一步继续第 1 版（体例、文风、人名、术语自检），并多找几份真实文档（论文、人文书）测。
