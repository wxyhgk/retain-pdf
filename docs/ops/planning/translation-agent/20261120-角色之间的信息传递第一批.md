# 角色之间的信息传递（第一批）

2026-11-20。

## 起因

用户：「提示词这边有问题，以及多 agent 的协作、他们的信息传递你看看。」拿《The Interloper》任务 `20261120000035-8c802a`
（209 页、Haiku、按节翻、复用上一次的通读）的运行记录和请求缓存逐个查：25 节、30 次节译、25 次审校、3 次逐页兜底。
查出的问题分三批改；这一批只修传错、传丢的，都是程序的事。

## 查出来的（这一批管的）

| 问题 | 证据 |
|---|---|
| 书名传错 | 所有角色收到的书名都是「Introduction」：书名取 OCR 的第一个标题块，这本书封面是图，第一个标题块是第一章 |
| 审校被逼着交单 | 请求强制调 `submit_review`；全书 70 张单子 50 张改法和原译一字不差，理由写「占位，无需修改」「译文无误，此条不成立」 |
| 审校自己否定的单子程序照改 | 采纳的 16 张里约 5 张理由写着「应忽略」「撤回」「这里不作修改」，只因改法和原译差几个字就改了，一处把索引条目改坏 |
| 兜底译者什么都不知道 | 3 次兜底请求上下文是空的（没有术语、人名、文风），为翻 5 块把整节 106 块塞进去，每次约 2.5 万字 |

## 改了什么

- **书名**：`agent_flow._document_title` 先看原 PDF 元数据里的书名，垃圾值（文件名、Microsoft Word 开头、untitled、纯数字）不要，
  再退回 OCR 第一个标题块。`execution_runner` 把 `source_pdf_path` 传给 agent 引擎。书库里用户改过的书名翻译阶段拿不到
  （stage spec 里没有），要的话以后从 spec 传。
- **审校**：单子加必填的 `must_fix`，排在 `reason` 后面、`fix` 前面（先写理由再定改不改）；`false` 程序不改，记 `withdrawn`。
  提示词写明单子只开给要改的地方、不是逐块打勾，没问题交空列表。没有 `must_fix` 的旧单子照旧处理。
- **兜底**：`section.fallback_page` 只放翻不过的段和前后各两段（只作上下文），配上下文包（术语、人名、缩写、文风、前面已译好的段）。
- 版本：`translation-agent-20`、`agent-section-4`。

## 实测（Haiku，第 42–69 页三节，复用原来的通读）

- 书名：请求里是「The Interloper」。
- 审校：只加 `must_fix` 时 Haiku 把审校当逐块打勾，三节开 40 张、几乎全是「无误」（都撤回了，没有误改，但输出 token 白花）；
  提示词加「只开给要改的地方」后三节 9 张，全部自己撤回。
- 审校会不会因此漏报：拿上一轮抓到的 3 处真错（加了原文没有的「大概」、perhaps 漏译等）和同节 6 段正确译文，两版提示词各审 3 次：
  收紧前抓到 0、0、1 处，收紧后 0、1、1 和 2、1、0 处（跑了两轮）；两版都没有误改对的段。收紧没让漏报变多。
- 这次两节重交一次就过了，没触发兜底；兜底请求的内容由单测钉着（只带前后两段、有术语人名文风）。
