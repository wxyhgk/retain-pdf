# 初译工具：全书搜原文、查术语表，交卷后的检查回到同一段对话

2026-11-19。

## 起因

用户（11-19）：「目前的 agent 没有给 tools 等工具，我感觉局限性很大」「不能搜索什么的，这个非常麻烦，能不能直接接入 pi？」。
后来又说：「转给后端，先做全书搜索那三个工具」。这件事是前端会话转过来的。

当时的情况：

- 每个角色一页只发一次请求。工具只用来强制交卷，用的是 `tool_choice` 指定那个工具。
- 模型只看得到这一页和上下文包（约 7000 token）。
- 一个词在全书别处怎么用、前面几页怎么译的，模型看不到。上下文包放不下的术语条目和歧义单，它也看不到。

## 用户定的

1. **调用方式**：用原生工具调用，先只接 Anthropic。
   - OpenAI 协议这次不开工具，行为和以前一样。
   - 原因：OpenAI 那条路的共用请求层（`request_chat_content`）和 Rust 执行器只交回文本，拿不到 `tool_calls`，要支持得改两层。
   - 等 agent_lab 对比出效果，再补这两层。
2. **自查不做成工具**：模型交卷后，程序照旧逐块校验和查术语。有错时，把问题接在同一段对话里回给模型，让它只重交出错的块。
   - 做成工具的话，模型要把整页草稿当参数写一遍，交卷时再写一遍，输出 token 约翻倍。
   - 公式里的反斜杠在 JSON 参数里还要转义。10-31 改成纯文本交卷，就是为了躲这个问题。
   - 程序自动查，也不怕模型忘了调。
3. **联网搜索**（查人名、书名的官方译法）这次不做：会把书的内容发给外部服务，要不要做、用哪家都还没定。
4. **pi 这次不接**。顾虑：
   - pi 自带 bash 和写文件，用户上传的 PDF 里的文字可能诱导模型执行命令；
   - 要多带一个 Node 运行时；
   - 会绕过共用请求层（用量台账、限流重试）；
   - 续跑和请求缓存都要重做。

## 做了什么

`backend/translation-agent`，只用标准库：

- **`tools.py`**：`BookTools`，由调度建，拿着全书各页的原文、术语表（和调度用的是同一个对象）、已经翻完的块的译文。两个工具：
  - `search_book(query)`：在全书别的页里按整词、不分大小写搜英文。
    - 交回原句，带页码、块 id、类别；那一页已经翻过的，同时交回那一块的译文。
    - 查询里有中文时，在已经翻过的译文里找，用来查自己前面有没有这么写过。
    - 离这一页近的排在前面，最多 8 处，每处最多 240 字；超过 8 处时告诉模型一共几处。
  - `lookup_term(source)`：按原文查术语表的完整条目。
    - 交回译法、类别、状态、作用域、报过的章、说明、各种译法被报了几次、第一次出现的地方、歧义单（最多 5 张）。
    - 没有这个词本身时，列出包含它的条目，最多 5 条。
  - 只读：工具不改术语表，也不改别的页。
- **`agent.py`**：
  - 开了工具时，初译走 `_converse`：模型调工具，程序执行，结果作为 `tool_result` 回给模型，直到模型交卷。
  - 每一轮的回答（含思考块）原样接进对话。
  - 一页最多 3 轮工具调用、一共 8 次。用完后下一轮 `tool_choice: none`，只能交卷；同一轮里超出的调用回"次数用完"。工具定义照带，提示词缓存的前缀不变。
  - 提示词缓存断点只打在最后一条消息上。断点最多 4 个，服务端会往前找到上一次缓存的前缀。
  - 交卷后检查出错的块（第 2 次、第 3 次尝试），把 `{check: [{id, problems}], required_ids}` 接在同一段对话里，不再另发一次重翻请求。
  - 系统提示末尾加一段工具说明（`TOOLS_PROMPT`）。不开工具时请求逐字节不变，所以 `PROMPT_VERSION` 不升。
  - 开了工具的块，`meta.tools_version` 记 `agent-tools-1`。
- **`runner.py`**：`DocumentRun(tools=True)` 时建 `BookTools`。每页开始前记下当前页，每页做完（含续跑读回的页）把译文记进去。跑完把 agent 的工具摘掉。
- **编辑部事件**：新增 `tool_call`，字段如下，前端据此画"查了什么"：
  - `page`、`role`（现在只有 translator）；
  - `tool`（`search_book` / `lookup_term`）；
  - `query`（最多 80 字）；
  - `found`（搜到几处、查到几条）；
  - `error`（只在出错时有，例如次数用完）。

  一页的几轮工具调用算同一次 `translate_call`，不再多发；检查后重交照旧发 `retry` 和 `translate_call`。
- **`agent_openai.py`**（OpenAI 协议换算层）：请求带了不是强制交卷的工具（`tool_choice` 是 auto / none）时直接报错，不会悄悄当成强制交卷的 JSON 请求。
- **agent_lab**：加 `--tools`，`summary` 里多出 `tools`、`tool_calls`、`tool_calls_by_tool`。

## 没做的

- **正式流程**（`agent_flow.py`）这次没开工具，任务照旧。
  - 先在 agent_lab 上对比开和不开：质量、请求数、token、费用。效果明显再接进正式流程，并推到审校和编辑重写。
  - 对比要跑真模型（Haiku），跑之前跟用户确认费用。
- 思考加工具循环在 Haiku 上的表现要实测：以前强制用工具时思考 token 是 0；这次 `tool_choice` 是 auto，应该会思考。
- OpenAI 协议的多轮工具：共用请求层和 Rust 执行器要能交回 `tool_calls`，另开分支做。

## 验证

- `backend/translation-agent/tests/test_tools.py`：
  - 搜索：不搜当前页；只认整词；按远近排序；带已有译文；中文在译文里搜；条数有上限。
  - 查术语：完整条目、歧义单，没有时列包含它的条目。
  - 多轮循环：思考块原样回传；只有一个缓存断点；`tool_call` 事件；次数用完转 `tool_choice: none`。
  - 检查问题接在同一段对话里重交。
  - 不开工具时请求不变；调度把前面几页的译文交给后面的搜索。
- `test_agent_openai.py`：多轮工具请求在 OpenAI 协议下报错。
- `test_agent_lab.py`：`--tools` 跑通，并数清工具调用次数。
