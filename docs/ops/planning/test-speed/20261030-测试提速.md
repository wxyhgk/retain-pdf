# 测试提速（2026-10-30）

用户："怎么测试这么慢？能不能优化一下"，"我建议直接看代码部分，肯定有很多没用的测试"。
5 路分头审查（Rust API、Rust 各包、Python 翻译、Python 渲染、Python 其余，只读、实测耗时）的结论：
慢不是因为测试多，是几个根因拖慢了全部；能删的没用测试约 40 个，但省不了多少时间。

## 根因和改法（按收益排）

| # | 根因 | 实测 | 改法 |
|---|---|---|---|
| 1 | 自带编译的 SQLite 默认开内存统计，每次分配都拿全进程一把锁；我们每次库操作都新开连接、重新解析表结构，并行的测试全在排队 | rust_api 557 个测试并行和串行一样慢；关掉后 109 s → 27 s，retainpdf-db 25 s → 5 s，retainpdf-data 57 s → 33 s | 第一次开连接前 `sqlite3_config(SQLITE_CONFIG_MEMSTATUS, 0)`（代码里设，所有构建方式都生效）。根治是 `Db` 复用连接（生产也在付这份开销），另写方案 |
| 2 | 架构检查同一个文件 `ast.parse` 约 10 遍；还有测试把整个检查再跑一遍 | 那条测试占渲染测试（不含 Typst）60% | 解析结果按路径缓存 |
| 3 | 翻译 agent 测试系统、OCR 查看器的样例每个用例重建一遍；样例生成每画一段字就提交一次页面 | 51 个用例约 90 CPU 秒 | 样例按模块共享；每页一次提交 |
| 4 | 真实的重试等待：WebDAV 同步退避、翻译探针的退避；结束 worker 的测试因子进程成了僵尸、每条白等 3 s；随手写的 1 万条事件 | 约 30–40 s | 等待时间做成参数、测试里给 0；回收子进程；事件数降到够用 |
| 5 | Typst 样本一个一个编译；翻译集成测试同一个用例跑 3 遍、每个参数组合起一个子进程 | Typst 22 s，翻译集成约 65 s | 合成一个多页文档编译；参数合并、子进程共享 |

另外查出的真问题：`tests/performance/pipeline/tools/analysis/audit_prompts.py` 只认旧文件名 `page-*-deepseek.json`；
`test_word_html_fit.py` 读本机 `data/jobs` 里最新的任务（不封闭，本机现在是红的）；Rust 测试的临时目录从不清理（系统临时目录里 8.9 万个）。

## 用户定的（10-30）

- 按上面的顺序做（1 → 2 → 3 → 4 → 5），再修三个真问题、删没用的测试；每步一个分支，说"合"再合。
- 合并前翻译测试的反向那遍只跑翻译单测：集成测试每个用例都在新进程里跑，顺序本来就影响不到，倒着再跑一遍是白花时间（CLAUDE.md 跟着改）。
