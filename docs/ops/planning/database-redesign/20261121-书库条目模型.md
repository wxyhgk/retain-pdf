# 书库条目模型

2026-11-21。接着[数据库重做总体设计](./20261120-数据库重做总体设计.md)。用户说后面要加**笔记、文献管理（学 Zotero）、划线**，
还有**能装的功能插件**（插件那边见 [能装的功能插件](../plugin-architecture/20261121-能装的功能插件.md)），问数据库是不是该做成
「一个主表 + 多个表」。

## 用户定的

- 书库按「**条目主表 + 各类型明细表**」重做，照 Zotero 的思路。
- **许可证保持 MIT**：Zotero 是 AGPL-3.0，只借它的数据模型、字段表、导入导出格式，**不搬代码**。
- 总体设计的第 1–4 步（任务那一侧）照做；**第 5 步（书库）改成按本文件做**，不再只是「书名状态并进书表」，免得加笔记时再重做一遍。
- 插件指能装能卸的功能插件，书库要给插件留存数据的位置。

## 一条分界：自己写的 vs 程序跑出来的

| | 用户自己写的（书库） | 程序跑出来的（任务） |
|---|---|---|
| 是什么 | 书目信息、笔记、划线、标签、文件夹、插件存的数据 | 任务、产物、进度事件、断点续跑记录 |
| 量 | 小 | 大（现在 512MB 的库几乎全是这些） |
| 丢了 | **找不回来** | 能重跑 |
| 同步 | 必须，多设备逐字段合并 | 现在也同步，以后可以只同步结果 |
| 清理 | 只有用户删、进回收站 | 按保留期自动清理 |

两边的表、同步、备份策略分开考虑。以后可以把书库拆成单独的库文件（小、备份快、坏了任务库能重建），**本文件先不拆**，
只保证书库的表不依赖任务的表（书库 → 任务只通过原文件的内容指纹关联，见下）。拆不拆等第 5 步做完再定。

## 借 Zotero 的什么

Zotero 的库：书、笔记、附件、批注**全是 `items` 里的一行**，带类型和父条目；书目字段、作者、笔记正文、附件、批注
各有明细表；标签、文件夹、关联、回收站、同步版本号对所有类型都一样。值得借的几点：

1. **书目信息和 PDF 文件是两个条目**：一条文献可以没有 PDF（从 Zotero / BibTeX 导进来的），一个 PDF 可以挂在文献下面，
   也可以单独存在；**批注挂在 PDF 附件上，不挂在文献上**。我们现在的 `documents` 把两件事揉在一起（`document_id` 就是 PDF 的
   sha256），加文献管理时一定要分开。
2. **作者单独一张表**（姓、名、角色、顺序），不是一坨 JSON；按作者查、导出引用格式都要用。
3. **标签、文件夹对所有类型都能用**；**回收站是一列删除时间**，清空回收站才真删。
4. **批注的位置存成整块**（页码 + 框），另存引文，排序用一个排序键。

**不借的：** 书目字段的「属性-值」三张表（`itemData`/`fields`/`itemDataValues`）——灵活但难查难改，正是我们这次要治的
「看不懂」；我们用**常用字段做列 + 其余字段整块存 CSL-JSON**（导出引用时整块读，正合「整块存取才用 JSON」的原则）。
笔记正文 Zotero 存 HTML，我们存 **Markdown**。

## 目标结构

```text
library_items              主表：每个条目一行
├─ item_references         文献的书目信息（常用字段是列）+ CSL-JSON 其余字段
│  └─ item_creators        作者、编者……（顺序、角色、姓、名）
├─ item_files              文件附件：PDF 等（内容指纹、文件名、大小、页数、存哪）
│  └─ （任务、译文版本、全文索引按内容指纹挂在这里）
├─ item_notes              笔记正文（Markdown）
├─ item_annotations        划线 / 批注（挂在文件附件上）
├─ tags / item_tags        标签
├─ collections / collection_items   文件夹（能装任何条目）
├─ item_relations          条目之间的关联
└─ plugin_data             插件存的数据（可以挂在条目上）
```

### `library_items`（主表）

| 列 | 说明 |
|---|---|
| `item_id` | 随机编号（不再用内容 sha256 当编号；内容指纹是文件附件的一列） |
| `item_type` | `reference` / `file` / `note` / `annotation`，插件的类型写 `plugin:<插件编号>/<类型>`；`CHECK` 钉住内置几种 + `plugin:` 前缀 |
| `parent_item_id` | 父条目：PDF 挂在文献下、笔记挂在文献或 PDF 下、批注挂在 PDF 下；独立的为空。外键，父条目真删时级联 |
| `created_at`、`updated_at` | |
| `deleted_at` | 进回收站的时间；为空 = 正常 |
| `owner_user_id` | 照多用户的约定留着不动 |

同步按条目走：一个条目（主表一行 + 它的明细表）是一个同步实体，沿用现在逐字段合并的同步机制。

### 各类型的明细表

- **`item_references`**：`item_id`、文献类型（CSL 的 `article-journal`、`book`、`thesis`……）、标题、短标题、日期（原样）和年份（查询用）、
  期刊/书名（container title）、卷、期、页码、出版社、DOI、ISBN、URL、语言、摘要、`extra_csl_json`（其余 CSL 字段，整块）、
  书名来源和是否锁定（现在的 `document_title_state` 并进来）。
- **`item_creators`**：`item_id`、顺序、角色（作者、编者、译者）、姓、名、或者整名（机构作者）。
- **`item_files`**：`item_id`、`content_sha256`（**就是现在的 `document_id`**）、原文件名、大小、页数、存在哪（数据目录里的相对路径）、
  阅读状态、最后打开时间、选用哪份译文（`chosen_version_id`，空 = 自动选最新，替代 `translation_version_choices` 和
  `documents.active_*`）。同一个内容指纹只能有一个文件条目（唯一索引）。
- **`item_notes`**：`item_id`、Markdown 正文、标题（从正文第一行算出来存着，列表用）。
- **`item_annotations`**：`item_id`（父条目必须是文件附件）、类型（划线、下划线、批注、框选区域）、颜色、评论（Markdown）、
  **位置**（整块 JSON：页码 + PDF 坐标的框，可以跨页）、**引文**（选中的原文 + 前后各几十字，原文对不上时靠它找回位置）、
  原文块编号（只是提示，重新识别版面后会变）、排序键（页码 + 纵坐标，列表按它排）、标在哪一面（`source` 原文 / `translation`
  译文 + 译文版本；默认原文，见「要定的」）。
- **`tags` / `item_tags`**：标签名、颜色；条目和标签多对多。
- **`collections` / `collection_items`**：文件夹照旧能嵌套；成员从「书」放宽到任何条目。
- **`item_relations`**：主语条目、关系、宾语条目（`related` 相关、`cites` 引用、`derived_from` 由……生成，例如笔记由划线生成）。
- **`plugin_data`**：`plugin_id`、`item_id`（可空：插件自己的全局数据）、键、值（JSON 整块）、更新时间。插件只能读写
  自己名下的；卸载插件时默认留着，用户选「连数据一起删」才删。同步：插件清单里声明要不要同步。

### 和任务那一侧怎么连

- 任务、译文版本、全文索引（`blocks_fts`）都按**原文件的内容指纹**（`content_sha256`，现在的 `document_id`）关联
  `item_files`，不直接指向文献条目。这样「一本书换了书目信息」「同一个 PDF 挂到另一条文献下」都不影响翻译。
- 现在的接口按 `document_id` 查书：`document_id` 继续是 PDF 的内容指纹，数据库层从 `item_files` + 父条目 `item_references`
  拼出 `DocumentRecord`，**接口不变**。
- 上传（`uploads`）是「这次传了个什么文件」的记录，并进 `item_files` 的来源信息或者保留为 `document_uploads`（第 5a 步定）。

### 现在的表怎么搬

| 现在 | 搬到 |
|---|---|
| `documents` 一行 | 一条 `reference` 条目（标题、作者、年份、DOI）+ 一条挂在它下面的 `file` 条目（文件名、大小、页数、阅读状态） |
| `documents.authors_json` | `item_creators` 一行一个作者 |
| `document_title_state` | `item_references` 的书名来源、是否锁定 |
| `document_metadata_suggestions` | 照旧，指向文献条目，改名 `item_title_suggestions` |
| `translation_version_choices`、`documents.active_job_id`、`active_version_id` | `item_files.chosen_version_id` |
| `collection_documents` | `collection_items`（成员是文献条目） |
| `uploads` | 第 5a 步定（见上） |
| `glossaries` | 不动（术语表不是书库条目） |

## 第 5 步拆成几步

第 5a、5b 是重做（接口不变，比对工具守着）；5c 以后是**新功能**（新接口 + 前端），每步单独开分支、单独合并。

| 步 | 内容 | 接口 |
|---|---|---|
| 5a | 主表 + 文献 + 作者 + 文件附件；现有的书搬成「文献 + PDF」两条；任务、译文版本改挂内容指纹；同步种类换成条目 | 不变（比对工具比 `document`、`upload`、`list` 类） |
| 5b | 标签、文件夹放宽到任何条目、回收站、条目关联 | 不变 + 只增（标签） |
| 5c | 笔记：建、改、删、挂到文献或 PDF、全文搜索 | 新接口 |
| 5d | 划线和批注：阅读页标在原文上、列表、跳转、导出成笔记 | 新接口（阅读页前端配合） |
| 5e | 文献管理：BibTeX / RIS / CSL-JSON 导入导出、读用户的 `zotero.sqlite` 导入、生成引用格式（Rust 的 hayagriva + CSL 样式文件，引入前核实许可证） | 新接口 |
| 5f | 插件数据表 + 插件登记表（和插件那边的 Q 步一起） | 新接口 |

## 要定的

1. **批注标在原文还是译文上**：倾向**只标原文**（位置稳定，重翻不丢），阅读页在译文一侧显示时按块对应过去；
   要不要允许直接标在译文上，等 5d 前和前端一起定。
2. **书库要不要拆成单独的库文件**：倾向 5a、5b 做完、量出书库到底多大以后再定。
3. **上传记录**：并进文件附件，还是留一张 `document_uploads`（同一个文件可能上传多次，现在有 45 条上传对 45 本书）。5a 开工前看代码里
   谁在用上传记录再定。
4. **翻译版本要不要同步**：现在 `translation_versions` 不在同步种类里（任务在），5a 顺带核实是有意的还是漏了。
