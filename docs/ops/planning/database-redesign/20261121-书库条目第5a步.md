# 书库条目第 5a 步

2026-11-21。[书库条目模型](./20261121-书库条目模型.md)第 5a 步（分支 `refactor/db-library-items`，迁移 v36）实际怎么做的，
和设计文件不一样的几处。

## 用户定的（开工前问的）

- **PDF 是条目下的文件记录，不单独当一个条目**（设计文件照 Zotero 把「文献」「PDF」做成两条）。做的时候发现分成两条同步很难办：
  一本书要拆成两个同步实体，两台设备各自上传同一个 PDF 时自动建的文献条目对不上。现在一本书 = 一个文献条目，它的 PDF 是
  `item_files` 里的一行（按内容指纹），划线以后挂在文件行上，笔记挂在条目上；没有 PDF 的文献（从 Zotero 导入）照样能建。
  缺点：一个 PDF 不能同时挂在两条文献下（很少见）。
- **上传 PDF 时自动建的条目，编号沿用 PDF 内容指纹**（`item_id = file_id = 以前的 document_id`）：接口的 `document_id` 不变、
  前端不用动，两台设备传同一个 PDF 还是同一本书。手工建的、导入的条目和笔记、划线以后用随机编号。

## 做法

- `documents` **原地改名**成 `item_files`（列 `document_id` → `file_id`），不重建：译文版本、文件夹成员用外键挂在它下面，
  迁移在开着外键的事务里跑，重建要删旧表，`DROP TABLE` 会把它们连带删掉；改名时 SQLite 把指向它的外键一起改。
  代价：`item_id` 只能用 `ADD COLUMN` 加成可空的外键列，非空由两个触发器守着。
- 书名、作者、年份、DOI 搬进 `item_references` / `item_creators`；`document_title_state` 并进 `item_references`；
  `translation_version_choices` 并进 `item_files.chosen_version_id`（只在本机、不同步，和以前一样）；
  `document_metadata_suggestions` 重建成 `item_title_suggestions`，挂在条目上。归属 `owner_user_id` 挪到条目上。
- `documents.active_version_id`（AI 改写文档留下的，真实库全空）删掉；契约里它本来就是「没有时整个键不出现」的可选字段，现在恒不出现。
- 接口不变：一本书从视图 `library_documents` 读（文件 + 所属条目的书目信息），`updated_at` 取条目、文件两边较新的。
- 文件夹成员 `collection_documents` 这一步不动（照旧指向文件），第 5b 步放宽到任何条目时再改。
- 同步：种类照旧叫 `document`、键照旧，根表换成 `library_items`；格式升到 6。旧结构的书（别的设备发来的、同步文件夹里的老包、
  本机记着的上次同步内容）按新结构改写，字段时钟一起换。写入别的设备的改动时 `item_files` 按主键覆盖、不先删
  （先删会把本机挂在文件下的译文版本连带删掉）。合并粒度的变化见[多设备同步](../../../api/09-同步/01-多设备同步.md)格式 6。
- 设计文件里「要定的」第 3、4 条：上传记录 `uploads` 这一步不动（同一个文件可以上传多次，书库列表、源 PDF、删书都按内容指纹找上传，
  没有要并的理由）；译文版本不同步是有意的（v30 迁移开头写明，一起的「选哪份译文」也不同步）。

## 验证

- 真实库副本（v35，46 本书、95 个译文版本、55 条书名建议）：迁移后外键检查无违规，一行没丢；
  比对工具 `retainpdf db-snapshot dump|diff` 迁移前后 742 条读出来一样（结果见合并说明）。
- 新测试：v35 的书升上来读出来一样、删书级联删干净；别的设备改书时本机的译文版本和选择留着；旧结构的书经同步写入、
  逐字段合并照旧；本机记着的旧同步状态开库时改写一次。
