# 书库条目第 5b 步

2026-11-21。[书库条目模型](./20261121-书库条目模型.md)第 5b 步（分支 `refactor/db-library-tags`，迁移 v37）。

## 用户定的（开工前问的）

- **回收站这步只做表，接口以后再加**：删书照旧彻底删。回收站要的那一列 `library_items.deleted_at` 5a 已经建好；
  移进去、恢复、清空、多久自动清，等前端要做这块时再定再加，免得现在定的规则以后要改。
- **标签的接口一起加，只增不改**：前端不接也不受影响。

## 做了什么

- `collection_documents`（成员是书的文件）重建成 `collection_items`（成员是任何条目）。没有表指向它，重建安全。
  接口照旧按书加、按书删，数据库层按文件找到它所属的条目。
- 标签 `tags` + 条目的标签 `item_tags`。**标签编号由名字算出来**（`tag-` + 名字去空白转小写后 sha256 的前 16 位），
  两台设备各自建的同名标签同步后是同一个；名字不加唯一约束（同步写入时撞了会卡住），查重在建标签、改名时做
  （同名的建标签返回已有的，改名撞名 409）。改过名的标签占着原来名字算出的编号，再建原来的名字就用随机编号。
- 条目之间的关联 `item_relations`（`related` / `cites` / `derived_from`），挂在主语条目上一起同步。这一步没有接口，
  给笔记、划线（5c、5d）用。
- 接口：`GET|POST /api/v1/tags`、`PATCH|DELETE /api/v1/tags/:tag_id`、`PUT /api/v1/documents/:document_id/tags`、
  书列表的 `tag_id` 筛选、书的记录多一个 `tags`（契约 `library-documents.v1` 只增）。
- 同步：新种类 `tag`；书的同步内容多了 `item_tags`、`item_relations`；合集成员换表；格式 7。旧结构的合集成员（别的设备、
  老包、本机记着的同步状态）按新表名、列名改写。

## 验证

- 真实库副本（v36，46 本书）：迁移后外键检查无违规；比对工具迁移前后 742 条，唯一的不同是每本书多了 `tags: []`
  （`--ignore document:record.tags` 以后一样）。真实库里还没有合集成员。
- 新测试：标签同名不重复建、编号由名字算、改名后再建原名不撞；给书设标签、按标签筛、删标签和删书级联；标签和书上的标签
  经同步到另一台设备、同名标签两边是同一个、删标签两边都去掉；旧结构的合集成员改写；契约测试覆盖 5 个新接口。
