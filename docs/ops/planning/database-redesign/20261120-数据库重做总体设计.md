# 数据库重做总体设计

2026-11-20。用户：「我感觉数据库需要大改，因为目前太乱太杂了」。前面的整理（[数据库整理](../database-cleanup/20261120-数据库整理.md)：
删死表、瘦身、表结构快照）只是清理，这里是重新设计。

## 用户定的

- **按领域逐块重做**（不是一次性换新库）：一次一个领域，设计新表、写迁移搬数据、改数据库层，**接口不变、前端不用动**；
  每块单独合并、单独验证，随时停在干净的状态。
- 要解决的四个痛点都要顾到：**看不懂、改不动、数据不可靠、太大太慢**。
- 多用户那组表（`users`、`sessions`、`invite_codes`、`page_ledger`、`job_page_charges`、`platform_settings`）和各表的
  `owner_user_id` **保留但不动**。
- 同步格式可以升版本，装旧版本的设备要一起升级。

## 原则

1. **一件事一个正本**。同一件事只存一处；别处要用就读出来时算，实在要存的写明是缓存、谁维护。
2. **要按字段查、改的拆成列，整块存取的才用 JSON**。状态、类别这类取值用纯文本列（不再是 `"succeeded"` 这种带引号的 JSON），
   能写 `CHECK` 的写上取值范围。
3. **表名按领域起头**：任务的都叫 `job_*`，书库的 `document_*`，看名字就知道归谁。
4. **外键写全**，删除时级联还是拦住写明白（现在 `events`、`event_source_versions` 没有指向 `jobs` 的外键，删任务靠代码记得删）。
5. **当前状态和历史分开**：当前状态一行、随时改；历史只追加、有保留期、会自动收缩。
6. **数据库层是唯一入口**：所有 SQL 只在 `retainpdf-db` 包里，表怎么改都不出这个包；接口的返回类型不变。
7. **每块都有快照守着**：`schema.sql` 表结构快照、「老库升上来和新库一样」的测试、接口三份快照（routes、file-responses、
   submissions）都不许意外变化。

## 现在乱在哪（按领域）

### 任务（15 张表，问题最多）

| 问题 | 在哪 |
|---|---|
| 「这个任务的产物」是一坨 32 个字段的 JSON | `artifacts.artifacts_json`（代码里 300 多处在读写 `JobArtifacts`）：一半是文件路径（和 `job_artifact_entries` 重复），另一半是 OCR 子任务编号和状态、追踪号、处理了哪些页、翻译条目数、各段耗时、OCR 诊断 |
| 同一件事存好几份 | 阶段：`jobs.stage` 和 `runtime_json.current_stage`；失败：`error`、`failure_json`、`runtime_json.final_failure_*`；进度：`progress_*` 列（153 个任务只有 11 个填了）和事件；阶段耗时：`runtime_json.stage_history` 和 `pipeline_stages` 的时间（要核实是不是同一回事） |
| 状态存成 JSON 字符串 | `jobs.status_json`、`workflow` 存的是 `"succeeded"`、`"book"`，查询要写 `status_json IN ('"queued"', …)` |
| 一次运行的信息散在任务表上 | `pid`、`worker_identity`、`result_json`（程序结果）、`run_generation` 在 `jobs` 上，只记最后一次；每次运行的记录在 `pipeline_attempts` |
| 进度事件存两份 | `events`（原始）和 `event_feed_items`（给前端的进度流，单条约是原始的 4 倍大），外加 `event_feeds`、`event_source_versions`、`event_feed_retention` 三张记账表 |
| 父子任务关系靠编号拼 | OCR 子任务编号是父任务编号加 `-ocr`（`ocr_child_job_id`），没有关系列 |

### 书库（10 张表）

| 问题 | 在哪 |
|---|---|
| 「这本书现在看哪份译文」有三种说法 | `documents.active_job_id`、`translation_version_choices`、`documents.active_version_id`（AI 改写文档留下的，一直是空） |
| 书和上传是两套编号 | 书 `document_id` 是原文的 sha256，上传 `upload_id` 另起；任务两个都记（`jobs.upload_id`、`jobs.document_id`） |
| 书名状态单独一张表 | `document_title_state`（来源、是否锁定、采用了哪条建议）是一本书一行，和 `documents` 一对一 |

### 术语表（1 张）

条目整块存在 `glossaries.entries_json`，改一条要读写整张；现在库里是 0 张，先不急。

### 同步（11 张）、账号（6 张）

同步的记账表本身结构清楚；它按表名、列名发行，所以别的表改了它要跟着改（`entity_spec`、触发器），每改一块升一次同步格式。
账号这组照用户定的不动。

## 目标结构

### 任务

| 新表 | 从哪来 | 放什么 |
|---|---|---|
| `jobs` | `jobs` 去掉重复列 | 身份和**当前状态**：`job_id`、`workflow`、`status`（纯文本）、`parent_job_id`（OCR 子任务指向父任务）、`document_id`、`upload_id`、`stage`、`stage_detail`、各时间点、`run_generation`、`request_json`（建任务的请求，整块）、`failure_json`（结构化失败信息，**失败的正本**） |
| `job_attempts` | `pipeline_attempts` 加上 `jobs` 的 `pid`、`worker_identity`、`result_json`、`command_json` | **每次运行**一行：第几次、代次、进程、命令、程序结果（输出只留末尾）、开始结束时间、自动续跑计数 |
| `job_stages`、`job_units`、`job_dispatches` | `pipeline_stages`、`pipeline_units`、`pipeline_dispatches` 改名 | 断点续跑的阶段、单元、外部服务调用记录（结构本来就清楚，只改名、补外键） |
| `job_files` | `job_artifact_entries` 加上 `artifacts_json` 里的文件路径 | **产物文件的正本**：一个文件一行（类别、相对路径、大小、校验和、哪个阶段产出） |
| `job_stats` | `artifacts_json` 里不是文件的那一半 | 处理了哪些页、翻译条目数、各段耗时、OCR 追踪号和诊断（一个任务一行，按需拆列） |
| `job_events` | `events` | 进度事件的**正本**，只追加，30 天滚动 |
| 进度流 | `event_feeds`、`event_feed_items` 等四张 | **待定**（见下面「要定的」）：要么只存「进度流第几条对应哪条原始事件」，不再复制一份大的内容；要么读的时候现算 |
| `model_sessions`、`model_operations` | 照旧 | 模型请求记账，结构清楚，只补外键 |

去掉：`artifacts` 表（拆进 `job_files`、`job_stats`）、`jobs` 上的 `error`（从 `failure_json` 现算）、`progress_*`（进度从事件算）、
`runtime_json`（当前阶段读 `stage`，失败读 `failure_json`，耗时从 `job_stages` / 事件算，**要先核实**）、`log_tail_json`（从事件现算）。
代码里的 `JobSnapshot`、`JobArtifacts` **结构不变**，由数据库层从新表拼出来，这样 300 多处读写不用跟着改，改动关在数据库包里。

### 书库

| 新表 | 从哪来 | 变化 |
|---|---|---|
| `documents` | `documents` 加上 `document_title_state` 的列 | 书名来源、是否锁定直接是书的列；去掉 `active_job_id`、`active_version_id` |
| `document_uploads` | `uploads` 改名 | 每次上传一行，指向书（`document_id`），原文件路径、上传时间 |
| `document_title_suggestions` | `document_metadata_suggestions` 改名 | 书名建议 |
| `translation_versions`、`translation_version_jobs` | 照旧 | **「现在看哪份译文」只看这里**：`translation_version_choices` 并成 `documents.chosen_version_id` 一列（为空 = 自动选最新） |
| `collections`、`collection_documents`、`blocks_fts` | 照旧 | 不动 |

### 术语表

先不动；以后要按条目编辑时再拆 `glossary_entries`。

## 怎么搬（每一块都一样）

1. 一个编号迁移完成：建新表 → `INSERT … SELECT` 搬数据（JSON 里的字段用 `json_extract` 拆）→ 核对行数 → 删旧表，
   在一个事务里，失败就整块回滚。升级前照旧自动备份。
2. 数据库层改成读写新表；`JobSnapshot` 等结构和接口返回不变，接口三份快照不许变。
3. 同步：这一块的种类改按新表发，升同步格式版本；旧版本设备连上时提示先升级。
4. 验证：
   - `schema.sql` 重新生成，看 diff 只有这一块的变化；
   - 「老库升上来和新库一样」测试要过；
   - 真实库副本上演练，迁移前后逐个任务、逐本书比对读出来的 `JobSnapshot`、书的信息完全一样（写一个比对工具，每块复用）；
   - 实跑一个翻译任务、打开阅读页、下载文件。
5. 合并后停开发栈、升级本机库（先备份）、再起。

| 步 | 分支 | 做什么 | 量 | 风险 |
|---|---|---|---|---|
| 0 | `feat/db-snapshot-diff` | 比对工具：迁移前后逐个读出 `JobSnapshot`、书的信息、文件清单，必须一致。后面每块都用 | 小 | 低 |

| 2 | `refactor/db-job-files` | 拆 `artifacts`：文件进 `job_files`，其余进 `job_stats` | 大 | 中高（`JobArtifacts` 要从新表拼） |
| 3 | `refactor/db-job-events` | 进度事件：`events` 改名、补外键；进度流按「要定的」第 1 条改 | 中 | 中（前端进度页靠它，接口不能变） |
| 4 | `refactor/db-job-pipeline` | `pipeline_*` 改名 `job_*`、补外键 | 小 | 低 |

## 要定的

1. **进度流两份怎么合**（第 3 步前定）：
   - A. 进度流只存「第几条对应哪条原始事件」和极少的元数据，内容读的时候从原始事件取。省一大半空间，读的时候多一次查询；
   - B. 不存进度流，读的时候按原始事件现算。最简单，但父子任务合并、分页游标要重新设计，前端进度页的游标可能要换。
   倾向 A：前端的游标和分页语义不变。
2. **改表名做不做**：按领域起头的表名（`job_*`、`document_*`）让「看不懂」好很多，但每个改名都要动全部 SQL 和同步。
   倾向做，和每步的结构调整一起改，不单独开步。
3. **`runtime_json` 能不能全去掉**：要先核实阶段耗时（`stage_history`）是不是和 `job_stages`、事件里的信息一致；不一致就留一份汇总。
