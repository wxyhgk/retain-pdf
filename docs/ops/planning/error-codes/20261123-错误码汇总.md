## 一、我们自己怎么分类、怎么显示

### 1.1 失败从哪来

任务失败时用户看到的标题、建议，来自任务详情的 `failure`（`GET /api/v1/jobs/{job_id}/reports/failure`）。分类有两个产生方：

1. **Python worker**：`backend/pipeline/retainpdf_pipeline/foundation/shared/structured_errors.py` 的 `classify_exception`。
   worker 把异常归类后打一行 `structured failure json: {...}`，Rust 解析到就直接用，下面的文本匹配不再跑。
   **注意**：只有包在 `run_with_structured_failure` 里的代码才会出这一行；worker 模块在包装之外 import
   （`backend/pipeline/retainpdf_pipeline/ocr/__main__.py` 里先 import 再包装），import 期崩溃没有结构化失败。
2. **Rust 兜底**：`backend/packages/retainpdf-core/src/job_failure.rs` 的 `classify_job_failure_inner`，
   在没有结构化失败时按错误文字和日志尾巴做子串、状态码匹配；OCR 服务商的分类（`OcrErrorCategory`）只有鉴权两类会被用上
   （`job_failure_structured.rs` 的 `classify_provider_auth_failure`）。
3. **恢复目录**：`backend/packages/retainpdf-core/src/job_failure_catalogue.rs`，按 `failure_code`（个别再按失败阶段）给
   `resume_from` 和一句 `recovery_hint`。前端只渲染后端给的 `summary`、`recovery_hint`，不再自己认分类。

翻译时上游错误先在请求层分流（重试还是直接停），见 `backend/translation/retainpdf_translation/llm/shared/upstream_resilience.py`
和 `backend/translation/retainpdf_translation/llm/providers/deepseek/{client,transport}.py`；
OCR 的重试在 `backend/pipeline/retainpdf_pipeline/ocr/retry.py`（Python：GLM-OCR、并行时的 Paddle）和
`backend/packages/retainpdf-data/src/ocr_provider/{paddle,mineru}/`（Rust：Paddle、MinerU）。

### 1.2 现有失败码（`failure_code`）

全表（产生方、`summary`、可不可重试、续跑起点、哪些上游大类落到它、issue 里见过）挪到了
[RetainPDF 失败码](../../../reference/error-codes/retainpdf/失败码.md)，从数据生成。要点：

- 很多上游错误落在兜底 `python_unhandled_exception` / `unknown`「任务失败，但暂未识别出明确根因」（#18 #38 #44 #84 #132 #7）；
- `auth_failed` 的建议文字写死「检查 MinerU Token…」，不分服务商；#81 的误判见 4.2；
- 限流在两边拼法不同（Python `upstream_rate_limited`、Rust `rate_limited`），恢复目录两个都登记了。

我们自己 API 的 HTTP 错误（400/401/404/409/500、`error.details.reason`）见 [认证与错误](../../../api/00-约定/02-认证与错误.md)。
issue 里出现过的两条：

| 用户看到的 | 意思 | issue | 状态 |
|---|---|---|---|
| `提交失败: 400 invalid pdf: Invalid file trailer` | 上传校验读不出页数（PDF 尾部不规范） | [#37](https://github.com/wxyhgk/retain-pdf/issues/37) | 4.1.2-beta1 已修（现在先尝试修复再判，失败才报 `invalid pdf after repair`，`backend/packages/retainpdf-ingest/src/uploads/service.rs`） |

## 二、各服务商错误码对照

逐家的表（服务商的码 / HTTP / 含义 / 给用户的提示 / 我们现在怎么处理 / 对不对得上 / 出处）挪到了生成的文档，每家一个文件：

| 厂商 | 文件 | 要点 |
|---|---|---|
| GLM-OCR | [ocr/glm_ocr.md](../../../reference/error-codes/ocr/glm_ocr.md) | 429 的额度类码第一次就停（#164 已修）；401/403/400 仍落「暂未识别出明确根因」（第五节第 5 条） |
| PaddleOCR | [ocr/paddle.md](../../../reference/error-codes/ocr/paddle.md) | 12001 当日额度被说成鉴权失败（高）；Python 路径丢掉 `errorCode`/`errorMsg`，且只读 `errorCode`（官方字段是 `code`）；10010 不重试 |
| MinerU | [ocr/mineru.md](../../../reference/error-codes/ocr/mineru.md) | 27 个码都有分类和中文建议，但任务层只认鉴权两类；官方说可重试的 -60001/-60010/-60016/-60020/-60021 不重试 |
| OpenAI | [llm/openai.md](../../../reference/error-codes/llm/openai.md) | 429 `insufficient_quota` / 花费上限被当限流（高）；404 `model_not_found` 不整份停下；#161、#163 已修 |
| Anthropic | [llm/anthropic.md](../../../reference/error-codes/llm/anthropic.md) | 花费封顶 429（没有 retry-after）、400 的花费上限 / 余额不足按普通请求失败 |
| DeepSeek | [llm/deepseek.md](../../../reference/error-codes/llm/deepseek.md) | 只按状态码区分，和请求层规则对得上；只剩 422 落兜底 |
| 智谱（翻译） | [llm/zhipu.md](../../../reference/error-codes/llm/zhipu.md) | 1113、1308–1321 在翻译侧仍当限流（高）；GLM-OCR 那边已按业务码处理 |
| 阿里云百炼 | [llm/qwen.md](../../../reference/error-codes/llm/qwen.md) | 429 下的欠费类码（CommodityNotPurchased 等）当限流（高）；Arrearage 走 400 |
| OpenCode | [llm/opencode.md](../../../reference/error-codes/llm/opencode.md) | 429 Policy budget exceeded 当限流；#144 已修 |

翻译请求层各家共用的处理（OpenAI chat、Responses、Anthropic Messages 三种协议，`model_wire.py` 组请求）：
401/403 整份停下归 `auth_failed`；402 整份停下归 `upstream_quota_exhausted`；400 只这个请求失败（拒收 `temperature`、
思考字段、`json_schema` 时自动降级）；408/429/5xx/529 退避重试、429 单个请求累计等待 300 秒放弃；其他 4xx 只这个请求失败、
冒到任务层是兜底。**只看状态码，不读响应体的 `error.code`**——这是第五节第 1 条的根。检测接口（`provider_probe/deepseek.rs`）把 429 报成「可用（当前被限流）」。

### 4.2 两个「分类说错了」的案例

- **#81 渲染失败被说成「鉴权失败」**（4.1.8-beta2）：结构化失败行里明明是 `render_failed`（`FileNotFoundError`），对外的
  `failure` 却是 `auth_failed`、「检查 MinerU Token、模型 API Key 或后端 X-API-Key 配置」。推测是当时的 Rust 文本兜底在日志里按裸子串找 401/403，
  而那次的任务号里正好含 `401` 这串数字。现在结构化失败优先、状态码按数字边界匹配（`job_failure.rs` `contains_http_status`），这一条已不复现。
- **#135 OCR worker import 期崩溃被说成「排版或编译阶段失败」**：import 在 `run_with_structured_failure` 外面，没有结构化失败；
  Rust 兜底的 `contains_render_failure_signal` 看到「No such file or directory」加上路径里的 `direct_typst_math.py`（含 typst），就判成渲染失败，
  三条提示全指错方向。打包问题修了，**这个误判路径还在**（见第五节第 3 条）。

## 五、待修清单（按用户影响排）

逐条（含低优先级）的现状和建议在数据里，汇总见 [服务商错误码 · 缺口汇总](../../../reference/error-codes/README.md#缺口汇总)。下面是按问题归并后的清单。

1. **额度用完被当成限流**（高）：OpenAI 429 `insufficient_quota` / 花费上限、智谱作翻译模型时的 1113 和 1308–1321、Anthropic 没有 `retry-after` 的花费封顶 429。
   现在每个请求退避到 300 秒才放弃，所有并发一起空等，最后提示「稍后重试即可，无需改动配置」——用户照做只会再等一轮。
   建议在 `upstream_resilience.py` 读响应正文的 `error.code`/`type`（不只看状态码），额度类按 402 处理：记成凭据被拒、整份停下、
   `upstream_quota_exhausted`、提示充值或等重置；检测接口的 429 也要区分额度和限流，额度类不能报「可用」。
   GLM-OCR 那一侧（#164）**已修**（2026-11-23 合进 main），翻译侧是另一处代码，需要单独修。
2. **PaddleOCR 当日额度 12001 被说成「鉴权失败」**（高）：Python 路径实测落 `auth_failed`，用户会去换 Token。
   同时 Python 路径把 Paddle 的 `errorCode`/`errorMsg` 整个丢掉（只留状态码和脱敏地址）。建议：从响应正文只取 `errorCode`、`errorMsg`、`logId`
   （不带地址）放进错误；12001、MinerU `-60018/-60019` 归一个额度类失败码（例如 `ocr_quota_exhausted`，「今日 OCR 额度已用完，明天再试或换 OCR」）。
3. **import 期、运行环境类崩溃没有分类，还会被误认成渲染失败**（高，#7 #135 #143 #162 都是这一类）：
   - 把 `ocr/__main__.py`（及其他 worker 入口）的模块 import 挪进 `run_with_structured_failure` 里面，让 import 错误也有结构化失败；
   - 新增一个环境类失败码（例如 `runtime_environment_broken`）：`ImportError`、`ModuleNotFoundError`、`undefined symbol`、`Library not loaded`、
     package-data 文件缺失，提示「安装包缺文件，请升级或重装，重试没用」，不可重试；
   - Rust 的 `contains_render_failure_signal` 不再凭路径里出现 typst 就判渲染失败，要求失败阶段确实是渲染。
4. **OCR 服务商分类没映射成任务失败码**（中）：Paddle、MinerU 的 `OcrErrorCategory` 已有 30 多种和中文建议，任务层只认鉴权两类，
   其余（文件太大、页数超限、格式不支持、解析失败、队列满）全是「暂未识别出明确根因」（#47 #84 就是这样）。
   建议加一张「OCR 分类 → `failure_code`」的表，`summary` 带服务商原话；同时把 `auth_failed` 建议里写死的「MinerU Token」改成按服务商出。
5. **GLM-OCR 的 401/403/400 落成「暂未识别出明确根因」**（中，实测）：`GlmOcrRequestRejected` 的文字分类器认不出（#164 的修复没动这一条）。
   建议 `GlmOcrRequestRejected` 带上 `status_code`，分类器按 401/403/400 认；1308–1321、1309/1311/1314/1315 已按额度 / 配置类处理（只限 GLM-OCR，智谱当翻译模型时的同一批码仍是第 1 条的缺口）。
6. **翻译时模型不存在（404 `model_not_found` / `not_found_error`）不整份停下**（中）：每个块各自失败，最后翻不出来也说不清原因。
   建议和 401/403 一样第一次就停，给 `model_not_found` 类，换模型后从翻译续跑。
7. **Paddle 队列满 10010 不重试、Python 路径还标成不可重试**（中，#148 的高峰排队）：服务端明确拒收，没有重复计费风险，可在提交处退避重试；
   最终标可重试。
8. **Anthropic 花费上限的 400**（中）：主路径当普通 400；按正文认 spend limit / credit balance 归额度类（开发用直连路径已经这样做）。
9. **本机环境类异常**（低到中）：`PermissionError`（#38）、`MemoryError`（#80）、Windows 长路径 `FileNotFoundError`（#79 #81）各给一句能照做的提示
   （「以管理员运行或检查安全软件」「文档太大，内存不够」「路径过长」），不再是「暂未识别出明确根因」。
10. **零碎**（低）：413 `request_too_large`、DeepSeek 422 归 `upstream_bad_request` 一类；chat 协议检查 `finish_reason`（`sensitive`、`content_filter`、`length`）；
    OpenAI 403 地区不支持单独文案；前端「读取术语表失败」带上状态码和请求编号（#156，前端改，交前端会话）。

已经修好、不用再动的：#24 #37 #41 #72 #79 #80 #132 #135（打包部分）#143 #144 #161；2026-11-23 合进 main、待发版的 #162 #163 #164。
