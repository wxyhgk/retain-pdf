## 一、我们自己怎么分类、怎么显示

### 1.1 失败从哪来

任务失败时用户看到的标题、建议，来自任务详情的 `failure`（`GET /api/v1/jobs/{job_id}/reports/failure`）。分类有两个产生方：

1. **Python worker**：`backend/pipeline/retainpdf_pipeline/foundation/shared/structured_errors.py` 的 `classify_exception`。
   worker 把异常归类后打一行 `structured failure json: {...}`，Rust 解析到就直接用，下面的文本匹配不再跑。
   **注意**：只有包在 `run_with_structured_failure` 里的代码才会出这一行；worker 模块在包装之外 import
   （`backend/pipeline/retainpdf_pipeline/ocr/__main__.py` 里先 import 再包装），import 期崩溃没有结构化失败。
2. **Rust 兜底**：`backend/packages/retainpdf-core/src/job_failure.rs` 的 `classify_job_failure_inner`，
   在没有结构化失败时按错误文字和日志尾巴做子串、状态码匹配；OCR 服务商的分类（`OcrErrorCategory`）只有鉴权两类会被用上
   （`job_failure_structured.rs` 的 `classify_provider_auth_failure`）。
3. **恢复目录**：`backend/packages/retainpdf-core/src/job_failure_catalogue.rs`，按 `failure_code`（个别再按失败阶段）给
   `resume_from` 和一句 `recovery_hint`。前端只渲染后端给的 `summary`、`recovery_hint`，不再自己认分类。

翻译时上游错误先在请求层分流（重试还是直接停），见 `backend/translation/retainpdf_translation/llm/shared/upstream_resilience.py`
和 `backend/translation/retainpdf_translation/llm/providers/deepseek/{client,transport}.py`；
OCR 的重试在 `backend/pipeline/retainpdf_pipeline/ocr/retry.py`（Python：GLM-OCR、并行时的 Paddle）和
`backend/packages/retainpdf-data/src/ocr_provider/{paddle,mineru}/`（Rust：Paddle、MinerU）。

### 2.4 翻译模型：各家共用的处理

翻译、通读、表格翻译都经同一个请求层（OpenAI chat、OpenAI Responses、Anthropic Messages 三种协议，`model_wire.py` 组请求）：

| HTTP | 现在怎么处理 | 代码 |
|---|---|---|
| 401、403 | 不重试。记下「这组 base_url + Key 被拒」，同一次运行里后面的请求不再发；整份翻译停下，`auth_failed`，换 Key 后可从翻译续跑 | `upstream_resilience.py` `is_credential_rejection`、`credential_rejected_error` |
| 402 | 同上，归 `upstream_quota_exhausted`「余额不足」，不可重试 | 同上 |
| 400 | 不重试。三种自动降级：拒收 `temperature` → 去掉重发并记住该模型（#161）；拒收思考字段 → 退下一组；`json_schema` 被拒 → 退 `json_object`（chat、Responses，不含 Anthropic） | `client.py` `request_chat_content` |
| 408、429、500、502、503、504、529 | 退避重试；429 认 `Retry-After`，单个请求累计等待超过 300 秒就放弃（`rate-limit wait budget exceeded`），归 `upstream_rate_limited` | `transport.py`、`client.py` |
| 其他 4xx（404、413、422…） | 不重试；只算这个请求失败，**不会**像 401/402/403 那样整份停下；冒到任务层是「暂未识别出明确根因」（实测 404、413） | `transport.py` `is_transport_error` |
| DNS、超时、连接断开 | 重试，DNS 失败加重试次数并清 DNS 缓存；归 `dns_resolution_failed` / `upstream_timeout` | `client.py`、`transport.py` |
| 200 但 `choices: []` 等解析不了 | 收尾请求槽和请求日志，记 `invalid_response` | `client.py` 末尾的 `except BaseException` |

agent 翻译引擎（`backend/translation-agent/retainpdf_translation_agent_engine/agent_openai.py` 的 `_stop_error`）照同一套：402 → `QuotaExhausted`，401/403 → `AuthFailed`，
429/5xx/529/网络错误用完重试 → `RateLimited`。只有开发用的直连 `agent.py` `classify_http_error` 另外看了正文里的 `credit balance`/`billing`/`quota`。

「检测接口」（设置页的探测，`backend/packages/retainpdf-providers/src/provider_probe/deepseek.rs`）：401/403 → `unauthorized`；402 → `insufficient_balance`；
4xx 指明参数不支持 → 说是参数问题（#161）；模型被拒 → `model_unavailable`；**429 → `ok=true`「可用（当前被限流）」**；5xx → `network_error`。

### 2.5 OpenAI（chat / Responses）

来源：[OpenAI 错误码](https://developers.openai.com/api/docs/guides/error-codes)。

| 码 / 类型 | HTTP | 定义 | 现在怎么处理 | issue | 缺口 / 建议 |
|---|---|---|---|---|---|
| Incorrect API key、Invalid Authentication、IP not authorized | 401 | Key 错、被撤销、IP 不在名单 | 整份停下，`auth_failed` | — | 已覆盖 |
| unsupported_country_region_territory | 403 | 所在地区不支持 | 同 401，文案说「Key 被上游拒绝，检查 Key」 | — | 低：403 的正文说地区时文案改成「所在地区不支持，换网络或服务商」 |
| `insufficient_quota` / `credit_balance_exhausted` | 429 | 预付额度用完 | **当限流**：每个请求退避到 300 秒上限才放弃，所有并发请求都这样；最后 `upstream_rate_limited`「稍后重试即可，无需改动配置」；检测接口说「可用（当前被限流）」 | — | **高**：读正文的 `error.code`/`type`，按 402 处理（整份停下、`upstream_quota_exhausted`、提示充值）。智谱 1113 是同一类问题 |
| `organization_spend_limit_exceeded`、`project_spend_limit_exceeded`、`organization_usage_limit_exceeded` | 429 | 花费上限 / 用量上限到了 | 同上，当限流 | — | 高：同上，文案说「到了花费上限，去控制台调高或等重置」 |
| Rate limit reached、`slow_down` | 429 | 真限流 | 退避重试 | — | 已覆盖 |
| `unsupported_value` / `unsupported_parameter`（temperature 等） | 400 | 模型不收这个参数值 | 自动去掉 `temperature` 重发并记住；检测接口写出参数名 | [#161](https://github.com/wxyhgk/retain-pdf/issues/161) | v2026.11.22 已修 |
| Responses：`json_schema` 不合要求、`json_object` 要求输入里出现 json | 400 | `text.format` 约束 | `json_schema` 被拒退 `json_object`，但 Responses 的系统提示放在 `instructions`，输入里没有 json 字样 → 再挨一次 400；日志 `response_format=none` 不准 | [#163](https://github.com/wxyhgk/retain-pdf/issues/163) | **修复中**（`fix/responses-json-fallback`） |
| `model_not_found` | 404 | 模型不存在或没权限 | 每个请求各自失败，不整份停下；检测接口能认出（`model_unavailable`） | — | 中：翻译时 404 且正文说模型，按配置错误整份停下，给 `model_not_found` 类，换模型后从翻译续跑 |
| `context_length_exceeded` | 400 | 超上下文 | 归 `upstream_bad_request`；这个块失败 | — | 低：批量时可自动拆小批再发 |
| `server_is_overloaded` / 500 | 503 / 500 | 服务端过载、内部错误 | 退避重试 | — | 已覆盖 |
| opencode 中转缺 `x-opencode-session` | — | 中转站要求的请求头 | 接口地址是 opencode.ai 时自动带上 | [#144](https://github.com/wxyhgk/retain-pdf/issues/144) | v2026.11.22 已修 |

### 2.6 Anthropic（Messages）

来源：[Claude API errors](https://platform.claude.com/docs/en/api/errors)。

| 类型 | HTTP | 定义 | 现在怎么处理 | 缺口 / 建议 |
|---|---|---|---|---|
| `authentication_error` | 401 | Key 无效、过期 | 整份停下，`auth_failed` | 已覆盖 |
| `permission_error` | 403 | Key 没权限用这个资源 | 同上 | 已覆盖 |
| `billing_error` | 402 | 账单或付款问题 | 整份停下，`upstream_quota_exhausted` | 已覆盖 |
| `invalid_request_error`（到了组织或工作区自设的花费上限） | 400 | 花费上限 | 当普通 400：这个请求失败，`upstream_bad_request`「检查模型配置与请求参数」；只有开发用直连路径认 `credit balance` | 中：正文提到 spend limit / credit balance / billing 时按额度处理 |
| `invalid_request_error`（temperature、thinking 不支持） | 400 | 参数不被该模型接受 | 自动去掉 `temperature`、退思考字段档位 | 已覆盖 |
| `not_found_error` | 404 | 模型或路径不存在 | 同 OpenAI 404 | 中：同 2.5 `model_not_found` |
| `request_too_large` | 413 | 请求体过大 | 不重试，冒到任务层是「暂未识别出明确根因」（实测） | 低：归 `upstream_bad_request` 一类并说明「单次请求太大」 |
| `rate_limit_error` | 429 | 限流，或到了月度花费封顶（**封顶时没有 `retry-after`，到期前一直失败**） | 退避到 300 秒上限 | 中：没有 `retry-after` 且正文说 spend cap 时按额度处理 |
| `api_error`、`timeout_error`、`overloaded_error` | 500、504、529 | 内部错误、超时、过载 | 退避重试（529 在重试名单里） | 已覆盖 |
| 流式中途的 `error` 事件 | 200 | 见文档 Error events | 默认不走流式（环境变量 `PDF_TRANSLATOR_DEEPSEEK_STREAM` 不开） | — |

### 2.7 DeepSeek

来源：[DeepSeek 错误码](../../../reference/LLM_api/DeepSeek/错误码.md)。

| HTTP | 定义 | 现在怎么处理 | 缺口 |
|---|---|---|---|
| 400 | 请求体格式错误 | 不重试，自动降级（见 2.4） | — |
| 401 | Key 错 | 整份停下，`auth_failed`；检测接口「DeepSeek API Key 无效」 | 已覆盖 |
| 402 | 余额不足 | 整份停下，`upstream_quota_exhausted`；检测接口另外查余额 | 已覆盖 |
| 422 | 参数错误 | 不重试，这个请求失败，冒到任务层是「暂未识别出明确根因」 | 低 |
| 429 | TPM/RPM 到上限 | 退避重试，认 `Retry-After` | 已覆盖；#56 维护者建议降并发避开 429 |
| 500、503 | 服务器故障、繁忙 | 退避重试 | 已覆盖 |

### 2.8 智谱作翻译模型（OpenAI 兼容 chat，如 glm-5.3-flash）

业务码同 2.1 的表，但走翻译请求层（2.4），处理不同：

| 业务码 | HTTP | 现在怎么处理 | 缺口 |
|---|---|---|---|
| 1113、1308–1321 | 429 | 当限流，每个请求退避到 300 秒上限 | **高**：同 OpenAI `insufficient_quota`，应整份停下、提示充值 / 等重置 |
| 1000–1005 | 401 | 整份停下，`auth_failed` | 已覆盖 |
| 1301 | 400 | 这个块失败 | 低：标成「内容审核未过」，保留原文 |
| 1261 | 400 | 这个块失败 | 低：拆小再发 |
| 流式时 `finish_reason` 里的 `sensitive`、`network_error` | 200 | chat 协议没检查 `finish_reason`（Responses 认 `refusal`，Anthropic 认空内容） | 低：`finish_reason` 为 `sensitive` / `content_filter` / `length` 时当这块没翻成 |

### 4.2 两个「分类说错了」的案例

- **#81 渲染失败被说成「鉴权失败」**（4.1.8-beta2）：结构化失败行里明明是 `render_failed`（`FileNotFoundError`），对外的
  `failure` 却是 `auth_failed`、「检查 MinerU Token、模型 API Key 或后端 X-API-Key 配置」。推测是当时的 Rust 文本兜底在日志里按裸子串找 401/403，
  而那次的任务号里正好含 `401` 这串数字。现在结构化失败优先、状态码按数字边界匹配（`job_failure.rs` `contains_http_status`），这一条已不复现。

## 五、待修清单（按用户影响排）

1. **额度用完被当成限流**（高）：OpenAI 429 `insufficient_quota` / 花费上限、智谱作翻译模型时的 1113 和 1308–1321、Anthropic 没有 `retry-after` 的花费封顶 429。
   现在每个请求退避到 300 秒才放弃，所有并发一起空等，最后提示「稍后重试即可，无需改动配置」——用户照做只会再等一轮。
   建议在 `upstream_resilience.py` 读响应正文的 `error.code`/`type`（不只看状态码），额度类按 402 处理：记成凭据被拒、整份停下、
   `upstream_quota_exhausted`、提示充值或等重置；检测接口的 429 也要区分额度和限流，额度类不能报「可用」。
   GLM-OCR 那一侧（#164）**修复中**，翻译侧是另一处代码，需要单独修。
2. **PaddleOCR 当日额度 12001 被说成「鉴权失败」**（高）：Python 路径实测落 `auth_failed`，用户会去换 Token。
   同时 Python 路径把 Paddle 的 `errorCode`/`errorMsg` 整个丢掉（只留状态码和脱敏地址）。建议：从响应正文只取 `errorCode`、`errorMsg`、`logId`
   （不带地址）放进错误；12001、MinerU `-60018/-60019` 归一个额度类失败码（例如 `ocr_quota_exhausted`，「今日 OCR 额度已用完，明天再试或换 OCR」）。
3. **import 期、运行环境类崩溃没有分类，还会被误认成渲染失败**（高，#7 #135 #143 #162 都是这一类）：
   - 把 `ocr/__main__.py`（及其他 worker 入口）的模块 import 挪进 `run_with_structured_failure` 里面，让 import 错误也有结构化失败；
   - 新增一个环境类失败码（例如 `runtime_environment_broken`）：`ImportError`、`ModuleNotFoundError`、`undefined symbol`、`Library not loaded`、
     package-data 文件缺失，提示「安装包缺文件，请升级或重装，重试没用」，不可重试；
   - Rust 的 `contains_render_failure_signal` 不再凭路径里出现 typst 就判渲染失败，要求失败阶段确实是渲染。
4. **OCR 服务商分类没映射成任务失败码**（中）：Paddle、MinerU 的 `OcrErrorCategory` 已有 30 多种和中文建议，任务层只认鉴权两类，
   其余（文件太大、页数超限、格式不支持、解析失败、队列满）全是「暂未识别出明确根因」（#47 #84 就是这样）。
   建议加一张「OCR 分类 → `failure_code`」的表，`summary` 带服务商原话；同时把 `auth_failed` 建议里写死的「MinerU Token」改成按服务商出。
5. **GLM-OCR 的 401/403/400 落成「暂未识别出明确根因」**（中，实测）：`GlmOcrRequestRejected` 的文字分类器认不出。和 #164 在同一个文件，
   请在 `fix/glm-ocr-error-codes` 之后另修；1308–1321、1309/1311/1314/1315 那个分支已经按额度 / 配置类处理了（只限 GLM-OCR，智谱当翻译模型时的同一批码仍是第 1 条的缺口）。
6. **翻译时模型不存在（404 `model_not_found` / `not_found_error`）不整份停下**（中）：每个块各自失败，最后翻不出来也说不清原因。
   建议和 401/403 一样第一次就停，给 `model_not_found` 类，换模型后从翻译续跑。
7. **Paddle 队列满 10010 不重试、Python 路径还标成不可重试**（中，#148 的高峰排队）：服务端明确拒收，没有重复计费风险，可在提交处退避重试；
   最终标可重试。
8. **Anthropic 花费上限的 400**（中）：主路径当普通 400；按正文认 spend limit / credit balance 归额度类（开发用直连路径已经这样做）。
9. **本机环境类异常**（低到中）：`PermissionError`（#38）、`MemoryError`（#80）、Windows 长路径 `FileNotFoundError`（#79 #81）各给一句能照做的提示
   （「以管理员运行或检查安全软件」「文档太大，内存不够」「路径过长」），不再是「暂未识别出明确根因」。
10. **零碎**（低）：413 `request_too_large`、DeepSeek 422 归 `upstream_bad_request` 一类；chat 协议检查 `finish_reason`（`sensitive`、`content_filter`、`length`）；
    OpenAI 403 地区不支持单独文案；前端「读取术语表失败」带上状态码和请求编号（#156，前端改，交前端会话）。
