# 前端报错线索与分工

2026-11-23 用户让前端会话看「报错的 API 还缺什么」，定了分工：后端 6 条交给后端会话（用户：「让后端开多 agent 去干」），
前端先做不用等后端的两条，后端的错误码目录合进 main 后再接提示。

## 后端（后端会话 5 个分支并行）

1. 任务失败加 `upstream: {provider, http_status, code}`；OCR 失败的 `provider` 直接写厂商编号（`feat/failure-upstream`）。
2. 检测、拉模型、问模型把 HTTP 状态码和厂商业务码拆开（`fix/probe-status-codes`）。
3. 欠费、额度类码按业务码整份停下，不当限流（`fix/translation-quota-codes`）。
4. 兜底「暂未识别出明确根因」的几类补分类（`fix/failure-fallback-classes`）。
5. 限流等待时进度事件里带出来（`feat/upstream-wait-events`）。

厂商编号统一用错误码目录的 vendor id。

## 前端这次做的（`feat/error-diagnostics`）

- **请求出错带编号**：`@retainpdf/api` 的 `attachRequestRef` 读后端日志里的编号（500 用 `error.details.error_id`，别的用回应头
  `X-Request-ID`），挂到错误的 `requestRef` 上；5xx 时接在提示后面「…（编号 …）」，后端 message 里已经有就不重复。接进了生成的
  请求函数（`request.ts`）、提交（`http.ts`）、备份、同步、凭据、术语表导出、字体列表。issue #156 那种只有一句「读取术语表失败」的，
  以后能凭编号在后端日志里找到那次请求。
- **复制诊断信息补全**：失败卡片复制时再取一次任务详情，补上失败码、上游（厂商、码、主机）、这次用的 OCR 和翻译模型（接口只留主机名）、
  后端的恢复建议、软件版本和平台；不带 Key。

## 接上错误码目录（同一个分支，后端 `feat/provider-error-codes` 合进 main 之后）

- `npm --prefix frontend/packages/api run generate:client` 生成 `listProviderErrorCodes`。
- `@retainpdf/api` 的 `fetchProviderErrorHint(厂商, 码 / 状态码)`：有业务码按码精确查；只有 HTTP 状态码时只认唯一的一条
  （同一个 429 可能是限流也可能是欠费，猜错比不说更糟）。按需查，不整份拉目录。
- 哪家、哪个码：失败里有 `upstream`（后端 `feat/failure-upstream`）就用它；没有时 OCR 阶段用建任务时的 `ocr.provider` 加失败里的
  `provider_code`；翻译阶段现在多半没有厂商的码，不查。
- 失败卡片在后端说法上面加一行「智谱 GLM-OCR 1113 智谱账号余额或资源包不足……」，鼠标停上去看官方说法；查不到不画。
- 接口登记表里 `GET /providers/error-codes` 的 `by(none)` 要后端改成 `by(web)`。

## 跟上后端合并的几个分支（`feat/error-followups`）

后端 `feat/failure-upstream`、`fix/probe-status-codes`、`fix/translation-quota-codes`、`fix/failure-fallback-classes`、
`feat/upstream-wait-events` 合进 main 以后：

- 失败简报加 `upstream`（前端失败简报的字段对账测试要求）；失败来源小标签把厂商编号换成设置里的名字，「OCR · ocr」这种不说明事的去掉。
- 新分类 `environment`（内存不够、路径太长、没权限、运行环境坏了）有自己的说法，标「重试解决不了」。
- 提交时检测翻译 Key：`quota_exceeded`（额度、花费上限用完）也弹提醒。
- 进度页状态行下面：`stage_snapshot.upstream_wait` 在时显示「服务商限流 / 繁忙 / 暂不可用，等待中（厂商，约 N 秒后重试）」。
- 设置「检测接口」没通过、有厂商的码或状态码时，查错误码目录把服务商的说法接在后面（自定义接口不查）。

## OCR 的 Token 检测（`feat/ocr-probe-hints`）

PaddleOCR、MinerU、GLM-OCR 的 Token 检测没通过、服务商回了码或状态码时，同样查错误码目录接在后面（Paddle 12001 当日额度、
智谱 1113 余额不足……）。翻译和 OCR 的检测共用 `features/credentials/domain/error-hint.ts`。

- 走 Rust 模型执行器的翻译失败暂时没有 `upstream`（后端在补），那些失败卡片上查不到厂商提示。
