# 前端报错线索与分工

2026-11-23 用户让前端会话看「报错的 API 还缺什么」，定了分工：后端 6 条交给后端会话（用户：「让后端开多 agent 去干」），
前端先做不用等后端的两条，后端的错误码目录合进 main 后再接提示。

## 后端（后端会话 5 个分支并行）

1. 任务失败加 `upstream: {provider, http_status, code}`；OCR 失败的 `provider` 直接写厂商编号（`feat/failure-upstream`）。
2. 检测、拉模型、问模型把 HTTP 状态码和厂商业务码拆开（`fix/probe-status-codes`）。
3. 欠费、额度类码按业务码整份停下，不当限流（`fix/translation-quota-codes`）。
4. 兜底「暂未识别出明确根因」的几类补分类（`fix/failure-fallback-classes`）。
5. 限流等待时进度事件里带出来（`feat/upstream-wait-events`）。

厂商编号统一用错误码目录的 vendor id。

## 前端这次做的（`feat/error-diagnostics`）

- **请求出错带编号**：`@retainpdf/api` 的 `attachRequestRef` 读后端日志里的编号（500 用 `error.details.error_id`，别的用回应头
  `X-Request-ID`），挂到错误的 `requestRef` 上；5xx 时接在提示后面「…（编号 …）」，后端 message 里已经有就不重复。接进了生成的
  请求函数（`request.ts`）、提交（`http.ts`）、备份、同步、凭据、术语表导出、字体列表。issue #156 那种只有一句「读取术语表失败」的，
  以后能凭编号在后端日志里找到那次请求。
- **复制诊断信息补全**：失败卡片复制时再取一次任务详情，补上失败码、上游（厂商、码、主机）、这次用的 OCR 和翻译模型（接口只留主机名）、
  后端的恢复建议、软件版本和平台；不带 Key。

## 等后端

- 错误码目录 `GET /providers/error-codes`（`feat/provider-error-codes`）合进 main 后：失败卡片在 `summary` 下面加一行厂商条目的
  `user_hint_zh`，查不到退回 `recovery_hint`；设置里的检测失败同样显示。
- 失败结构加了 `upstream` 以后，诊断信息和提示改读它。
