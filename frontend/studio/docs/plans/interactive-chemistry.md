# 联动的计算可视化

## 要做什么，为什么

计算化学的文章里，能量、结构、谱图本来是连在一起的。但现在它们是三张互不相干的图：PDF 和 Notion 都只能放静态图片，读者看不出「这个峰是哪个振动」「曲线上这一点的结构长什么样」。

终端里的 AI 能生成文件，却给不了「拖一下、点一下就看到」的体验。我们要做的就是这个，而且在 Studio 里写的时候和博客上读的时候效果一样。具体是四件：

1. **路径播放**：IRC、柔性扫描、几何优化的输出，显示成一条能量曲线加一个 3D 结构。在曲线上拖动或悬停，结构跟着走；可以按「播放」。
2. **谱图和振动联动**：频率计算的输出画出 IR 谱（可调展宽和校正因子），点一个峰，分子就按那个振动模式动起来。激发态计算画出 UV-Vis 谱。
3. **结构叠加比较**：两个结构（比如反应物和过渡态）对齐后叠在一起，标出变化大的键长。
4. **能量图和结构联动**：```energy 图里的一个能级可以指向一个输出文件，点能级就看到那个结构。

## 分几期

### 第 1 期：解析器补上路径数据

- Gaussian 和 ORCA 的优化、IRC、扫描：读出每一步的结构，和那一步的能量对上。
- IRC：读出反应坐标，分清正向和反向，按坐标排好。扫描：读出被扫描的坐标和它的值。
- 加进 `QcOutput`，例如加一个 `path: { kind: 'opt' | 'irc' | 'scan', coordinate: string | null, points: { x: number | null, energy: number, atoms: Atom[] }[] } | null`。名字可以改，但要写进 `qc.mjs` 的类型说明和 `README.md`。
- 测试：在 `packages/compute/test/`（或解析器旁边现有测试的位置）放真实的小输出文件，Gaussian、ORCA 各一份 IRC、一份扫描、一份优化，断言点数、首尾能量、某一点的某个原子坐标。
- 完成标准：`npm run test:unit` 通过，这几种输出的路径都读得对。

### 第 2 期：路径播放

- 在 ```qc 的卡片或详情里，输出有路径时多一个视图：左边能量曲线（SVG，横轴是反应坐标或步数，纵轴是相对能量，单位 kcal/mol），右边 3D 结构。
- 在曲线上悬停或拖动，结构切到最近的那一点；有「播放」按钮；当前点在曲线上标出来。
- Studio 和博客一样：`build.mjs` 把曲线画好、把路径数据写进页面；`page.ts` 和 Studio 里的块负责交互。
- 路径数据可能很大（几百个点乘几十个原子），坐标保留 4 位小数，只在用户打开这个视图时才建 3D 视图。
- 完成标准：
  - 浏览器测试：在一篇有 IRC 输出的文章里打开这个视图，拖到曲线中间，结构变化（比较 fast-mol 拿到的坐标），播放结束停在最后一点。
  - 发布的博客页面上做同样的检查。

### 第 3 期：谱图和振动联动

- 频率计算的输出：画 IR 谱。每个振动用洛伦兹函数展宽，半峰宽可调（默认 10 cm⁻¹），可以乘校正因子；虚频不画进谱里，单独列出。
- 点一个峰（或峰附近），3D 结构播放这个振动模式（fast-mol 已经能画振动箭头和动画）；当前模式在谱上标出来。
- 激发态输出：画 UV-Vis 谱。用高斯展宽，横轴可以切换 nm 和 eV，强度用振子强度。
- 完成标准：
  - 测试里点 IR 谱上最强的峰，3D 视图切到对应的振动模式；
  - 调展宽，谱线跟着变；
  - 截一张亮色、一张暗色的图看一眼。

### 第 4 期：结构叠加比较

- 新的代码块，例如：

      ```compare
      @file ./assets/reactant.log
      @file ./assets/ts.log
      ```

  也可以写 XYZ。两个结构的原子数和顺序相同时，用 Kabsch 算法对齐；顺序不同时先报错，不要猜。
- 叠加显示：一个实心，一个半透明或线框。列出变化超过 0.1 Å 的键长（前后值都给），在 3D 里标出来。
- 完成标准：单元测试检查对齐算法（已知旋转加平移后，RMSD 应接近 0）；浏览器测试检查表格里的键长变化。

### 第 5 期：能量图和结构联动

- ```energy 的一行可以带一个文件：`TS1 12.3 @./assets/ts1.log`。不带文件的写法照旧可用，原有文章不受影响。
- 点能级，就在旁边或弹出的视图里显示那个结构；有频率时，显示虚频。
- 完成标准：原有的 ```energy 测试照常通过，新写法有自己的测试。

## 必须遵守的约定

- **纯 Markdown**：文章里只写代码块，以及 `@file` 指向文章 `assets/` 里的文件。不要引入要靠 Studio 才能读懂的格式。
- **两边一样**：同一个块，在 Studio 里和发布的博客上看起来、用起来一样。
- **配色**：只用黑、白、灰，跟随页面的亮暗主题（用页面的 CSS 变量，比如 `--surface`、`--gray-dark`）；红色只用于删除和出错。曲线、当前点、谱线都用灰阶，靠深浅和线型区分。
- **fast-mol 不能直接改**：不要改 `../fast-mol`，也不要改 `packages/science/third-party/fast-mol/` 里的构建。需要 fast-mol 加新功能（比如半透明、叠加两个分子、按位移播放）时，把需求写进本文末尾的「问题」一节，由作者转给维护 fast-mol 的会话。能用现有接口凑出来的，就先用现有接口。
- **性能**：页面上可能有很多块，3D 视图只在需要时建；不要在每次滚动、每次按键时遍历整篇文章（见 `docs/long-articles.md` 的「规矩」）。
- **测试**：
  - 浏览器测试只用隔离模式：`E2E_ISOLATED=1 npx playwright test -c tests/e2e/playwright.config.ts <文件>`。
  - 不要在仓库根目录上再开第二个 `astro dev`。
  - Mac 应用用的是 WebKit，交互部分也要在 WebKit 里试一遍（参考 `tests/e2e/long-article-webkit.spec.ts` 的写法）。
- **git**：
  - 在自己的分支或 worktree 上做，可以提交，**不要推送**。
  - 提交说明用中文，写清楚做了什么、怎么测的。
  - 仓库是公开的：不要写进本机路径、用户名、主机名。
- **文档**：每期做完，在 `docs/studio.md` 里补用法，在 `plugins/` 相应的说明里补格式；在本文对应的那一期后面写上提交号。
