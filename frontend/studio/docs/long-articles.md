# 超长文章：开发记录

压力场景：一本 500 页的书 OCR 成一篇文章（约 62 万字、2400 个块、4500 个行内公式），还要在里面大量编辑。前后改了三轮，这里记下每轮卡在哪里、怎么改、哪些路走不通，以后改编辑器时照着检查。

## 结果

Mac 应用（WebKit）里，先打开另一篇文章，再从列表点这篇：

| | 最初 | 现在 |
|---|---|---|
| 点击到看见文章 | 7 秒多 | 约 0.15 秒 |
| 全部接上 | 和看见同时 | 约 3 秒，期间照常滚动、打字，每帧约 26 毫秒 |
| 打字，每个键 | 165 毫秒 | 约 30 毫秒 |
| 停手后整页冻住 | 4.6 秒 | 几十毫秒 |
| 往下滚，超过 50 毫秒的帧 | 约一半 | 约 2% |
| 点目录跳到远处的标题 | 偏几千像素 | 停在标题上 |

## 第一轮：每次改动的工作量跟着改动走

最初每停手一次，Studio 都把整篇写成两遍 Markdown，再和原文整篇对比。文章越长越慢，跟改了多少无关。

- **按块写 Markdown**（`src/studio/editor/blockwise-markdown.ts`）。ProseMirror 改动时，没动过的节点还是原来那个对象，所以每块写出的 Markdown 按节点对象记住，下次只写改过的一两块。
  - 相邻的两个列表要一起写，否则写出来会连成一个列表。
  - 空段落不能记：它在中间写成 `<br />`，是最后一块时写成空。
- **合并只看改动附近**（`packages/document/merge.ts`、`parse.ts`）：
  - 只重新切改动前后的块（`reparseBodyBlocks`）；
  - 每块的「含义」算过就记住；
  - 对齐先跳过首尾相同的块，字节相同的块直接算相同，不再算含义。原来是「块数 × 块数」的整张表。
- **插件只看改了的那一段**（`packages/editor-kit/changed-range.ts`）：段内换行、引用编号、公式编号。
- **关掉 Astro 开发工具栏**。它的无障碍检查每次改动都把整页查一遍，500 页时约 1.2 秒。

## 第二轮：Mac 应用里点开慢、滚动卡

第一轮只在 Chrome 里测了打开、打字、保存，没测滚动；Mac 应用用的 WebKit 表现很不一样。

- **公式到屏幕附近才画**（`packages/editor-kit/near-screen.ts`）。4500 个行内公式用 KaTeX 画出来有十几万个元素，占了打开时间的大半，排版也慢。长文章里的公式先显示 LaTeX 原文，滚到附近再成批画：附近一屏还有没画的，就把上下几屏一起画掉。不要滚一点画一点，否则每帧都让 WebKit 把整篇重新排版。
- **滚动时不要从头量所有块**。滚动锚定、目录找当前标题、行间公式量宽度，都改成二分查找屏幕附近的块。也不给每个公式挂一个 IntersectionObserver，那样每帧都要算几千个位置。
- **点目录直接跳过去，再按真实位置校正**，不用平滑滚动：平滑滚动的终点在开始时就算好了，途中公式画出来、高度一变就偏。

**走不通的路：`content-visibility: auto`（屏幕外的块不排版）。**
- 在 WebKit 里，没排过版的块只有估计高度。往上滚时它们排出真实高度，页面会一直往下跳（往上滚 2000 像素再滚回来，差 5000 像素），点目录也停不准。
- 公式改成延后画以后，页面元素本来就少了，它在 WebKit 里反而让打字更慢。
- `tests/e2e/long-article-webkit.spec.ts` 专门防它回来：把它加回去，测试会偏 3864 像素并失败。

## 第三轮：分段显示，点开就看见

第二轮之后点开还要约 2.6 秒：解析整篇约 0.4 秒，建出整篇的编辑器页面约 0.9 秒，WebKit 排版约 1.1 秒。

思源笔记秒开，是因为它一开始只加载一小段。ProseMirror 要求整篇文档都在编辑器里，所以这里换个做法：**先放开头，其余的接着放**。

### 怎么分段

正文超过 5 万字（现有最长的文章约 2.4 万字）时：
1. 先解析、画出开头约 1.2 万字，几屏的量，画出来约 0.15 秒。
2. 其余每段 1.2 万字，每段分两帧做完：
   - 一帧读这段，并把上一段写成 Markdown；
   - 下一帧把这段放进编辑器。
3. 每帧的工作只有十几到二十几毫秒，加载中照常滚动、打字。

分段的位置必须保证「这段单独读」和「放在全文里读」结果一样（`parse.ts` 的 `bodyParts`）：
- 从正文里取一段窗口来切块，窗口最后一块可能没完（比如被截断的代码块），留给下一段，前面的块都是完整的。CommonMark 是从前往后读的，后面的内容不会改变前面已经结束的块。
- 只在顶格开始的块前断，避免缩进的列表项被当成新列表。
- 编辑器会把 `<details>…</details>`、分栏的 `<div>` 合成一个块，它们中间不断。
- 有链接定义或脚注定义（`[x]: …`）的文章整篇一段：定义可以写在使用之后。

### 接上去的段不算编辑

- 不进撤销历史。
- 不经过插件对编辑的处理（appendTransaction），跟第一段一样，因为第一段打开时也不经过（`applyInner`）。
- 标题 id 在同一个事务里给好（Milkdown fork 的 `syncHeadingIds`）。原来标题 id 插件会在每段之后再发一个事务，整篇多排一次版。
- 每段插在「上一段的末尾」，这个位置会随着用户的编辑移动（`nextPart` 插件）。所以加载中打的字会留着，后面的段接在它之后，全部接上后作为一次编辑上报。
- 编辑器在文末自动补的空段落始终留在最后。
- 审阅（AI 改动的对比）等全部接上再开始。
- 从磁盘重新载入时仍整篇一次打开，为了停在原来的位置。

### 打开时别的地方不能抢先整篇解析

这一轮查出来几个跟编辑器无关、但同样拖慢打开的地方：
- 文件面板要知道文章引用了哪些文件，原来在文章显示之前就整篇解析一次（0.34 秒），现在放到显示之后。
- Studio 页面原来要等文章全部打开才露出来，现在第一段画出来就露出来。
- 合并时增量切块的起点如果是别的文章的上次编辑结果，跟这篇几乎没有共同部分，等于整篇重切（收尾卡 0.4 秒）。现在只用同一篇原文的结果。
- 同一份正文只切一次块：分段时顺便切出的块会记住，合并和文件面板直接用。

## 第四轮：普通文章在侧边栏里点来点去

用户说点侧边栏「卡卡的」。在 WebKit 里点了 8 篇真实文章，量出来：

| | 改之前 | 改之后 |
|---|---|---|
| 点击到列表里高亮 | 和正文一起出来，40–520 毫秒 | 约 5 毫秒 |
| 公式多的文章（约 150 个公式、4 个 widget）：点击到看见 | 300–520 毫秒，期间整帧卡住 | 约 110 毫秒 |
| 同一篇：之后最长的一帧 | 150–250 毫秒 | 约 110 毫秒 |
| 普通文章：点击到看见 | 40–75 毫秒 | 差不多 |

- **点了马上有反应**：原来列表的高亮要等新文章整个建好才和正文一起出来，期间什么都没变，就觉得卡。现在一点就先高亮；打不开时再退回原来那篇。
- **标题 id 在建编辑器之前给好**（`editorStateOptionsCtx` 里调用 `syncHeadingIds`）：原来编辑器建好后，标题 id 插件会再发一个事务给所有标题补 id，整篇又更新一遍。
- **打开时公式先画屏幕附近的**：打开任何文章时（编辑器上有 `is-opening` 这个 class），公式先显示原文。第一次画出来之前，屏幕附近的就已经画好，所以看不到闪烁；远处的在后台每帧画 8 毫秒，几百毫秒内画完（`near-screen.ts`）。打开以后新写的公式照常立刻画。
- **打开后的往返核对分帧做**：整篇写成 Markdown 原来独占一帧（公式多的文章 50–70 毫秒），现在每帧写 40 块。

- **编辑器只建一次**（`studio-editor.ts` 的 `showDocument`）：原来每次切换都把编辑器连同菜单、工具栏整个销毁重建。现在保留编辑器，换上新文章的文档（一个新的 ProseMirror 状态）：
  - 上一篇的撤销历史、插件状态都不会带过来；
  - 滚动回到顶部；
  - 只有插件的块或斜杠命令变了（插件重新加载）时，才重建编辑器。

  WebKit 里普通文章从点击到画出来快了约 10–20 毫秒，比如 65 毫秒对 82 毫秒。比预想的 30 毫秒少，因为新文档的每一块还是要重新建视图，省掉的只是编辑器外壳。

## 规矩

- **在 WebKit 里测**，并且要测滚动和点目录，不能只测打开和打字。Chrome 的数字参考价值有限。
- 不要加每次滚动、每次按键都遍历全部块的工作；不要给每个公式、每个块挂观察器。
- 不要在文章显示之前做整篇的工作（解析、写 Markdown、读引用）；能放到显示之后、能分段做的都分段做。
- 新加「把很多内容一次放进编辑器」的功能时，参考 `showRest`：自己的事务里给好标题 id，不进撤销历史。
- 机器忙的时候（别的程序在编译），测出来的数字会差三倍左右。比较新旧代码要在同一台机器、同一时间、用同一个测试跑。

## 怎么测

- 速度（Chrome，只在要的时候跑）：
  ```sh
  E2E_PERF=1 E2E_ISOLATED=1 npx playwright test -c tests/e2e/playwright.config.ts long-article
  ```
- WebKit 里点目录、来回滚动：`tests/e2e/long-article-webkit.spec.ts`。要先装 WebKit：`npx playwright install webkit`。
- 分段显示的正确性：`tests/e2e/long-article-parts.spec.ts`。在页面上设 `window.STUDIO_PARTS = { from, first, rest }`，就能让短文章也按很小的段打开，每种块都会落在段的边界上。
- 切块：`tests/incremental-sync.test.ts`。它在全部文章上随机改几千次，并按各种长度分段，结果都要和整篇切的一样。
- 测试页：「Studio 功能测试」下的「超长文章：500 页 OCR」，在 Studio 里直接打开试。
